# docs 十主题体系重构计划

| 编号 | 新主题 | 内容来源 | 性质 |
|------|--------|---------|------|

## 阶段 0：边界宪章与迁移矩阵（串行，1 个 Coding 代理）

在 `docs/_refactor/`（临时工作目录，最后删除）产出三份契约文件，是后续所有写作的唯一裁决依据：

1. `boundary-charter.md` — 10 主题各一句话主场定义 + 五处模糊边界裁定：认证归属（连接级→Gateway、动作级→Guardrails）；注入归属（组装时机→Context、内容来源→Memory）；执行归属（注册调度→Tools、隔离后端→Runtime）；SessionDB 双重归属（恢复用途→State、回放/审计用途→Observability）；Skills 归 Tools，其 prompt 注入面在 Context 留一句互引。
2. `migration-matrix.md` — 65 个旧文件 × H2/H3 小节级归属表，**每个旧小节只归属一个新主题**（杜绝同一内容被两个主题各抄一遍产生漂移）；跨界内容（旧 10-security 的密钥管理、输出脱敏、面试题 2/3）指定唯一主写方，另一方只写交叉引用；要求旧文档 100% 小节覆盖，有意舍弃的须写明理由。
3. `style-template.md` — 固化现有六段式模板（读前思考→核心问题→方案展示→横向对比/执行流 trace→面试要点）、术语表、篇幅预算（单篇 ≤ 旧篇均值 1.3 倍，约 20KB）。

## 阶段 1：源码研究（并行 2-3 个 Research 代理，与阶段 2 波一重叠执行）

研究笔记统一落盘 `docs/_refactor/research/`，单一写者、后续五个写作者（1 对比 + 4 项目）复用，避免同一源码被重复研究。按 AGENTS.md 第三步的子代理写作计划模板产出（核心文件清单/架构总览/主流程 trace/设计选择/工程优化/边界情况/接口）：

- **State 研究**（缺口最大）：claudecode `claudecode/session/`（storage.py、recovery.py、history.py、task_registry.py）；hermes `hermes-agent/gateway/session.py`、session_context.py、turn_lease.py、根目录 `hermes_state.py`；deer-flow `backend/packages/harness/deerflow/persistence/`、checkpoint_patches.py；openclaw `openclaw-2026.7.1/src/` 会话树与 session 管理文件 + `openclaw-python/backend/src/`。
- **Runtime 研究**：deer-flow `backend/packages/harness/deerflow/sandbox/`（4 后端生命周期）；hermes `tools/code_execution_tool.py` 与 5 执行后端；openclaw sandbox/ 目录与工作区越界守卫；claudecode 无沙箱——研究其依赖 Guardrails 的定位论证。
- **Context 补充素材研究**（可选，若迁移素材不足）：claudecode 的系统提示词结构（其 02 篇无此节）；各项目 prompt 组装与历史消息管理细节。

## 阶段 2：50 篇新文档写作（每主题 1 个 Coding 代理，独占该主题的 5 个文件）

编排方式：**一个主题一个写作代理**，产出该主题的 1 篇 comparisons + 4 篇项目文档。这保证 comparisons 与项目篇之间满足 AGENTS.md 的"无 ≥2 句原文重复、comparisons 只留结论+指向"规则。分两波：

**波一（迁移型 5 主题，可立即启动）**：02-model、06-memory、10-observability、01-gateway、03-orchestrator。要点：
- model/memory/observability 近乎整体迁移，重命名编号、补"读前思考"、改写互引（memory 的短期记忆边界声明改指 05-context；observability 补"评估"一节）。
- gateway 合并 14+09（旧体系已有边界声明切分，渠道适配降为一节）；claudecode 篇沿用"无 Gateway 是进程形态决定的"诚实写法。
- orchestrator 合并 02+07，State 相关段落只留一句指向 04-state。

**波二（合并/拆分/新写 5 主题）**：07-tools、05-context、09-guardrails、08-runtime、04-state。
- tools 四合一难度最高：不拼接、按"注册发现 → Function Calling 执行 → MCP 协议接入 → Skill 指令能力 → Plugin 模块扩展"重新选 2-3 个设计主线，细节下沉到项目篇控制篇幅。
- context 以旧 13 为主体 + 抽取各项目 02 篇"系统提示词结构"节；4 篇项目级 Context 文档为全新产出（旧体系项目级无 13 篇）。
- guardrails/runtime 按矩阵小节级归属拆分旧 10-security；两篇对比文档特别做重复性检查。
- state 全新写作，输入 = 迁移矩阵碎片锚点 + `docs/_refactor/research/` 笔记；建议最后写（与 orchestrator/context 的边界互引一次写对）。波二内各主题仍有单篇级依赖：state/runtime 篇须等对应研究笔记完成。

每篇产出后写作代理自行过 AGENTS.md 写作自检清单 9 项 + 文档体检清单 10 项（重点：代码符号数上限、表格重合 ≤2 行、mermaid 状态语言、无比喻、无成段代码）。

## Test Plan

1. 文件数断言：comparisons、deer-flow、hermes-agent、openclaw、claudecode 各目录恰好 10 篇，文件名与新网格一致。
2. 引用完整性：grep 全部旧文件名零命中；overview.md 链接全部可达。
3. 内容完整性：迁移矩阵 100% 小节核销，舍弃项有理由记录。
4. 规范合规：每篇过写作自检清单 + 文档体检清单；spot-check 合并篇（tools/gateway）篇幅与"2-3 个设计选择"约束、新写篇（state/runtime）含完整执行流 trace。
5. AGENTS.md 与新体系一致（模块清单、边界定义、文件布局均为 10 主题）。

## Rejected Alternatives

- **稀疏编号（10-gateway/20-model…）**：为未来插入主题留间隙，但与现有 01-14 惯例和用户给定顺序不符，静态文档集扩展需求低，选择稠密 01-10。
- **每篇文档一个写作代理（50 个代理、8-10 并发）**：总轮次更少，但同一主题的 comparisons 与 4 篇项目文档分属不同代理，难保证"无重复、只留结论+指向"的跨文档规则；每主题一代理牺牲少量并行度换取主题内一致性。
- **先删旧文档再写新文档 / 原地改名编辑**：丢失回滚锚点且拆分合并场景下原地编辑易污染素材，旧文档保持只读直到最后删除。
- **完全重写全部 50 篇**：工作量约 2-3 倍且无质量收益，存量教学素材质量已达标，仅对缺口主题回源码新写。
- **保留旧 11-config 为附录或第 11 篇**：违背用户"10 主题"目标，化整为零后在 overview 中保留分配说明即可。
