# Agent 异步会话网关项目架构书

## 1. 项目概述

本项目建设一个面向 Agent 长任务场景的异步会话网关。

网关位于客户端与 Agent 执行系统之间，负责维护客户端连接和业务 Session，将客户端请求转换为异步任务提交给后端执行系统，并在任务执行过程中持续接收结果事件，再将结果准确推送回对应客户端。

网关本身不参与 Agent 推理和业务执行。

整个系统以 `sessionId` 作为客户端连接与后端异步任务之间的核心关联标识，实现客户端连接、Gateway 节点和 Agent Worker 三者之间的解耦。

项目最终需要实现：

- 客户端连接长期保持；
- Agent 任务异步执行；
- 网关不等待任务完成；
- Agent Worker 无需感知客户端所在节点；
- 执行结果可以准确返回对应 Session；
- 支持流式结果；
- 支持客户端断线重连；
- 支持 Gateway 故障恢复；
- 支持 Gateway 和 Agent Worker 独立水平扩展。

------

# 2. 架构目标

系统架构主要围绕以下几个目标设计。

### 2.1 请求与执行解耦

客户端请求到达 Gateway 后，Gateway 只负责完成任务创建和异步提交，不同步等待 Agent 执行结果。

Agent Task 的生命周期独立于当前网络请求。

即：

```text
请求生命周期 != Agent Task 生命周期
```

------

### 2.2 连接与执行解耦

客户端连接由 Gateway 管理。

Agent 任务由 Worker 执行。

Worker 不需要知道客户端连接在哪台 Gateway，也不需要知道 WebSocket、SSE 等连接信息。

Worker 只需要处理：

```text
sessionId
taskId
业务输入
```

并在执行过程中产生：

```text
sessionId
taskId
执行结果
```

------

### 2.3 Session 与 Gateway 解耦

Session 是业务层面的长期会话，不应与某一个 Gateway 进程生命周期绑定。

Gateway 节点发生故障时，Session 和正在执行的 Task 仍然继续存在。

Gateway 恢复后，可以根据未完成 Session 重新恢复结果接收，而不重新执行 Agent Task。原方案中同样要求节点恢复后重新恢复未完成 Session，并继续取得故障期间产生的消息。

------

### 2.4 结果准确回流

Agent Worker 在任意节点执行任务后，产生的结果必须能够重新返回当前持有该 Session 客户端连接的 Gateway。

网关收到结果后，根据：

```text
sessionId -> connection
```

完成最终推送。

这是整个网关最核心的路由能力。源方案中的核心设计也是让异步执行后的结果最终重新回到持有原 Session 的网关。

------

# 3. 总体架构

系统整体划分为五个逻辑部分：

```text
Client
   │
   ▼
Gateway Cluster
   │
   ▼
Async Task / Event Layer
   │
   ▼
Agent Worker Cluster
   │
   ▼
Model / Tool / External System

同时：

Gateway Cluster
   │
   └──── Session / Recovery Store
```

各部分职责如下。

### Client

负责建立长连接、提交用户请求以及接收 Agent 执行过程中产生的流式结果。

### Gateway Cluster

负责客户端连接、Session、Task 提交以及 Event 回流。

### Async Task / Event Layer

负责 Gateway 和 Agent Worker 之间的异步任务传递与结果事件传递。

具体底层消息实现不属于 Gateway 架构本身。

### Agent Worker Cluster

负责真正执行 Agent Task，包括模型调用、Tool 调用和其他业务处理。

### Session / Recovery Store

负责保存 Gateway 故障恢复所需要的 Session 元数据和未完成任务状态。

------

# 4. Gateway 内部架构

单个 Gateway 节点由以下核心模块组成：

```text
Gateway
├── Connection Manager
├── Session Manager
├── Request Handler
├── Task Dispatcher
├── Event Receiver
└── Recovery Manager
```

------

## 4.1 Connection Manager

Connection Manager 负责客户端长连接管理。

支持的连接方式主要包括：

- WebSocket；
- SSE。

核心职责是维护本机：

```text
sessionId -> connection
```

映射。

例如：

```text
S10001 -> WebSocket Connection A
S10002 -> WebSocket Connection B
S10003 -> SSE Connection C
```

收到 Agent Event 后，Gateway 可以通过 `sessionId` 找到当前连接并直接推送。

Connection 属于节点本地资源。

连接关闭以后，不代表对应 Session 被删除。

------

# 5. Session Manager

Session Manager 负责管理业务会话。

Session 是整个系统中最重要的稳定身份。

一个 Session 可以持续多轮交互，也可以包含多个 Agent Task。

核心模型：

```text
Session
├── Task 1
├── Task 2
├── Task 3
└── ...
```

Session 至少需要维护：

```text
sessionId
status
connectionId
gatewayNode
createdAt
updatedAt
```

其中：

`sessionId` 是系统全局唯一的会话标识。

`connectionId` 表示当前客户端连接。

`gatewayNode` 表示当前承载该客户端连接的 Gateway 节点。

Session 与 Connection 生命周期分离。

客户端连接断开时，可以删除 Connection，但 Session 本身仍可以继续存在。

------

# 6. Request Handler

Request Handler 负责处理客户端进入 Gateway 的业务请求。

请求进入后主要完成：

1. 校验 Session；
2. 解析用户输入；
3. 创建 Task；
4. 交给 Task Dispatcher；
5. 返回任务已经接受。

Request Handler 不负责等待 Agent 返回最终结果。

因此调用过程从传统的：

```text
Request
   ↓
Agent
   ↓
等待
   ↓
Response
```

改为：

```text
Request
   ↓
Create Task
   ↓
Submit
   ↓
Return
```

后续执行结果通过独立的 Event 链路返回。

------

# 7. Task Dispatcher

Task Dispatcher 负责将 Gateway 创建的 Task 异步提交到后端执行系统。

Task 是一次独立的 Agent 执行单元。

最小结构：

```text
Task {
    taskId
    sessionId
    input
    status
    createdAt
}
```

一个 Session 可以连续创建多个 Task。

例如：

```text
Session S10001
    ├── Task T001
    ├── Task T002
    └── Task T003
```

Gateway 创建 Task 后，将其交给异步任务层，然后立即释放当前业务处理资源。

Task 后续在哪台 Worker 执行，对 Gateway 不透明。

------

# 8. Agent Worker

Agent Worker 是实际的任务执行节点。

Worker 接收到 Task 后执行：

```text
获取 Task
    ↓
加载必要上下文
    ↓
执行 Agent
    ↓
调用 Model / Tool
    ↓
产生执行事件
    ↓
输出 Event
```

Worker 只关注：

```text
taskId
sessionId
task input
```

不关注：

```text
Client IP
Gateway IP
Connection ID
WebSocket Connection
```

因此 Worker 与 Gateway 之间不存在节点级绑定关系。

Gateway 和 Worker 可以独立进行扩容。

------

# 9. Event 模型

Agent 执行结果统一抽象为 Event。

不将执行结果设计成单一 Response，是因为 Agent Task 可能在执行过程中持续产生数据。

例如：

```text
START
PROGRESS
TOKEN
TOOL_CALL
TOOL_RESULT
FINAL
ERROR
```

Event 基本结构：

```text
Event {
    eventId
    sessionId
    taskId
    type
    payload
    createdAt
}
```

其中：

`sessionId` 用于结果路由。

`taskId` 用于确定 Event 属于哪一次 Agent 执行。

`eventId` 用于唯一标识事件。

`type` 用于客户端判断当前事件类型。

------

# 10. Event Receiver

Event Receiver 是 Gateway 的结果入口。

Agent Worker 执行过程中不断产生 Event。

Event Receiver 收到 Event 后，首先读取：

```text
sessionId
```

然后查询本机 Connection Manager。

如果当前 Gateway 持有对应 Session：

```text
sessionId
    ↓
Connection
    ↓
Client
```

Gateway 立即将 Event 推送给客户端。

因此 Agent 执行链和客户端连接链通过 Session 建立联系：

```text
Agent Task
    ↓
Event
    ↓
sessionId
    ↓
Gateway
    ↓
Connection
    ↓
Client
```

这就是整个异步网关的核心数据路径。

------

# 11. 流式结果处理

Agent Task 可以产生多个连续 Event。

例如一次完整执行可能是：

```text
START
 ↓
TOKEN
 ↓
TOKEN
 ↓
TOOL_CALL
 ↓
TOOL_RESULT
 ↓
TOKEN
 ↓
FINAL
```

Gateway 收到 Event 后直接向客户端推送，不等待 Task 完成。

这样客户端能够实时看到 Agent 的执行过程。

收到 `FINAL` 后，当前 Task 进入完成状态。

收到 `ERROR` 后，当前 Task 进入失败状态。

无论 Task 完成还是失败，都不代表 Session 自动关闭。

用户仍然可以继续在同一个 Session 中创建新的 Task。

------

# 12. 客户端断线与重连

Connection 和 Session 必须严格分离。

客户端断线时：

```text
Connection -> Closed
Session -> 保留
Task -> 继续运行
```

正在执行的 Agent Task 不因为客户端断线而停止。

客户端重新连接后携带原有：

```text
sessionId
```

Gateway 重新建立：

```text
sessionId -> new connection
```

关系。

之后该 Session 新产生的 Event 继续推送到新的客户端连接。

因此：

```text
Connection
```

属于短生命周期对象，

而：

```text
Session
```

属于长期业务对象。

------

# 13. Gateway 故障恢复

Gateway 节点异常不能影响 Agent Task 生命周期。

典型场景：

```text
Client
   ↓
Gateway A
   ↓
Task
   ↓
Agent Worker
```

此时 Gateway A 宕机。

Agent Worker 可以继续执行：

```text
Agent Worker
   ↓
Model / Tool
   ↓
Event
```

系统需要保证 Event 不因为 Gateway 暂时不可用而丢失。

Gateway 恢复以后，Recovery Manager 读取当前仍未结束的 Session。

然后恢复这些 Session 对应的 Event 接收能力。

流程为：

```text
Gateway Restart
      ↓
Load Unfinished Session
      ↓
Restore Session
      ↓
Restore Event Receiving
      ↓
Continue Processing Event
```

核心原则是：

> Gateway 故障只影响当前连接节点，不重新启动已经执行中的 Agent Task。

------

# 14. Recovery Manager

Recovery Manager 专门负责 Gateway 启动和故障恢复。

需要维护的恢复信息至少包括：

```text
sessionId
session status
unfinished task
```

节点启动后扫描未完成 Session。

对于仍有运行任务的 Session，重新恢复其结果接收能力。

如果客户端尚未重新建立连接，Session 可以保持等待状态。

当客户端重新连接以后，再重新建立：

```text
sessionId -> connection
```

映射。

------

# 15. 多 Gateway 部署

Gateway 以集群方式部署。

例如：

```text
Gateway A
Gateway B
Gateway C
Gateway D
```

客户端首次建立连接时，可以由负载均衡分配到任意 Gateway。

假设：

```text
Session S001 -> Gateway A
Session S002 -> Gateway B
Session S003 -> Gateway C
```

后端 Worker 不需要知道这些关系。

Agent Worker 只产生：

```text
Event(sessionId)
```

系统负责确保 Event 最终进入当前持有该 Session 的 Gateway。

这样 Gateway 可以根据客户端连接数量独立扩容，而 Agent Worker 可以根据模型任务数量独立扩容。

------

# 16. Session 迁移

Session 不能永久绑定某台 Gateway。

例如：

```text
第一次：

Session S001
    ↓
Gateway A
```

客户端断线以后重新建立连接：

```text
Session S001
    ↓
Gateway C
```

此时 Session 的当前 Owner 发生变化。

系统需要更新：

```text
S001 -> Gateway C
```

后续结果全部由 Gateway C 接收。

因此 Gateway Node 是 Session 的临时承载者，而不是 Session 的永久所有者。

------

# 17. 核心数据模型

整个系统主要包含三个业务对象。

## Session

代表长期会话：

```text
Session {
    sessionId
    status
    gatewayNode
    connectionId
    createdAt
    updatedAt
}
```

------

## Task

代表一次 Agent 执行：

```text
Task {
    taskId
    sessionId
    status
    input
    createdAt
    updatedAt
}
```

------

## Event

代表 Task 执行过程中的输出：

```text
Event {
    eventId
    taskId
    sessionId
    type
    payload
    createdAt
}
```

三者关系：

```text
Session
    ↓
多个 Task
    ↓
每个 Task 产生多个 Event
```

------

# 18. 核心业务链路

一次完整 Agent 请求过程如下。

客户端首先建立 WebSocket 或 SSE 连接。

Gateway 创建或者恢复 Session，并维护当前 Session 与 Connection 的关系。

用户发起 Agent 请求。

Gateway 创建新的 Task，并携带当前 `sessionId`。

Task Dispatcher 将 Task 异步提交至后端。

Gateway 完成任务提交以后，不等待 Agent 执行结束。

Worker 获取 Task 并开始执行 Agent。

Agent 根据需要调用模型、工具或者其他系统。

执行过程中 Worker 持续产生 Event。

每个 Event 都携带原始 `sessionId` 和 `taskId`。

Event 被返回 Gateway。

Gateway 根据 `sessionId` 找到当前 Session。

随后通过 Connection Manager 找到当前客户端连接。

Gateway 将 Event 实时推送给客户端。

收到 FINAL Event 后，本次 Task 完成。

Session 继续保持，可以接受下一轮用户请求。

------

# 19. 模块职责边界

整个架构中必须明确各模块职责。

### Gateway

负责：

- Connection；
- Session；
- 请求接入；
- Task 创建；
- Task 提交；
- Event 接收；
- Event 推送；
- Session 恢复。

Gateway 不负责 Agent 执行。

### Agent Worker

负责：

- Task 执行；
- Agent Runtime；
- Model 调用；
- Tool 调用；
- Event 产生。

Worker 不负责客户端连接。

### 异步任务层

负责：

- Task 传输；
- Event 传输；
- Gateway 与 Worker 解耦。

### Session / Recovery Store

负责：

- Session 元数据；
- 未完成任务信息；
- Gateway 故障恢复所需要的数据。

------

# 20. 部署架构

生产环境采用 Gateway Cluster + Worker Cluster 的部署模式。

Gateway 前部署统一负载均衡。

Gateway Cluster 负责承载客户端长连接。

Worker Cluster 根据实际 Agent 执行压力独立扩容。

整体关系：

```text
                Load Balancer
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      Gateway A  Gateway B  Gateway C
          │          │          │
          └──────────┼──────────┘
                     │
              Async Task Layer
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Worker A   Worker B   Worker C
          │          │          │
          └──────────┼──────────┘
                     │
              Model / Tool
```

Gateway 和 Worker 不要求数量一致。

两类节点根据各自压力独立扩缩容。

------

# 21. 可观测性设计

整个异步链路需要统一使用：

```text
sessionId
taskId
eventId
```

作为主要追踪字段。

必须能够通过 `sessionId` 查询完整业务链路，包括：

- Session 当前状态；
- 当前 Gateway；
- Session 包含哪些 Task；
- Task 当前状态；
- Task 执行时长；
- Task 产生过哪些 Event；
- 最终是否成功返回客户端。

建议所有日志统一携带：

```text
sessionId
taskId
eventId
gatewayNode
workerNode
```

从而实现端到端问题定位。

------

# 22. 高可用原则

系统需要满足以下基本原则。

第一，Gateway 节点故障不能导致 Agent Task 丢失。

第二，Gateway 重启不能重新执行已经提交的 Agent Task。

第三，客户端断线不能自动终止后台任务。

第四，Worker 节点和 Gateway 节点之间不存在固定绑定。

第五，Session 必须能够跨 Gateway 节点恢复。

第六，执行结果必须始终能够通过 Session 找回正确客户端。

------

# 23. 最终架构模型

整个项目最终可以抽象成四个核心职责：

**Connection 管客户端网络连接。**

**Session 管长期业务身份。**

**Task 管一次 Agent 执行。**

**Event 管 Agent 执行过程和结果。**

数据链路为：

```text
Connection
    ↓
Session
    ↓
Task
    ↓
Agent Execute
    ↓
Event
    ↓
Session
    ↓
Connection
```

因此整个 Agent 异步会话网关的本质是：

> **以 Session 为中心，将客户端长期连接与后端异步 Agent Task 解耦，并建立一套可靠的任务提交、结果回流和故障恢复机制，使 Agent 可以在任意 Worker 上独立执行，而所有执行结果最终都能够重新回到正确的用户会话。**
