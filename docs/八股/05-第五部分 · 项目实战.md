### 13 项目实战：hermes

#### 13.1 主循环与自我优化

- Agent 主循环与消息处理管道
- 为什么Hermes不搞多Agent编排而选择单Agent持久循环？
  1. 单 Agent 的持久循环是刻意的架构取舍，而非技术能力不足所致。
  2. 目标是从上下文链中提炼 Skill、积累 Hindsight；每切换一次 Agent 就会中断一次链路，因此选择不切换。
- 为什么保持六千行的单函数而不拆状态机或中间件链？这个选择在什么条件下会失败？
  1. 核心权衡在于控制流可见性与模块化。状态机的优势是节点可独立测试、转换边显式可见，但当异常路径较多时，每增加一种异常均需新增多条转换边，状态图反而更难以理解。
  2. 采用单体循环与子程序提取相结合的方式，使主循环始终明确当前执行进度；各异常分支按固定顺序排列，职责通过子程序拆分，但整体顺序由主循环统一编排。
  3. 若失败条件为团队超过五人同时修改同一函数，合并冲突将成为主要成本，此时应迁移至中间件链模式；判断标准为异常路径交互密度与并行修改人数的乘积。
- 外部记忆注入为什么在 Phase 4 执行，而不是在主循环每轮迭代内执行？
  1. Pre-LLM 插件钩子返回的 context 注入当前轮次的用户消息，且不破坏 system prompt 缓存。
  2. 外部 Memory Provider 的 Prefetch 在整个循环中仅调用一次，单次 turn 内不会每轮迭代都查询外部记忆服务。
  3. Prefetch 的语义是指令性记忆（期望 Agent 记住的行为），而非对话记忆，因此置于主循环之前。
- Hermes 的 IterationBudget 是什么？为什么默认限制为 90 轮？
  1. IterationBudget 是一个计数器，默认值为 90，每次迭代调用 consume() 消耗 1 个计数。
  2. 达到上限后，_handle_max_iterations() 会在去工具化的单次调用中要求 LLM 给出最终结论，避免任务中途结束。
  3. 限制 90 轮主要用于成本控制：每一轮都对应一次模型调用，无上限的 Agent 循环会导致 API 请求开销不可控。
- 请描述 Hermes Agent 中一条消息从发送到响应的完整生命周期（核心循环的 7 个阶段）？
  1. 初始化阶段（Turn 初始化）：保护 stdio 通道、确保 SQLite 会话记录存在、清理 surrogate 字符、生成 task_id 与 turn_id、重置 12 个计数器、清理失效 TCP 连接，并构建 IterationBudget(90)。
  2. 系统提示词构建阶段：按 Stable（稳定层）、Context（上下文层）、Volatile（易变层）三层架构一次性构建完整提示词，并在整个会话期间缓存复用。
  3. 预压缩阶段（Preflight）：当上下文长度超过上下文窗口的 50% 时，执行最多 3 轮有损压缩，仅保留前 3 轮与后 20 轮对话内容。
  4. 外部记忆注入阶段：执行 Pre-LLM 插件钩子与外部 Memory Provider 预取，将当前轮次的用户消息注入上下文，并启用 Prompt Caching。
  5. 主循环阶段：中断检查、API 消息准备、流式 API 调用（带速率限制保护）、响应验证（兼容 Chat Completion、Codex、Anthropic 三种格式）、finish_reason 分流、Guardrail 检查通过后执行工具（execute_code 等内部 RPC 不计入迭代次数）、空响应兜底。
  6. 回合结束阶段：预算耗尽时调用 _handle_max_iterations() 做去工具化最终调用生成总结；执行 transform_llm_output 与 post_llm_call 插件钩子；文件变更验证器校验 write_file/patch 真实落盘，失败补 warning。
  7. 后置处理阶段：在后台线程中提炼记忆与技能摘要，不阻塞最终回答返回给用户。
- 为什么Memory/Skill提炼放在后台线程？
  1. Memory/Skill 提炼在后台线程中执行，用户可先获取回答，无需阻塞等待。
  2. 后台线程将提炼出的新 Memory 写入 Hindsight，并检查、创建或更新 SKILL.md，实现每轮对话间隙的自动进化。
- API调用为什么优先使用Streaming模式？
  1. 即使没有消费者监听，仍应使用 Streaming：流式传输提供健康检测能力，一旦断流可提前判断模型异常。
  2. API 调用设有重试次数上限 _api_max_retries 次；外部还设有跨 Session 共享的 Nous Portal Rate Limit Guard（速率限制守卫）。
- 反思与自进化机制
- 错误恢复与失败重试
- 错误分类学方案在什么情况下会失效？如何改进？
  1. 失效场景：新提供商返回的错误格式不在规则库中时触发未知兜底；同一 HTTP 状态码在不同提供商间含义可能不同。
  2. 改进方向：使分类器支持插件式规则注册，每个传输自带分类规则，但可能削弱全局一致性；判断标准为错误空间的稳定性与提供商增长速度。
- 限流错误时，立即重试、换API key、切换备用模型这三种策略能否共存？由谁统一决定？
  1. 三种策略可同时并存，由集中式错误分类器统一决策。
  2. 分类器将任意异常映射为四个布尔恢复提示：是否可重试、是否应压缩上下文、是否应更换 Key、是否应切换模型；重试循环仅读取这些提示，不自行解析错误字符串。
- 模型返回空响应时有哪些降级策略？
  1. 空响应降级链：块检测→Streaming 恢复→前序 Turn 回退→Nudge→Prefill→最多 3 次重试→Fallback Provider→最终返回 '(empty)' 哨兵值。
  2. 该机制避免早期直接抛异常，防止会话终止与用户上下文丢失。
- Hermes有哪些故障恢复策略？
  1. conversation_loop.py 中内置 15+ 种独立故障恢复策略，涵盖计数器重置、Streaming 恢复、空响应降级链、Fallback Provider、Rate Limit Guard、文件写入验证等。
  2. 这些策略采用分层部署，当前层级无法恢复时进入下一层级，最大程度降低用户对故障的感知。
- Hermes Agent如何兼容不同API格式？
  1. 支持 Chat Completion、Codex Response、Anthropic Messages 三种 API mode，system prompt 格式由 anthropic_adapter.py 统一转换。
  2. model_metadata.py 通过 MODEL_CONTEXT_LENGTHS 常量表实现 token 估算，供 context compressor 与 context file 截断逻辑使用。
  3. 采用 Transport 策略模式，结合导入时自动注册表，将每种协议封装为独立传输类，统一实现基类定义的四个方法；对话循环按协议名获取对应实例，新增提供商仅需新增一个文件即可接入，核心循环逻辑无需改动。
  4. 适配器函数适用于提供商数量固定的场景；当提供商数量超过五个，且协议差异属于结构性差异时，策略模式可避免协议分支随提供商数量线性膨胀，维护成本更优。
- 非标准字段受控字典的设计边界在哪？什么时候该把字段'毕业'为标准字段？
  1. 判断依据为写入方数量与读取方数量的乘积：当某字段被三个以上写入方写入，且对话循环中存在两个以上调用点读取时，该字段应升级为规范化响应的标准字段。
  2. 受控字典的价值在于降低新协议特性的引入成本，待模式稳定后再固化；推理内容字段即是先进入字典、后毕业为标准字段的实例。

#### 13.2 上下文、记忆与可靠性

- 上下文管理与压缩
- Hermes 的 Preflight Context Compression 如何工作？为什么保留前 3 轮和后 20 轮？
  1. 进入主循环前，若会话历史超过上下文窗口的 50%，则触发压缩，压缩最多执行 3 轮。
  2. 每轮压缩中间 N 个轮次，保留前 3 轮与后 20 轮不变，使用辅助 LLM 对旧轮次进行有损摘要。
  3. 保留前 3 轮以维持任务初始上下文，保留后 20 轮以保留最近的推理链，中间过程可压缩。
- Hermes 的 System Prompt 为什么采用三层架构并只构建一次？
  1. 三层按更新频率划分：Stable 层（SOUL.md、工具行为规则、Skills 索引、环境提示等）整个 Session 不变，Context 层（按优先级加载 .hermes.md/AGENTS.md/CLAUDE.md/.cursorrules 等项目文件）Session 级可变，Volatile 层（Memory 快照、外部记忆 prefetch 结果、时间戳等）每个 Turn 变化。
  2. 只构建一次是为保证前缀完全一致、命中 Anthropic 的 prompt caching；每次重建都会破坏缓存，带来时间与费用代价。
  3. 代价是 session 内无法热更新 System Prompt，修改 SOUL.md 等内容需下次 session 生效；缓存失效唯一路径为 invalidate_system_prompt()，仅在 context compression 触发时重建。
  4. 拼接顺序固定为 stable → context → volatile，各层之间以 \n\n 连接；构建时 build_system_prompt_parts() 生成三层内容，build_system_prompt() 按序拼接后缓存至 agent._cached_system_prompt，API 调用时读取并追加 ephemeral_system_prompt。
  5. 每条发送至 API 的请求均应保存精确字节副本，避免重新序列化产生字节漂移，导致缓存静默失效。
  6. 分层的代价：构建函数需维护各层条件逻辑；可变层排在最后会降低模型对记忆快照等内容的注意力；重建时机需显式管理，漏掉触发条件会发送过期内容。
  7. 判断标准为会话长度与请求频率的乘积：短会话的缓存收益无法覆盖分层复杂度，以天计的长期助手才值得采用。
- Volatile层包含什么？为什么时间戳只用日期精度？
  1. System Prompt 包含 MEMORY.md 与 USER.md 快照、外部 Memory Provider 的 system prompt 块，以及时间戳。
  2. 日期精度可保证 System Prompt 全天字节稳定；分钟精度会导致每次重建都使前缀缓存 KV 失效。
- Context层如何发现和注入context文件？
  1. 按当前目录逐级向上查找 .hermes.md / HERMES.md → AGENTS.md → CLAUDE.md → .cursorrules，直至 Git 根目录。
  2. 剥离 YAML frontmatter，仅保留正文；单文件上限为 20K 字符或动态上限（取模型 context window 的 15%，下限 20K，上限 500K）。
- Stable层包含哪些内容？
  1. 系统提示涵盖 SOUL.md 或默认 Agent 身份声明、工具行为引导、Kanban 流程条件注入、Tool-Use Enforcement 分层配置、模型家族定制指引、Skills Index 二层缓存、Alibaba API 兼容补丁、环境提示、Python 工具链探测与 Profile 身份声明。
  2. 工具引导仅注入已加载工具对应的文本，未加载工具不占用 Token；模型家族指引针对已知失败模式定制（如 Gemini 使用绝对路径，OpenAI 需验证结果）。
- 短期/长期记忆与状态持久化
- SQLite 会话存储（state.db）有哪些关键设计？
  1. 采用 SQLite 的 FTS5 全文搜索，维护 standard 与 trigram 两张 FTS 表，以兼顾中英文分词需求。
  2. 当 WAL 模式在 NFS、SMB、FUSE 等文件系统上不可用时，自动回退为 DELETE 日志模式。
  3. 写竞争采用 BEGIN IMMEDIATE 事务加抖动重试机制（20–150ms，最多 15 次），通过引入抖动避免 convoy effect。
- 全文检索与向量语义检索的适用场景分别是什么？为什么默认使用全文检索？
  1. 全文检索擅长精确关键词命中，结果确定、便于调试，且零依赖（SQLite FTS5 随标准库提供）；向量检索擅长语义模糊匹配，例如查询“怎么联系他”可匹配到标题为“邮箱”的条目。
  2. 个人助手记忆规模通常为数百至数千条，查询以精确问题为主，全文检索排序已够用；当记忆规模上万且查询偏向语义模糊时，才值得引入向量后端。
- Hindsight 的记忆写入和读取流程是怎样的？
  1. 写入路径：每个 turn 结束后，由 MemoryManager.sync_all() 触发 HindsightProvider.sync_turn()，累计达到 retain_every_n_turns（默认 20）后调用 Hindsight API retain，将结果写入 PostgreSQL 并完成向量化。
  2. 读取路径：Agent 通过 hindsight_recall 工具发起调用，经 MemoryManager 与 HindsightProvider 访问 Hindsight API recall，执行语义向量检索与重排序后返回最终结果。
- 异步提取记忆时，“什么值得记住”的判断失误会带来什么后果？如何缓解？
  1. 记忆写入噪声会稀释检索质量：top-N 快照被无用条目占满，有效记忆被挤出。
  2. 缓解措施包括定期清理长期未使用的记忆条目，并在提取时要求每条记忆均为原子事实。
  3. 要点遗漏会导致用户重复说明；缓解措施是让模型在对话中主动调用记忆工具写入，而非完全依赖后台提取。
- Hindsight 的 prefetch 结果注入到哪里？为什么需要特殊注记？
  1. Hindsight 的 prefetch 结果注入到 Tool Results 中，而非 System Prompt，其注入通道与 MEMORY.md 不同。
  2. 通过特殊注记告知 Agent 该内容为被召回的记忆上下文，而非新的用户输入，应将其作为权威参考数据，避免被误当作注入指令。
- MemoryManager 为什么只允许注册一个外部 provider？
  1. 防止 Tool Schema 膨胀，避免记忆后端冲突。
  2. 多个外部 Provider 会延长 Agent Loop 的等待时间，并导致工具命名空间混乱。
- 为什么告诉 Agent “记住 X” 后，新开 Session 可能不记得？
  1. MEMORY.md 仅在 Session 启动时读取并注入 System Prompt；会话中途通过 memory 工具写入的内容需等待下一次 Session 才会被加载。
  2. 同一 Session 内可正常回答，是因为写入后暂存于当前 volatile 层；若写入未落入正确的记忆层级，或 MEMORY.md 超出 System Prompt 容量上限被截断，新 Session 将无法读取。
  3. 合理前提是会话中途产生的临时性新信息大多不紧急，用户偏好、环境细节等长期记忆延迟一个会话生效通常无害。
  4. 若每轮重新检索并注入记忆，会破坏字节稳定性、导致缓存失效，同时增加检索开销。
  5. 不合理场景是会话内自我学习：同一会话中被纠正的重要偏好需等到下次会话才生效，显得迟钝。
  6. Hermes 的折中方案是保留模型主动调用记忆工具的能力：写入即时生效，读取延至下次会话。
  7. 判断标准是记忆新鲜度价值与缓存折扣的权衡：新鲜度价值高的场景需提供实时注入通道。
  8. 会话早期写入的新记忆不会包含在冻结快照中，几十轮后被追问时，只能依赖记忆工具查询或对话历史回忆；若上下文压缩将该段历史摘要化，可能导致记忆断裂，因此需在压缩策略中保护关键记忆或主动回写。
- Hermes Agent 的记忆系统由哪几层构成？每层的作用是什么？
  1. 记忆体系分为三层：文件记忆层（SOUL.md、MEMORY.md、USER.md，由内置 Provider 注入 System Prompt）、Hindsight 层（外部向量服务，支持实时语义检索）、state.db 层（SQLite + FTS5，用于会话历史存储）。
  2. 文件记忆作为 Session 级快照负责基础 System Prompt 注入，Hindsight 负责实时语义检索与容量扩展，SQLite 提供跨会话全文搜索兜底。
  3. 每一层均为上一层的降级与兜底：MEMORY.md 被截断时由 Hindsight 补充，Hindsight 故障时由 MEMORY.md 兜底，两者均失效时通过 session_search 在对话历史中搜索。
- 如何设计个人助手的长期记忆加载策略，在保留关键信息的同时控制 token 开销？
  1. 采用冻结快照与实时查询双通道：会话启动时检索相关记忆并注入系统提示词后冻结，对话过程中通过记忆工具实时查询最新状态。
  2. 记忆提取在轮次结束后异步执行，不占用主对话时间，且可基于完整对话内容进行提取，质量更高。
  3. 记忆存储采用多后端插件化设计，默认使用全文索引（SQLite FTS5），可选向量语义检索，按需在精确性与资源开销之间权衡。
- 使用记忆系统有哪些常见陷阱？
  1. 记忆工具写入的生效具有延迟性：MEMORY.md 需在下个 Session 生效；Hindsight 写入后即可检索。
  2. MEMORY.md 注入 System Prompt 存在约 2200 字符的上限，超出部分不会显示，并非文件本身被截断。
  3. Hindsight 默认每 20 个 turn 自动执行一次 retain，可通过 retain_every_n_turns 调整频率；频率越高，Token 消耗越大。
  4. session_search 仅检索对话记录，不支持结构化知识检索；只能匹配用户说过的话，无法匹配已被记忆的事实。
- 工具调用与执行
- check_fn 的 TTL 缓存是如何设计的？为什么是 30 秒？
  1. check_fn 结果缓存时长为 30 秒，且在单次 get_definitions() 调用内，同一 check_fn 不会重复执行。
  2. 30 秒是折中值：过短会因频繁探测造成资源浪费，过长则导致用户启用工具集后生效延迟；该时长在实时性与性能之间取得平衡。
- 跨工具集重名保护是如何工作的？
  1. 当同名工具已存在且所属 toolset 不同时，默认拒绝注册。MCP 插件工具默认不得覆盖内置工具，仅当 MCP 服务间或插件显式设置 override=True 时方可覆盖。
  2. 当两个 MCP 服务注册同名工具时，允许后注册者覆盖先注册者。
  3. register() 在注册的同时递增版本号 _generation，使下游工具列表缓存失效。
- 为什么用 AST 扫描而不是直接导入工具模块？
  1. AST 扫描无副作用，可避免因依赖库未安装导致 import 失败，进而引发级联崩溃。
  2. 导入所有文件的问题不在于性能，而在于副作用：辅助模块可能触发平台检测、依赖检查甚至界面初始化。
  3. 通过 AST 预筛，仅导入包含顶层注册调用的模块，从而将启动副作用降至最低。
  4. 其代价是条件注册或运行时注册无法被静态发现；需要条件加载的场景应改用带缓存的可用性检查函数，而非条件注册。
  5. 判断标准在于工具注册是否为模块级确定性行为：若是，则 AST 预筛方案足够。
- Hermes Agent 工具系统如何实现自注册发现？
  1. 工具文件在模块顶层调用 registry.register() 完成自注册，无需维护显式 import 列表。
  2. discover_builtin_tools() 遍历 tools 目录下的 .py 文件，通过 AST 扫描检测模块级是否存在 registry.register() 调用，匹配通过后再用 importlib 导入。
  3. skills_tool.py 在模块顶层通过 registry.register() 自注册三个工具：skills_list、skill_view、skill_manage。
  4. 注册表的 check_fn 为常量 check_skills_requirements()，始终返回 True；由于 Skills 目录在首次使用时自动创建，因此该工具集始终可用。
- 如何统一管理不同来源的工具（内置、MCP、技能、插件）？不同来源的生命周期差异在哪一层解决？
  1. 采用统一注册表贯穿四个环节：内置工具自注册、MCP 工具按命名空间注册、技能与插件各自独立管理，工具调度路径统一。
  2. 工具发现通过 AST 静态扫描预筛与模块自注册完成，无需维护中心化清单，新增工具只需编写文件，索引维护成本为零。
  3. 注册时附带可用性检查函数，结合 TTL 缓存与宽限窗口，依赖短暂超时不会立即剥夺工具，从而避免工具列表抖动。
  4. MCP 工具以命名空间前缀注册，双下划线前缀确保远程工具永远不会覆盖内置工具。
  5. 不同来源的生命周期差异由各自管理面处理：内置工具随版本更新，MCP 支持重连与注销，技能由 Curator 自动归档；统一注册表仅负责调度。
- get_definitions() 如何解析工具集并过滤工具？
  1. 工具集解析采用 enabled_toolsets 做加法、disabled_toolsets 做减法，默认加载全部工具集；并对 HERMES_KANBAN_TASK 环境变量做特殊处理，强制注入 kanban 工具集。
  2. 最终结果以注册表 _generation、配置文件指纹等作为缓存键，借助 check_fn 的 TTL 缓存实现多层缓存。
- 动态 Schema 重写是如何实现的？
  1. 通过 dynamic_schema_overrides 回调，在每次调用 get_definitions() 时动态执行，并返回与静态 Schema 浅合并的字典。
  2. 典型场景包括：execute_code 的 sandbox_allowed_tools 根据实际启用的工具集实时调整，discord 工具按 Bot intents 隐藏不支持的操作，delegate_task 的参数描述随配置动态更新。
- 工具调用的 dispatch() 分发流程是怎样的？
  1. Agent 主循环通过 registry.dispatch(name, args) 分发工具调用；未匹配到工具时返回 {"error": "Unknown tool"}。异步工具由 _run_async 包装执行。
  2. 异常信息经 _sanitize_tool_error() 过滤，去除 framing token、CDATA、反引号等结构性噪音，避免污染模型后续推理。
- 并发安全白名单与声明式并发安全相比，哪种更安全？为什么？
  1. 白名单机制更安全：第三方工具默认不在白名单内，即使其声明支持并发安全，也一律按顺序执行。
  2. 声明式策略必须对所有非内置来源强制降级为不并发执行，否则框架无法校验声明真实性。
  3. 白名单的代价是维护成本：每个新增内置工具均需人工标注。
  4. 判断依据在于信任边界的归属：信任框架维护者采用白名单，信任工具作者采用声明式；工具来源越不可控，越应倾向中心化管控。
- 工具处理结果和错误如何返回？
  1. 工具处理函数须返回 JSON 字符串；注册表内置 tool_result() 与 tool_error() 两个通用辅助函数，统一构造返回值。
- 工具结果控制为什么需要三层预算？每层分别防什么失败？
  1. 仅做一层截断的问题在于决策权归属：若只在回注前截断，工具作者无法控制被截掉的内容；若只依赖工具内部截断，粗心的作者容易遗漏。
  2. 第一层：工具内部按语义自行截断，赋予作者语义感知的截断权；第二层：注册表单条上限，超限内容写入磁盘，内联仅保留预览与路径；第三层：整轮总量检查，超限后从最大结果开始溢出至磁盘。
  3. 单条预算按模型上下文窗口比例缩放；文件读取工具被特殊标记为永不落盘，避免“落盘→回读→再落盘”的无限循环。
  4. 判断标准为工具作者可信度与输出大小方差的乘积：内置小工具集一层即可，异构大工具集必须分层。
- 记忆污染防护

#### 13.3 安全与注入防护

- Hermes Agent如何防御Prompt Injection？
  1. 设置三道安全拦截：通过 _scan_for_threats() 进行正则模式检测，命中威胁时将整个文件替换为 BLOCKED 占位符；设定上下文截断上限，限制 context file 大小；借助 Steer 引导，在 System Prompt 中告知 Agent 合法输入边界。
  2. 检测采用较宽松的标准，以避免误伤安全文档。
  3. skills_tool.py 中硬编码了 _INJECTION_PATTERNS 检测模式列表，涵盖 ignore previous instructions、you are now、system prompt:、<|im_start|> 等典型注入特征。
  4. 检测逻辑在 skill_view() 加载内容时触发；若不可信的 SKILL.md 包含上述模式，Hermes 将发出告警。
- 一个 Agent 能在用户本机执行任意 shell 命令，如果 LLM 被 prompt injection 诱导执行危险命令，防线应该画在哪里？
  1. 模型输出端过滤不可靠：危险命令存在无数变体，模式匹配无法覆盖生成端的全部可能。
  2. 执行端拦截更可靠：无论命令如何生成，执行前均需经过统一校验闸口。
  3. hermes-agent 采用执行端包含式模式匹配，结合用户审批、会话级记忆与启动时冻结的旁路开关。
- 如果用户自己明确要求执行带危险模式的操作，安全系统应该阻止还是放行？安全与可用的边界怎么画？
  1. hermes-agent 采用审批机制而非直接阻止：命中危险模式时暂停执行，由用户选择本次允许、拒绝或本会话内始终允许。
  2. 用户拒绝时，模型接收拒绝原因，并可自行改用更安全的替代方案。
  3. 高级用户可启用 YOLO 模式（启动时冻结），跳过全部审批环节。
  4. 安全边界的设计理念是保护用户而非限制用户；在用户明确授权后，允许执行危险操作。
- 危险命令用黑名单（拦已知危险）还是白名单（只放已知安全）？hermes-agent 为什么选了前者？什么场景下应该反过来？
  1. 黑名单机制假设大多数命令安全、仅少数危险，与个人助手的使用模式相匹配；白名单机制则适用于不信任用户输入的多租户场景。
  2. hermes-agent 的用户为本机所有者，信任自身而不信任模型的判断，黑名单误报所带来的摩擦可通过“永远允许”机制消化。
  3. 选择标准取决于防护对象与合法命令空间的开放度：用户可信且命令空间开放时采用黑名单，用户不可信时采用白名单。
- YOLO 冻结这个设计具体防御了什么攻击？还有没有绕过可能？
  1. 防御的攻击链为：恶意内容诱导模型执行设置旁路环境变量的命令，致使后续危险命令跳过审批。
  2. 旁路开关在模块导入时读取一次并冻结，之后审批逻辑仅识别冻结值，运行时修改环境变量不生效。
  3. 残余绕过分为两类：一是用户启动进程时主动开启，属于用户选择而非绕过；二是恶意代码已在解释器进程内直接改写冻结变量，此时系统已被攻陷，不在同一威胁模型内。
  4. 安全关键配置必须在启动时确定，且运行时不可变更。
- MCP 子进程的环境变量为什么用白名单而不是和工具侧一样的黑名单？
  1. 工具侧执行的是用户自身的脚本，黑名单过滤已知敏感词已足够；MCP 子进程运行的是任意第三方 npm 包，其代码完全不可信。
  2. 黑名单无法覆盖未知命名变体（如自定义前缀的凭据变量），而白名单遵循“未列名即不提供”的最小权限原则。
  3. 过滤方向应由执行代码的来源可信度决定，而非全局统一处理。

#### 13.4 Skill 系统

- 什么是 Hermes Agent 的 Skill？SKILL.md 的元数据由哪些部分组成？
  1. Skill 本质上是一种带元数据的可执行工作流文档，采用 YAML frontmatter 与 Markdown 正文组合的结构。
  2. 每个 Skill 对应一个独立目录：~/.hermes/skills/<category>/<skill-name>/，其中 SKILL.md 为主文件，references/ 存放参考文档，templates/ 存放输出模板。
  3. frontmatter 关键字段包括 name、description、version、category、tags、related_skills、platforms、required_environment_variables；解析时兼容旧版 prerequisites 与 prerequisites.env_vars 字段。
  4. required_environment_variables 支持三种输入格式：字符串列表、带描述的字典，以及旧版 prerequisites.env_vars 格式。

- Skills Index 是如何加载的？如何节省 System Prompt Token？
  1. Skills Index 是 Skill 系统与 System Prompt 之间的桥梁，采用进程内 LRU 缓存与磁盘快照两级缓存机制，磁盘快照路径为 ~/.hermes/.skills_prompt_snapshot.json。
  2. build_skills_system_prompt() 返回 Skill 索引而非完整内容，每行格式为 tools/skill_name: 简短描述，描述长度为 10-30 字。
  3. 在 compact_categories 编码模式下，非编码类 Skill 在索引中仅显示名称而不显示描述，可节省约 60%-80% 的 Index Token。

- 斜杠命令如何加载 Skill？路径安全如何保证？
  1. skill_commands.py 将 Skill 加载与 CLI 斜杠命令绑定，用户输入 /my-skill 时通过 _load_skill_payload() 加载，支持绝对路径与相对路径。
  2. skill_view() 处理绝对路径时仅允许 SKILLS_DIR 与外部技能目录范围内的路径，防止读取 /etc/passwd 等系统文件。
- 请描述一条完整 Skill 从创建到执行的链路？
  1. 用户创建 SKILL.md 并存放于 ~/.hermes/skills/<category>/<skill-name>/ 目录；Agent 启动时，prompt_builder 调用 build_skills_system_prompt() 扫描目录并读取 frontmatter，经两层缓存生成 Skills Index 后注入 System Prompt。
  2. 用户输入斜杠命令后，skill_commands._load_skill_payload() 通过 skill_view() 读取 SKILL.md，执行注入检测、平台检查、环境检查与环境变量检查，然后 Agent 按 Skill 定义的工作流执行。
  3. 任务完成后，Hindsight 自动进行 retain 总结；若复杂度达标，将新建或更新 SKILL.md，完成技能进化。
- 哪些情况下 Skill 不会被加载或不可用？
  1. 平台不匹配时不加载该技能。例如，SKILL.md 中声明 `platforms: [macos]`，在 Linux 机器上会被跳过。
  2. 环境不匹配属于 offer-time 级别，仅在工具发现阶段生效；显式调用 `skill_view("my-skill")` 会强制加载，不受环境检查影响。
  3. 所需环境变量缺失时，Gateway 端返回提示，引导用户前往 CLI 配置；CLI 端则直接弹窗供用户输入。

### 15 项目实战：claude code

#### 15.1 主循环与工具系统

- Query Loop 状态机
- 工具系统（Bash/文件编辑）
- 什么是 Hooks 机制？以 Claude Code 为例说明它的类型与工作方式，为什么它很重要？
  1. Hooks 是 Agentic Coding 工具提供的事件钩子机制，允许在 AI Agent 工具调用前后插入自定义逻辑（脚本、校验、通知），实现自动化的安全审查与流程控制。
  2. Claude Code 的 hook 类型包括：PreToolUse（工具调用前执行安全检查、命令白名单、文件保护）、PostToolUse（工具调用后执行自动 lint/format、日志记录、触发测试）、Notification（需要用户注意时发送通知）、Stop（Agent 结束时生成报告）。
  3. 输入输出契约：hook 通过 stdin 接收 JSON（包含工具名、参数、文件路径等），以 exit code 控制行为（0 放行、2 阻止），stdout 可注入反馈信息供模型参考。
  4. 价值体现为：安全护栏（阻止危险命令、保护 package-lock.json/.env 等关键文件）、代码质量（写入后自动格式化与 lint）、合规审计（记录所有 AI 修改操作）、流程集成（CI/CD 与通知）、企业级自定义安全策略。
- 终端执行用长驻 shell 还是每次调用新建？各在什么条件下成立？状态恢复怎么补偿？
  1. 设计选择为每次调用新建执行上下文（spawn-per-call），而非采用长驻 shell。
  2. 长驻 shell 可节省启动开销、适合低延迟交互，但状态漂移会导致执行结果不可复现；spawn-per-call 干净且可复现，代价是启动与环境恢复成本。
  3. 状态补偿分为两层：会话快照恢复环境级状态，持久挂载的工作目录保留文件级状态。
  4. 判断标准为状态漂移风险与启动成本的权衡：任务对确定性要求越高、启动成本越可接受，越应选择每次新建执行上下文。
- 权限与审批模型
- Claude Code 的三层纵深防御架构是什么？每层的作用？
  1. 第一层：应用级命令安全检查。通过静态分析检测注入、混淆等恶意命令。
  2. 第二层：沙箱入口的权限决策引擎。决定命令是否需在沙箱中执行及执行模式。
  3. 第三层：系统级OS沙箱执行。使用Seatbelt或Bubblewrap提供进程隔离、文件系统与网络控制。
  4. 核心：任何一层均可独立阻断威胁，实现纵深防御。
- Claude Code 的网络隔离是如何实现的？为什么不用直接禁用网络？
  1. HTTP 代理（MITM）：拦截 HTTP 请求，只放行 allowedDomains 白名单中的域名（如 npm registry）；SOCKS 代理：拦截 TCP 连接，非白名单域名直接拒绝。
  2. seccomp 阻断 Unix Domain Sockets，防止 /var/run/docker.sock 逃逸。
  3. 不禁网的原因：npm install、pip install、git clone 等正常开发能力依赖网络，直接禁网会让 Agent 失去实用性；代理 + 白名单实现最小权限网络。
- 什么是裸 Git 仓库攻击？Claude Code 如何防御？
  1. 攻击原理：攻击者创建裸 Git 仓库并设置 core.fsmonitor 指向恶意脚本，Agent 执行 git status 时 Git 自动执行该脚本，绕过沙箱命令安全检查——因为命令不是 Agent 生成的，而是 Git 自己执行的。
  2. 防御：进入沙箱前扫描并清除裸 Git 仓库的危险配置（scrubBareGitRepoFiles）。
  3. 这是针对真实攻击向量的深度防御：不仅检查 Agent 生成的命令，还防御第三方工具被利用的间接执行。
- Claude Code 的权限系统为什么不是一个函数，而是一个系统？
  1. 单一权限检查函数无法应对多维度威胁，权限系统由 20+ 个模块组成，每个模块单一职责。
  2. 典型模块：bashClassifier（命令分类器，判断命令安全性）、shadowedRuleDetection（检测用户规则是否被更高优先级规则覆盖）、denialTracking（记录被拒绝的命令，避免重复弹窗）、permissionExplainer（向用户解释拦截原因）、bypassPermissionsKillswitch（紧急熔断，一键禁用所有权限绕过）。
  3. 设计原则是关注点分离：每个模块独立测试、可组合使用。
- Claude Code 如何通过 Prompt 引导 LLM 正确使用沙箱？
  1. System Prompt 明确引导：默认应在沙箱内运行命令，除非特定条件否则不要设置 dangerouslyDisableSandbox: true，让 LLM 生成的命令从源头走沙箱路径，而不是等命令生成后再拦截。
  2. dangerouslyDisableSandbox 需显式声明，且逐个重置回沙箱，不会因为一次禁用就永久绕过。
  3. 这是 Prompt Engineering 与 Safety Engineering 交叉的典型案例。
- 如何决定哪些环境需要人工审批？“隔离强度决定治理强度”的假设是什么？什么情况下会失效？
  1. 治理强度由隔离强度决定：容器与云后端自带操作系统边界，可跳过危险命令审批；本机与 Docker 后端直接接触用户机器，需走完整审批链。
  2. 其假设是强隔离后端自带操作系统边界，危险命令的破坏范围已被环境限制，额外审批只会重复打断用户。
  3. 失效条件：后端配置被弱化（如开启网络、挂载目录）但联动仍按后端类型跳过审批；新增后端漏配豁免规则，导致应审批的未审批或不应拦截的被拦截。
  4. 修复方向：豁免条件应检查实际配置而非后端类型标签，因为后端语义可能发生漂移。
- 为什么用环境变量驱动后端选择，而不是配置文件或代码分支？
  1. 环境变量可在部署层注入，容器化部署与CI环境中无需修改代码或配置模板即可切换隔离等级。
  2. 代码中仅保留一个工厂分发点，新增后端零侵入；代价是环境变量为全局隐式配置，排查当前后端需查看部署配置。
  3. 判断标准在于部署切换频率与代码改动面：部署频繁、代码改动面大时，采用环境变量驱动收益更明显。
- 一个执行层要支持多种环境，安全逻辑怎么写才能不写六份？
  1. 通过环境工厂统一抽象，定义抽象基类作为所有后端执行引擎的统一契约，工具层与审批层无需感知具体后端差异。
  2. 后端选择由环境变量驱动，新增后端仅需实现对应类即可接入，代码层面无需引入分支逻辑。
  3. 审批链仅维护一套实现，通过“是否跳过审批”的联动接口与执行环境解耦，避免为每种环境重复编写安全控制逻辑。

#### 15.3 Harness 设计与安全架构

- Claude Code 的 Harness 设计思路是什么？核心参数如何构成安全架构？
  1. --allowedTools 工具白名单限制可用工具，实现权限控制。
  2. --max-turns 限制最大循环轮次，防止无限循环与资源耗尽。
  3. --model 指定使用的模型；--verbose 输出详细日志提供可观测性。
  4. headless 无交互纯命令行模式，支持 CI/CD 集成。
  5. CLAUDE.md 实现项目级知识注入，等价于 AGENTS.md 机制。
  6. 「headless + allowedTools + max-turns」构成最小可行的 Harness 安全架构：无需 GUI 交互与人工审批，靠参数约束实现安全运行。
  7. 参数之下是三层纵深防御：命令安全检查（23+ 验证器）→ 权限决策引擎（shouldUseSandbox 三步决策 + 5 层设置源合并）→ OS 沙箱执行（Seatbelt/Bubblewrap + seccomp）。

### 16 框架对比与选型

- OpenClaw 和 Hermes 作为两个热门开源 AI agent 框架，它们的本质区别是什么？请从定位、架构、记忆系统、凭证管理、插件生态、渠道支持六个维度对比，并说明各自的适用场景？
  1. 定位不同：OpenClaw 是跨平台的个人 AI 助手网关，核心在于将 Agent 能力接入各类 messaging 平台；Hermes 是自我学习的 AI Agent，强调在持续使用中自我改进、不断成长。
  2. 架构不同：OpenClaw 将 runtime 视为一等公民，内置多个 runtime（如 Codex、Claude CLI），支持 ACP 协议，可调度多个独立进程并行工作；Hermes 使用原生 sync agent loop 运行所有模型，Codex 仅为可选 runtime，通过全局开关切换。
  3. 记忆系统不同：OpenClaw 采用纯 Markdown 文件存储，长期记忆存于 memory.md，每日工作记忆按日期命名，无隐藏状态，透明可审计；Hermes 基于 memory.md 与 user.md，外层叠加 SQLite 数据库与全文检索，并支持 8 个可选外部 Memory Provider。
  4. 凭证管理不同：OpenClaw 采用集中式管理，所有凭证统一存放于 auth profiles.json，由框架统一管理和分发；Hermes 采用委托式管理，基础凭证由自身管理，Codex runtime 的凭证交由 Codex CLI 各自负责。
  5. 插件生态不同：OpenClaw 拥有官方注册中心 ClawHub，支持 Skills、Code Plugins、Bundle Plugins 等多种类型，兼容多种客户端格式；Hermes 采用 pip 入口点发现机制，支持 agentskills.io 开放标准，可自我管理技能库。
  6. 渠道支持不同：OpenClaw 支持 27 个以上 messaging 平台，覆盖主流及国内外平台，横向覆盖面更广；Hermes 支持 19 个以上 messaging 平台，但深度集成 IDE（VS Code、JetBrains 等），纵向集成更深。
  7. 适用场景：需要广泛的 messaging 平台集成、使用订阅制凭证、看重本地透明可控、愿意手动维护配置时，选择 OpenClaw；需要自我学习能力、长时间无人值守运行、深度 IDE 集成、希望系统自动管理技能库时，选择 Hermes。

#### 16.1 Agent 框架选型与评价

- 主流 Agent 框架有哪些？如何选型？评价指标是什么？
- Copilot、Cursor、Claude Code 分别代表了什么产品理念？
  1. Copilot 代表“增强现有工作流”路线：嵌入已有 IDE，最小化改变开发者习惯，渐进式提升效率。
  2. Cursor 代表“重新设计 IDE”路线：以 AI 为核心重构编辑器体验，实现深度集成。
  3. Claude Code 代表“替代 IDE”路线：回归终端，将 AI 作为独立编程 Agent，不依赖图形界面。
  4. 三者从保守到激进，分别代表 AI 编程工具的不同进化方向。
- 比较 Claude Code 和 Cursor 的架构差异与适用场景？
  1. Claude Code 是 CLI Agent：终端运行、无 GUI 依赖，深度理解项目上下文，擅长复杂重构与自动化；扩展机制为 Hooks、MCP 与自定义命令。
  2. Cursor 是 VS Code fork 的完整 IDE：集成 Tab 补全、Chat、Agent 三种模式；Composer 的 Agent 模式支持跨文件编辑，并支持多模型切换与可视化 diff 预览。
  3. 项目级定制方式不同：Cursor 依赖 .cursorrules 文件，Claude Code 采用配置与 Hooks 体系。
  4. 核心差异可概括为：Claude Code 偏“Agent 驱动”，Cursor 偏“IDE 增强”；前者适合终端重度用户与复杂重构，后者适合依赖图形界面的日常开发。
- Claude Code、Cursor、GitHub Copilot、Windsurf、Codex CLI 这些主流 AI 编程工具如何对比与选型？
  1. 形态差异：Claude Code 与 Codex CLI 为 CLI Agent；Cursor 与 Windsurf 为 VS Code fork 的完整 IDE；GitHub Copilot 为 IDE 插件。
  2. Claude Code 与终端工作流无缝集成，深度理解项目上下文，擅长大规模重构；扩展机制为 Hooks、MCP 与自定义命令，适合终端重度用户。
  3. Cursor 提供 IDE 级体验，Tab 补全、Chat、Agent 三合一；Composer Agent 支持跨文件编辑，.cursorrules 定制项目指令，支持多模型切换。
  4. GitHub Copilot 与 GitHub 生态（PR、Issue、Actions）深度集成，补全最成熟且延迟低；Copilot Workspace 支持 Issue-to-PR 自动化，适合企业与 GitHub 重度用户。
  5. Windsurf 的 Cascade Agent 提供编辑器、终端与浏览器工具的全栈开发体验。
  6. 定价模式：Claude Code 与 Codex CLI 按 API 计量计费；Cursor 约 20-40 美元/月，Copilot 约 10-19 美元/月，Windsurf 约 15 美元/月。
- 面对不同的工程诉求，应该如何选择合适的 Agent 框架？
  1. 日常开发与终端自动化：采用 Codex CLI、Claude Code——开箱即用，审批流成熟。
  2. 复杂有状态工作流且需人工介入：采用 LangGraph——图编排、checkpoint 与 HITL 支持最完整。
  3. 端到端自主代码任务且需强隔离：采用 OpenHands——Docker 沙箱加事件流保证可审计性。
  4. 团队式角色化内容流程：采用 CrewAI——角色抽象直观，落地快。
  5. 多代理对话研究与群聊调度：采用 AutoGen——对话原语最灵活，偏研究生态。
  6. 统一管理多种 Harness：采用 OpenHands Agent Canvas——通过 ACP 拉起 Codex、Claude Code、Gemini CLI。
  1. LangGraph 采用状态机式编排，适合需要精确控制流程的复杂 Agent；CrewAI 采用角色扮演式多 Agent 协作，适合团队协作场景；AutoGen 由微软推出，采用对话式多 Agent 并支持人机协作，适合研究场景。
  2. Dify 是低代码 Agent 平台，适合快速原型和非技术用户；Coze（字节跳动）是面向消费者的 Agent 构建平台。
  3. 可控性：能否精确控制执行流程和错误处理；可观测性：日志、trace、调试工具是否完善。
  4. 扩展性：自定义工具、模型、存储的便捷度；社区生态：文档质量、社区活跃度、第三方集成。
  5. 生产就绪度：并发、容错、监控、部署支持。

### 23 AI 辅助编码实践

- 如何调试 AI 生成的代码？
  1. 既不盲目信任亦不全部重写，而是先复现问题，精准定位出错的具体逻辑。
  2. 阅读并理解相关代码段后再修改，采取最小化修复而非推倒重来。
  3. 修复后运行测试或构造边界用例验证，确认未引入新问题。
- 如何平衡 AI 生成代码的效率与代码可维护性？
  1. AI 倾向于生成可运行的代码，但不一定是结构清晰、易于维护的优质代码。
  2. 合入前审查命名、函数拆分与重复逻辑，必要时重构后再提交。
  3. 以团队编码规范与 lint 规则约束 AI 输出风格，保持代码库一致性。
- 什么是 Vibe Coding？为什么要避免？
  1. Vibe Coding 指不理解 AI 生成代码就直接采纳使用的开发方式。
  2. 这种做法等同于积累技术债务：问题无法定位，代码无人真正掌控。
  3. 正确做法是逐行理解关键逻辑，确保每段代码均可解释、可维护。
- AI 反复生成错误代码时你应该怎么办？
  1. 避免使用相同话术反复重试，应切换解决思路或技术方案。
  2. 为 AI 补充更多上下文：完整报错信息、相关代码与已尝试过的方案。
  3. 自行分析根因后精确提问，将问题缩小至具体函数或逻辑，再交由 AI 修复。
- 如何利用 Cursor 的 Agent 模式进行项目级修改？
  1. 使用 @file、@folder 精确引用需修改的文件与目录，提供充分作用域上下文。
  2. 使用 @git 关联版本历史，帮助 AI 理解近期改动意图。
  3. 先用 Plan Mode 让 AI 制定修改计划，确认方案无误后再执行批量改动。

#### 23.1 人机边界与质量门禁

- AI Coding 场景如何划分人机边界并设置质量门禁？
  1. 边界划分以风险与重复度为依据：低风险高重复任务（样板代码、测试补全、文档）交由 AI 自动生成；高风险动作（删库、权限变更、生产配置、密钥操作）强制人工执行或确认。
  2. 质量门禁按阶段分层：提交前执行 lint 与类型检查，PR 阶段运行自动测试并实施代码审查，合并前执行集成测试，层层拦截问题代码。
  3. AI 生成代码应具备可追溯性：标记生成来源及所涉 diff 范围，问题发生时便于回溯定位。
  4. 信任等级随验证记录渐进放开：某类任务连续达到验收标准后提高自动化级别，出现偏差时则相应收紧。
  5. 底线是验证成本必须低于生成成本：无法自动验证的产出，不应未经审核直接合入。

#### 23.2 AI 代码审查与调试

- AI 生成了代码之后，审查和调试环节怎么做才合格？
  1. 逐行审查 AI 生成的代码后再接受；盲目接受并完全依赖 AI、不做任何手动修改是大忌。
  2. 发现 AI 的错误时应手动修正，以体现自身技术判断。
  3. AI 犯错时应调整策略：改用更明确的提示词、补充上下文或更换思路，而非反复使用相同提示词重试。
  4. 编写测试验证 AI 生成的代码，以运行结果为准。
  5. 对代码负有完全的理解责任：被问及关键代码时，应能解释其作用与决策理由，不能以“AI 写的我不清楚”作答。

#### 23.3 AI 代码审查与调试

- 用 AI 定位 bug 的正确方法是什么？
  1. 问题定位遵循“看日志 → 读代码 → 缩小范围”的路径，反对瞎猜后改一行试一下的碰运气式调试。
  2. 向 AI 提供完整的错误信息与上下文（如堆栈跟踪、相关代码片段），而不是只丢一句“帮我修 bug”。
  3. 阅读堆栈跟踪与错误日志是基本功，需要刻意练习。
  4. 了解高频 Bug 类型有助于快速定位：基础级包括语法错误、类型错误、导入缺失、配置错误；中级包括竞态条件、内存泄漏、SQL 注入、循环依赖、异步错误处理缺失。

#### 23.4 AI 代码审查与调试

- 修复一个 bug 之后还必须做什么？
  1. 修复后运行测试确认生效，而不是改了就说“好了”。
  2. 举一反三检查同类问题：同一模式的 Bug 往往不止一处，仅修复报错的那一处不够。
  3. 复盘时讲清根因与修复逻辑，警惕级联 Bug——修复一个可能触发另一个。
  4. 留意高级陷阱类别：XSS/CSRF 等安全漏洞、数据库锁、UTF-8 编码问题、隐藏的性能瓶颈。

#### 23.5 开发前规划与架构设计

- 用 AI 编程工具限时开发全栈应用，动手之前应该做什么？
  1. 先理清需求再动手：明确功能范围与技术约束后再着手实现，而非直接让 AI 编写代码。
  2. 先手写架构再实现：在草稿或注释中先完成架构设计，由人确定架构、AI 负责执行，而非将架构决策完全交由 AI。
  3. 指令质量决定产出：向 AI 提供的 prompt 应清晰、分步且包含上下文，例如主动说明项目采用的架构与技术约定。
  4. 方案需有取舍意识：应能解释为何选择当前方案而非其他备选方案（例如后端选用 FastAPI 而非 Express 的理由）。

### 32 项目实战：发帖 Agent

- 如何实现一个能代替用户完成平台发帖全流程的 AI Agent？让世界适应 AI 是什么思路？
  1. 核心思路是让世界适应 AI，优先通过结构化 API 接口完成任务，而非依赖视觉识别模拟人类操作 UI。
  2. 任务分解链路：意图理解（明确用户发布目标）→ 内容生成（撰写文案并选择或生成图片）→ 标签推荐（基于内容匹配话题标签）→ 发布执行（调用发帖 API）→ 效果跟踪（监控数据反馈）。
  3. 每个步骤均设置校验节点，关键步骤（实际发布）加入人工确认环节。
  4. API 方案可靠性远高于 UI 自动化，不受页面改版、弹窗、加载动画等因素影响。
  5. 该题考察对模型中心论的批判：当环境侧结构化接口可用时，不应依赖模型的多模态屏幕操作能力。
