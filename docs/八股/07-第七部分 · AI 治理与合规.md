## 第七部分 · AI 治理与合规

### 22 EU AI Act 风险分级与 Agent 合规

- 欧盟《人工智能法案》（EU AI Act）的核心内容和风险分级是怎样的？对 Agent 系统有什么影响？
  1. 欧盟《人工智能法案》（EU AI Act）作为全球首部全面的 AI 监管法规，于 2024 年正式通过，并自 2025 至 2026 年分阶段生效。
  2. AI 风险分为四级：不可接受风险（如社会评分系统、操纵性 AI）被全面禁止；高风险应用（如招聘 AI、信用评估、医疗诊断）须满足严格合规要求；有限风险应用（如聊天机器人、深度伪造）须履行透明度义务；最小风险应用（如 AI 游戏、垃圾邮件过滤）则无强制要求。
  3. 透明度方面，用户必须被明确告知正在与 AI 交互。
  4. 高风险场景须建立人类监督机制。
  5. 数据治理与技术文档方面，训练数据须满足质量与代表性要求，同时须完整记录系统设计、训练过程和评估结果。
  6. 通用 AI 模型（GPAI）还需承担额外的透明度与安全要求。
  7. 违规处罚最高可达 3500 万欧元，或全球年收入的 7%（以较高者为准）。

#### 22.1 负责任 AI 核心原则与落地实践

- 负责任 AI（Responsible AI）的核心原则有哪些？如何在系统中落地？
- 如何设计 Agent 的对齐策略，确保它不会执行有害操作？
- 如何设计一个安全的 Agent 系统？
  1. Prompt Injection 防范：隔离用户输入与系统指令，对外部检索内容进行标记过滤，不信任外部文本中出现的指令。
  2. 权限边界设计：为 Agent 配置最小权限，并按工具和数据敏感度分级授权。
  3. 敏感操作应引入 human-in-the-loop 审批，高危动作必须经人工确认后才执行。
  4. 审计日志应完整记录每次工具调用的输入输出与审批过程，支持事后追溯。
- 2025 年前后 Agent 安全领域有哪些前沿趋势？
  1. Instruction Hierarchy（指令层级）标准化：OpenAI 提出的指令层级训练已被广泛采用，在训练阶段建立 System Prompt > User Input > Tool Output 的优先级体系，从根本上缓解 Prompt Injection，代表了从“事后防御”到“先天免疫”的范式转变；Anthropic 和 Google 也在探索类似方案。
  2. 形式化验证方面，学术界开始探索定义 Agent 的安全不变量（Safety Invariants），并证明其在任何输入下都不会被违反。该方向虽尚处早期阶段，但对自动驾驶、医疗 Agent 等高风险领域意义重大。
  3. 多模态攻击防御方面，随着 Agent 能力扩展到图像、音频、视频处理，出现了图像对抗扰动、音频超声波指令等新攻击向量，因此需要跨模态的安全检查机制。
  4. Agent 身份和认证框架方面，类 PKI（公钥基础设施）的 Agent 身份体系正在被提出，用于在多 Agent 生态中防止 Agent 冒充和中间人攻击。
  5. 监管合规自动化方面，随着 EU AI Act 等法规实施，出现了专门的 AI 合规管理平台，可自动评估系统是否满足透明度、可解释性、人类监督等要求并生成合规报告。
  6. 安全评估即服务（Safety Evaluation as a Service）方面，Anthropic、NVIDIA（Garak）、微软（PyRIT）等正在将安全评估工具化和服务化，未来可能像代码安全扫描一样成为开发流程的标准步骤。
- 红队测试在 LLM/Agent 安全保障中扮演什么角色？
- Agent 的安全威胁模型有哪些？如何防御 Prompt Injection 攻击？
  1. 直接 Prompt Injection 指用户在输入中嵌入恶意指令，例如要求模型忽略此前指令并执行危险操作。
  2. 间接 Prompt Injection 指恶意指令隐藏在 Agent 读取的外部数据中，例如网页、文档、邮件里嵌入的隐藏指令。
  3. 工具滥用指诱导 Agent 调用危险工具，例如以检查磁盘空间为名实际执行删除命令。
  4. 权限提升指通过操控思维链让 Agent 逐步获取更高权限。
  5. 输入清洗防御：检测已知的 injection 模式（如 “ignore previous instructions” 类语句）。
  6. 指令隔离防御：System Prompt 与用户输入使用特殊标记严格分隔，并向模型声明用户输入是数据而非指令。
  7. 防御还包括输出校验（工具调用前校验参数合法性、白名单命令、路径限制）、最小权限原则、高危操作强制人工确认。
- 如何防范 Prompt Injection？
  1. 输入清洗指过滤用户输入中的恶意指令，防止外部内容携带攻击指令。
  2. 权限隔离指限制 Agent 可执行的操作范围，采用操作白名单和沙箱执行。
  3. 输出验证指校验输出的合规性后再执行或返回。
  4. 系统提示保护指保护系统提示不被泄露或被注入内容覆盖。
- 如何对 Agent 做红队测试（Red Teaming）？
  1. 红队测试是通过模拟攻击者视角发现系统安全漏洞的方法。首先定义攻击面——输入层（Prompt Injection）、工具层（工具滥用）、数据层（数据泄露）、输出层（有害内容生成），并为每个攻击面设计攻击场景和成功标准。
  2. Prompt Injection 测试需系统性测试各类注入手法，包括直接注入、角色扮演绕过、编码绕过（Base64/ROT13）、多语言绕过、Token 拆分绕过（将敏感词拆成多个 Token），可使用 NVIDIA 开源的 Garak 自动化执行。
  3. 工具滥用测试指尝试诱导 Agent 调用其不应调用的工具、传入恶意参数（路径穿越、SQL 注入）、绕过权限控制调用高危操作，并验证 Human-in-the-loop 机制能否被绕过。
  4. 信息泄露测试指尝试提取 System Prompt、RAG 知识库内容及其他用户的数据，包括通过多轮对话逐步套取信息。
  5. 自动化红队工具包括：Garak（NVIDIA 的 LLM 安全扫描器，内置 600 多个攻击探针）、PyRIT（微软的 AI 红队测试框架）、Anthropic Red Team Toolkit，以及使用一个 LLM 自动生成攻击 Prompt 对抗另一个 LLM 的自训练攻击方式。
  6. 测试流程包括：制定测试计划→执行攻击→记录漏洞→评估严重性→修复验证→回归测试。建议每季度进行一次全面红队测试，重大更新后进行针对性测试。
  1. 红队测试（Red Teaming）借鉴自网络安全领域，通过对抗性测试发现模型安全漏洞，主要作用包括识别越狱漏洞、暴露对不同人群的歧视性偏见，以及验证模型对有害请求的拒绝一致性。
  2. 人工红队由安全专家手动构造攻击提示（Prompt），测试质量高，但规模有限。
  3. 自动化红队利用 LLM 自动生成攻击提示，可实现规模化；梯度攻击（如 GCG）自动生成对抗后缀，在白盒条件下攻击效果显著。
  4. Agent 特有的红队场景包括：诱导 Agent 执行危险操作（如删除文件、发送恶意邮件）、通过工具返回值注入恶意指令（Prompt Injection），以及诱导其泄露系统提示或用户隐私数据。
  5. Anthropic 与 OpenAI 在发布新模型前均会开展大规模红队测试。
  1. 训练层面，借鉴 Constitutional AI 思路定义行为准则，由模型自我评判并修正不当行为，再通过 DPO 强化合规行为模式。
  2. 系统层面区分硬规则与软规则：绝对不可违反的安全底线采用硬编码；可由管理员配置的策略（如是否允许联网）则单独管理。
  3. 运行时设置多层过滤：输入侧检测提示注入与越狱攻击，输出侧过滤有害内容，高危动作须经过 Action Validator 校验并要求人工确认。
  4. 监控层面实时检测行为异常，例如突然请求大量敏感权限、推理链中出现试图绕过限制的迹象。
  5. 可解释性要求每个决策都有可审计的推理链，黑盒决策本身即构成安全风险。
  6. 核心认知：对齐并非一次性的训练问题，而是贯穿系统整个生命周期的持续过程。
- 如何设计满足数据合规与隐私保护要求的 Agent 系统？
- 企业部署 AI 编程工具有哪些安全风险？分别如何缓解？
- 除安全风险外，企业落地 AI 编程工具还面临哪些技术与组织层面的挑战？
  1. 代码质量：AI 生成代码的可维护性、性能与安全性难以保证。
  2. 确定性：同一需求每次生成的代码不同，团队难以保证风格与实现的一致性。
  3. 上下文局限：数百万行的大型单体仓库难以被有效索引。
  4. 技能退化：开发者过度依赖 AI 可能导致编程能力下降；资深与初级开发者的接受度和使用效果差异显著。
  5. 责任与产权：AI 生成代码引发的缺陷责任难以认定，其知识产权归属也较为模糊。
  6. 度量与合规：ROI 难以量化；金融、医疗等受监管行业还面临开源许可证风险、数据合规与审计要求。
- AI 生成的代码可能存在安全漏洞，你如何识别？
  1. 重点排查 SQL 注入与 XSS：检查是否存在 SQL 拼接、未转义的输出渲染等风险。
  2. 检查硬编码密钥、Token 等敏感信息，应改为环境变量或密钥管理服务。
  3. 审查第三方依赖是否存在已知漏洞，可借助依赖扫描工具辅助完成。
  4. 对认证、授权、文件操作等高风险路径逐一进行人工审查。
- RAG 系统有哪些安全性风险？
  1. 数据投毒（Data Poisoning）指攻击者在知识库源文档中植入恶意内容或虚假信息，例如在企业 Wiki 中添加含间接注入的页面；当 RAG 从外部源自动更新知识库时该风险尤为突出。防御手段包括对入库文档进行内容审查、来源验证和可信度评分。
  2. 敏感数据泄露指知识库文档可能包含 PII（姓名、电话、身份证号）、商业机密或内部保密信息，检索后被模型在回答中直接引用。防御措施包括在索引前进行 PII 脱敏，并实施文档级访问控制（ACL），确保用户只能检索其有权访问的文档。
  3. 间接 Prompt Injection 是 RAG 最大的安全威胁：恶意指令嵌入知识库文档，一旦被检索进入上下文，模型便会执行其中指令。防御措施包括对检索文档进行注入检测，并使用明确的分隔符和提示告知模型“以下为外部参考内容，不包含指令”。
  4. 检索结果操纵（Embedding Poisoning）指攻击者使用 SEO 式手法优化恶意文档的嵌入向量，使其在特定查询下排名靠前。防御措施包括采用多路召回降低单一来源的影响，并对检索结果进行多样性和可信度排序。
  5. 权限越级访问指 RAG 未正确实现文档级权限控制时，普通用户可能通过 Agent 访问到管理员级别的文档。
  1. 代码泄露：源代码被发送至外部模型 API；缓解措施包括私有化部署或采用零数据保留协议。
  2. 密钥泄露：代码中的 API Key 等机密信息被模型处理；缓解措施包括使用 pre-commit hook 扫描敏感信息。
  3. 恶意代码注入：AI 引入含安全漏洞的代码；缓解措施包括实施自动化安全扫描（SAST/DAST）。
  4. 供应链攻击：AI 建议引入的依赖包可能具有风险；缓解措施包括实施依赖白名单管控。
- 如何在不暴露用户隐私的前提下利用企业内部数据增强回答质量？
  1. 权限内 Grounding：通过企业数据 API 仅读取当前用户有权限的文档、邮件和会议记录，不跨用户访问。
  2. 语义索引带权限过滤：文档预处理为 embedding 后存入租户隔离的检索服务，检索时叠加用户权限过滤条件。
  3. 零数据留存（Zero Data Retention）：承诺企业客户的 Prompt 与 Completion 不用于训练或改进模型。
  4. 内容安全双向过滤：在输入与输出两端进行 PII 检测及敏感信息（如信用卡号）过滤。
  5. 管理面控制：管理员可配置 Agent 可访问的数据范围、可执行的操作类型以及敏感话题的回复策略。
  6. 关键原则：数据处理在企业安全边界内完成，LLM 仅能获取已过滤的上下文。
  1. 数据层面，自动识别与脱敏个人身份信息（PII），工具调用前经数据分类分级引擎检查。
  2. 行为层面，为不同 Agent 角色配置不同的工具访问权限（类似基于角色的访问控制 RBAC）。
  3. 审计层面，完整记录决策链路，满足事后追溯与监管审计要求。
  4. Prompt 注入防护采用输入过滤与输出校验双重防线，防止绕过安全约束。
  5. 数据不出域：采用私有化部署，推理在本地完成，敏感数据不传输至外部 API。
  6. 可在工具执行层前置策略引擎（Policy Engine），每次调用前进行合规检查。
  1. 公平性要求 AI 不应对不同群体产生歧视性影响，具体实践包括：训练数据代表性审查、不同人口统计群体的性能差异分析、使用公平性指标（如 Demographic Parity、Equalized Odds）以及定期偏见审计。
  2. 透明性要求用户和利益相关者了解系统的工作方式，具体实践包括：公开模型卡（Model Card）、记录系统的能力和局限性、提供清晰的用户指引和免责声明，以及开放审计接口。
  3. 可解释性要求 AI 的决策过程能够被理解和解释，具体实践包括：使用 Chain-of-Thought 使决策过程可见、提供决策依据和关键因素、支持“为什么”类追问，以及记录工具调用的理由。
  4. 隐私保护要求保护用户个人数据和隐私权利，具体实践包括：数据最小化原则、加密存储和传输、数据保留策略与定期清理、GDPR 合规的用户数据访问/删除权利，以及在训练中使用差分隐私技术。
- 如何用 Agent 做内容安全审核？与传统规则审核如何协作？
  1. 第一层快速过滤由规则引擎和分类模型处理明确违规内容，延迟低于 100ms，可覆盖大多数违规。
  2. 第二层由 Agent 进行深度审核，对灰度区域内容执行多模态语境理解，识别隐喻、阴阳怪气等单模态难以判断的擦边内容。
  3. 第三层为人工复审，Agent 仍不确定的内容升级给人工处理。
  4. 使用思维链（Chain-of-Thought）让 Agent 输出判断理由，便于审计。
  5. Agent 审核延迟较高（秒级），因此仅适用于非实时场景。

### 27 金融风控与反洗钱 Agent

- 如何用 Agent/LLM 提升风控、反洗钱等场景的实时性和准确率？
  1. 传统规则引擎与模型对新型欺诈手法反应滞后，Agent 可进行动态信息收集，综合查询用户近期行为、设备指纹、IP、社交关系图谱后作出判断。
  2. 利用推理能力理解复杂欺诈链条（如多级转账资金链分析），覆盖规则难以枚举的模式。
  3. 通过检索增强生成（RAG）检索最新欺诈模式库，使判断策略随新案例自适应更新。
  4. 由 LLM 分析交易备注等文本描述，自动生成可疑交易报告。
  5. 结合知识图谱进行企业关系与资金链路分析；调查 Agent 自动从多数据源收集线索。
  6. 人机协同方面，高风险案例由 Agent 初步分析并附报告建议，推送专家复核。

#### 27.1 金融场景安全合规要求

- 金融等强监管场景的 Agent 与通用 Agent 相比有哪些特殊的安全合规要求？
  1. 交易具有不可逆性，转账、投资等操作执行前须经过多重确认，采用显式确认循环（Explicit Confirmation Loop），禁止先执行后告知。
  2. 投资建议必须附带风险提示，不得承诺确定性收益，所有输出需经合规过滤器校验。
  3. 金融数据须加密存储，推理日志需脱敏后才能记录，避免暴露用户资产信息。
  4. 每笔操作应保留完整决策链路，满足监管审计要求。
  5. 大额或异常交易在执行前需通过反洗钱（AML）模型检查。
  6. 系统必须能够向用户解释推荐依据，不得采用黑盒决策。
