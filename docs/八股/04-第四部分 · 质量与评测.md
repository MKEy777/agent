## 第四部分 · 质量与评测

### 10 提示词工程与生成质量

#### 10.1 提示词设计

- 角色与任务约束
- Prompt工程在Agent中的作用是什么？
  1. Prompt作为Agent的核心指令规范。
  2. 用于定义Agent的角色、工作规则、任务流程、输出格式和兜底策略。
  3. 高质量的Prompt能够有效规范Agent的意图识别、工具调用逻辑以及反思与评估标准。
  4. 可显著降低模型输出的随机性，从而提升Agent在复杂任务中的执行稳定性与结果一致性。
  5. 是低成本优化Agent整体效果与可靠性的核心手段。
- 示例驱动
- Skill 匹配的混合策略是什么？为什么单一策略不够？
  1. 混合策略包括：规则匹配优先（因其确定性高），语义匹配作为兜底（因其覆盖面广），关键词匹配作为补充（因其速度快）。
  2. 单一策略存在局限性：关键词匹配对隐式表述无效，语义匹配在精确模式匹配上效率低于规则匹配，规则匹配无法覆盖新表述。
  3. 混合策略通过互补各策略短板，实现优势最大化。
- Few-Shot在Agent中的作用？常见使用误区是什么？
  1. Few-Shot 能够以较低成本对齐输出规范、推理逻辑与格式标准，显著降低模型输出的随机性。
  2. 常见误区：盲目堆砌大量示例会导致上下文占用过高、推理速度下降、Token 消耗激增；示例杂乱无章反而会对模型产生误导。
  3. 正确做法是精选高质量、高适配的示例并控制数量，同时搭配固定规则 Prompt 使用。
- 任务分解与推理引导
- Skill 自动沉淀为什么要求“3次以上成功率>80%”？如何避免沉淀低质量 Skill？
  1. 操作模式需重复‘3次以上’以确保稳定可复用，而非偶然；‘80%成功率’作为经验阈值，保障模式可靠性。
  2. 避免低质量沉淀需采用成功率阈值过滤、持续监控质量指标、半自动沉淀需用户确认、版本管理支持回滚等措施。
- 三层 Skill 体系中，L1 组合层的职责是什么？
  1. 负责工作流编排，组合多个L0原子操作，按步骤顺序执行完整流程。
  2. 其职责是确保工作流步骤的顺序、依赖关系和中间结果正确传递，而非执行原子操作或理解业务语义。
- Prompt 模板与动态组装
- 上下文注入与路由
- 低资源、小众业务场景，Agent推理能力不足怎么优化？
  1. 构建场景专属推理示例库，通过 Few-Shot 引导模型精准推理，无需微调大模型。
  2. 细化场景任务拆解规则，用固定规则辅助模型弱化推理短板。
  3. 接入场景专属 RAG 知识库，用外部知识辅助推理决策。
  4. 增加推理结果二次校验，低置信度结果直接兜底或转人工，保证业务稳定。
- 什么是「反思（Reflection）」机制？自我反思是否必须依赖外部反馈？如何设计高效Reflection Prompt？
  1. 反思机制：完成任务单步或全程后主动复盘执行过程，识别推理错误、工具调用失误与信息缺失，并修正后续策略。
  2. 反思不依赖外部反馈：自主内省反思（仅靠任务轨迹与工具返回结果校验）与外部反馈反思（接收用户/系统评价）两种模式。
  3. 高效反思 Prompt 要素：要求复盘完整推理与工具调用步骤；设定校验维度（信息完整性、逻辑正确性、参数准确性、是否幻觉）；要求输出明确修正方案而非仅指出问题；结构化输出便于程序解析复用。
- 什么是「元提示（Meta-Prompt）」？如何让Agent自动生成子任务Prompt？
  1. Meta-Prompt 是规范模型「生成其他提示词」行为的顶层引导指令，不直接指导业务任务，是提示词的顶层生产规则。
  2. 落地方法：编写标准元提示，明确子任务 Prompt 必备要素（角色定位、任务目标、执行约束、输出格式、避坑要求）；顶层模型按规范自动填充生成子任务专属 Prompt；下发给对应执行 Agent。
- 设计System Message时，通常包含哪些核心要素以保证Agent行为一致性？
  1. 角色定位：明确 Agent 身份、专业能力与业务边界。
  2. 任务目标：清晰标注本次需要完成的最终交付物。
  3. 行为约束：写明禁止操作、权限限制、禁止编造信息。
  4. 输出规范：固定返回格式、语言风格与内容结构。
  5. 异常处理：信息缺失如何追问、工具调用失败如何重试。
  6. 五大要素齐全，才能保证多轮对话与多次工具调用行为稳定不跑偏。

#### 10.2 结构化输出

- JSON 与 Schema 约束
- 工业级 Agent 如何管理工具描述的 Token 预算？截断降级策略是什么？
  1. 预算分配：工具列表占上下文窗口的固定小比例（如1%），且单条描述设有字符上限。
  2. 截断降级：设计多级截断策略（例如完整截断、截断whenToUse字段、截断description字段、使用省略号），逐条截断以确保所有工具至少存在。
  3. 与Tool RAG的适用场景不同：当工具数量超过100时，使用RAG更准确；当工具数量在10到50之间时，可用预算制确保不遗漏工具。
- 字段类型与取值校验
- 输出解析与格式修复
- 失败重试与兜底
- 什么是「约束解码」？如何通过强制LLM输出JSON等Schema提升工具调用成功率？
  1. 约束解码：推理阶段对模型施加输出格式限制，强制按预定义 Schema 生成结构化文本，禁止自由文本输出。
  2. 提升工具调用成功率：预定义工具调用 JSON Schema（字段名、数据类型、取值范围、是否必填）；强制标准 JSON 输出，无多余解释与残缺参数；后端直接解析无需文本清洗；规避自由文本带来的幻觉参数问题。

#### 10.3 幻觉治理（方法论主场）

- 输入信息约束
- 检索与证据增强
- 大模型幻觉是什么？Agent如何缓解幻觉问题？
  1. 大模型幻觉指模型在无充分依据的情况下生成内容、数据或案例。
  2. Agent通过RAG检索真实素材，以替代模型的原生生成。
  3. 通过工具调用校验关键数据。
  4. 实现结果溯源，将输出内容与检索来源绑定。
  5. 禁止在无依据的情况下补全未知信息；当资料不足时，应直接提示用户，而非编造内容。
- 大厂自研底座Agent的幻觉问题，和开源模型Agent幻觉有什么差异？
  1. 开源Agent的幻觉问题主要表现为无依据编造、逻辑断裂及事实完全错误。
  2. 自研底座Agent的原生幻觉相对较少，主要集中在实时新知识缺失、小众垂直领域知识精度不足，以及多步骤推理中的逻辑衔接偏差。
  3. 防幻觉策略应重点聚焦实时检索补强、垂直知识校准与推理步骤校验，而非依赖全局内容拦截。
- 内容创作Agent如何避免编造素材、虚假数据？
  1. 核心素材与数据应通过RAG检索或官方资产库获取，严禁模型自由生成关键信息。
  2. 所有输出素材需绑定唯一ID与来源，确保可溯源性。
  3. 未检索到有效素材时，应主动提示信息缺失，禁止强行补全或编造。
  4. 新增内容需自动进行真实性校验，拦截虚假信息。
  5. 在工具输出后增设细节校验环节，核对参数完整性、时间有效性及数据逻辑一致性。
  6. 建立细节错误专属拦截库，沉淀高频错误案例，持续迭代校验规则。
  7. 事实层刚性约束：数据、案例、素材、时间、人物等关键信息必须走 RAG 检索/官方库调用，禁止模型自由生成。
  8. 创意层灵活放开：文案排版、语句润色、逻辑梳理保留创作自由度
  9. 输出后事实专项校验拦截虚假内容。
- 事实校验
- 输出审核
- 拒答与不确定性表达
- Critic 或 Quality Agent
- 多 Agent 交叉验证
- （RAG 专属机制见 05.5）
- 如何实现Agent的「内容审核」，防止生成违法违规信息？
  1. 输入前置审核：拦截用户违规提问与敏感请求，从源头规避风险。
  2. 输出实时风控：接入专业内容审核接口，识别色情、暴力、政治、谣言等违规内容。
  3. 自定义词库规则：针对业务场景配置专属敏感词与违规话术，补充通用风控短板。
  4. 疑似人工复核：不确定内容拦截输出、转入人工审核，批量复盘迭代规则。
  5. 违规记录沉淀：违规案例入库，持续优化风控模型与规则。

- 什么是电商RAG幻觉？最常见幻觉类型是什么？
  1. RAG 幻觉指模型输出知识库不存在、与商品真实信息不符的内容。
  2. 高频幻觉：编造优惠活动、虚构商品规格、错误解读售后规则、混淆相似商品参数、大促叠加优惠计算错误。

- 超长内容检索出现局部正确、整体错误的幻觉怎么治理？
  1. 全局语义对齐，不依赖局部片段匹配
  2. 价格、优惠、时效等关键字段结构化二次校验。
  3. 风控 Agent 兜底比对全文档信息纠正局部错误
  4. 高风险回答强制溯源引文，无原文依据直接拦截。

### 11 评测与质量保障

#### 11.1 评测方法论

- 离线评测与在线评测
- 自动评测与人工评测
- LLM-as-a-Judge
- LLM-as-Judge 是什么？有什么优缺点？
  1. 原理：用另一个更强的 LLM 评判 Agent 输出质量，给定评分维度和标准，Judge 输出分数和评语。
  2. 优点：快、便宜、可大规模评估。
  3. 缺点：有自身偏差（偏好长回答、偏好同模型输出）、对细微事实错误不敏感、评分一致性不如人工。
  4. 最佳实践：LLM-as-Judge 做大规模初筛，人工标注做最终验收。
- LangSmith 的核心功能有哪些？
  1. Trace 追踪：利用 @traceable 装饰器，自动收集 Agent 执行全链路中每一步的输入输出、Token 消耗及延迟数据，构建可追溯的执行轨迹。
  2. Dataset 管理：创建并管理用于评估的数据集，维护结构化的输入-输出样本对，并支持版本化管理，确保评估过程的可重复性与可比性。
  3. 自动化评估：通过 evaluate() 函数批量执行 Agent 任务，并调用自定义评估器对结果进行自动化打分，实现系统化的质量度量。
  4. 实验对比：通过设置 experiment_prefix 标识符来区分不同版本的 Agent 或策略，在评估平台上实现各项关键指标的可视化对比与分析。
  5. 在线监控：在生产环境中对 Agent 的 Trace 进行实时监控，支持按时间范围、所属项目、执行状态等维度进行查询、检索与异常告警，形成运行时的质量保障闭环。
- 测试集构建
- 回归测试
- 怎么设计 Agent 的回归测试集？
  1. 代表性：基于真实日志提取高频问题，全面覆盖主要使用场景。
  2. 多样性：测试用例需涵盖简单（30%）、中等（50%）、困难（20%）三个难度级别。
  3. 边界覆盖：涵盖空输入、超长文本、提示注入等异常用例。
  4. 可演进：将线上发现的坏案例定期纳入回归测试集，持续扩充。
  5. 实践建议：回归测试集应至少包含50个用例，集成到CI/CD流水线；每次PR自动运行，确保退化用例数为0才允许合并；按功能模块分组管理以加快问题定位。
- 在零依赖约束下，如何验证修改提示词后 Agent 没有变笨？
  1. 采用批量回归测试：从数据集中读取提示词，以多进程并行方式运行 Agent，输出标准化轨迹并聚合工具使用统计；修改提示词后重跑同一数据集，对比轨迹与统计结果以发现回归。
  2. 配套 SWE 任务运行器执行真实编码任务，轨迹可进入压缩管线；通过 tests 目录下的回归守卫测试固化关键行为（如会话隔离、审批隔离）。
  3. 该方案依赖离线数据集与人工轨迹比对，无自动评分机制；运行期不评估单条输出质量。
- Bad Case 管理与分析
- 线上监控与效果分析
- 离线评估和在线评估有什么区别？怎么配合使用？
  1. 离线评估：在固定数据集上执行评估器评分，具备可重复、快速迭代、低成本的优势，适用于开发阶段的提示词优化与模型选型，但存在覆盖范围有限、无法发现新问题的局限。
  2. 在线评估：在生产环境中收集真实用户反馈与行为数据，具备高度真实性并持续运行，适用于线上质量监控与 bad case 发现，但存在反馈延迟、噪声较大的不足。
  3. 配合方式：离线评估用于快速迭代（每日多次），在线评估用于长期监控（持续运行）；线上发现的 bad case 定期补充至离线评估集，形成完整闭环。
- Agent 可观测性的三个层次是什么？
  1. 日志（Logging）：记录每一步操作，包括用户输入、LLM 调用、工具调用及返回结果，为基础组件。
  2. 指标（Metrics）：聚合统计 Token 消耗、响应延迟、成功率及工具调用次数，用于监控与告警。
  3. 追踪（Tracing）：全链路追踪一次请求的所有步骤，涵盖每次 LLM 调用的完整 prompt 与 response，用于调试与优化。
- LangSmith 和 Langfuse 有什么区别？怎么选？
  1. LangSmith：LangChain官方推出的可观测产品，与LangChain/LangGraph框架深度集成，以SaaS模式为主，属于闭源产品。
  2. Langfuse：开源可观测平台，设计上与具体框架无关（可支持任何LLM应用），支持自主部署与数据私有化管控。
  3. 选择建议：若使用LangChain技术栈，建议优先选择LangSmith以获得最佳集成体验；若需自主部署或需支持跨框架监控，则应选择Langfuse，其开源特性更具灵活性。
- Prompt 迭代与效果对比
- 线上Agent效果变差，你会从哪些维度排查优化？
  1. 意图维度：识别准确率下降、需求误判。
  2. 规划维度：任务拆解混乱、步骤冗余。
  3. 工具维度：调用失败、参数错误、检索质量变差。
  4. 记忆维度：记忆污染、有效记忆丢失。
  5. 生成维度：话术混乱、幻觉增多、不符合业务规则。
  6. 针对性优化对应模块，同时埋点监控数据迭代。
  7. 输入层：用户请求特征变化、恶意请求激增、输入异常
  8. 模型层：版本迭代、推理精度波动、随机性变大。
  9. 工具层：接口超时、检索质量下降、参数解析错误
  10. 记忆层：记忆污染、新旧冲突、有效记忆丢失
  11. 工程层：限流、队列拥堵、资源不足、服务抖动。
  12. 定位根因后快速修复、灰度上线验证，并沉淀标准化排查规则降低复现概率。
- Agent推理出错、步骤拆解混乱，线上如何快速排查优化？
  1. 先止损：增加推理步骤校验机制，混乱步骤直接拦截、重新规划，避免错误执行。
  2. 再排查：复盘 prompt 指令、任务拆解逻辑、上下文信息，定位是指令模糊还是模型推理能力不足。
  3. 后优化：细化任务拆解规则、强制分步推理输出、优化示例 prompt、对复杂任务拆分更细粒度。
- 多Agent系统的「可观测性」包括哪些维度？如何监控协作状态？
  1. 链路追踪：记录任务全链路流转、Agent 调用顺序与消息传递轨迹，实现问题溯源。
  2. 指标监控：任务成功率、耗时、Token 消耗、并发量与错误率，量化系统运行状态。
  3. 日志审计：完整记录 Prompt、工具调用、状态变更与异常报错，支持复盘追溯。
  4. 状态可视化：实时展示 Agent 空闲/忙碌/故障状态、任务队列堆积与协作进度。
- 用户报告“Agent 昨天做了件怪事”，可观测性系统如何支持事后调查？缺什么信息？
  1. 调查路径：按日期列出会话，回放完整对话以查看输入输出与工具调用记录，最后查阅日志文件获取 API 细节与错误恢复信息。
  2. 缺失信息：未开启 verbose 时，DEBUG 日志无法恢复；系统提示词的精确内容未写入 SessionDB；未输出到响应中的推理过程不会被记录。
  3. 改进方向：将系统提示词哈希记录到会话元数据中，以便事后重建当时的上下文。
- 如何设计Agent的评测集？除最终结果，如何量化中间步骤（规划、工具使用）准确性？
  1. 评测集分层构建：覆盖简单、中等、复杂任务，包含闲聊、工具调用、多步骤推理与决策类场景。
  2. 最终结果评测：准确率、匹配度、完整性、合规性打分。
  3. 中间过程量化：任务规划合理性打分、工具选择正确率、参数填写准确率、步骤冗余率、逻辑连贯性。
  4. 自动化 + 人工评测：机器批量打分统计指标，人工复盘疑难案例，迭代评测标准。
  5. 版本对比评测：新旧版本同数据集对比，精准量化迭代效果。
- Agent 评估的 5 大核心指标是什么？分别怎么计算？
  1. 任务完成率：完成任务数 / 总任务数 × 100%，衡量任务完成度。
  2. 步数效率：实际步数 / 最优步数，比值接近1说明规划能力强。
  3. Token 成本：prompt_tokens与completion_tokens之和乘以单价，用于成本控制。
  4. 准确率：正确回答数 / 总回答数 × 100%，衡量事实准确性。
  5. 鲁棒性：异常输入下正常处理数 / 异常输入总数 × 100%，衡量稳定性。

- 业务Agent和传统机器学习推荐的核心迭代差异是什么？
  1. 迭代模式：传统算法依赖离线样本训练、周期更新、迭代滞后
  2. 推荐 Agent 支持在线实时复盘、动态策略调整、即时迭代优化。
  3. 决策能力：传统算法是固定规则+模型拟合，无逻辑推理
  4. Agent 具备语义推理、场景判断与归因分析，可处理复杂动态场景。
  5. 优化维度：传统算法仅拟合数据指标
  6. Agent 可结合业务场景、用户情绪与内容价值多维优化，更贴合平台长期生态。
- Agent 评估为什么比传统软件难？有哪些维度？
  1. 难点：LLM输出具有随机性（相同输入可能产生不同输出）、目标正确性难以定义、涉及多步骤与多轮交互过程。
  2. 评估通常涵盖六个维度：任务完成率、准确性、效率（步数、Token消耗与响应时间）、安全性、鲁棒性以及用户满意度。
  3. 传统软件主要关注功能正确性，而Agent则需要进行全方位评估。
- 什么是评估驱动开发（EDD）？它和 TDD 有什么区别？
  1. EDD（评估驱动开发）：首先设计评估数据集和评估器，随后开发Agent逻辑；每次修改后执行评估，直至分数达到预设阈值再部署上线。
  2. 与TDD的区别：TDD采用确定性单元测试（如断言相等），EDD使用概率性LLM评估器（通过打分与阈值判断）；TDD侧重功能正确性，EDD侧重多维度性能表现；TDD断言结果为二值（通过/失败），EDD评估结果为连续分数。
  3. 核心价值：避免基于主观直觉修改Prompt的盲目迭代，确保每次调整均有数据依据。
- 什么是影子测试（Shadow Testing）？在 Agent 评估中有什么作用？
  1. 影子测试：在生产环境并行运行新旧两套 Agent 逻辑，对比输出差异以验证优化效果，类似 A/B 测试但不影响用户体验——用户仅接触旧版，新版结果用于内部对比。
  2. 验证新版本性能是否优于旧版本，而不仅依赖离线指标。
  3. 发现离线评估未能覆盖的生产环境边缘情况。
  4. 降低新版本上线风险，通过影子测试运行验证无异常后再进行正式切换。
  5. 影子测试是连接离线评估与上线部署的关键验证环节，体现了系统的评估方法论。

#### 11.2 指标目录

- Agent 任务：任务完成率、工具调用准确率、参数与调用链准确率、幻觉率、稳定性与鲁棒性
- RAG：召回质量、排序质量、上下文相关性、回答准确性、忠实度与引用准确率
- RAG 系统如何评估？
  1. 评估机制分为检索质量评估与生成质量评估两个阶段。
  2. 检索质量评估指标包括召回率（衡量相关文档是否被成功检索）、精确率（衡量检索结果中相关文档的比例）以及MRR（平均倒数排名）。
  3. 生成质量评估指标包括忠实度（评估回答是否严格基于检索内容，是否存在幻觉）、相关性（评估回答是否切题）以及完整性（评估回答是否覆盖了问题的所有方面）。
  4. 工具层面，可采用 Ragas 框架执行自动化评估。
- 提示词：主要通过 11.1 的回归对比与 Bad Case 分析度量
- 如何区分Agent的「在线链路」与「离线链路」？各自关注的指标是什么？
  1. 在线链路（用户实时交互）：面向用户对话、实时问答与即时工具调用，核心追求用户体验；指标：TTFT 首字延迟、整体响应耗时、成功率、用户满意度、报错率。
  2. 离线链路（后台自动化任务）：面向批量文档处理、定时任务、数据复盘与知识库更新，无用户实时等待；指标：任务吞吐量、批量完成率、任务耗时、资源利用率、失败重试率。
  3. 链路分层设计可实现资源隔离、指标独立观测与针对性优化，避免离线任务抢占在线算力。
- 如何评估一个Agent的性能？关键指标有哪些？（成功率、步数、Token消耗、延迟）
  1. 任务成功率：任务完整完成、符合预期的比例，衡量最终效果。
  2. 执行步数效率：平均工具调用次数与冗余步数占比，衡量执行智能化程度。
  3. Token 成本指标：单任务平均输入/输出 Token、缓存命中率与单位任务成本，衡量降本能力。
  4. 延迟体验指标：TTFT 首字延迟、总响应耗时与超时率，衡量用户体验。
  5. 辅以报错率、重试率与用户满意度，形成完整量化评估闭环。
  6. 质量维度：结果准确率、细节错误率与幻觉发生率。
  7. 效率维度（补充）：单任务资源开销（内存、存储、外部 API 占用）。
  8. 稳定维度：空转率、死循环率与并发故障率。
  9. 体验维度：需求误判率、交互友好度、可人工干预性与问题可追溯性。
- 怎么量化评估一个 Agent 的性能好坏？四维评估框架是什么？
  1. 核心任务成功率：最终能完整解决用户需求的比例，是最根本的指标——能干成事才是硬道理，生产环境要求 >90%。
  2. 平均推理步数：步数越少 → 推理成本越低 → 响应速度越快 → 体验更好，反映 Agent 的效率而非能力。
  3. 工具调用准确率：避免无效/错误的工具调用，选对了工具、传对了参数才算成功，反映 Agent 决策精准度。
  4. 影子测试：生产环境同时运行新旧两套逻辑对比输出差异，验证优化效果，避免凭感觉说优化了的模糊表述。
  5. 四维框架覆盖能力（成功率）、效率（步数）、精准度（工具准确率）、验证（影子测试），体现系统化评估思维。
- 生产环境 Agent 必须监控的黄金指标有哪些？
  1. 质量指标：任务成功率（>90%）、幻觉率（<5%）、满意度（>80%）。
  2. 性能指标：首 token 延迟（P95<2s）、端到端延迟（P95<30s）、Token 消耗。
  3. 安全指标：提示注入次数、敏感信息泄露、危险工具调用、无限循环。
  4. 业务指标：DAU、会话长度、留存率、每次对话成本。
