## 第一部分 · Agent runtime

### 01 Agent 架构与工程化

#### 1.1 Agent 核心架构

- 规划、执行、记忆与工具模块
- AI Agent的五大核心能力是什么？
  1. 感知与理解：解析用户自然语言指令，识别其意图及模糊需求。
  2. 任务规划：将复杂需求分解为可执行的细分任务步骤。
  3. 工具调用与执行：自主调用搜索、API、代码执行、数据库等工具完成任务。
  4. 记忆管理：对短期会话上下文与长期用户记忆进行管理与维护。
  5. 反思与纠错：校验执行结果，在失败时进行重试并优化后续执行策略。
  6. 自主感知理解需识别隐性诉求与场景约束，而非依赖精准指令。
  7. 自主规划推理需支持优先级排序，并根据执行情况动态调整路径。
  8. 自主工具决策需支持按需组合工具，并拒绝无效工具调用。
  9. 自主反思迭代需在复盘错误后沉淀可复用经验，修正后续决策逻辑。
- 业务推荐Agent的四大核心能力是什么？
  1. 用户理解能力：解析用户画像、浏览习惯、互动行为与兴趣变迁，实时捕捉用户偏好。
  2. 内容甄别能力：识别内容质量、标签属性、热度潜力与违规风险，区分优质、低质与违规内容。
  3. 流量匹配能力：实现人、内容、场景三维精准匹配，完成个性化流量分发。
  4. 迭代优化能力：依据分发效果数据自主调整匹配策略，持续优化业务指标。
- 新账号冷启动场景，如何提升初始流量精准度？
  1. 无画像兜底：推送多品类高热度优质内容，快速获取初始行为数据。
  2. 快速画像构建：基于初期点赞、停留与划走行为，快速锁定核心兴趣，淘汰无效品类。
  3. 流量梯度放开：初始以小流量试探，验证精准度后逐步放大优质内容流量，规避冷启动乱推导致留存流失。
- 用户需求模糊、表述不完整，Agent怎么处理？
  1. 当用户需求信息不完整时，主动进行追问以获取关键信息，确保任务执行的准确性。
  2. 对于表述简单或模糊的需求，可参照用户历史记忆进行合理推断与适配。
  3. 面对复杂或开放性需求，避免直接盲目拆解执行，而是生成多种可行方案供用户评估与选择。
  4. 保留完整的对话记录，作为任务执行的依据，避免因主观臆断而导致任务偏差。
  5. 典型问题：过度自主脑补需求、私自补全缺失信息、自主推进错误任务且无任何提示。
  6. 执行前输出简明确认摘要供用户核验，降低需求理解偏差。
  7. 需求变更时实时终止旧任务并重置执行逻辑；模糊场景下降低自主权限，提升人工兜底优先级。
  8. 通过自主意图识别，区分核心诉求、次要诉求与缺失信息。
  9. 采用分层置信度判断：高置信度需求直接执行，低置信度需求定向追问。
  10. 依靠场景规则兜底，结合长期记忆与业务规则补全合理约束。
  11. 执行前进行摘要确认：模糊场景先输出执行方案，无冲突后自主落地，兼顾自主性与准确性。
- LLM驱动的自主代理系统的核心组件有哪些？
  1. LLM 是 Agent 的核心控制单元，负责主要决策与控制。
  2. 三个关键组件：规划、记忆与工具使用。
- Planner–Executor 等任务执行模式
- Agent 框架与运行机制（主循环）
- Agent Loop 的 6 步执行流程是什么？为什么是循环而不是一次生成？
  1. 六步循环：感知（Perceive）→ 推理（Reason）→ 规划（Plan）→ 执行（Act）→ 观察（Observe）→ 评估（Evaluate）。
  2. 循环而非一次生成的原因：Agent 需要根据工具返回结果动态调整策略，单次生成无法应对「API 返回错误」「数据格式不符」等真实场景。
  3. 每轮工具调用的结果会触发下一轮推理，这是事件驱动的本质；类比人是「边做边调整」，而非「想完一次做完」。
- 通俗解释什么是AI Agent？和普通大模型有什么区别？
  1. AI Agent 是以目标为驱动、具备自主闭环能力的智能实体。其核心能力包括感知、决策、工具调用、记忆存储与反思纠错。
  2. 普通大模型仅能被动响应单轮对话，缺乏自主规划能力。相比之下，Agent 能够自主拆解复杂任务，进行多步骤执行并具备容错纠错能力，从而完成开放式的复杂工作。
- 平台定制Agent和通用开源Agent的核心区别是什么？
  1. 平台定制Agent与特定大模型原生能力深度耦合，在中文场景、知识问答与多模态任务上具备专属优化。
  2. 平台定制Agent内置成熟的工具生态、检索能力与安全风控体系，开箱即用性更强。
  3. 平台定制Agent针对线上高并发、高稳定性业务进行了大量盲区修复与容错优化，更适配工业化落地。
  4. 核心架构由六大模块组成：大模型大脑、规划调度层、工具执行层、记忆管理层、安全隔离层与端云部署层。
  5. 与通用 Agent 的本质区别在于原生支持云边端一体化部署、内核级安全隔离、精细化权限管控、断点续跑与高并发高可用。
  6. 适配政企私有化、国产化与合规化落地场景。
- 业务推荐Agent和通用工具Agent的本质区别是什么？
  1. 通用Agent以功能任务完成为目标，不受业务指标约束。
  2. 业务推荐Agent以优化核心业务指标（完播率、留存率、转化率、互动率）为导向，紧密围绕流量与用户体验，与业务深度绑定。
- 一站式低代码智能体平台的核心优势是什么？
  1. 支持低代码快速构建，通过自然语言描述业务逻辑即可生成专属Agent。
  2. 原生适配华为云生态，无缝对接云服务、数据库、IoT设备及安全体系。
  3. 具备企业级可靠性，内置容错、隔离、权限、审计与运维全套能力，解决难落地、难规模化、难合规问题。
- 什么是Agent反思（Reflection）？作用是什么？
  1. 反思是 Agent 的自我纠错机制：任务执行完成或失败后，自动校验执行结果。
  2. 排查工具调用错误、步骤漏洞与结果偏差，记录问题并优化执行逻辑。
  3. 支持失败重试与策略迭代，大幅提升复杂任务的准确率与稳定性。
  4. 缺乏反思机制时，Agent 会重复执行错误决策与无效工具调用，难以适应场景变化。
  5. 边缘场景仅能依赖人工兜底，系统将长期停留在初始 Demo 水平。
  6. 反思机制使 Agent 具备『单次执行、多次成长』的能力，是工业化落地的核心前提。
  7. 无明确任务验收标准，Agent 无法判定失败
  8. 反思 Prompt 过于笼统，无细化纠错规则，复盘流于形式。
  9. 工具调用结果无结构化校验，无法识别隐性错误
  10. 反思结果不沉淀、不迭代，纠错经验无法复用。
- Agent长期运行，如何避免决策逻辑固化、能力僵化？
  1. 记忆动态更新：新场景与新解法实时沉淀，自动替换过期旧经验。
  2. 定期自主复盘：批量复盘历史任务，持续优化决策短板并修正错误逻辑。
  3. 低风险探索机制：在低风险场景允许自主尝试新方案，逐步拓展能力边界。
  4. 人工弱干预：仅进行方向校准，不干预具体执行，保留自主进化空间。
- Agent的「自主迭代闭环」完整链路是什么？
  1. 执行采集：完整记录任务推理、决策、执行与结果的全链路数据。
  2. 自主复盘：识别错误点、低效点与可优化点，并进行归因分析。
  3. 经验沉淀：将优化逻辑、正确案例与避坑经验写入长期记忆。
  4. 迭代落地：后续同类任务自动复用优化方案，规避历史问题，实现无需人工更新的持续进化。
- 什么是Agent推理能力？它和普通对话生成有什么本质区别？
  1. 推理能力指针对复杂、模糊、多步骤问题自主思考、逻辑拆解、分步推导的能力。
  2. 普通大模型是单轮被动生成，无思考过程与逻辑闭环。
  3. Agent 推理具备前置思考、分步推导、逻辑校验、结果复盘的完整链路，能解决开放式复杂业务问题。
  4. 普通CoT仅完成分步输出答案，属于静态推理；自主推理则覆盖前置校验、执行校验与事后复盘，形成动态闭环推理。
  5. 前置需求校验：先判断需求完整性，确定是否需要补充信息。
  6. 动态任务拆解：根据场景实时调整执行步骤，而非一次性固定路径。
- 单智能体的完整工作链路是什么？核心四大模块？
  1. 感知理解模块：解析自然语言、识别真实意图、区分模糊与精准需求。
  2. 推理规划模块：拆解复杂任务、制定分步执行计划、确定执行优先级。
  3. 工具执行模块：自主调用工具完成业务操作、输出阶段性结果。
  4. 记忆反思模块：沉淀有效经验、过滤无效信息、复盘问题、迭代优化。
- 怎么理解Agent的「自主性」？和传统自动化脚本有什么区别？
  1. 自主性：无需人工干预，自主完成需求理解、任务拆解、异常处理与复盘迭代。
  2. 传统脚本是固定规则、固定流程，无法适配模糊需求与未知场景。
  3. Agent 依托大模型推理能力适配开放式、个性化场景，并通过反思与记忆持续优化执行效果。
- Agent的通用抽象架构是什么？「感知、规划、行动、记忆」四模块如何闭环协作？
  1. 感知模块：接收用户提问、工具返回结果与环境信息，同步传递给规划层。
  2. 规划模块：结合记忆中的历史数据，将总目标拆分为可执行的子任务。
  3. 行动模块：根据规划结果调用工具、执行操作，产出执行结果。
  4. 记忆模块：存储本轮对话、规划轨迹与工具返回数据，供下一轮感知与规划复用。
  5. 四模块循环往复，形成完整任务执行闭环。
- 从0设计一套生产级自主Agent，完整架构是什么？
  1. 感知理解层：负责需求解析、模糊识别、场景判别与缺失信息检测，为自主理解提供支撑。
  2. 自主规划层：承担动态任务拆解、优先级排序、执行路径优化与异常预案生成，是核心决策中枢。
  3. 工具执行层：实现自主工具选型、参数组装、批量执行与结果接收，负责落地执行能力。
  4. 反思校验层：执行结果核验、错误归因、方案优化与自主纠错，保障整体执行质量。
  5. 记忆迭代层：长短时记忆分层存储、经验沉淀、去重优化与自主进化，支撑持续能力提升。
  6. 安全管控层：实施权限分级、风险拦截、操作留痕与合规兜底，实现可控自主。
  7. 整体设计理念：高自主、高稳定、高安全、可迭代，追求零或最少人工干预。
- 业务推荐Agent的整体架构分为哪五层？各自负责什么？
  1. 感知层：采集用户行为、内容特征与场景信息。
  2. 理解层：通过大模型对用户兴趣、内容标签与场景属性进行语义解析，生成个性化匹配特征。
  3. 决策层：自主判断分发权重、流量配比与推荐优先级，规避同质化与低质内容。
  4. 执行层：对接流量分发系统，完成短视频、直播、电商内容的个性化推送。
  5. 迭代层：采集分发效果数据，复盘指标短板，自主优化决策策略。
- 内容完播率低，推荐Agent如何自主优化分发策略？
  1. 归因分析：自主判断完播率低的核心原因，如人群匹配度不足、内容时长不符、题材兴趣度偏低。
  2. 精准人群收缩：缩小分发范围，仅覆盖高匹配潜在用户，减少无效曝光。
  3. 降低低完播内容的推荐权重，优先推送同类型高完播内容。
  4. 场景适配优化：短时长内容匹配碎片化时段，长时长内容匹配休闲时段，提升完播概率。
- 低质内容蹭流量，如何精准甄别并限流？
  1. 内容特征识别：解析原创度、画面质量、文案逻辑与信息密度，识别洗稿、搬运及模板化低质内容。
  2. 行为数据佐证：结合完播率、点赞率、评论质量与二次传播数据，辅助判断内容真实质量。
  3. 流量分层管控：优质内容加权扶持，低质蹭流内容限流降权，违规内容直接拦截清理。
- 电商带货场景，如何平衡「内容体验」和「带货转化」？
  1. 人群精准分层：识别购物意愿、消费能力与品类偏好，仅向高意向用户加大带货内容推送力度。
  2. 内容质量前置校验：优先推送优质种草内容，拦截硬广与低质带货视频，保障浏览体验。
  3. 转化效果复盘迭代：依据点击、加购与成交数据调整带货分发权重，淘汰低转化劣质内容。
- 业务推荐Agent的实时性体现在哪里？为什么极其重要？
  1. 实时性表现为即时行为实时采集、兴趣画像实时更新、分发策略实时调整与热点内容实时响应。
  2. 短视频时效性强且用户兴趣动态多变，离线更新难以适配热点爆发与临时兴趣变迁。
  3. 实时决策可最大化捕获流量窗口。
- 直播场景和短视频场景的推荐设计差异是什么？
  1. 核心依据不同：短视频侧重内容画面、文案、标签与历史互动数据；直播侧重实时在线人数、弹幕互动、停留时长、转粉率与实时氛围。
  2. 决策时效不同：短视频分发可离线决策；直播需秒级实时调整流量，以适配直播状态的动态波动。
  3. 优化目标不同：短视频优先完播、点赞、转发；直播优先停留、互动、成交与转粉留存。
- Agent的「自主性」体现在哪些方面？如何衡量自主程度？
  1. 四大体现：自主决策（判断是否调用工具、是否追问用户）、自主任务拆解、自主纠错复盘、自主迭代（依靠历史记忆优化执行逻辑）。
  2. 衡量指标：人工干预次数、任务自主完成率、异常场景自主修复成功率、工具自主调用准确率。
- 办公场景Agent，如何自动处理批量复杂文档任务？
  1. 自主任务拆分：将批量文档任务分解为读取、解析、清洗、统计、排版与汇总等子任务。
  2. 自主工具调度：按需调用文档解析、表格统计、格式渲染等工具。
  3. 自主规则适配：根据文档类型与业务规范自动适配排版统计规则。
  4. 自主结果校验：核对数据完整性与格式规范性，自动修正瑕疵，批量输出标准化成品，全程无需人工分步干预。
- 为什么极其看重Agent的「自主性」？核心业务价值是什么？
  1. 解决传统Agent对人工依赖度高的问题，避免频繁调参、反复修改Prompt及人工干预流程。
  2. 适用于Office、Azure、企业办公等开放式、非标准化且复杂多变的业务场景。
  3. 支持大规模批量任务自动化落地，提升执行效率并降低人工成本。
  4. 通过长期迭代沉淀业务专属智能能力。
- 为什么业务推荐必须用Agent，传统算法推荐有什么短板？
  1. 传统算法规则固化、泛化性差，难以捕捉模糊兴趣与实时场景变化，易导致结果同质化与审美疲劳。
  2. 传统算法无法自主适配热点事件、节日氛围、用户情绪等动态场景。
  3. Agent具备语义理解、场景推理、动态决策与自主迭代能力，能够突破规则限制，精准匹配个性化隐性需求。
- 推荐Agent为什么要做「去同质化」设计？核心技术思路是什么？
  1. 同质化推荐引发审美疲劳、划走率飙升与留存下降，是推荐系统的核心痛点。
  2. 核心技术思路包括内容特征差异化校验、兴趣多样性加权、同类内容流量限流与跨品类兴趣拓展。
  3. 在贴合核心喜好的前提下丰富内容维度，平衡推荐精准度与内容多样性。
- 如何解决「用户越刷越窄」的流量困境？
  1. 兴趣多样性加权：设置核心兴趣与拓展兴趣双权重，核心兴趣保障基础体验，拓展兴趣打破内容固化。
  2. 同类内容限流：对长期浏览的单一品类设置最大推送比例，避免内容过度集中。
  3. 弱兴趣试探推送：以低权重推送关联新内容，捕捉潜在新兴趣，动态拓宽兴趣边界。
- 热点内容爆发场景，如何平衡「流量热度」和「内容泛滥」？
  1. 热点流量放大：识别合规优质热点，短期内提升分发权重，抢占流量红利并拉升用户活跃度。
  2. 泛滥风控限流：对同质化热点与低质跟风翻拍内容自动降权，防止内容刷屏泛滥。
  3. 个性化差异化推送：对偏好热点的用户增加推送频次，对反感热点的用户直接屏蔽，实现热点内容的千人千面适配。
- 什么是「Agentic AI」？与传统AI系统的本质差异是什么？
  1. Agentic AI：以目标驱动自主完成完整业务流程，具备规划、工具调用、记忆、自我反思全套能力的新一代 AI 范式。
  2. 传统 AI 被动、功能固定、输入输出一一对应，仅能完成预先定义的单一功能。
  3. Agentic AI 主动目标驱动、无固定执行流程，可自主拆解任务、调用外部工具、依靠记忆迭代优化，适配任意复杂开放式任务。
  4. 自主Agent与传统被动Agent的本质区别在于端到端自主闭环：需求理解、任务拆解、决策规划、工具执行、异常纠错与复盘迭代全流程无需人工分段介入。
  5. 传统被动Agent依赖精准的人工Prompt，缺乏自主判断能力；这是传统AI被动响应模式在Agent场景下的具体体现。
  6. 自主Agent能够适配模糊、残缺、复杂的目标，自主补全缺失信息并修正执行偏差。
  7. 传统Agent不具备迭代能力；自主Agent基于历史执行经验持续优化后续决策，越用越智能。
- 简述LLM作为Agent「大脑」的优势与局限性
  1. 优势：自然语言理解强（能读懂模糊口语需求）、具备基础推理与任务拆解能力、能读懂工具描述并生成调用参数、泛化能力强（未见过的任务也能拆解执行）。
  2. 局限：幻觉问题、长上下文记忆弱（超长任务丢失前置信息）、多轮推理延迟高（不适合超高并发实时场景）、调用成本高、复杂数学与精准计算弱。
- 多轮对话中，Agent如何判断「直接回复」「调用工具」「请求澄清」三种决策？
  1. 直接回复：用户需求清晰，回答所需信息已存在于上下文或模型内置知识，无需调用外部工具。
  2. 调用工具：内置知识无法给出客观准确答案，需要实时外部数据（天气、数据库、业务接口、文档）时，自主选择对应工具获取。
  3. 请求澄清：指令语义模糊存在多种解读、缺少工具调用必填关键参数、或需求存在逻辑冲突时，主动提问确认。

- 意图识别不准，简单需求误判、复杂需求漏判怎么优化？
  1. 分层意图识别：先识别核心诉求再细分子场景，避免笼统判断
  2. 低置信度不盲目执行，主动追问补全。
  3. 沉淀线上误判样本持续微调意图模型、优化 Prompt 规则
  4. 结合用户历史记忆与对话上下文辅助判断。
- 智能体支持哪些使用渠道？
  1. 支持网页对话、IM 机器人、API 调用、网页 URL、CLI、流水线及定时运行等多种使用渠道。
- 什么是子智能体？如何创建自定义智能体？
  1. 子智能体是根据开发场景组合提示词、工具与知识库构建的专属智能体，可在默认Agent对话中按需动态调用。
  2. 配置项包含名称、描述（用于意图匹配）、Prompt、工具、MCP与知识库。
- 推荐的团队子智能体配置有哪些？
  1. 需求分析专家负责解析需求文档并生成 requirements.md，关联需求管理工具 MCP。
  2. 架构设计专家负责分析项目架构并提供设计建议，关联团队技术文档与知识库。
  3. 数据库专家负责数据库设计、SQL 优化与 Schema 分析，关联数据库 MCP。
  4. Code Review 专家负责代码审查，关联团队编码规范与代码托管 MCP。
  5. 运维排障专家负责分析日志并定位问题，关联运维手册与监控告警 MCP。
- 如何提升子智能体被调用概率？
  1. 为智能体配置明确的职责描述，并启用「子智能体」选项。
  2. 在职责描述中补充触发条件，例如：当用户提出与数据库、数据查询、报表或EDA相关的请求时，必须调用该子智能体。

#### 1.2 任务编排与工作流

- 任务拆解与执行流程设计
- 在Planning组件中，任务分解的方法有哪些？
  1. 思维链（CoT）引导模型逐步思考，将任务拆解为连续步骤。
  2. 思维树（ToT）拓展CoT，探索多个推理路径并构建推理树。
  3. 任务分解可采用基础LLM提示、任务特定指令或人类输入等方式实现。
  4. LLM+P借助外部经典规划器，通过PDDL接口进行长期规划。
- 节点编排与条件路由
- 串行、并行与异步执行
- 状态机与工作流控制
- 解释Agent的「目标导向」与「反应式」两种设计理念，各适合什么场景？
  1. 反应式：无长期目标，仅根据当下实时输入即时响应，无任务规划环节；适合智能客服问答、实时设备告警等简单低复杂度实时场景。
  2. 目标导向：以最终业务目标为核心，自主规划多步执行流程、调用多工具完成长链路任务；适合数据分析、自动写代码、旅行方案规划等复杂多步骤场景。
- 对比「Workflow」与「Agent」的适用场景：什么时候用流程，什么时候用智能体？
  1. Workflow：步骤、分支、工具调用顺序预先人工定义，流程固定；适合需求固定、步骤统一、无动态分支的标准化业务（表单审批、数据同步、模板报表）。
  2. Agent：无预先固定流程，根据用户需求与工具返回结果动态调整步骤；适合需求模糊、步骤不确定、多动态分支、需自主调用多工具的开放式任务。
- 执行编排与多 Agent 协作怎么做？
  1. 采用“3+1 Phase”标准化工作流：Phase 1 计划阶段通过 Plan 模式生成 requirements.md，人工审核后创建 task.md；Phase 2 编码阶段由 Generator 加载 Rules、Skills 与 MCP 实现；Phase 3 交付阶段由 Evaluator 执行规范检查与逻辑审查；Phase 4 沉淀阶段归档 Spec 并更新知识库。
  2. 多 Agent 角色分工：Planner 负责理解需求与拆解任务，Generator 按方案编写代码，Evaluator 执行代码审查与规范检查，Archiver 归档变更并更新知识库。
  3. 实际执行时，使用 Plan 模式进行架构分析，Agent 模式负责具体实现，AI Code Review 进行质量把关；整体遵循 SDD 工作流，且每个任务必须设定明确完成标准。
- Plan模式开发流程是什么？
  1. Plan 模式是规范驱动开发的核心手段，在 AI 编写代码前生成结构化需求文档与任务清单，经人工审核后按计划执行。
  2. 开发流程分为四个阶段（4 Stage）：Stage 1 在 Plan 模式下描述需求，AI 生成需求文档，并产出 .codebuddy/ 目录下的文档。
- 什么场景绝对不适合用Agent？
  1. 超高实时性场景：毫秒级响应需求下，Agent多步推理与工具调用引入延迟，难以满足时效要求。
  2. 固定强规则场景：逻辑完全固定，Agent自主推理带来不确定性，稳定性不及传统脚本。
  3. 零容错核心交易场景：不允许任何推理偏差，Agent的随机性带来业务风险。
  4. 简单单文本处理场景：任务简单无需规划，Agent架构冗余、成本过高、收益极低。
- 什么是ReAct范式？从「推理轨迹」和「行动空间」解释其原理
  1. ReAct 将推理（Thought）与行动（Action）交替循环：先思考推理，再执行工具行动，接收观测结果后再次推理，循环直至任务完成。
  2. 推理轨迹：每轮行动前强制生成思考文本，梳理当前目标、缺失信息与下一步，约束模型不直接编造答案。
  3. 行动空间：推理发现信息不足时主动调用 API、检索数据获取真实外部信息，解决纯模型凭空推理的幻觉问题。
- ReAct循环中Agent陷入死循环或幻觉行动，算法层面有哪些破局策略？
- ReAct、ReWOO、LLM Compiler、Reflexion 四种 Loop 模式的核心区别？
  1. ReAct范式：推理与行动交替执行，灵活性强且过程可解释，但LLM调用频率较高。
  2. ReWOO范式：采用规划、执行、求解三阶段流程，显著减少LLM调用次数，但规划阶段固定。
  3. LLM Compiler范式：支持工具并行执行，执行效率高，但依赖任务本身的可并行性。
  4. Reflexion范式：在任务执行后进行反思与自我纠正，支持持续能力改进，但反思轮次可能过多。
  5. 选型建议：多数通用场景可选用ReAct范式；若需减少LLM调用次数，可选用ReWOO范式；若追求并行执行效率，可选用LLM Compiler范式；若需要自我纠正能力，可选用Reflexion范式。
  1. 死循环：步数阈值限制（最大循环步数强制终止）、轨迹状态校验（重复轨迹判定循环并终止）、分支熔断（连续多轮无进展中断循环并向用户澄清需求）。
  2. 幻觉行动：工具返回结果校验（格式与值域校验识别虚假数据）、约束解码（强制规范 JSON 输出）、结果二次复盘（每次行动后反思有效性）。
  3. 自主状态判别：实时监测任务是否陷入循环、无进展或参数重复状态。
  4. 阈值自主熔断：设定思考轮次、执行耗时与重复次数阈值，超限后自动终止任务。
  5. 路径动态切换：单一路径受阻时，自主更换解题思路与工具组合。
  6. 空转场景沉淀：将无效执行场景记录为负面案例，后续同类场景直接规避，实现自主优化。
- 对比Plan-and-Execute与ReAct架构的异同，何时更优？
  1. 相同点：均包含推理思考、工具行动与任务执行环节，都支持外部工具调用。
  2. ReAct：单步推理+单步行动交替，无全局前置规划，灵活但长任务易循环、效率偏低。
  3. Plan-and-Execute：先全局规划一次性拆解全部分支与子步骤，再按计划分步执行；全局目标清晰，长任务稳定性强。
  4. 适用：长周期、多固定子步骤、框架清晰的大型任务选 Plan-and-Execute；短任务选 ReAct。
  5. 标准化场景强行套用 ReAct 会引入冗余开销；复杂场景采用固定规划则无法适配动态变更。
- 什么是 Loop Engineering？
  1. Loop Engineering 是由谷歌工程师 Addy Osmani 提出的 AI 编程新范式，其核心是围绕大模型构建自主循环运行系统，使 AI 从单次响应工具升级为长期自治代理。
  2. 核心理念是让人从循环内部的操作者转变为循环之上的监督者与目标设定者，由 AI 自行决策“怎么做”与“下一步是什么”，直至目标达成或确认不可达。
  3. 类比传统 PDCA 循环，模型担任执行者，Loop 作为控制中枢，规则框架构成边界约束。
- Loop Engineering 为什么重要？
  1. 当模型能力足够强时，循环设计成为决定AI自主性与可靠性的关键瓶颈。
  2. 设计良好的循环可支撑AI连续工作数十轮以完成复杂重构，而设计糟糕的循环可能在第三轮即失控。
  3. 它被视为继Prompt Engineering、Context & Harness Engineering之后的“AI编程第三次革命”，开发者角色由“提示词工程师”升级为“AI系统架构师”。
- Loop Engineering 与 ReAct 的区别是什么？
  1. ReAct 是 Loop Engineering 的 Inner Loop，解决单次任务内“怎么一步步做”的问题；Loop Engineering 是 Outer Loop，解决跨任务“做什么、谁来做、何时停、怎么续”的问题。
  2. ReAct 聚焦单次任务执行过程，循环粒度细；Loop 聚焦跨任务编排调度，循环粒度粗。
  3. ReAct 依赖上下文窗口内记忆；Loop 将状态外置到文件或数据库，每次迭代使用全新上下文。
  4. ReAct 由模型自行判断完成状态并进行自我检查；Loop 由独立评估器验证可度量条件，采用对抗验证。
  5. ReAct 采用单 Agent 串行执行、单次对话；Loop 支持多 Agent 并行、工作树隔离、断点续跑，可持续运行数小时甚至数天。
- ReAct 有哪些局限？Loop Engineering 如何补位？
  1. 针对上下文窗口有限导致的长任务遗忘问题，可通过状态外置解决：每轮迭代从全新上下文开始，从持久化文件中读取状态。
  2. 自我检查存在盲区，同一模型同时承担编码与检查易产生确认偏误；可采用对抗验证方式，由执行者与评估者使用不同模型或指令。
  3. 缺乏跨任务进度跟踪时，中途崩溃只能从头执行；可通过状态文件记录进度，实现断点续跑。
  4. 缺少编排能力时，单 Agent 只能串行执行；可采用多 Agent 并行，并辅以工作树隔离。
  5. Loop Engineering 并非替代 ReAct，而是在其之上增加一层编排能力。
- 状态外置哲学是什么？
  1. 所有状态存储于外部系统（如文件、数据库），而非模型的上下文窗口。
  2. 每次循环迭代均从全新的上下文窗口开始，基于实际持久化内容进行工作。
  3. 从根本上解决模型遗忘、信息漂移与上下文压缩问题。
- Loop Engineering 的核心架构是什么？
  1. 五阶段循环机制：Discover → Plan → Execute → Verify → Iterate，形成完整闭环。
  2. Discover 阶段自动读取 CI 失败、Issue、代码审查等信号，输入源需结构化且可订阅；Plan 阶段将目标分解为具体步骤，温度设置适中以避免过早收敛。
  3. Execute 阶段执行代码编辑与工具调用，工具调用需具备幂等性与可回滚能力；Verify 阶段通过测试、Lint、类型检查等客观信号进行验证，验证标准必须可被机器判定。
  4. Iterate 阶段在失败时自动修复并重新循环，成功后进入下一任务；状态需持久化以支持断点续跑。
  5. 双层循环模型：Outer Loop 负责目标拆解、任务分配、结果汇总与再计划；Inner Loop 负责感知、推理、规划、行动、观察、评估与修正。
  6. 六要素构建体系包括自动化（循环心跳）、工作树、技能（SKILL.md）、连接器（MCP）、子智能体与状态文件。
- Loop Engineering 实践中有哪些常见陷阱和注意事项？
  1. 验证责任不可转移：关键变更仍需人工审查，Loop 不能替代 Code Review。
  2. 理解债务会加速累积：应定期审查 AI 的变更，保持对代码库的持续理解。
  3. 存在认知投降风险：开发者应将 AI 视为协作者而非权威，对每个变更保持质疑。
  4. Token 成本约束：需设置 stop after N turns 上限，并采用小模型评估器以控制开销。
  5. 条件模糊会导致无效循环：完成条件应写成可由 AI 自身输出验证的形式。
- Loop Engineering 的三种循环驱动机制是什么？
  1. /goal：条件驱动的持续工作模式，设定可验证的完成条件后，跨多轮自动执行直至条件满足。
  2. /loop：时间驱动的循环任务，按固定时间间隔重复执行指令，适用于监控、巡检等持续性场景。
  3. Automations：跨会话的持久化定时任务，按 cron 规则周期性执行，或在指定时间点一次性触发。
- /goal 的用法和条件设计要点是什么？
  1. 基本语法：/goal <完成条件>，可附加兜底上限，例如 /goal all tests pass or stop after 20 turns。
  2. 支持非交互模式：codebuddy -p "/goal CHANGELOG.md has an entry for every PR merged this week"。
  3. 编写完成条件的三要素：可度量的终态、可证明的验证方式、不可破坏的约束。
  4. 检查清单包括：终态可度量、验证方式明确、约束不可破坏、始终附加兜底上限、条件长度不超过 4000 字符。
- /goal 的评估机制是怎样的？
  1. 每轮结束后，由独立小模型评估器判断完成条件是否满足；评估器仅基于 transcript 判断，不调用任何工具。
  2. 评估器采用三态判定：ok:true 表示条件满足并清除 goal；ok:false 表示条件未满足，将 reason 注入 history 后继续下一轮；ok:false 且 impossible:true 表示目标不可达，立即清除 goal。
  3. 评估器采用独立小模型（如 gemini-2.5-flash），与执行 Agent 使用不同模型，形成对抗验证机制。
- /loop 的用法和特性是什么？
  1. 语法：`/loop [时间间隔] <指令>`，例如 `/loop 3m 检查流水线是否跑完`。
  2. 特性：最小间隔 1 分钟，每会话上限 50 个任务，超时 3 天自动清除，生命周期为会话级，会话退出后任务消失，仅在会话空闲时触发。
- Automations 是什么？
  1. Automations 为跨会话持久化定时任务，不随会话退出而消失，适用于长期运行的监控场景。
  2. 支持 Recurring 与 Once 两种模式：Recurring 按 cron 规则周期重复执行，Once 在指定时间点一次性触发。
- /goal、/loop、Automations 三种方式有什么区别？
  1. /goal 在上一轮结束后立即启动，由评估器确认条件满足后终止，适用于具有明确终态的实质性任务。
  2. /loop 按固定时间间隔触发，由用户主动停止或模型判定结束，适用于监控、巡检与定期检查等持续性场景。
  3. Automations 依据 cron 规则触发，可永久生效或设定有效期，适用于跨会话的长期监控任务。
- 如何选择不同的循环模式？
  1. 对具备明确终态的实质性工作（如迁移、重构、功能实现）采用 /goal 模式。
  2. 对持续性监控与巡检任务（如 CI 状态、PR 审查、性能回归）采用 /loop 模式。
  3. 对跨会话的长期定期任务（如每日构建检查、每周代码审查汇总）采用 Automations 模式。
  4. 对需要多角色协作的复杂任务（如规划、执行、评审）采用 Team 模式配合 /goal 执行。
- CoT与ToT在复杂推理中的路径差异是什么？
  1. CoT：线性单路径推理，每一步仅基于上一步结论，速度快、Token 消耗少；中途出错则整体失效。
  2. ToT：关键推理节点生成多条独立分支并行推演，评估打分后淘汰错误分支、择优深入；适合数学推理、逻辑谜题，但 Token 消耗与延迟更高。
- 解释「意图增强」：用户指令模糊时如何提升执行准确性？
  1. 意图分类识别：预设业务意图分类库，判定核心需求类型（查数据/写文档/工具查询），锁定任务大方向。
  2. 缺失信息追问补全：识别缺少的关键参数（时间、范围、对象），主动向用户追问收集完整信息。
  3. 指令重写标准化：将碎片化、口语化提问重写为逻辑完整、参数齐全、无歧义的标准化指令，作为后续规划与工具调用输入。
- 什么是「LLM Compiler」范式？如何通过并行化多Agent任务降低延迟？
  1. 编译阶段：对用户总需求静态解析，拆分为大量相互独立、无依赖的原子子任务。
  2. 执行阶段：调度多个 Agent/模型实例并行执行独立子任务，最后汇总结果生成最终答案。
  3. 降延迟原理：串行总耗时=各步骤耗时之和，并行总耗时=最长单条子任务耗时；无依赖任务并行执行大幅压缩端到端延迟。
- 简述「状态机Agent」的设计思路，如何实现规划-执行-反思闭环？
  1. 将任务流程拆解为多个离散标准状态，预定义各状态执行逻辑、切换条件与异常跳转规则。
  2. 规划状态：接收需求与历史记忆，拆解子步骤生成计划；执行状态：调用工具执行并记录数据；反思状态：复盘轨迹、校验结果。
  3. 反思发现失败或信息不足时触发状态回滚，跳回规划状态重新调整；全部完成则进入结束状态输出结果，三状态循环构成闭环。
- Agent有限状态机的核心作用，解决了什么隐形痛点？
  1. 针对通用Agent任务状态无序、流转混乱、异常无记录、断点无法恢复等隐性痛点，提供系统性解决能力。
  2. 核心作用：标准化任务状态，规范状态流转规则，禁止跨状态乱执行，确保流程有序可控。
  3. 支持任务断点续跑与异常恢复，并可精准统计各阶段成功率与故障率，便于问题定位与质量复盘。
- Agent 链式推理（CoT）的核心原理是什么？为什么能提升效果？
  1. 引导模型先输出中间推理过程再给出最终结果，打破大模型单次生成的思维局限。
  2. 拆解复杂问题降低解题难度；暴露逻辑漏洞便于后续反思纠错。
  3. 约束模型生成逻辑，减少幻觉与随机错误。
  4. 适配数学计算、逻辑判断、业务拆解等高精度场景。
- 用户需求变更频繁，Agent如何保证推理逻辑不混乱？
  1. 实时感知需求变更，终止原执行任务，避免无效执行。
  2. 推理模块优先更新最新需求，覆盖历史过期需求。
  3. 保留需求变更记录用于复盘，区分临时变更与固定需求。
  4. 变更后重新拆解任务、重置执行步骤，保证新需求推理逻辑闭环、无冲突。
- 请简述Agent「规划-执行-反思」完整闭环
  1. 规划：接收用户需求，拆解为有序、可执行的细分任务步骤，明确验收标准。
  2. 执行：按照步骤自主调用工具、执行对应操作，输出阶段性结果。
  3. 反思：校验结果是否达标，排查执行漏洞与工具错误。
  4. 迭代优化：根据反思结果重试或调整策略，任务达标后结束闭环，沉淀有效经验。
- 对比「反应式Agent」「目标导向Agent」「分层Agent」的架构特点与适用场景
  1. 反应式：无全局任务规划，仅实时响应输入，逻辑简单、响应快；适合简单问答、设备告警等即时场景。
  2. 目标导向：以业务目标为核心，自主拆解多步骤任务，支持连续工具调用；适合数据分析、行程规划、文档撰写等中等复杂度任务。
  3. 分层：多层级分工，顶层全局规划、中层调度、底层执行，支持多分支多角色协同；适合大型项目开发、企业全链路自动化。
- 简述「任务拆解」的核心逻辑，如何从总目标拆分为可执行子步骤？
  1. 核心逻辑：将庞大、模糊、无法一次性完成的总目标，拆分为分层、有序、独立、可调用工具执行的最小原子任务，并梳理子任务依赖与执行优先级。
  2. 目标澄清：梳理最终交付成果，区分刚需需求与附加需求。
  3. 分层拆分：自上而下逐层拆解，大目标拆一级子任务，再细化到最小可执行步骤。
  4. 依赖梳理：标记串行前置任务与无依赖可并行执行的任务。
  5. 可行性校验：每个拆分后的步骤都能通过单次推理或单一工具直接执行。
- 如何协调依赖多工具的任务流程（如先查天气再查航班）？
  1. Prompt 层约束：System Message 写明工具执行前置约束——后置工具必须等待前置工具返回数据、禁止无序调用、调用时携带前置结果作为筛选条件。
  2. 代码层编排：用状态机定义带前置触发条件的任务节点（如天气查询节点、航班筛选节点）。
  3. 前置依赖判定：仅当前置节点完成且上下文存在有效数据时，才允许进入后置节点；前置失败直接熔断并向用户反馈。
  4. 数据自动流转：前置节点输出自动作为后置节点入参，无需模型自行管理数据传递；Prompt 负责规则引导，代码层强制管控流程。
- LangGraph中的「状态（State）」概念是什么？如何协调多Agent工作流？
  1. State 是 LangGraph 的全局统一数据容器，存储全局上下文、任务进度、工具结果与节点状态，是所有工作流节点的唯一数据来源。
  2. 全局唯一状态：所有 Agent 读写同一份 State，保证信息统一、无数据偏差。
  3. 节点流转调度：依据 State 字段值判断分支、循环与终止条件，自动调度不同 Agent 执行任务。
  4. 状态迭代更新：每个 Agent 执行完成后更新 State，作为下一个节点的执行依据；State 可存档，支持断点续跑、流程回溯与故障恢复。
  5. 编译图时挂载检查点器（checkpointer），在每个超级步结束时保存全量图状态快照。
  6. 支持人在回路（Human-in-the-Loop）：图可在任意节点暂停，待人工检查、修改、批准后从断点恢复执行。
  7. 支持记忆、时间旅行调试与容错：可保留多轮上下文，回溯历史检查点重放或分叉流程，节点失败后从最近成功步骤重启。
  8. 挂起写入（pending writes）设计：同一超级步中某节点失败时，其他已成功节点的输出予以保留，恢复时无需重跑成功节点。
- 为什么LangChain的Chain模式逐渐被LangGraph的Graph模式取代？
  1. Chain 痛点：纯线性执行，不支持分支判断、循环重试与流程跳转；无全局状态管理，上下文流转混乱，复杂任务不可控、不可回溯。
  2. Graph 优势：支持分支、循环与条件跳转；全局 State 统一管理状态；支持断点续跑、故障重试与流程回溯。
  3. 结论：Graph 完美适配多步骤、多工具、多轮迭代的复杂 Agent 任务，成为行业主流。
- Dify平台中Workflow与Chatflow的底层执行引擎区别？如何自定义Plugin？
  1. Chatflow：对话驱动引擎，适配用户实时聊天场景，上下文联动即时响应，流程轻量、交互优先。
  2. Workflow：后台自动化引擎，支持复杂分支、循环、批量任务与异步执行，可脱离对话独立运行，主打工程自动化。
  3. 自定义 Plugin：基于 Dify 插件规范，编写工具入参、出参与业务逻辑，封装 API 或 Python 能力，配置插件描述与 Schema，发布后即可在流程中直接调用。
- 如何优化Agent的「步数效率」，减少完成任务的工具调用次数？
  1. 前置任务规划：执行前先判断任务目标、梳理所需工具，杜绝盲目试探性调用。
  2. 多工具合并调用：支持批量参数传入，单次调用完成多维度查询，替代多次重复调用。
  3. 历史记忆复用：已有历史结果直接复用，无需重复调用工具。
  4. 终止条件明确：设定清晰的任务完成标准，达标立即终止流程，避免过度执行。
  5. 错误复盘迭代：统计冗余步数，迭代 Prompt 与工作流规则，持续优化决策精度。
- Agent 陷入死循环怎么解决？
  1. Loop 层：设置最大轮次上限（max_turns），超限时自动终止或降级处理。
  2. Runtime 层：实施熔断机制，对连续失败的工具进行降级或策略切换，并设置重试策略。
  3. Sandbox 层：提供超时保护，单个工具调用超时则自动终止进程。

- 进程重启后，被打断的对话要不要自动继续？在什么条件下继续、什么条件下放弃？
  1. 优雅关闭时，对排空超时后被打断的会话打上待续接标记并记录中断原因；重启后，恢复调度器列出全部待续接会话并预加载，完成恢复后再放行排队消息。
  2. 续接必须通过新鲜度门控：默认在一小时窗口内自动续接，过期则清除标记并作为新对话处理；若无条件续接，长时间中断的话题会被自动延续，而用户可能已切换上下文，续接反而造成混乱。
  3. 窗口长度应根据会话中断时长与用户上下文切换频率调整：IM 日常对话窗口可短，长任务窗口应长；窗口过短会切断跨夜讨论，过长会污染新对话。
  4. 交互平台续接时注入恢复提示，询问用户是否继续；非交互平台直接继续未完成工作；同时设置空消息安全网，确保模型不收到空白轮次。
  5. 反复恢复失败时，用户可发送停止命令置挂起标记以打破循环，下次访问自动重置；若进程直接崩溃导致无标记，则恢复依赖数据库中已有的消息与状态。

- 什么是Agent幂等性？线上不做幂等会出现什么严重问题？
  1. 幂等性是指同一请求或同一任务被重复触发时，最终执行结果保持一致，且不会重复生效。
  2. 缺乏幂等性将导致工具重复调用、数据重复写入、订单重复提交、批量任务重复执行，进而引发数据错乱与业务事故。
  3. 幂等保障机制包括任务唯一标识、执行状态标记与重复请求拦截三重机制。

- Agent开发的核心挑战有哪些？
  1. 模型幻觉：编造虚假数据与错误结论，导致工具调用、任务规划出错。
  2. 工具调用不稳定：无法精准生成规范参数，参数缺失、格式错误导致 API 调用失败。
  3. 长上下文瓶颈：任务轮次过多超出上下文窗口，信息丢失、注意力衰退。
  4. 高额运行成本：多轮 LLM 推理、海量向量检索与高频工具请求的算力与接口费用。
  5. 衍生问题：循环死锁、多智能体冲突、安全注入攻击。
- 从0设计一个生产级Agent，重点规避哪些核心盲区？
  1. 安全层：实施输入脱敏、注入拦截、权限隔离与高危操作审批机制。
  2. 执行层：通过状态机管控、幂等设计、超时熔断、防空转与防重复调用保障流程稳定。
  3. 记忆层：采用分层隔离、去重降噪、遗忘机制，防范记忆污染与有效信息被覆盖。
  4. 推理层：进行分步校验、Few-Shot对齐、逻辑纠错与细节核验，规避隐性幻觉。
  5. 性能层：落实并发隔离、资源限流、Token管控与异步调度。
  6. 运维层：建立全链路日志、异常埋点与指标监控，确保问题可追溯、可迭代。
  7. 整体遵循“先防坑、后功能、再优化”的落地思维。
  8. 架构选型：基于AgentArts/Versatile平台搭建，采用Harness托管架构，保障高可用、可自愈与断点续传。
  9. 部署设计：适配公有云、私有化与混合云三种模式，落地云边端协同架构，平衡延迟、算力与隐私需求。
  10. 安全设计补充：通过内核沙箱隔离、临时密钥体系与数据不出域机制，满足政企合规要求。
  11. 能力设计补充：实现工具调用可追溯、任务调度可自愈与异常容错兜底。
  12. 运维设计补充：具备风险监控、态势感知与版本迭代可控能力，支撑大规模企业级落地。
  13. 核心理念：安全为先、稳定为本、架构可控、全端适配、合规可溯。
- 生产级自主Agent，核心要解决哪四大工程难题？
  1. 自主性难题：应对模糊需求与动态场景，实现无人工干预的自主决策。
  2. 稳定性难题：规避空转、重复执行、逻辑错乱与异常崩溃，保障流程可靠。
  3. 安全性难题：防范过度自主、越权操作、数据泄露与合规风险。
  4. 迭代性难题：破除能力僵化与进化停滞，沉淀经验，避免重复踩坑。
  5. 上述四大难题全部攻克，方为生产级可用的自主Agent。
- 什么是「检查点机制」？长链条任务中如何设计以保证鲁棒性与可恢复性？
  1. 检查点机制：长链路任务在关键节点持久化完整任务状态，包括规划轨迹、工具返回数据、上下文与子任务进度。
  2. 节点划分：任务阶段切换、工具执行完成、子任务结束时设置存档点。
  3. 状态存储：将任务数据序列化存入数据库、缓存或本地文件。
  4. 异常恢复：服务崩溃、接口超时重启后读取最新存档，恢复上下文断点续跑。
  5. 数据清理：定期删除已完成任务的过期存档，节省存储资源。
  6. 执行全程进行埋点，记录每一步的状态，而不仅是在关键节点存档。
  7. 通过日志重放还原执行进度，避免重复操作与数据错乱。
- 做客服Agent时，用户情绪激动、投诉不满，怎么调整处理策略？
  1. 话术层面柔性安抚情绪、降低对立感，核心业务规则保持不变。
  2. 退款、赔付、权限调整等核心业务动作严格遵循规则，不因用户情绪私自承诺。
  3. 高风险诉求或无法自主处理的问题直接触发转人工，避免风险事故。
- Agent什么时候需要主动转人工？核心触发条件是什么？
  1. 意图识别置信度极低，无法判断用户需求。
  2. 用户明确拒绝 Agent 自动处理、要求人工对接。
  3. 命中高风险场景：纠纷投诉、大额赔付、违规咨询、模糊灰色需求。
  4. 转人工时同步对话摘要、已执行动作与问题卡点，方便人工快速接手。

- 生产环境 Agent Loop 的五大稳定性保障机制是什么？

  2. 死循环检测：通过设置最大循环轮次或执行耗时上限，防止Agent陷入无效重复循环而导致任务卡死。
  3. 压缩降级链：采用层次化的上下文压缩策略，依次尝试AI生成摘要、基于规则的摘要以及硬截断，确保历史信息在有限窗口内得到高效保留。
  4. Checkpoint恢复：将Agent的循环状态与中间变量序列化持久化，支持在意外中断后恢复到最近检查点继续执行。
  5. 心跳检测：当Agent在特定时间内无实质性进展或操作时，系统自动暂停任务以释放计算资源，避免空闲占用。
  6. 核心原则：系统设计应优先保证确定性与安全性，在面临潜在风险时宁可提前安全终止，也不应允许带错误或不稳定状态持续运行。
- Agent 需要哪些资源限制？为什么？
  1. 步数限制（防止无限循环）、Token 限制（控制成本）、时间限制（避免长时间运行）、工具调用频率限制（防止 API 滥用）、并发限制（防止资源耗尽）。
  2. 这些限制确保 Agent 即使出现故障或遭受攻击，也不会导致不可挽回的损失（如成本失控或服务不可用）。
  1. 轻度失败：自动重试 1-2 次，优化参数重新执行。
  2. 中度失败：简化任务方案，完成核心诉求，放弃非必要细节。
  3. 重度失败：终止自动执行，清晰告知失败原因，提供人工对接入口，并上报日志供迭代优化。
  4. 结果校验：自主比对执行结果、业务规则与用户诉求，识别异常与偏差。
  5. 归因推理：判断错误类型，包括参数问题、工具问题、推理问题与场景适配问题。
  6. 动态修正：针对性调整任务步骤、工具选型与入参逻辑。
  7. 将错误案例沉淀至长期记忆，避免同类错误再次发生。
- 智能客服Agent，如何通过推理能力处理复杂售后纠纷？
  1. 语义推理：梳理用户纠纷核心诉求、问题场景与情绪倾向。
  2. 规则推理：匹配售后规则、订单状态、权限标准，判断可执行方案。
  3. 逻辑推理：对比用户描述与系统数据，排查矛盾点、规避虚假诉求。
  4. 结果推理：给出合规最优方案；无法自主判定的纠纷转人工，并同步推理过程辅助处理。
- 你理解的生产级Agent，和Demo版Agent最大的区别是什么？
  1. 稳定性：Demo 只适配简单场景，生产级支持复杂场景、异常容错、防死循环、防崩溃。
  2. 安全性：生产级有权限隔离、防注入、数据脱敏、审计溯源。
  3. 工程性：生产级有日志埋点、监控告警、迭代复盘、过期清理机制。
  4. 落地性：Demo 追求功能实现，生产级贴合业务规则、风险可控、可规模化复用。

- 业务容错Agent和通用Agent的核心区别？
  1. 其他大厂优先追求模型智能性与用户体验流畅度
  2. 美团以业务准确、资金安全、用户零客诉为第一优先级。
  3. 异常场景精细化区分处理，严控重试风险：宁可降级不用，绝不冒风险输出错误答案，适配本地生活高严谨度业务。

### 02 工具系统与 Function Calling

#### 2.1 Function Calling 原理与 Schema

- Function Calling 基本原理
- Function Calling 的完整流程是什么？
  1. Agent 通过定义工具的 JSON Schema 将其与用户请求一并提交给 LLM。
  2. LLM 分析请求并判断是否需要调用外部工具，若需要则输出结构化的函数调用指令，包含函数名与参数。
  3. Agent 框架解析该指令，执行相应函数并将执行结果回传给 LLM，以生成最终回答。
  4. 核心机制在于 LLM 仅负责决策“调用什么工具”，实际执行由 Agent 框架完成。
- Agent 为什么要使用工具？LLM 本身不够吗？
  1. LLM 存在明确的能力边界，例如无法获取实时信息、执行精确计算、读写文件或与外部服务交互。
  2. 工具弥补了 LLM 的上述局限，使其能够执行具体操作。其中，LLM 负责推理与决策，而工具负责执行。
- 什么是Agent工具调用？核心流程是什么？
  1. 工具调用是 Agent 作为自主系统的核心能力，使其能与外部环境交互并执行具体操作。
  2. 一个完整的工具调用周期涵盖：工具注册、用户意图识别、参数结构化解析、工具执行、结果回收，以及将结果整合至模型后续输出，形成闭环。
- Tool Schema 设计
- Agent推理和工具调用的关系？二者如何协同工作？
  1. 推理是决策核心，工具调用是执行载体，二者双向协同。
  2. 推理模块判断当前任务是否需要工具、需要什么工具、需要哪些参数。
  3. 工具返回结果后，推理模块再次校验结果、判断是否达标、是否需要二次调用。
  4. 结合工具结果完成最终逻辑闭环，解决纯模型生成的幻觉与能力局限问题。
- 工具选择与参数生成
- 参数语法与语义校验
- Toolformer的核心思想是什么？模型如何在无大量标注下学会自发调用API？
  1. 核心思想：无需人工标注大量工具调用样本，依托海量无标注文本通过自监督学习，让模型自主判断调用 API 时机、生成查询参数、利用工具结果完善文本。
  2. 文本筛选：定位文本中缺少外部客观信息的段落。
  3. 模拟调用：模型自主生成 API 查询语句，模拟工具执行。
  4. 文本重构：将工具真实返回信息回填原文，生成带工具轨迹的训练样本。
  5. 自监督微调：用重构文本微调模型，学习「需求-调用工具-补充信息」的完整逻辑。
- 如何设计一个「好的工具」？工具描述如何平衡详细程度与Token消耗？
  1. 优质工具三标准：原子单一功能（一个工具只做一件事）、描述清晰无歧义（作用、适用场景、输入输出含义）、参数约束完整（名称、类型、取值范围、必填/选填）。
  2. Token 平衡：保留核心信息（用途、必填参数、格式约束、使用限制），删除无关背景、重复解释与修饰语句。
  3. 分层精简：高频核心工具保留完整参数说明，低频冷门工具大幅简化。
  4. 动态加载：不一次性加载全部工具描述，按需检索少量相关工具传入上下文。
- 面对成百上千个工具，Agent如何实现高效路由选择？
  1. 两段式路由：向量检索粗筛 + LLM 模型精排，规避全量遍历带来的高 Token 消耗与延迟。
  2. 粗筛：将工具功能描述向量化存入向量库，用户需求向量化后做相似度检索，快速召回少量高相似度候选工具，过滤大部分无关工具。
  3. 精排：将候选工具送入大模型，结合用户真实需求判断匹配度，筛选出本次任务要调用的工具并生成对应参数。
- LangChain中Tool与StructuredTool的区别？如何快速封装Python函数为Agent工具？
  1. Tool：基础工具基类，仅接收单一字符串参数，多字段需拼接成一段文本，适合极简单参数工具，易出现参数解析错误。
  2. StructuredTool：结构化工具基类，支持自定义多参数（名称、数据类型、描述、必填），自动生成调用 Schema，适配多参数复杂 API，大幅降低参数生成错误。
  3. 快速封装：@tool 装饰器（自动解析函数入参与注释生成工具描述与 Schema）；StructuredTool.from_function()（手动补充工具名称与功能描述）。

- Agent工具调用和普通函数调用的核心区别？
  1. 稳定性不同：普通函数运行环境可控
  2. 工具调用对接外部第三方业务接口，常出现超时、限流、空数据等异常，必须自带容错机制。
  3. 决策能力不同：函数调用逻辑固定
  4. Agent 可根据工具返回结果自主重试、降级、切换执行策略。
  5. 安全要求不同：订单、库存、资金场景的工具调用必须严格保证幂等性，杜绝重复操作引发业务事故。

#### 2.2 调用执行与生命周期

- 工具返回结果解析
- 循环调用与调用深度控制
- Agent调用工具出现死循环、重复调用，怎么解决？
  1. 设定调用轮次上限与单任务超时阈值，触发时强制终止
  2. 引入结果校验机制，验证结果是否满足任务目标，达标即刻终止
  3. 优化规划逻辑，避免重复执行冗余步骤
  4. 增加异常日志埋点，复盘死循环成因并持续迭代
  5. 通过意图前置校验，明确区分需调用工具与纯对话应答两类场景，避免无效工具调用。
  6. 调用前进行参数校验，无有效入参时直接拦截；同时检测同一工具相同参数的重复调用，阻断空转循环。
  7. 优化 Prompt 以明确工具使用边界，并对空调用、无效调用建立指标统计与复盘迭代机制。
  8. 四层机制：前置规则拦截简单问答、单轮对话限制最大调用次数、短期缓存复用查询结果、语义去重拦截同义请求。
  9. 有效节省接口资源、提升响应速度，避免触发平台限流。
- 超时、重试与降级
- 怎么保证 Agent 的工具调用可靠性？工具调用不稳定、参数报错怎么解决？
  1. 语义层：启用 JSON 输出模式，并借助 Pydantic 等工具对参数进行强类型约束。
  2. 逻辑层：引入人工确认机制（Human-in-the-Loop），专门用于处理高风险操作。
  3. 异常层：配置自动重试与修复逻辑，将错误信息反馈给 LLM 以自主修正参数。
- 工具调用失败（参数错误、API超时）时，如何设计容错、重试与自我修复机制？
  1. 前置参数校验：调用前校验参数类型、值域、必填项，不合法直接返回提示引导 Agent 修正，避免无效请求。
  2. 指数退避重试：设置最大重试次数（一般 3 次），重试间隔指数递增，防止频繁请求压垮第三方接口。
  3. 熔断降级：连续多次失败判定接口不可用，触发熔断停止重复调用，节省系统资源。
  4. 备用工具兜底：自动切换功能等价的备用工具；无备用工具时告知用户调用失败，确认是否调整需求。
  5. 最易被忽略的失败原因：上下文冗余信息干扰结构化解析，多轮对话语义冲突导致模型输出混合内容。
  6. 模型原生格式兼容细节未适配，工具 Schema 定义模糊，参数边界不清晰。
  7. 解决思路：通过格式清洗、冗余过滤、解析失败重试与 Schema 严格校验构成多层兜底机制。
  8. 直接重试可能导致业务操作重复提交，引发数据错乱，加剧服务压力，甚至造成雪崩效应。
  9. 超时后标记任务状态，禁止重复触发；对超时任务单独进行日志埋点与复盘；关键业务超时直接转人工兜底。
  10. 优先短时指数重试，失败后立即停止调用、触发优雅降级。
  11. 前端不展示技术报错代码，用友好话术兜底用户
  12. 完整日志埋点记录异常场景，复盘优化接口稳定性。
- 并行工具调用如何实现？LLM如何在单次推理中输出多个独立工具请求？
  1. 定义：单次推理同时生成多个无依赖、可独立执行的工具调用请求，后端并发调用 API，全部返回后统一回填上下文，大幅缩短串行总耗时。
  2. 批量 Schema：工具调用输出规范支持数组格式，允许返回工具调用列表而非单一工具。
  3. 提示词约束：System Message 明确告知模型，无依赖任务可一次性输出多条工具调用。
  4. 约束解码：强制输出标准化 JSON 数组，数组内每一项为独立工具调用。
  5. 后端并发调度：多协程/多线程并发发起全部 API 请求，汇总结果统一传入上下文。
- 如何解决「工具参数幻觉」问题？除Prompt外，代码层面有哪些校验机制？
  1. 参数幻觉：模型凭空编造不存在的参数名、错误参数类型、超出合理范围的数值或遗漏必填参数，导致 API 调用失败。
  2. 强类型校验：依据工具 Schema 强制校验模型输出参数类型，不匹配直接驳回要求重新生成。
  3. 值域/枚举校验：预设合法取值集合，参数不在合法区间即判定为幻觉参数。
  4. 必填参数非空校验：遍历 Schema 必填字段，检测空值与缺失，缺失直接返回错误引导补齐。
  5. 业务逻辑交叉校验：校验多参数关联约束（如结束时间不早于开始时间、页码≥1），识别违背业务规则的幻觉参数。
- 如何实现「工具调用结果过滤」，避免无关信息污染Agent上下文？
  1. 字段白名单过滤：结构化 API 返回仅保留完成当前任务必需的字段，剔除日志、广告、内部埋点等冗余字段。
  2. 文本摘要压缩：超长文档、网页返回时调用轻量摘要模型，提取与用户需求强相关的核心信息，删减无关段落与重复描述。
  3. 相关性匹配过滤：多条检索结果与用户原始需求做相似度匹配，过滤低相似度条目，仅保留高相关 Top 结果写入上下文。

- 工具调用4大高频异常是什么？
  1. 参数异常、服务超时异常、空数据异常、并发限流异常。
  2. 参数异常属于前端入参错误，不可重试
  3. 其余三类为服务及场景异常，可针对性重试或降级处理。

- 查询返回空数据，如何区分「无数据」和「查询失败」？
  1. 通过返回结构体区分：正常空结构体代表暂无订单，直接告知用户。
  2. 超时、报错等异常结构体代表查询失败，提示系统繁忙、建议稍后重试，避免用户误解。

- 高峰期接口限流，如何降级？
  1. 识别限流后立即停止重试请求，保护下游接口。
  2. 放弃实时精准时效查询，切换离线知识库的通用配送规则兜底，主动降低用户预期，保障高峰期整体稳定。

- 工具返回数据正常，但逻辑离谱怎么处理？
  1. 内置业务阈值自检机制，过滤价格、时效、距离等离谱数据。
  2. 多源数据交叉比对校验，舍弃异常数据
  3. 无法校验时触发人工兜底，杜绝错误数据误导用户。

- 工具调用频繁超时，是模型问题还是工程问题？怎么区分？
  1. 模型问题：参数解析错误、重复无效调用、调用逻辑混乱、选错工具——表现为未超时但执行失败、无意义调用。
  2. 工程问题：接口响应慢、网络波动、队列拥堵、资源限流、下游抖动——表现为有效调用但响应超时、大批量任务集体卡顿。
  3. 排查优先看日志，区分调用逻辑问题与链路性能问题，针对性优化。

#### 2.3 工具权限与安全控制

- 工具权限与安全控制
- Prompt注入攻击是什么？Agent如何防护？
  1. Prompt 注入是用户输入恶意指令，绕过原有规则、诱导 Agent 越权操作或泄露数据的攻击方式。
  2. 设置指令白名单，拦截恶意、越权、违规指令。
  3. 区分系统指令与用户输入，隔离权限；输入内容脱敏、恶意关键词拦截。
  4. 高风险操作二次校验，禁止模型无条件遵从用户恶意指令。
  5. 输出层增设二次校验，防止提示注入导致违规输出与数据泄露。
  6. 规则隔离：核心 Prompt 与安全规则固化加密，用户无法覆盖或篡改。
  7. 插件管控：实施插件白名单机制，禁止未知插件加载运行，拦截恶意插件投毒。
  8. 态势感知：实时监测异常操作与高频攻击，自动拦截并告警。
- 如何防止Prompt注入攻击诱导Agent调用敏感工具（如数据库删除）？
  1. 权限分级隔离：数据库删除、文件销毁等高敏感工具仅对指定角色开放，普通工具放开调用。
  2. 用户输入过滤转义：识别篡改系统指令、伪造工具调用的恶意文本，特殊控制字符转义，防止逃逸上下文分隔符。
  3. 敏感操作二次确认：高危工具调用前向用户展示操作风险与操作对象，等待确认后再执行。
  4. 全量操作审计日志：记录所有工具调用的操作者、参数、时间与结果，恶意操作可追溯。
  5. 上下文隔离：严格分隔 System Message 与用户输入，避免用户文本覆盖顶层系统规则。
- 如何设计Agent的「安全护栏」？防止越权操作、数据泄露、恶意利用
  1. 权限隔离层：最小权限原则，严格限制 Agent 对文件、数据库、接口的操作权限，杜绝越权。
  2. 输入过滤层：清洗恶意指令与敏感输入，拦截攻击与违规请求。
  3. 执行校验层：工具调用前置校验，拦截高危操作、批量删除、隐私读取等风险行为。
  4. 输出审核层：过滤违规输出、脱敏隐私数据，防止数据泄露。
  5. 日志审计层：所有操作留痕存档，可追溯、可复盘、可追责。
  6. 身份权限层：实施强身份认证与临时凭证机制，防止越权访问。
  7. 运行环境层：采用内核沙箱隔离与轻量级虚拟机防护，防止环境逃逸。
  8. 网络传输层：通过专线隔离、流量监控与加密传输，防止数据窃听与外流。
  9. 数据存储层：依托硬件加密、数据胶囊与本地存管，防止数据泄露。
  10. 运维审计层：提供风险态势感知与合规归档能力。
  11. 权限分级自主控制：普通任务由 Agent 完全自主执行，高危、敏感任务自动触发人工审批。
  12. 规则硬约束：核心业务规则预先固化，自主决策不得逾越合规边界。
  13. 高风险决策须先校验后执行，杜绝擅自修改核心数据。
- 什么是 Human-in-the-Loop？在安全中起什么作用？
  1. Human-in-the-Loop 是一种在 Agent 决策流程中引入人类参与的机制。
  2. 在安全模块中，对高危操作如删除文件、发送邮件或资金操作实施暂停执行并等待人工审批，作为最后一道防线；即使前几层防御被绕过，人工审批也能有效拦截危险操作。
  3. LangGraph 的 Checkpoint 机制使得暂停、审批与恢复流程能够开箱即用。
- Agent 的三层权限模型是什么？
  1. 声明式权限层：通过配置定义可用工具白名单，未声明的工具一律禁用。
  2. 运行时拦截层：在工具执行前实时校验参数，拦截路径穿越、SQL注入、敏感信息外泄等风险操作。
  3. 审计日志层：记录所有工具调用日志，支持事后追溯与攻击模式分析。
- MCP 安全管理的三原则是什么？敏感操作为什么需要二次确认？
  1. 安全三原则涵盖：最小权限原则（每个MCP Server仅申请必需权限）、默认拒绝原则（未明确授权的操作默认拒绝）、可审计原则（每次调用均留日志，异常可追溯）。
  2. 二次确认的必要性在于：部分操作后果不可逆（如删除文件、转账或发布内容），执行后无法撤销。
  3. 恶意Prompt可能通过Agent间接调用MCP Server执行危险操作（即Prompt Injection风险），二次确认使用户能在执行前审查并拒绝，构成Agent代理执行的安全护栏。
  4. 不同敏感级别（critical/high/medium）对应差异化的通知渠道与确认要求。
- 什么是Agent最小权限原则？如何落地？
  1. 定义：Agent仅拥有完成当前任务所必需的最小操作权限、数据访问权限与资源调用权限，无冗余、不超范围。
  2. 落地：按任务、场景、租户进行权限精细化拆分与分级授权。
  3. 禁用通用全权密钥，统一使用限时、受限的临时凭证。
  4. 高危操作单独审批、二次校验，权限定期回收清理，全程监控使用行为。
- Agent调用数据库、文件系统等敏感资源时，如何做权限控制与审计？
  1. 最小权限分配：区分查询、修改、删除权限，默认只读，高危操作单独授权。
  2. 资源隔离：业务库、测试库、隐私文件严格隔离，禁止跨域访问。
  3. 操作白名单：仅允许预设合法 SQL 与文件操作指令，拦截高危语法。
  4. 全量审计日志：记录操作人、时间、指令、结果与 IP，支持风险溯源与故障排查。
  5. 高危操作人工审批：删除、批量修改等操作强制人工确认。
- 临时AK/SK机制的作用？为什么不使用固定密钥？
  1. 固定密钥长期有效，一旦泄露将导致永久越权、数据泄露与接口滥用风险。
  2. 临时AK/SK限时有效、按需生成、自动过期，实现权限最小化。
  3. 可精准管控权限范围、使用场景与有效期，全程可审计，适配政企安全合规要求。
- Agent系统的「隐私保护」策略有哪些？（数据脱敏、联邦学习、隐私计算）
  1. 数据脱敏：手机号、身份证、地址、姓名等隐私数据做掩码、替换、加密处理，禁止明文传输存储。
  2. 数据最小化：只采集、存储业务必需数据，无用隐私数据即时清理。
  3. 联邦学习：多节点本地训练、不上传原始数据，仅传输模型参数，规避数据聚合泄露风险。
  4. 隐私计算：基于可信执行环境 TEE 与同态加密，实现加密数据推理与计算。
  5. 权限与时效管控：隐私数据限时存储、分级访问、操作审计。
- 如何防止 Agent 泄露敏感信息？
  1. 输入脱敏：在数据送入LLM前，使用正则表达式替换手机号、身份证、邮箱、银行卡及API Key等敏感信息。
  2. 输出过滤：检查Agent回答中是否包含System Prompt内容、内部路径或密钥等敏感信息。
  3. 路径白名单：限制Agent仅能访问指定目录，禁止访问/etc、~/.ssh等系统敏感路径。
  4. 私有部署：对于高度敏感数据场景，采用本地部署的LLM（例如Ollama），确保数据不离开内网。
- 沙箱隔离机制原理，为什么要用轻量化microVM沙箱？
  1. 基于CloudHypervisor构建microVM级内核沙箱，为每个Agent任务提供独立的轻量虚拟运行环境，实现进程、资源、网络与数据的全面隔离。
  2. 传统虚拟机开销大、启动慢，难以支撑高并发场景。
  3. microVM具备3-13MiB超低内存开销、毫秒级启动能力，支持数千级并发部署，兼顾强隔离安全性与高并发性能。
- Docker 容器和 Firecracker 微虚拟机做 Sandbox 有什么区别？
  1. Docker 共享宿主机内核，隔离在进程/文件系统层面，内核漏洞可逃逸；Firecracker 每个沙箱运行独立内核，内核级隔离，逃逸难度极高。
  2. 代价对比：Docker 启动秒级、资源开销小；Firecracker 启动约 125ms、资源开销更大。
  3. 选型原则：金融/医疗等高安全场景选 Firecracker，一般 Web 场景 Docker 够用，不想自建选 E2B/Modal 等云沙箱服务。

#### 2.4 MCP 与 Skills：职责边界

- Skills、MCP 与 Function Calling 的职责边界（MCP 协议机制见 09.5）
- 什么是Agent的「技能（Skill）」？与「工具（Tool）」有何区别？
- MCP 协议解决了什么问题？与 Function Calling 是什么关系？
  1. MCP 通过提供统一的工具定义与发现协议，有效解决了工具定义碎片化问题。
  2. MCP 与 Function Calling 并不冲突。Function Calling 是 LLM 层面的结构化调用能力，而 MCP 作为协议层面的标准，为 Function Calling 提供统一的工具描述。
- MCP Gateway 解决了什么问题？它的路由策略有哪些？
  1. Agent 在同时连接多个 MCP Server 时，需逐一管理其健康状态、版本兼容性和负载分布，导致复杂度较高。
  2. MCP Gateway 作为统一入口管理所有 Server，Agent 仅连接 Gateway 一个端点，由 Gateway 代理转发、智能路由和安全管控。
  3. 路由策略包括：按工具类型路由（如 search_* 路由至搜索 Server）、按服务优先级路由（官方 Server 优先，故障时降级到社区 Server）、按负载均衡路由（采用轮询或最少连接数算法选择最空闲实例）。
- MCP 客户端如何发现服务器的可用能力？
  1. 能力协商（Capabilities Negotiation）机制在 initialize 握手阶段实现：Client 声明自身能力（如 roots、sampling），Server 返回自身能力声明（如 tools、resources、prompts）。
  2. 握手完成后，Client 通过 tools/list、resources/list、prompts/list 方法在运行时动态发现具体能力，无需提前硬编码。
- 谁在支持 MCP？它的发展前景如何？
  1. 客户端支持情况：Claude Desktop、Cursor、Windsurf、Cline 等均已支持；服务端已有超过 100 个官方与社区 Server，覆盖 GitHub、Slack、Google Drive、PostgreSQL 等常用服务。
  2. 框架集成情况：LangChain、Spring AI、Google ADK、OpenClaw 等主流框架均已原生支持。
  3. MCP 正在成为 Agent 工具生态的事实标准，由 Anthropic 主导但保持开放，地位类似 HTTP 之于 Web；截至 2025-2026 年，其月下载量已突破 9700 万至 1.1 亿次，技能生态超过 8.5 万个。
- MCP 的传输方式有哪些？各适用什么场景？
  1. stdio：Server 作为 Client 的子进程，通过标准输入与标准输出通信，零网络开销、最简单，适用于本地工具（如文件系统、本地数据库）。
  2. SSE（已废弃）：基于 HTTP 的 SSE 双通道长连接，支持跨机器通信，但需维持长连接状态、断线不可恢复，是远程工具的旧有方案。
  3. Streamable HTTP（推荐，替代 SSE）：无需维持长连接、支持断线恢复、Serverless 友好、纯 HTTP 兼容基础设施，适用于远程工具、云服务与 Serverless 部署。
  4. 传输层可插拔：分层设计支持未来扩展 WebSocket、gRPC 等传输方式，不影响上层协议逻辑。
- MCP 的三个核心概念是什么？
  1. Tools（工具）：可由LLM自主调用的函数，具备输入参数与返回值，用于执行搜索、查询等具体操作。
  2. Resources（资源）：可被LLM读取的只读数据，通过URI进行标识，用于提供文件内容、数据库记录等上下文信息。
  3. Prompts（提示模板）：预定义的提示词模板，可接受参数以生成完整提示，用于标准化代码审查等知识传递流程。
  4. 总结：Tools负责执行操作，Resources提供数据上下文，Prompts用于标准化提示生成。
- Tool 和 Skill 的区别是什么？
  1. Tool 是原子工具，即单个函数，粒度细且可组合。
  2. Skill 是技能包，由多个工具、提示词与流程组合而成，粒度粗且可直接使用。
  3. Skill 让 Agent 直接调用预设流程，无需每次从头推理工具组合。
  1. Tool：最小原子单元，单一独立基础能力，仅能完成单一操作，例如查天气 API、数据库查询、文件读取。
  2. Skill：基于多个基础工具封装而成的复合能力，面向完整子任务，内部自动协调多次工具调用，例如「出行规划技能」自动调用天气、机票、酒店三类工具。
  3. 将高频复杂工具链路、任务流程、校验规则封装成标准化可复用能力。
  4. 作用：简化规划压力减少重复拆解
  5. 统一执行标准避免调用出错
  6. 降低模型依赖提升稳定性
  7. 便于迭代运维与批量优化。
- 如何创建Skill？验证步骤是什么？
  1. 在客户端的 Skills 管理界面安装 skill-creator。
  2. 由 AI 分析现有代码并生成标准 Skill 文件，随后审查其是否包含准确的 name/description、前置条件、步骤、代码模板与注意事项。
  3. 验证阶段：提出相关任务，AI 应能自动识别并加载对应 Skill。
  4. 上传阶段：将 Skill 复制至团队仓库 skills 目录并提交推送。
- Skill文件结构规范是什么？
  1. Skill 文件通过 YAML frontmatter 定义 name 与 description，其中 description 决定 AI 触发该 Skill 的时机。
  2. 正文涵盖前置条件、分步骤操作指引、代码模板、注意事项与错误处理。
- Skills 有哪些类型？
  1. 工具接入类：封装内部工具链的接入规范；代码生成类：固化特定模式的代码生成逻辑。
  2. 元技能类：使 AI 具备自我扩展能力，如 skill-creator 根据现有代码创建新 Skill。
  3. 搜索发现类：从社区技能库中搜索并安装可用 Skill，如 find-skills。
- MCP Skills 市场与传统 App Store 的本质区别是什么？
  1. App Store 提供的核心是产品：面向终端用户的完整应用程序，以独立进程运行，由于沙箱隔离，应用间难以组合，审核重点在于隐私合规与用户体验。
  2. Skills 市场提供的核心是能力：供 Agent 组合使用的专业技能模块，内嵌于 Agent 的调用流程中，支持灵活的组合与编排，共享 Agent 上下文，审核重点在于权限边界与 MCP 兼容性。
  3. 两者的本质区别在于：前者面向终端用户提供直接交互，后者面向 Agent（代表用户进行间接交互）；Skills 更注重可组合性与标准接口，而非独立的用户体验。
- 工具系统由哪几部分组成？
  1. 工具系统包含三大模块：MCP 连接外部数据源，Skills 封装领域专家经验，知识库注入业务上下文。
  2. 通俗比喻：MCP 是开门的钥匙，Skills 是开门后要做的事，知识库是进门前读的说明书。
- 知识库有哪些类型？
  1. 文档库：挂载团队 Wiki 空间，沉淀团队技术文档、运维手册等。
  2. 代码库知识：挂载 Git 仓库中的公共组件、SDK 与框架源码。
  3. 生成式知识库：基于代码库自动生成结构化知识文档，辅助理解项目架构与模块逻辑。
  4. 自定义文件：上传需求文档、设计稿、会议纪要等非结构化资料。
  5. 使用方式：显式引用（对话中 @ 指定知识库）、自动引用（开启自动参考后按问题自动检索）与团队共享。
  6. 推荐优先级：优先团队技术文档与核心公共库（P0），其次业务需求文档与项目级生成知识（P1），最后运维手册等低频资料（P2）。
- 什么是「工具学习」Agent？如何让Agent通过阅读文档、试错学会新工具？
  1. 定义：无需人工预先编写完整工具 Schema 与描述，Agent 自主读取接口文档、通过多次试错调用，学习工具功能、入参规范与适用场景。
  2. 文档阅读学习：解析 OpenAPI 接口文档（接口名称、功能、请求参数、数据类型、返回结构），自动生成标准化工具描述与 Schema，完成工具注册。
  3. 试错迭代学习：初次调用报错时读取错误信息，复盘参数缺失、类型错误、取值越界等问题，修正后重试并沉淀记忆，后续不再重复出错。
- 解释MCP（Model Context Protocol）协议，解决了传统Function Call的哪些痛点？
  1. MCP：面向大模型与 Agent 生态的标准化开放通信协议，统一工具调用、上下文传递、多智能体交互的数据格式与通信流程，实现跨框架无缝互通。
  2. 解决框架不兼容：LangChain、AutoGen 等框架 Function Call 格式独立，MCP 统一标准化报文，任意框架均可解析交互。
  3. 解决上下文割裂：统一封装完整上下文载体，跨服务传递信息流转完整不丢失。
  4. 解决工具生态绑定：工具标准化接入，一次适配全框架复用，更换框架无需重新适配工具。
  5. 解决多轮交互无规范：内置完整多轮任务交互规范，标准化处理串行/并行调用与反思重试流程。
  6. 统一多工具、多系统接入规范，避免适配混乱
  7. 标准化参数校验、异常返回与日志格式，便于故障排查。
  8. 支持工具热更新、插拔式接入，无需改动 Agent 主逻辑
  9. 提升多 Agent 协作的通信稳定性与兼容性。
- MCP 如何让 AI Agent 使用知识库？
  1. 通过 MCP 暴露 search/ask/build_index 等工具，任何 Agent 经 JSON-RPC 调用；instructions 注入引导 Agent 优先使用 ask/search，避免 read_document 遍历整个文档的反模式。
  2. 一个知识库可同时服务 Claude Desktop、Cursor、Copilot 与自研 Agent，无需为每个工具单独对接。
  3. MCP 解决的是工具调用标准化问题，RAG + MCP 即「知识库即服务」。
- 在什么情况下不应该使用MCP？
  1. 对于简单的脚本或天气查询等可直接调用API的场景，无需引入MCP。
  2. 纯逻辑推理、创意写作与代码生成等场景中，MCP几乎没有发挥作用的空间。
  3. 当引入MCP所带来的复杂度超出其解决的问题时，应避免使用MCP。
- MCP 有哪些类型？
  1. DB MCP 自动读取数据库 Schema，避免 AI 生成不存在的字段，保证 SQL 准确。
  2. Knowledge Base MCP 挂载团队内部文档，为 AI 提供业务上下文。
  3. API MCP 实时查询服务接口定义，确保微服务联调时参数保持一致。
  4. 运维 MCP 接入 CI/CD 与监控系统，使 AI 可直接触发构建、查看日志并分析告警。
- 如何验证MCP连接？排查思路是什么？
  1. 通过 DB MCP 读取当前数据库 users 表结构进行验证。
  2. 失败时排查：确认 MCP Server 已正常启动（查看客户端输出面板日志）、数据库连接信息正确、网络可达、Agent 模式已开启。
### 03 多 Agent 协作

#### 3.1 角色与职责划分

- Agent 角色与职责划分
- 推荐Agent和风控Agent的分工关系是什么？
  1. 推荐Agent发挥正向赋能作用，优化流量、互动与留存指标，筛选优质合规内容以实现精准分发。
  2. 风控Agent承担反向兜底职责，拦截违规、低质与擦边内容，清理不良流量。
  3. 协同逻辑：风控前置过滤风险内容，推荐Agent在合规优质内容池内进行个性化分发，兼顾内容安全与业务指标。
- 单智能体在复杂多任务场景下的瓶颈是什么？
  1. 推理瓶颈：多任务并行时逻辑混乱、优先级错乱。
  2. 记忆瓶颈：多任务记忆交叉污染、信息混淆。
  3. 能力瓶颈：单一智能体无法同时精通多领域复杂业务。
  4. 效率瓶颈：多任务串行执行速度慢、容错率低，无法适配大规模高并发场景——这是多智能体诞生的核心原因。
  5. 必须引入多自主Agent的场景包括：跨领域复杂任务、多角色分工任务、高精度校验任务、大规模批量落地任务，以及需要互评纠错的严谨场景。
- 什么是多智能体协作？和单智能体相比核心优势是什么？
  1. 将不同能力、不同职责的多个 Agent 组合，通过分工、通信、协同完成超复杂综合任务。
  2. 分工明确：拆解推理、检索、执行、复盘等职责，专属 Agent 负责专属模块。
  3. 能力更强、稳定性更高：突破单智能体能力边界，单一 Agent 故障不影响整体流程。
  4. 迭代更灵活：可单独优化、替换单个智能体，无需整体重构。
  5. 自主通信：Agent 之间自主发起对话、同步信息、协商分歧，无需人工预定义交互逻辑。
  6. 动态分工：根据任务难度自主分配角色、调整分工，不局限于固定流程。
  7. 自主互评纠错：多 Agent 相互校验执行结果、通过辩论优化输出，提升精度。
  8. 与传统多 Agent 的区别：传统多 Agent 依赖人工定义角色、流程与交互逻辑；自主多 Agent 通过自主通信、动态分工与协商完成协作，低耦合、高扩展，适合工业化大规模落地。
- 自主Agent和多智能体的关系？是包含还是独立关系？
  1. 自主Agent与多智能体是基础与进阶的包含关系；单智能体具备自主能力即可实现单任务闭环。
  2. 多智能体协作的前提是每个子Agent均具备自主能力，否则无法实现自主分工、沟通与纠错。
  3. 落地逻辑为先构建单Agent自主闭环，再通过多智能体协同放大能力；缺乏自主能力的多智能体仅是简单流程拼接。
- 生产级多智能体架构的设计思路是什么？核心考量点？
  1. 权责拆分：按业务能力拆分智能体，职责清晰、互不干扰。
  2. 通信可控：统一交互规则，杜绝信息混乱与冗余。
  3. 容错兜底：单 Agent 故障可降级、重试、替换，保障整体任务闭环。
  4. 记忆隔离：各智能体记忆分层隔离，避免跨模块记忆污染。
  5. 可迭代性：支持单个 Agent 独立优化、升级、替换，适配业务快速迭代。
- 多智能体系统的常见架构模式有哪些？（如MetaGPT、AutoGen、CrewAI）
  1. AutoGen：对话驱动多 Agent，自由交互、灵活协商，适合快速实验与开放式协作任务。
  2. CrewAI：角色分工 + 任务流水线，强流程、强顺序，适合标准化业务流程落地。
  3. MetaGPT：标准化 SOP + 消息池机制，高度工程化、层级清晰，适合复杂项目、软件开发与团队协同工程任务。
- 通俗解释AutoGen框架？它和普通Agent框架的差异？
  1. AutoGen 是微软开源的多智能体自主协作框架。
  2. 通用框架聚焦单 Agent 的工具调用与对话应答；AutoGen 支持多自主 Agent 自定义角色、自主对话、自主分工与自主纠错。
  3. AutoGen 原生支持任务自治、角色解耦与流程动态调整，主打零人工干预闭环，是落地自主 Agent 的核心工业级框架。
- 构建软件开发团队Agent时，如何模拟产品经理、架构师、工程师等角色Prompt？
  1. 产品经理 Agent：聚焦需求拆解、场景梳理、PRD 撰写与需求校验；禁止写代码、做架构；输出结构化需求文档、功能清单与边界约束。
  2. 架构师 Agent：聚焦技术选型、模块拆分、流程设计与风险评估；禁止细粒度编码；输出架构图、技术方案、模块依赖与落地规范。
  3. 工程师 Agent：聚焦编码实现、接口开发、Bug 修复与单元测试；禁止改动需求与架构；输出可运行代码、注释与测试用例。
  4. 统一约束：各司其职、不越权、不重复工作，按岗位固定格式输出成果。
- 对比「中心化多Agent」与「去中心化多Agent」的优缺点与适用场景
  1. 中心化优点：流程可控、秩序稳定、易运维、故障易定位；缺点：中心节点性能瓶颈、灵活性弱；适用标准化流程、固定工作流与企业级落地业务。
  2. 去中心化优点：无单点瓶颈、灵活自适应、并行效率高；缺点：协作不可控、运维复杂、易出现循环与冲突；适用大规模并行计算、动态复杂任务与蜂群智能场景。
- 对比LangChain、LangGraph、AutoGPT、MetaGPT、CrewAI等框架的核心差异
  1. LangChain：基础组件框架，提供工具、记忆、链能力，适合快速搭建简单 Agent，无原生复杂工作流。
  2. LangGraph：工作流编排框架，支持分支、循环与状态持久化，专治复杂多步骤、可回溯任务。
  3. AutoGPT：自主任务 Agent，擅长自主拆解目标、持续迭代执行，适合开放式探索任务。
  4. CrewAI：角色分工流水线框架，强流程、强顺序，适合标准化业务落地。
  5. MetaGPT：工程化多智能体框架，SOP 标准化、层级清晰，适合软件开发与复杂工程项目落地。
  6. LangGraph 采用有向图与条件边，内置检查点与时间旅行机制，同一任务约消耗 2000 token，适用于长时运行、需审计与回滚的生产管线，已成为企业生产事实标准。
  7. CrewAI 采用角色化 Crew 协作模式，任务输出按序列传递，约消耗 3500 token，适合规范化角色分工协作场景。
  8. AutoGen 采用对话式 GroupChat，以对话历史为核心，约消耗 8000 token，适合多模型对话协调的探索性任务。
  9. Google ADK 采用结构化图架构，支持分层协调与 A2A 协议，以代码优先（Code-First）为理念，面向企业级部署。
  10. Token 消耗差异源于图结构将智能体间对话转化为状态转换，省去相互转述背景信息的冗余开销。
  11. Anthropic 提醒：框架与抽象层会掩盖提示和响应细节，增加调试难度；建议优先直接使用 LLM API，采用框架时务必理解底层实现。
- 未来Agent的形态是「超级大脑」还是「协作蜂群」？从算力、延迟、可靠性分析
  1. 超级大脑（单 Agent 强推理）：大参数、全能力单体。优势：逻辑统一、延迟可控、决策一致性强、无协作冲突；劣势：算力成本极高、单点故障风险、大规模并行效率低；适配精密决策、代码开发、复杂逻辑推理等场景。
  2. 协作蜂群（多 Agent 分布式）：轻量化 Agent 集群自主协作。优势：算力分散、负载均衡、容错性强、并行效率高、成本可控；劣势：协作延迟高、易逻辑冲突、一致性难保障；适配海量批量任务、文档处理、多维度并行分析。
  3. 未来趋势：核心关键决策由超级大脑兜底，大规模执行任务由蜂群集群并行落地，形成「强核心 + 广集群」的融合架构。

- 高并发业务多Agent集群，和通用多智能体的区别与落地难点？
  1. 流量结构不同：通用多 Agent 流量平稳均匀
  2. 拼多多依托电商大促存在瞬时脉冲流量，峰值并发是日常的百倍千倍。
  3. 核心矛盾不同：通用侧重协作完成任务
  4. 拼多多重点解决算力抢占、任务拥堵、资源冲突。
  5. 精度要求不同：商品价格、库存、售后禁止幻觉造假
  6. 优化目标从追求智能化变为追求高可用、低延迟、零虚假信息。
  7. 流量波动极端：大促瞬时流量暴涨，通用架构无法适配脉冲式并发。
  8. 资源冲突严重：多 Agent 共享算力缓存易拥堵死锁，需精细化调度
  9. 幻觉风险极高：商品长文本复杂、规则叠加多。
  10. 数据迭代极快：商品、价格、活动每日更新，知识对齐难度远高于通用场景。

- 业务多Agent包含哪些核心角色？各自负责什么？
  1. 检索 Agent：超长商品文本解析、知识库召回、内容检索。
  2. 搜广推 Agent：按用户意图匹配商品、分发流量、优化曝光。
  3. 风控纠错 Agent：拦截检索幻觉、虚假价格、错误售后信息。
  4. 调度 Agent：大促高峰期统一分配算力、限流、熔断、任务排队。

- 单Agent和多Agent架构，核心适用场景区别是什么？怎么选型？
  1. 单 Agent 适用：流程简单、任务链路短、无需多角色分工（单轮问答、简单文案、基础查询），优势是链路简单、低延迟、无协作冲突、维护成本低。
  2. 多 Agent 适用：业务复杂、流程拆分明确、需分工校验与高容错（内容审核+创作双链路、用户分层运营、复杂工单），各司其职、互为兜底，规避单点故障。
  3. 选型原则：简单场景优先单 Agent 避免过度设计，复杂高可靠场景优先多 Agent 分工架构。
  4. Anthropic 提出子智能体的三个适用场景：上下文保护（子任务产生超过 1000 token 但与主任务无关的信息时，使用子智能体隔离）、可并行（任务可切分为独立分支）、专业化（不同步骤需要不同工具、提示或专注度）。
  5. 成本数据显示，多智能体系统在内部评测中性能超过单智能体 90.2%，但 token 消耗约为单智能体的 15 倍，且 80% 的性能方差可由 token 用量解释。
  6. 对于单目标、单领域且具备明确停止条件的任务，使用清晰的 Loop 结构最优；强行拆分为多智能体只会徒增延迟、成本与调试难度。
  7. 治理红线在于：工作图（任务如何拆分/合并）可以快速变化；角色图（谁有权修改数据库、谁能绕过审批）必须慢变且可审计。

- 设计一套「多Agent协同内容生产架构」？
  1. 调度 Agent：需求解析、任务拆解、流程统筹、资源分配。
  2. 创作 Agent：文案生成、内容润色、结构排版
  3. 检索素材 Agent：真实素材、数据、案例检索，降低幻觉。
  4. 合规审核 Agent：内容风控、违规拦截、事实校验
  5. 反思迭代 Agent：输出复盘、问题记录、策略优化。
  6. 整体中心化调度+分层执行，分工清晰、互为兜底，控制故障影响范围，支持规模化迭代。

- 多Agent协作最大的工程难点是什么？如何系统性解决？
  1. 核心难点：职责边界模糊、任务冲突、通信异常、故障串联、运维成本高。
  2. 方案：标准化职责拆分明确能力边界
  3. 统一 MCP 通信接口规范交互与异常返回
  4. 中心调度统一管控
  5. 全链路日志埋点与单 Agent 故障隔离
  6. 分层监控告警快速定位协作异常。

#### 3.2 任务分发与路由

- 任务分发与路由
- 如何设计多Agent系统的「任务分配」策略，实现负载均衡与效率最优？
  1. 能力匹配分配：根据 Agent 角色、工具权限与专业能力匹配对应类型任务，专业事交给专业 Agent。
  2. 负载感知分配：实时监控各 Agent 任务堆积量，优先分配给空闲、低负载节点，避免忙闲不均。
  3. 优先级调度：高紧急、高权重任务优先执行，普通任务队列排队，保障核心链路时效。
  4. 动态容错分配：节点超时、故障时自动迁移任务至正常节点，保证整体流程不中断。

#### 3.3 通信与状态共享

- Agent 间通信与状态共享（协议机制见 09.5 的 A2A）
- 多智能体协作最大的痛点是什么？如何解决通信混乱问题？
  1. 最大痛点：通信冗余、信息不对称、协作混乱、任务冲突。
  2. 统一通信协议与输出格式，规范 Agent 之间的信息交互标准。
  3. 增设调度中心 Agent，统一分发任务、管控进度、协调冲突。
  4. 过滤冗余通信信息，只传递核心有效数据；明确各智能体权责边界，避免重复执行与任务推诿。
- 子代理“隔离但继承”的边界画在哪？继承太多或太少各会怎样？
  1. hermes-agent 的边界原则为“继承配置、隔离状态”：凭证、工具集、降级链等不随对话变化的配置项执行继承，对话历史、记忆等随对话变化的状态项相互隔离。
  2. 继承过多（如完整对话历史）会挤占子代理的任务空间，并可能将父代理的闲聊误作为任务上下文；继承过少（如凭证）则每个子代理都需重复配置，导致启动开销与配置复杂度上升。
  3. 工具集取交集可保证安全策略的传递性，父代理禁用的工具子代理同样不可用；凭证采用共享引用而非复制，父代理密钥轮换对子代理即时生效。
  4. 子代理被标记为跳过记忆写入，避免多个子代理并发写入共享记忆产生竞态；子代理不可再创建子代理，嵌套层级默认仅允许一层。
- A2A（Agent-to-Agent）协议的设计初衷是什么？如何解决跨框架通信互操作性？
  1. 设计初衷：各类 Agent 开发框架与运行环境互不兼容，Agent 之间无法直接传递任务、共享上下文、分发子任务；A2A 制定独立于框架与模型厂商的标准化消息通信规范。
  2. 标准化消息载体：统一 JSON 结构化消息格式，固定收发 Agent 标识、任务指令、上下文、工具结果、消息类型等字段。
  3. 通用传输层适配：兼容 HTTP、WebSocket、RPC 各类传输通道，不绑定框架专属通信模块。
  4. 统一任务语义规范：标准化任务请求、结果回复、异常报错三类基础语义，跨框架 Agent 可解析对方消息的业务含义。
  5. 统一身份鉴权：标准化 Agent 身份标识与权限校验规则，跨框架协作时完成身份校验，保障通信安全。
- 多Agent之间的通信方式有哪些？如何设计消息协议保证兼容性？
  1. 常见通信方式：一对一单播、广播群发、消息池订阅、RPC 调用、WebSocket 实时推送。
  2. 兼容协议设计：统一 JSON 结构化消息，固定发送方、接收方、任务类型、上下文与状态码字段。
  3. 统一语义规范与统一错误码，适配多传输层，实现跨框架、跨 Agent 互通。
- MetaGPT的「消息池机制」如何工作？如何解决多Agent信息共享问题？
  1. 消息池是全局统一消息中心：所有 Agent 的输出、任务、日志统一写入公共消息池。
  2. Agent 按需订阅、读取对应消息，实现全局信息共享。
  3. 基于角色权限做消息隔离，无关消息不可见。
  4. 统一消息时序，保证团队协作有序推进，避免信息不对称。
- AgentScope的「分布式Agent」如何处理跨进程/机器通信？
  1. 核心是统一消息总线 + 节点解耦通信：所有 Agent 节点注册统一消息总线，任务消息、执行日志、结果数据统一中转，彻底解耦节点依赖。
  2. 跨节点寻址：通过唯一 Agent ID 与节点 IP 端口实现精准消息投递，支持一对一、广播与订阅式通信。
  3. 进程隔离机制：不同进程/机器的 Agent 资源独立、互不抢占，避免单机故障扩散。
  4. 状态同步：跨机器同步任务状态与上下文进度，保证分布式任务断点续跑、状态一致。

#### 3.4 执行模式与结果聚合

- 串行与并行协作
- 冲突处理与结果聚合
- 多智能体常见的三种协作模式是什么？
  1. 流水线模式：按固定流程串行执行，上一 Agent 输出作为下一 Agent 输入，适合标准化流程任务。
  2. 辩论互评模式：多个同质 Agent 独立输出结果、相互校验纠错，输出最优解，适合高精度高严谨性场景。
  3. 统筹调度模式：设置调度主 Agent 负责任务分发、分工、进度管控、结果汇总，多个子 Agent 并行执行，适合复杂多任务场景。
- 委派（有执行能力）和咨询（只出建议）在什么场景下应互相替代？有没有两者都不适合的场景？
  1. 委派适用于可独立完成的明确子任务，子代理为具备工具与执行能力的完整代理实例，独立完成任务后返回摘要 JSON 并注入父上下文。
  2. 咨询适用于需要多视角的决策场景，多个模型仅返回纯文本建议，不能调用工具，安全性更高但能力受限，结果作为建议文本注入主循环。
  3. 两者均不适合需紧密协作的并行任务：子代理之间需频繁交换中间结果时，委派的隔离性阻断中间通信，咨询又无法执行操作，需采用共享工作区与多轮协调的升级编排方案。
  4. 判断标准为子任务之间是否需要运行时通信：不需要时可选委派或咨询，需要时则升级为共享状态编排。
- 多Agent系统中的「共识机制」如何达成？多个Agent意见冲突时如何仲裁？
  1. 投票机制：多 Agent 结果投票、少数服从多数，解决普通分歧。
  2. 角色优先级：专业领域 Agent 权重更高，专业结果优先采信。
  3. 主 Agent 仲裁：设置全局调度 Agent，出现冲突统一终审决策，保证任务唯一出口。
- 多Agent系统中「协作」与「竞争」的关系？哪些场景需要引入竞争机制？
  1. 协作是多 Agent 分工互补、共同完成目标；竞争是多 Agent 独立输出、择优筛选结果，二者互补适配不同业务场景。
  2. 竞争机制适用场景：方案评审（多架构 Agent 输出方案择优）、答案校验（多问答 Agent 独立作答、交叉校验修正幻觉）、任务择优（多执行 Agent 完成同一任务、筛选最高质量产出）、容错兜底（单一 Agent 出错时竞争胜出结果补位）。
- 什么是「蜂群智能（Swarm Intelligence）」在多Agent系统中的应用？
  1. 定义：去中心化多 Agent 协作模式，无中心调度节点，个体 Agent 遵循简单局部规则，通过群体交互自发涌现出整体智能，完成复杂任务。
  2. 落地场景：大规模文档并行拆解、检索与总结；多维度并行推理与多角度答案校验；海量子任务分布式并行执行与自适应负载；动态任务场景无需人工预设流程，群体自适应调整协作策略。

- 多Agent协作出现任务冲突、互相抢占资源，怎么解决？
  1. 职责边界拆分：明确各 Agent 专属能力，减少职责重叠与重复作业。
  2. 任务优先级管控：核心任务优先、次要任务避让
  3. 资源隔离：工具、缓存、算力分层隔离
  4. 主 Agent 统一调度避免无序竞争。

#### 3.5 死循环与失控控制

- 协作流程中的死循环控制
- 如何解决多Agent对话中的「无限循环」问题？给出检测与熔断机制
  1. 循环检测：监控连续轮次语义重复、任务状态无更新、来回无进展的对话，判定为循环。
  2. 最大轮次限制：单任务交互超限自动终止。
  3. 状态熔断：连续多轮状态无变更，强制结束对话。
  4. 人工兜底：触发熔断后输出总结结果，请求用户确认后续动作。
- 多Agent系统的「安全护栏」如何设计？防止单个Agent错误影响全局？
  1. 资源隔离：各 Agent 独立进程、独立上下文，内存与资源互不抢占。
  2. 熔断降级：单 Agent 持续报错自动熔断、停止调度，避免错误扩散。
  3. 结果校验拦截：Agent 输出前置校验，拦截幻觉、错误与违规结果，不流入全局流程。
  4. 兜底备用机制：单点故障自动切换备用 Agent 或兜底逻辑，保证流程不中断。

- 大促场景下，多Agent为什么容易出现任务死锁？
  1. 大促瞬时任务暴增，检索、推流、风控 Agent 互相抢占缓存、数据库、算力资源。
  2. 任务互相依赖、资源持有不释放，形成循环等待，最终导致集群死锁、服务超时。

### 04 记忆与上下文管理

> 边界：短期记忆 = 单会话内上下文窗口管理（4.1）；长期记忆 = 跨会话持久化（4.2）。状态持久化已移至 01.3，这里只讲记忆本身的机制。

#### 4.1 上下文管理（短期记忆）

- 上下文窗口限制
- 什么是上下文窗口？为什么 agent 更费窗口？
  1. 上下文窗口是大模型处理的 token 总量上限，包括系统提示、所有历史对话和当前问题。
  2. Agent 消耗更多上下文窗口，原因包括固定初始开销（如系统提示占用 5k-10k token）、工具调用产生 tool_use 和 tool_result 记录并累积（tool_result 可能包含大量内容且每轮重新加载），以及大文件读取占用大量 token。
- 为什么 CLAUDE.md 限制 200 行 / 25KB？超了怎么办？
  1. 设置上下文窗口限制，是为了预留空间容纳用户对话、工具返回结果等其他必要内容。
  2. 当上下文超限时，系统依次触发三级压缩链：首先是 microCompact，用于去除冗余信息；其次是 autoCompact，由大语言模型生成摘要；最后是 sessionMemoryCompact，进行会话级压缩。
  3. 若压缩后仍超限，则截断最旧的内容。其中，autoCompact 阶段会为摘要保留 20,000 token 的空间，并预留 13,000 token 的缓冲。
- LLM-Wiki 和 RAG 的区别是什么？什么时候用哪个？
- 多轮工具调用的 Context 膨胀问题如何解决？
  1. 核心原则是“记录要点，存储细节”，即将关键摘要置于上下文（Context），完整结果存储于向量库。
  2. 具体策略包括：使用摘要替代原始结果；选择性保留关键字段；将完整结果归档至向量库。
- 上下文工程如何优化工具管理？JIT 加载和 Tool RAG 的核心思路是什么？
  1. 核心思路在于为LLM提供恰好满足需求的工具描述信息，以最小化无效的token消耗。
  2. JIT加载：依据用户意图，仅加载与当前任务相关的少数工具描述。Tool RAG：将所有工具描述进行向量化处理，在检索时仅传入相关性最高的Top-K工具描述。
  3. 相较于全量工具描述传入，采用JIT或Tool RAG策略可显著减少token消耗，并提升LLM的工具选择准确率。
  1. LLM-Wiki 采用文件系统方式进行全量上下文注入，而 RAG 则采用向量检索方式进行按需的 Top-K 片段注入。
  2. 两者核心区别在于 LLM-Wiki 具备知识持续沉淀与积累的特性，而 RAG 每次检索均为独立无累积的片段检索。
  3. 选择标准：在知识量较小（如小于25KB）且每次对话均需完整使用的场景下，建议选用 LLM-Wiki；当知识量较大且仅需检索相关片段时，更适合采用 RAG。
  4. 两者并非互斥，在实际项目中通常结合使用，以兼顾知识的全面性与检索的精准性。
- Agent上下文窗口不足的显性问题和隐形盲区分别是什么？
  1. 显性问题：超长对话与长文档处理中，上下文被截断、关键信息丢失，导致任务执行失败。
  2. 隐性盲区：上下文被挤压后，推理逻辑可能隐性断裂、关键参数遗漏、输出出现局部偏差，任务看似成功实则出错。
  3. 优化方式：采用上下文分层裁剪、关键信息优先保留、长文本分片处理，并以记忆沉淀替代临时上下文。
- 历史消息截断
- 滑动窗口
- 摘要与压缩
- 业界常见的上下文方案有哪些？为什么不够看？
  1. 常见方案包括滑动窗口（从最早消息开始删除）、每N轮摘要（定期总结并替换原对话）、向量召回历史（基于相似度检索历史片段）。
  2. 滑动窗口可能移除关键信息导致Agent失控（如全局指令或工具调用依赖）；每N轮摘要触发时机固定、摘要粒度较粗导致细节丢失；向量召回可能破坏时序依赖和工具调用成对性，从而漏掉关键信息。
- 滚动摘要和全量重摘的错误累积模式有什么不同？什么场景该选哪个？
  1. 滚动摘要以“上次摘要+新消息”为输入增量改写，输入规模恒定较小，不随会话长度膨胀；但错误会跨压缩传递，一次写坏将持续污染后续更新，且无法自我修正。
  2. 全量重摘每次都从头重读全部历史，各次错误相互独立，天然具备自我修正机会；但输入随会话长度线性膨胀，摘要调用本身可能先发生溢出。
  3. 选择取决于摘要出错概率与会话长度：会话越长，滚动摘要越节省资源，但对摘要质量监控的要求越高；hermes 通过结构化检查点模板、凭据脱敏、时间锚定与节省率检查来强化监控。
  4. hermes 选择滚动更新，因为在以天为单位的会话中，压缩属于高频事件，必须将摘要调用的输入压缩为恒定小规模。
- Auto-Compact 的整体思路是什么？
  1. 核心策略是：基于Token数量设置绝对阈值触发机制，通过全量重写历史消息并送入摘要器进行压缩，同时将关键信息（如文件内容、项目规范文档、异步任务状态）通过独立通道重新注入当前上下文。
  2. 其核心原则是：接受对话历史可能过时，通过保留结构化状态（如目标、进度、错误记录、下一步计划）而非原始对话来维持任务连续性。
- Claude Code 的上下文管理是如何设计的？
  1. 采用五层压缩金字塔架构：第一层，大结果存储至磁盘（单工具结果超过50KB时写入磁盘并保留预览）；第二层，Snip机制标记并删除历史无用消息；第三层，Micro-Compact时间衰减（超过60分钟清空旧工具结果）；第四层，Context Collapse读时投影（上下文占用达90%时动态压缩视图）；第五层，Auto-Compact全量摘要（上下文逼近上限时重写对话）。
  2. 设计原则遵循从轻到重，尽可能避免不必要的压缩；第四层与第五层互斥，同一时刻仅启用一个。
- 关键信息提取
- 什么时候触发压缩？触发阈值怎么算？
  1. 触发时机为当前对话token数超过上下文窗口上限的预设缓冲值，而非基于对话轮数或比例计算。
  2. 有效上下文窗口计算方式：原始窗口减去20k预留摘要输出空间，再扣除13k安全缓冲，最终有效容量约为33k tokens。
  3. 手动触发（/compact命令）可传入自定义指令；自动触发时会暂停用户输入，并设置熔断机制：连续失败3次后停止重试。
- Token 预算管理
- 压缩时压什么、留什么、丢什么？
  1. 对全部历史消息进行摘要重写，不区分新旧。
  2. 压缩后的对话结构包含边界标记（记录压缩元数据）、摘要消息（总结全对话）、附件（恢复关键信息）与Hook结果。
  3. 保留内容包括：语义信息写入摘要；状态信息（如最近读取的文件内容、CLAUDE.md、异步任务状态）通过附件重新加载；系统提示词在每次交互时重新构建。
  4. 原始对话历史将被丢弃，但关键信息通过上述附件与摘要通道恢复。
- 长文本分治
- 摘要 prompt 是怎么设计的？
  1. 防呆设计：禁止工具调用，并在提示词开头和结尾强调，防止模型在摘要时调用工具。
  2. 输出格式：采用 XML 格式，包含 analysis 草稿（供模型思考，后剥离）和 summary 摘要（进入对话），summary 包含 9 个固定章节。
  3. 关键章节包括枚举所有用户消息（确保不丢失需求变更）和最细颗粒度的当前进度（如具体调试哪个文件的哪个函数）。
- 如何定义Agent的「上下文」？与传统NLP的上下文有何不同？
  1. Agent 上下文是任务全链路的完整多维信息集合：用户对话、当前任务执行状态、历史规划轨迹、工具返回结果、记忆召回内容。
  2. 传统 NLP 上下文仅存储轮次对话文本，无任务状态、工具数据与规划信息，仅服务于单次对话生成。
  3. Agent 上下文是任务执行的完整状态载体，支撑多轮迭代、连续工具调用与步骤接续执行。
- 压完之后怎么接续对话？
  1. 压缩后对话采用四段式结构：边界标记、摘要消息、附件、hook结果。
  2. 文件恢复：最多加载5个最近活跃文件，单文件上限5k token，总预算50k token。
  3. CLAUDE.md通过缓存清理在下一轮对话自动重新加载；system prompt以新方法重建更新工具列表；异步任务状态作为附件注入。
- 解释「上下文工程（Context Engineering）」与传统Prompt Engineering的区别
  1. Prompt Engineering 仅负责设计系统提示词与用户指令，解决单次对话的指令引导问题。
  2. Context Engineering 覆盖 Agent 全生命周期上下文治理：信息过滤、冗余压缩、分层存储、跨步骤流转、无效信息清理。
  3. 核心差异：Prompt 只管控指令；上下文工程管理全流程所有信息，适配多轮、多工具、长任务场景。
- 上下文管理如何实现？
  1. 采用渐进式披露：以约 100 行的 AGENTS.md 作为索引目录，指向 ARCHITECTURE.md、Rules 等细分文档，避免一次性灌输数千行。
  2. 通过 Spec 文件（requirement.md/task.md）将需求与设计写入 Git 仓库，作为 AI 的长期记忆；利用 changes/ 目录实现变更隔离。
  3. 知识分层：Skills 按需加载，遵循“描述→指令→详细步骤”的层级；挂载知识库（团队文档库、代码库、生成式知识库）注入业务上下文。
  4. 原则：避免向 AI 灌输数千行规范文件，建立分层索引，将仓库知识视为系统记录，不依赖聊天历史。
- AGENTS.md的作用是什么？应包含哪些内容？
  1. AGENTS.md 是 AI 的说明书，篇幅控制在约 100 行以内，作为目录索引指向更细分的文档。
  2. 内容包括项目概述、架构说明、目录结构、开发规范、常用命令、当前进行中的需求与注意事项。
- 对比Full History、Sliding Window、Summary Memory、Vector Store Memory四种记忆方案的优劣
  1. Full History：信息零丢失、对话最连贯；Token 爆炸、超长对话卡顿、成本极高，适合短对话测试场景。
  2. Sliding Window：成本可控、实现简单、实时性强；丢失早期关键信息，长任务易断上下文，适合高频轻量闲聊。
  3. Summary Memory：极致压缩 Token、保留核心逻辑；细节丢失、摘要偏差会导致决策错误，适合超长历史复盘与长会话留存。
  4. Vector Store Memory：精准按需召回、不占上下文、支持海量长期记忆；有检索成本、依赖嵌入质量，适合企业知识库与长期用户记忆。
- 长对话超出上下文窗口时，有哪些上下文压缩与筛选策略？
  1. 智能截断：不暴力从头截断，优先丢弃无效闲聊与重复内容，保留关键任务步骤。
  2. 分层摘要压缩：对超长历史做阶段性摘要，用结论替代原始长文本。
  3. 记忆召回替代：超长历史不全部载入上下文，通过向量检索按需召回关键片段。
  4. 冷热分离：近期热数据进上下文，远期冷数据下沉至长期记忆。
- 解释「注意力衰退」现象在长上下文中的表现，给出三种工程解决方案
  1. 现象：长上下文推理时模型对远端历史信息的注意力权重降低，出现遗忘前置条件、忽略关键约束、前后逻辑不一致。
  2. 关键信息置顶：将任务目标、约束规则、前置条件固定在上下文头部。
  3. 分段摘要刷新：长对话分段总结，持续刷新核心信息，弱化衰退影响。
  4. 精准记忆召回：通过向量检索主动拉取远端关键信息，补足注意力盲区。
- 什么是「上下文污染」？如何治理以保证Agent决策准确性？
  1. 定义：冗余、重复、错误、过期、无关的信息混入上下文，导致模型决策偏差、幻觉与逻辑混乱。
  2. 前置过滤：清洗无效日志、乱码与重复文本。
  3. 信息隔离：规则、记忆、工具结果分区存放，互不干扰。
  4. 动态淘汰：及时清理过期、低价值上下文。
  5. 结果校验：工具返回信息做合法性校验，杜绝错误数据进入上下文。
- 多模态Agent中，如何处理图像/文本/音频混合输入的上下文对齐问题？
  1. 统一表征：图像、音频通过 Encoder 转为统一向量空间，与文本向量对齐。
  2. 时序对齐：标记不同模态输入的时间顺序，保证上下文时序不乱。
  3. 语义融合：多模态信息统一拼接、加权融合，共同参与推理。
  4. 模态过滤：过滤无效噪声模态数据，避免多源信息互相干扰。

- 什么是Agent上下文漂移？线上为什么会频繁出现？
  1. 上下文漂移：多轮对话中随轮次增加、冗余信息堆积，逐渐偏离用户原始核心需求，出现答非所问、任务跑偏。
  2. 高频原因：上下文过长有效信息被稀释
  3. 记忆无筛选，无效、情绪化信息干扰
  4. 任务迭代中目标模糊无强制锚定机制
  5. 模型随机性累积逐步偏离初始需求。

#### 4.2 记忆体系（长期记忆）

- 短期记忆与长期记忆
- CLAUDE.md 的四类型记忆分类是什么？为什么要分类？
  1. 记忆分类为四种类型：user（用户偏好）、feedback（纠正错误）、project（项目架构）、reference（资料索引）。
  2. 分类管理便于针对不同类型记忆的生命周期和可信度设置差异化的过期策略。
  3. 记忆写入遵循“仅存储无法从当前项目状态推导的上下文”原则，结构为规则 → Why → How to apply。
- Agent短期记忆和长期记忆的区别？分别怎么用？
  1. 短期记忆主要管理单次会话的上下文窗口，存储对话与临时任务信息，确保多轮交互的连贯性。
  2. 长期记忆则负责跨会话的持久化存储，用于保存用户偏好、历史经验与业务知识，在后续任务中持续复用。
  3. 在工程实现上，需设计状态隔离机制，防止短期临时信息对长期记忆库造成干扰。
  4. 短期记忆存储当前任务进度、推理步骤与工具执行结果，保障单任务自主连贯执行，并实时支撑动态决策。
  5. 长期记忆沉淀历史任务经验、错误案例、场景规则与用户偏好，支撑自主适配场景、规避历史坑点、优化决策逻辑。
- 推荐Agent的「用户记忆能力」有什么作用？
  1. 短期会话记忆用于记录实时浏览行为，捕捉用户临时兴趣，从而实时调整推荐内容。
  2. 长期用户记忆用于沉淀长期兴趣、内容偏好与排斥内容，构建稳定的用户画像。
  3. 业务价值在于解决短期行为干扰长期画像、推荐内容杂乱及同质化严重的问题，提升用户长期留存率。
- 用户、会话与任务记忆
- 记忆存储与召回
- 记忆更新、去重与过期
- Agent多轮对话中，如何避免记忆污染？
  1. 记忆采用分层存储，临时对话信息仅存储于短期记忆，不写入长期记忆库。
  2. 新增记忆条目前进行可信度校验，过滤无效、错误或情绪化信息。
  3. 建立记忆过期清理机制，淘汰过期或失效数据。
  4. 区分用户专属记忆，避免不同用户间数据交叉污染。
  5. 需防止临时性情绪化或偶发行为覆盖用户长期稳定偏好，避免短期行为对长期偏好的错误覆盖。
  6. 针对碎片化无效记忆堆积稀释关键有效记忆的问题，引入记忆打分机制，综合时效性、可信度与用户反馈权重排序，提升记忆召回质量。
  7. 定期压缩与归档冗余碎片化记忆，避免其对有效记忆造成稀释，保障核心记忆的可用性。
- 记忆一致性与权限控制
- 在多用户场景下，Agent系统如何实现会话与记忆的隔离？
  1. Agent内部存在两种需隔离的状态：临时会话上下文（Context）和跨会话长期记忆（Memory）。
  2. 会话隔离的核心是确保单一会话的上下文仅服务于当前用户，防止跨用户共享。
  3. 具体实现：为每个会话分配独立Session ID（绑定user_id和conversation_id），所有临时上下文均挂载于此。
  4. 请求级沙箱执行：工具调用（如数据库查询）必须强制携带用户身份（如user_id）作为过滤条件，避免模型自行推断。
  5. 会话生命周期管理：对话结束或超时后，应及时清空或归档临时状态，防止跨会话干扰和内存泄漏。
  6. 记忆隔离的核心是确保跨会话长期记忆仅可在授权用户的命名空间内检索。
  7. 命名空间隔离：在向量数据库中为每个用户独立创建namespace或collection，检索时强制执行过滤。
  8. 元数据过滤：在记忆条目上附加访问控制标签（如owner_id, access_level），检索时实施双重过滤。
  9. 多租户（SaaS）场景下，需实施租户级隔离，通常采用tenant_id/user_id二级命名空间结构。
  10. 设计原则：Agent系统的记忆架构本质上是一套权限系统，而非仅存储系统。
- 多用户、多租户场景下，Agent如何做好权限隔离？
  1. 遵循最小权限原则，将权限拆分为身份、资源、动作三类，实现细粒度权限控制。
  2. 工具调用时需携带专属权限标识，权限不足时直接拦截。
  3. 租户数据实施物理隔离与检索隔离，杜绝跨租户数据泄露风险。
  4. 实施操作审计日志记录，确保所有调用可追溯，便于事后审计。
  5. 运行隔离：不同租户的 Agent 在独立沙箱中运行，实现进程与资源的完全隔离。
  6. 数据隔离：各租户数据独立加密存储。
  7. 权限隔离：租户账号与密钥独立管控。
  8. 审计隔离：操作日志独立归档，支持独立溯源。
  9. 租户 ID 强绑定：记忆、知识库、工具数据、操作日志均携带唯一租户标识。
  10. 检索强过滤：向量检索与数据查询自动追加租户筛选条件
  11. 工具权限校验：每次调用前置鉴权
  12. 结果脱敏+审计：输出脱敏、全程留痕。
- 企业级Agent的记忆架构和通用Agent有什么差异？
  1. 企业级 Agent 采用三层记忆架构：短时会话记忆、中长期业务记忆、政企合规归档记忆。
  2. 核心差异化能力包括记忆权限管控、操作日志留痕、敏感记忆加密存储与过期记忆合规销毁。
  3. 以此满足政企数据合规、溯源与保密要求。
- 什么是Agent记忆机制？为什么Agent必须要有记忆，普通大模型不需要？
  1. 记忆机制是专门用于存储、筛选、更新、调用对话与业务信息的模块，分为短期对话记忆、中长期用户记忆、业务知识库记忆。
  2. 普通大模型仅依赖单次上下文窗口，无持久化存储能力，无法沉淀用户数据与业务经验。
  3. Agent 面向长期、多轮、连续的复杂任务，必须依靠记忆实现个性化适配、经验复用与任务连贯执行。
- 请详细说说Agent三级记忆架构：短时、中时、长时记忆
  1. 短时记忆：依托上下文窗口，存储当前对话与临时任务信息，仅单次任务生效，负责对话连贯。
  2. 中时记忆：持久存储近期高频行为、短期用户偏好、未完成任务，留存周期数天至数十天。
  3. 长时记忆：结构化沉淀用户固定属性、长期习惯、核心业务规则、历史最优执行经验，永久留存、按需调用。
  4. 三级分层可有效隔离数据，避免记忆混乱与污染。
- Agent记忆检索的核心逻辑是什么？常用的检索方式有哪些？
  1. 核心：精准匹配当前任务需求，筛选高关联、高可信度的历史记忆，辅助当前推理与执行。
  2. 向量相似度检索：匹配语义相近的历史对话与任务。
  3. 关键词精准检索：定位固定业务规则与核心信息；时序检索优先调用近期有效记忆。
  4. 权重排序检索：结合相似度、时效性、可信度综合打分筛选。
- 电商场景下，用户多次咨询同类问题，Agent如何通过记忆优化体验？
  1. 将用户高频咨询问题、偏好类目、常用售后方式沉淀为长期记忆。
  2. 同类问题无需重复追问基础信息，直接调取历史偏好应答。
  3. 对用户反复纠结的问题，主动补充精准解答与避坑提示。
  4. 过滤一次性、无效的临时提问，避免记忆冗余，保证个性化体验精准度。
- 如何解决Agent记忆过载、记忆冗余的问题？
  1. 建立记忆打分机制，按时效性、相似度、用户反馈打分，低分冗余记忆自动淘汰。
  2. 记忆合并：将同类、重复的碎片化记忆整合为结构化信息。
  3. 分层清理：短时记忆任务结束自动清空，中长时记忆定期归档、去重、降噪。
  4. 精准筛选：仅高价值、有效的用户行为与业务经验允许写入长期记忆。
- Agent长期记忆更新和覆盖的规则是什么？如何避免有效记忆被覆盖？
  1. 核心规则：新有效信息迭代旧过期信息，高可信度覆盖低可信度，不随意覆盖稳定长期记忆。
  2. 固定用户核心属性、长期偏好设为锁定记忆，禁止自动覆盖。
  3. 新增记忆需经可信度校验，与历史记忆无冲突再更新；临时、短期行为不写入长期记忆。
  4. 记忆更新留痕，支持回溯恢复，防止误更新丢失有效信息。
- 什么是「分层记忆架构」？数据如何在层级间流转？
  1. 闪存记忆：当前轮次瞬时上下文，仅本轮生效，实时更新、即时销毁。
  2. 短期记忆：当前会话滚动窗口，保存近期对话，超容量自动淘汰旧数据。
  3. 长期记忆：跨会话向量库持久存储，固化高价值信息。
  4. 流转逻辑：闪存内容迭代后沉淀至短期记忆 → 短期记忆定时摘要、向量化 → 高价值数据固化为长期记忆 → 推理时召回长期记忆并入短期上下文 → 无效数据定时遗忘淘汰。
- 如何实现「向量检索记忆」？如何优化检索准确性与召回率？
  1. 实现：将历史对话与任务记录向量化存入向量库，用户提问时做相似度匹配，召回相关历史信息并入上下文辅助决策。
  2. 切块优化：语义切块而非固定长度切块，避免语义断裂。
  3. 嵌入微调：用业务数据微调 Embedding，提升领域匹配度。
  4. 检索重排：向量粗筛 + Rerank 精排，剔除相似无关内容。
  5. 混合检索：向量语义检索与关键词检索结合，兼顾语义模糊匹配与精准命中。
- 如何设计「共享记忆」与「独立记忆」以避免多Agent上下文爆炸？
  1. 独立记忆：单 Agent 私有任务状态、私有对话记录与个人工作进度，严格隔离，防止任务互相干扰。
  2. 共享记忆：团队公共规则、全局任务目标、公共知识库与统一约束，所有 Agent 共用一份，避免重复存储与重复加载。
  3. 通过「私有隔离 + 全局共享」分层设计，极大减少冗余上下文，解决多 Agent 内存与 Token 爆炸问题。
- AutoGPT如何实现「长期记忆」管理？如何通过文件系统读写维护状态？
  1. 基于本地文件系统 + 向量库实现：任务过程、思考链路、执行日志持续落地为本地文件。
  2. 自动解析文件内容向量化，存入本地向量索引。
  3. 新任务启动时读取历史文件与向量记忆，恢复任务状态。
  4. 持续迭代更新文件记录，实现跨会话、跨重启的状态延续。
- 状态与记忆如何实现？
  1. 记忆分为四类：短期记忆（会话上下文）、中期记忆（Memories 功能，跨会话持久化）、长期记忆（Git 仓库中的 Spec 文件）、变更记忆（changes/ 目录下的 Spec Deltas）。
  2. 实践建议：使用 Git 记录规范变更，通过 Memories 沉淀编程习惯与项目信息，并在每次变更归档后更新 .codebuddy/plan/ 归档记录。
- 什么是「记忆固化」？如何通过读写JSON/Markdown/代码文件实现长期记忆？
  1. 定义：将 Agent 临时思考、任务状态、关键结论与用户信息，从易丢失的上下文持久化为结构化文件，实现永久复用。
  2. JSON：存储结构化状态、参数配置与任务进度，方便代码读取解析。
  3. Markdown：存储总结报告、复盘结论与长文本知识库，可读性强。
  4. 代码文件：固化执行逻辑、工具调用模板与固定工作流，实现能力沉淀。
- 如何设计「记忆遗忘机制」，避免无效信息占用上下文？
  1. 时效淘汰：设置记忆过期时间，长期未调用自动失效。
  2. 热度筛选：根据调用频次保留高热度记忆，淘汰低频无效数据。
  3. 冗余去重：自动合并重复、相似记录，压缩记忆体积。
  4. 价值过滤：通过模型评分丢弃低价值闲聊与无效日志，只留存核心决策信息。
- 如何实现「记忆检索增强」，让Agent主动召回相关历史信息辅助决策？
  1. 核心：被动存储转为主动召回——用户提问时先向向量库发起语义检索，匹配相关历史任务、对话与知识库。
  2. 将高关联记忆拼接进本轮上下文。
  3. 让模型基于「当前问题 + 历史经验」联合推理。
  4. 召回结果实时更新记忆权重，实现越用越精准。

- 用户兴趣突变场景，如何快速适配调整？
  1. 突变行为监测：实时识别短期行为偏移，判断是偶然点击还是真实兴趣切换。
  2. 权重动态迁移：短期提升新兴趣内容权重、逐步降低旧兴趣权重，平滑过渡推荐内容。
  3. 双向兜底机制：保留少量旧兴趣内容，避免兴趣误判导致体验断层，保证适配稳定性。

- 长期记忆为什么不能直接拼接进Prompt？有什么弊端？
  1. 上下文溢出：数据量大超出窗口限制导致截断报错
  2. 信息干扰：无效、老旧、过期记忆污染当前判断。
  3. 性能损耗：每次请求加载全量记忆，推理耗时暴涨、Token 成本极高、延迟飙升。
  4. 正确做法：语义检索按需加载关联记忆，过滤无效信息，轻量化注入。

### 05 RAG 检索增强

- RAG和Agent是什么关系？二者可以互相替代吗？
  1. 不可替代、互补协作：RAG 解决知识实时性、准确性、幻觉问题，是 Agent 的核心工具之一。
  2. Agent 解决任务自主规划、多步骤执行问题：RAG 负责「找对知识」，Agent 负责「用知识做事」。
  3. 完整业务场景需要二者结合。
#### 5.1 文档处理

- 文档解析与清洗
- Chunk 切分策略
- 语义完整性与跨块信息处理
- 元数据设计

- 三层知识库结构？各自作用？
  1. 离线静态库：存储平台固定规则、配送规范、用户 FAQ 等长期不变内容，支撑标准化答疑。
  2. 实时业务库：同步库存、价格、营业时间、订单状态等动态数据，保障业务决策真实有效。
  3. 会话临时库：保存单轮对话上下文与用户临时需求，保证对话连贯性与个性化。

- 知识库最大痛点是什么？与实时业务数据冲突怎么解？
  1. 核心痛点是多库数据冲突、知识更新滞后：离线静态库更新周期长，而价格、活动、商家状态实时变动，极易出现静态知识与实时业务数据不符。
  2. 后果：模型采信旧知识、输出错误答案。
  3. 严格执行数据优先级：以实时业务工具查询结果为最终依据，摒弃过期离线知识。
  4. 精准告知用户活动已结束
  5. 自动标记过期文档并推送运维迭代更新，从源头规避同类冲突。

- 多知识库内容冲突的解决流程与自动自愈体系？
  1. 第一步校验知识更新时间，优先采信最新内容
  2. 第二步执行固定优先级规则。
  3. 第三步以结构化实时业务数据为最终判定标准
  4. 最后标记冲突内容、归档记录并推动知识库更新迭代。
  5. 自愈闭环：时效监控预警过期知识、定时巡检比对多库冲突、低风险内容自动迭代更新、高风险内容人工审核上线。
  6. 全程日志留痕可追溯，常态化解决知识滞后与数据打架问题。
  7. 所有商品规则添加时间戳，新数据优先级高于旧数据
  8. 定时巡检比对线上实时数据，标记过期知识。
  9. 大促期间开启高频更新预热，实时同步活动规则
  10. 冲突数据自动屏蔽旧内容，只采信生效中最新规则。

- 电商长文本RAG检索，和普通短文本检索的核心差异？
  1. 商品文本超长、层级多、参数杂、规则分散，普通检索易截断丢失关键信息，出现局部匹配正确、整体答案错误的片段幻觉。
  2. 电商对价格、规格、售后等关键信息精度要求极高，不允许模糊匹配
  3. 短文本侧重速度，电商长文本侧重精准+防幻觉+高召回。

- 长文本预处理核心手段有哪些？
  1. 五大手段：层级切片、语义分块、关键信息加权、无效降噪、参数结构化。
  2. 剔除冗余文案，保留价格、规格、售后、优惠核心字段，提升检索精准度。

- RAG为什么不适用通用切片策略？
  1. 通用固定长度切片容易割裂电商层级化、关联性强的商品规则，导致关键参数碎片化，引发漏召与幻觉频发。
  2. 拼多多采用语义切片+规则边界保护，保证完整优惠、规格、售后内容不被截断。
- tree-sitter 符号感知分块是什么？为什么代码 RAG 需要它？
  1. 传统按字符切分会截断函数或类，检索到的代码片段不完整，函数签名与参数定义丢失，AI 无法理解。
  2. tree-sitter 构建 AST，按符号边界（函数/类/方法/结构体）切分，每个 chunk 携带符号名、符号类型、起止行号等元数据。
  3. 检索时可按符号类型过滤：先混合检索，再按符号类型筛选只返回函数定义，过滤掉注释与 import；支持 TS/JS/Python/Rust/Go/Java 等语言。
  4. 代码 RAG 与文本 RAG 的核心差异在分块策略（按 AST 符号切而非按字符切）与检索过滤（按符号类型过滤而非盲目返回）。
- 什么是两步思维链摄入（Two-Step Chain-of-Thought Ingest）？为什么要拆成两步？
  1. 两步摄入流程包括分析步骤（LLM 解析输入内容并生成结构化分析结果，通常为 JSON 格式）与生成步骤（LLM 根据分析结果生成最终的 Wiki 文件）。
  2. 分离的优势在于：分析与生成属于不同认知任务，分离后可提升各自质量；分析结果便于缓存与审查；同时支持对长内容进行链式思考。
  3. 工程实现上通常结合 SHA256 增量缓存与持久化队列以优化性能。

#### 5.2 向量化

- Embedding 模型选择
- 向量表示质量
- 向量数据库和传统数据库有什么区别？
  1. 核心区别：传统数据库执行精确匹配（如通过WHERE id=123进行查询），而向量数据库执行相似度搜索（旨在寻找最接近的K个向量）。
  2. 技术实现：向量数据库采用ANN（近似最近邻）算法进行索引（如HNSW、IVF），可在百万级向量规模下实现毫秒级响应。
  3. 主流方案：包括Chroma（适用于原型开发）、Pinecone（云托管服务）、Milvus（支持大规模自部署）以及pgvector（PostgreSQL数据库插件）。
- HNSW 索引的原理是什么？为什么不直接用线性扫描？
  1. HNSW 是分层小世界图：上层稀疏（高速公路）、下层稠密（城市道路），搜索时从上层快速定位区域，再在下层精细搜索，采用贪心最佳优先搜索 + 优先级队列。
  2. 性能对比：10 万向量线性扫描 O(n) 约 200ms，HNSW O(log n) 约 2ms，快约 100 倍。
  3. 本质是用空间换时间：构建图需要额外内存存储邻居指针，但搜索从 O(n) 降到 O(log n)，收益远大于代价。
- 如何在不引入外部向量数据库的情况下实现 RAG？
  1. SQLite 三件套：SQLite 存数据 + BLOB 存向量（二进制序列化，比 JSON 省约 75% 空间）+ 手写 HNSW 索引 + FTS5 全文索引，一个 .db 文件搞定存储、向量与全文检索，零外部依赖。
  2. Embedding 复用：若已有 LLM API 网关，复用其渠道调度做向量化，零额外 API Key 与配置。
  3. 适合中小规模知识库（万级 chunk），大规模仍需 Milvus/Qdrant；嵌入式方案适合桌面应用、小团队与私有部署。

#### 5.3 检索策略

- 语义检索
- 关键词检索
- 混合检索
- 知识图谱的四信号关联度模型是什么？各信号权重如何？
  1. 四信号模型包括直接链接（×3.0）、来源重叠（×4.0）、Adamic-Adar（×1.5）和类型亲和（×1.0）。
  2. 来源重叠的权重最高，因为共享同一原始资料通常意味着内容具有强语义关联。
  3. 综合分数用于确定知识图谱中边的粗细以及最终的检索排序。
- GraphRAG 和向量 RAG 的区别是什么？各自适合什么场景？
  1. 核心区别在于向量 RAG 通过语义相似度检索相似的文本块，而 GraphRAG 从文档中抽取实体和关系构建知识图谱，并通过图遍历检索关联信息。
  2. 适用场景方面，向量 RAG 适用于事实性问答和单点查询，构建成本较低；GraphRAG 则擅长多跳推理、关系分析、全局摘要以及跨文档关联。
  3. 最佳实践是混合使用两种方法：向量 RAG 用于日常问答（约占90%场景），GraphRAG 用于复杂关联分析（约占10%场景），两者互补而非替代。
- 什么是混合检索？为什么要做重排序？
  1. 混合检索：融合BM25关键词匹配与向量检索语义匹配，通过加权实现优势互补。
  2. 重排序原因：向量检索召回速度快但精度有限，重排序采用Cross-Encoder对召回的候选集进行精细打分。
  3. 两阶段流程：首先快速召回Top-50（毫秒级），随后通过重排序精选Top-5（百毫秒级），以兼顾速度与精度。
- 多路召回
- Query 改写与扩展
- 如何解决 RAG 检索不到相关文档的问题？
  1. Query改写：利用LLM对用户问题进行语义改写，生成多个角度的查询语句以并行检索。
  2. HyDE：让LLM先生成假设性回答，再以此为查询依据进行检索（假设性回答语义更丰富）。
  3. 调整分块策略：调整chunk_size在512至1024之间，以平衡语义单元的精确性与完整性。
  4. 混合检索：结合BM25等稀疏检索技术，弥补向量检索在关键词精确匹配方面的不足。
  5. 增加召回量：采用两阶段召回策略，先召回Top-20候选结果，再通过精排模型筛选至Top-5。
- 召回过滤与权限控制
- 面对新闻/股价等实时更新知识库，RAG 怎么适配？
  1. 动态路由Agent：先判断问题是否需要实时数据。需要实时数据时，优先调用搜索或实时API；否则，默认采用向量库检索。
  2. 流式增量更新：通过消息队列监听知识库的实时变动，动态新增或更新向量数据，避免全量重构。
  3. 缓存失效机制：为高频问题设置缓存时效，元数据更新后立即清空旧缓存，以确保答案的时效性。
- 企业 RAG 怎么解决权限隔离问题？会不会泄露涉密数据？
  1. 其核心方案为检索增强生成权限对齐机制，即在数据源头实施访问控制过滤。
  2. 在数据存入向量数据库时，需为每条向量记录绑定相应的访问控制元数据，例如部门、角色或保密等级。
  3. 在检索阶段，当用户发起查询时，系统会自动依据该用户的身份与权限信息进行过滤。
  4. 该机制的关键在于过滤操作发生在向量检索的源头，而非检索结果返回之后，从而从根源上杜绝数据泄露的风险。
- 处理本地大量文件时，对比关键词检索、向量检索、GraphRAG的文件检索策略
  1. 关键词检索：精准匹配文本字符，速度快、零成本；无法理解语义，同义词与模糊问题检索失效，适合结构化明确文档。
  2. 向量检索：语义匹配、支持模糊提问、理解意图；缺乏逻辑关联、碎片化严重，适合通用知识库与问答检索。
  3. GraphRAG：抽取实体与关系构建知识图谱，支持逻辑推理、溯源与关联分析；成本最高、耗时最长，适合复杂文档、多文件关联与知识推理场景。
- 如何优化RAG系统的检索速度与准确性？（混合检索、RRF重排、语义切块）
  1. 切块优化：摒弃固定长度切块，采用语义切块保证片段语义完整，避免信息断裂。
  2. 混合检索：向量语义检索 + 关键词精准检索融合，兼顾语义模糊匹配与专有名词精准命中。
  3. RRF 融合重排：融合多路检索结果，加权去重排序，优于单一排序算法，提升结果综合性。
  4. 二级重排机制：粗筛 TopN 结果后通过 Rerank 模型精排，过滤无关内容。
  5. 索引优化：向量索引分层、增量更新，降低检索耗时，提升响应速度。
- RAG检索最容易踩的3个盲区是什么？
  1. 语义相似但业务无关的检索结果易形成“相似度陷阱”，冗余信息干扰任务判断。
  2. 存在时序盲区，优先匹配旧数据而忽略最新有效信息，导致结果滞后出错。
  3. 检索片段过粗或过细形成粒度盲区，关键信息缺失或无效信息过多。
  4. 优化方案：综合相似度、时效性与业务权重进行多维排序，精准截取片段，并对新旧信息分层过滤。

- 相似内容海量堆砌，检索串品、错召怎么解决？
  1. 增加商品 ID、规格参数、品类维度的精准过滤
  2. 相似商品做差异化向量聚类，避免向量扎堆误召。
  3. 精排阶段强化核心参数比对，过滤相似不相关商品
  4. 沉淀相似商品错题库，持续优化检索阈值。

- 高峰期，如何平衡检索速度和准确率？
  1. 日常场景优先准确率严控幻觉
  2. 大促峰值热点商品走预热缓存提速、冷门商品精准检索兜底。
  3. 非关键信息适度简化，价格、规格、售后核心信息绝不降级精度，分级响应兼顾吞吐与准确性。

  2. 多智能体辩论：不同 Agent 针对冲突的文档内容进行对比论证，梳理矛盾点，筛选逻辑最通顺的答案。

- RAG 系统中 Token 超限怎么办？降级策略怎么设计？
  1. Token 估算：ASCII 约 4 字符/token，CJK 约 2 字符/token；context_limit 设为模型上限的 70%，预留 30% 给 Response。
  2. 三级降级：第一级裁低分 chunk（保留高分 chunk 与完整历史）；第二级裁历史只留最近 2 条（保留高分 chunk）；第三级紧急模式（无历史，只留 top-3 chunk，简化 prompt）。
  3. 降级不是简单截断，而是优先级裁剪：保高分 chunk（检索质量优先）、保最近历史（对话连贯性优先）。

#### 5.5 生成质量与幻觉控制

- 检索与生成协同
- Agentic RAG 什么时候触发检索？和传统 RAG pipeline 有什么本质区别？
  1. 本质区别：传统 RAG 采用固定流程，每次均执行检索；Agentic RAG 引入 Agent 进行动态决策，具备决策、反思与迭代能力。
  2. 触发检索的决策能力：Agent 判断问题类型，简单问题直接响应无需检索，仅对事实性问题触发检索。
  3. 反思能力：每轮检索后，Agent 评估已检索文档是否充分，不足时触发再检索。
  4. 迭代能力：根据反思结果改写查询，调整角度重新检索。通常设定最大检索次数（如3轮）以防止死循环。
- Deep Research 和 Agentic RAG 有什么区别？
  1. Agentic RAG：检索 → 反思 → 再检索，侧重「信息够不够」，输出简短回答，通常不超过 3 轮，是答题思维。
  2. Deep Research：检索 → 分析 → 追问 → 再检索 → 综合，侧重「信息全不全」，输出综合报告，通常 3-10 轮，是调研思维。
  3. 典型场景：「限流策略和降级策略分别是什么？」用 Agentic RAG；「分析所有模块的技术选型和设计权衡」用 Deep Research。
  4. 两者互补而非替代：Agentic RAG 侧重宽度（够不够），Deep Research 侧重深度（全不全）。
- 怎么系统提升 RAG 问答准确率？三层体系是什么？
  1. 第一层（深度解析层）：采用布局感知解析模型理解文档结构（如标题、表格），依据结构语义进行语义完整切块，而非简单字符切分。
  2. 第二层（检索增强层）：采用向量检索与BM25关键词检索的混合检索模式；使用重排序模型对初筛内容进行精排；扩展Query生成多个同义问题以并行检索。
  3. 第三层（生成校验层）：答案生成前进行自检。第一层检验检索内容是否充分；第二层检验答案是否严格基于检索结果，杜绝幻觉。
- RAG 的原理是什么？和微调有什么区别？
  1. RAG 原理：先从外部知识库检索相关文档，将检索结果作为上下文提供给大语言模型，再生成最终回答。
  2. 与微调的区别：RAG 作为“外挂知识库”，不修改模型参数，知识可实时更新，成本较低；微调则“内化知识”，通过修改模型参数定制输出风格或格式，成本较高。
  3. 最佳实践：结合使用以发挥各自优势：微调优化输出风格与格式，RAG 提供实时更新的知识。
