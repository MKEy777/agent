- 线程、进程与协程

- 线程安全与并发控制
- 为什么用按解析后会话 ID 的轮次租约，而不是全局锁或按路由键的锁？
  1. 按路由键加锁存在盲区：路由键到会话 ID 为多对一映射，两个不同路由键各自持锁时仍可能在同一份转录上并发刷写，且该冲突无法被路由键级守卫识别。
  2. 全局锁虽能堵住并发漏洞，但会导致所有会话串行化；单个工具调用的长轮次可能持续数分钟，期间无关会话全部被阻塞。
  3. 轮次租约在会话解析定型后、加载转录前按会话 ID 加锁，串行化整个“加载历史—运行—刷写”区间；竞争仅出现在真正共享会话 ID 的别名路径上，其余路径零竞争，锁开销可忽略。
  4. 释放时校验所有权与运行代数，防止旧清理误释放新轮次；等待超时采取失败开放策略（降级为不串行继续执行并显式报错，可用性优先于强一致性）；注册表有界且仅驱逐空闲项，压缩期间会话 ID 轮换时同一租约对象重新绑定。
  5. 该租约仅覆盖进程内；CLI 与网关多进程共享同一会话是已知限制，需引入数据库级租约。
  6. 判断标准：锁的键应取决于被保护资源的属主；当路由键到属主的映射为多对一时，必须在解析定型后补加一把按属主（会话 ID）维度的锁。

#### 8.2 缓存与状态存储

- Redis 等缓存系统
- 如何设计一个排行榜（Top-K）系统？
  1. 基于 Redis Sorted Set 实现：使用 ZADD 更新分数，ZREVRANGE 获取 Top-K，ZINCRBY 进行增量加分。
  2. 单个 Sorted Set 受内存容量限制，数据量较大时可按时间窗口或榜单类型分片存储。
  3. 持久化与实时性需权衡取舍：可定时将数据落库，查询时优先走缓存。
  4. 分数并列时需引入次级排序键（如时间戳）打破平局。
- Redis 分布式锁怎么实现？有什么问题？
  1. 基本实现采用 SETNX（或 SET NX EX）抢占锁，并设置过期时间防止死锁。
  2. 锁过期但业务未完成时，可通过 watchdog 续期机制解决。
  3. 主从切换时锁丢失（异步复制）问题，RedLock 多节点方案试图解决但存在争议。
  4. 不可重入问题可用计数器或 hash 结构实现可重入锁。
  5. 释放锁时需校验持有者身份，通过 Lua 原子执行比对并删除，防止误删他人的锁。
- 缓存更新与淘汰
- 对话历史与任务状态存储
- 如何回溯 Agent 在哪一步走偏？完整对话存储会带来什么成本？
  1. 仅凭最终输出无法定位走偏步骤，需记录完整对话上下文（含工具调用与结果），方可重建模型每一步的所见信息。
  2. 完整持久化的成本在于磁盘占用随工具结果线性增长，且会话文件数量庞大、缺乏自动清理机制。
- 为什么选SQLite单行增量而不是JSONL追加或每轮全量写？
  1. JSONL 追加写入依赖锁机制协调并发，且无法支持历史数据查询；每轮全量写入则存在写放大问题。
  2. SQLite WAL 模式支持读写并发，且零外部依赖；单行增量写入使崩溃时最多丢失未提交的一条记录，并可通过 SQL 聚合查询会话数据。
  3. 代价是 Schema 版本治理与迁移脚本成为长期维护负担，当前版本号已迭代至 23，每次结构变更均需编写迁移脚本。
  4. SQLite 以单文件承载全部会话数据，具备事务原子性与并发读安全，适配 MCP 多客户端同时查询。
  5. JSONL 直接写路径免事务、无锁竞争，且可用标准文本工具处理，但并发读需额外加锁。
  6. 选型判据：读侧是否需要查询与并发 × 写侧是否单一追加者；两者均低时文件存储即可满足，任一升高则需引入数据库。
- 热数据与冷数据分层
- 存储容量不足时的压缩与清理
- 高频调用场景下，如何设计缓存策略以减少LLM调用次数？
  1. 冷热分层缓存：高频固定问答、工具结果与配置信息设为热缓存长期常驻，低频任务不缓存节省空间。
  2. 语义缓存 + 精准缓存：精准匹配固定问题，语义匹配相似问题，双重兜底减少调用。
  3. 时效过期策略：按业务场景设置 TTL，动态过期刷新，避免陈旧数据。
  4. 主动更新 + 被动淘汰：知识库、规则变更时主动清空对应缓存，自动淘汰冗余失效缓存，保证数据一致性。
  5. 缓存击穿兜底：热点 Key 加互斥锁，避免瞬时大量穿透请求打爆 LLM 接口。
- 缓存应该如何设计？哪些数据适合本地缓存，哪些数据不能依赖本地缓存？
- LLM 应用系统中如何做缓存？
  1. 多层缓存架构：L1 本地内存缓存（热点数据）→ L2 Redis 分布式缓存 → L3 持久化存储。
  2. 缓存对象：Embedding 结果、向量检索结果、LLM 完整回复、Rerank 结果。
  3. Semantic Cache：不只精确匹配 query，而是用 embedding 相似度判断，语义接近的 query 可复用缓存答案（如 GPTCache）。
  4. 缓存策略：TTL 按数据更新频率设定，知识库不常变用长 TTL，实时数据用短 TTL 或不缓存。
  5. 缓存失效：知识库更新时主动清除相关缓存，以 version tag 标记数据版本。
  6. 带个性化因素的请求需将用户特征纳入缓存 key，因为不同画像对应不同答案。

- 用户核心信息变更后，如何避免调用旧数据？
  1. 收货地址、手机号等核心信息变更后立即清空本地缓存。
  2. 每次工具调用前前置校验最新用户数据，同步刷新会话知识库上下文，全程杜绝旧数据调用。

- 用户高频重复提问，如何优化效率？
  1. 高频同类问题做语义缓存，同义问题直接复用历史结果，减少重复工具调用与知识检索；辅以定时刷新机制保证缓存时效性。
- Redis 语义缓存如何判断相似问法命中？如何避免缓存污染？
  1. 命中判断：query 经 embedding 后与缓存中的向量做相似度检索，相似度超过设定阈值即视为相同意图，直接返回缓存答案。
  2. 阈值权衡：阈值过高则命中率低，过低则把不同问题误判为相同，需按业务场景调优。
  3. 防污染：依赖时效性信息或用户私有上下文的答案不缓存；低置信命中回退真实执行并视情况更新缓存。
  4. 失效机制：知识库更新后批量失效相关缓存条目，并设置 TTL 兜底。

- 多Agent协作中，如何避免重复检索、无效调用？
  1. 搭建多 Agent 共享缓存，同商品、同规则检索结果全局复用
  2. 语义去重拦截同类重复请求。
  3. 调度 Agent 统一分发任务，避免多 Agent 并行重复执行
  4. 大促热点商品数据预热缓存。

#### 8.3 数据库

- 关系型、文档型与向量数据库选型
- 向量数据库如何选型？为什么不一定要用 Milvus 或 Elasticsearch？
  1. 选型首要依据是规模与延迟要求：中小规模用 pgvector/FAISS，亿级以上考虑专用分布式向量库。
  2. 过滤需求：需要标量过滤与向量检索混合的场景，应选择支持属性过滤的方案。
  3. 混合检索：当 BM25 与向量融合需求较强时，选择 ES 或内置混合检索的方案可减少组件数量。
  4. 运维成本需纳入选型考量：托管服务省运维但费用高，自建可控但需投入人力。
  5. 选型本质是匹配业务规模与团队运维能力，而非默认引入最重的组件。

#### 8.4 系统架构

- 高并发服务设计
- 设计一个高并发排队系统，你的思路是什么？
  1. 在接入层实施限流与削峰，保护后端服务免受过载冲击。
  2. 排队层基于 Redis 有序集合按优先级或时间戳排队。
  3. 处理层通过消费者线程池或工作协程异步消费队列。
  4. 使用分布式锁协调多个消费者，避免重复消费。
  5. 必要时引入优先级队列，区分 VIP 与普通请求的调度顺序。
- 高并发场景下，Agent的核心性能瓶颈和隐形坑是什么？
  1. 显性瓶颈主要表现为Token消耗过高、单任务响应延迟增大以及工具调用排队拥堵。
  2. 隐性盲区包括并发场景下任务状态错乱、异步回调丢失、上下文复用冲突以及多任务记忆交叉干扰。
  3. 超时阈值设置不合理会导致静默失败，缺乏流量限流则可能引发服务雪崩。
  4. 解决方案包括任务状态隔离、异步独立调度、超时熔断、流量限流以及资源分片复用。
- 你的Agent是怎么应对高并发的？
  1. 计算真实负载：基于用户请求量、平均执行步数及每步扇出数估算下游调用量；需统计入口请求数、运行中任务数、模型Token吞吐与工具并发调用数，并对任务进行分级。
  2. 入口准入与背压：实施用户级与租户级限流，控制运行中任务数、Token预算及最大步骤数；使用有界队列，队列满时触发背压机制，设置优先级与截止时间。
  3. 长任务异步化：短任务采用同步流式返回，长任务通过消息队列异步执行；Worker无状态化，其状态与检查点存储于Redis或数据库中，支持任务取消、超时回收与断点续跑。
  4. 分层并发预算：为系统、租户、模型与工具设置多级并发预算；模型侧约束RPM、TPM、上下文长度与并发序列，工具侧使用独立连接池与Worker池。
  5. 资源隔离与状态一致性：采用隔舱模式隔离资源，为每个下游调用设置独立超时、熔断与有限重试；业务操作通过幂等键确保一致性。
  6. 过载降级：设计分级降级策略，包括缩短上下文、使用缓存、切换小模型、暂停低优先级任务，但不降级安全校验；基于多种信号触发并逐级恢复。
  7. 容量规划与可观测性：监控队列深度、Token吞吐、429比例及资源占用等关键指标；扩容绑定真实瓶颈，进行涵盖真实任务分布与故障注入的压力测试。
- 高并发企业场景，Agent如何保证决策稳定、不混乱？
  1. 任务隔离：多任务各自维护独立上下文、独立记忆与独立执行状态，从机制上杜绝交叉干扰。
  2. 优先级自主调度：根据任务紧急程度与权重自动排序执行，确保关键任务优先处理。
  3. 状态机管控：以标准化状态机约束任务流转，禁止无序执行与状态错乱。
  4. 限流熔断：突发高并发场景下自主降级与限流，优先保障核心任务稳定落地。
- 一个消息网关有30+平台同时进消息，同一段对话可能从多个入口进来，数据库里会话该怎么建模，才能让多平台的消息落成同一条主线而不是各记各的？
  1. 会话身份采用确定性路由键（平台/聊天类型/线程组合），通过路由键定型将多平台入口映射到稳定会话 ID，使同一对话收敛至单一会话主线。
  2. 路由键到会话 ID 为多对一映射：通过第二个聊天恢复命名会话、命令行续接、委派回指等别名键路径，不同路由键可指向同一会话。
  3. 数据库建模方面，会话表包含来源、路由键、父会话、结束原因、回退计数、交接状态、压缩冷却、归档标志等字段；消息表采用单行增量写入，附带软删除/压缩标志及 API 内容字节级保真旁路。
  4. 多平台并发写入通过 SQLite WAL 保证事务安全：消息在写事务内单行插入，会话级计数器同步更新，崩溃时仅丢失未提交的一条。

- 高并发企业办公场景，如何保障服务高可用？
  1. 资源隔离：多Agent沙箱独立运行，单任务故障不会扩散至全局。
  2. 容错自愈：支持断点续传、异常重试与故障实例替换，无需人工介入。
  3. 流量管控：通过限流、熔断与降级机制，有效抵御突发高并发冲击。
  4. 集群部署：多实例负载均衡，消除单点故障，保障7×24小时稳定运行。
- 如何实现多Agent系统的「灰度发布」，按用户/流量比例逐步启用新功能？
  1. 版本隔离：新旧版本 Agent 服务并行部署，独立运行、互不干扰。
  2. 流量灰度：按用户 ID、请求比例或场景维度分配流量，小比例放行新版本。
  3. 指标观测：实时监控新版本成功率、报错率与延迟，对比基线数据。
  4. 渐进放量 + 快速回滚：指标稳定逐步全量，出现异常立即切回旧版本，控制故障范围。
- 如何设计支持流式输出（SSE）的Agent框架？前端与后端如何配合？
  1. 后端层：基于 SSE 协议建立长连接，模型生成 Token 实时分片推送，工具调用、思考过程与异常信息同步流式返回。
  2. 数据分片规范：区分普通文本、工具调用与结束标记，结构化分片推送，避免前端解析混乱。
  3. 前端层：监听 SSE 长连接实时拼接渲染内容，监听结束标记关闭连接，异常自动重连。
  4. 异常处理：断连重连、超时兜底与流式中断收尾，保证用户体验完整。
- SSE（Server-Sent Events）有什么局限性？
  1. SSE 为单向通道：服务器向客户端推送事件，客户端至服务器的消息需另走 HTTP 请求。
  2. HTTP/1.1 下受浏览器同域名连接数限制（约 6 个），HTTP/2 缓解该限制。
  3. 中间代理与负载均衡可能缓冲事件流引入延迟，需专门配置禁用缓冲。
  4. SSE 为文本协议，不直接支持二进制传输。
  5. 断线重连依赖 Last-Event-ID 机制，服务端需自行保存事件方可支持续传；相比 WebSocket 无法双向通信，但对单向推送场景更轻量。
- Agent服务如何部署到Kubernetes？无状态API层与有状态任务Worker如何分离？
  1. 无状态 API 层（Deployment）：负责接收请求、参数校验与路由分发，不存储任何任务状态，支持水平弹性扩容扛高并发。
  2. 有状态 Worker 层（StatefulSet）：负责任务执行、工具调用、状态持久化与断点续跑，独占任务状态保证执行唯一性。
  3. 消息队列解耦：API 层接收请求投递队列，Worker 消费执行，彻底隔离请求接入与任务计算。
- 设计企业级 Agent 部署架构需要注意哪些方面？
  1. 多租户隔离在数据、索引与执行环境三个层面实现租户间资源与访问边界隔离，防止越权访问。
  2. RBAC 权限控制按角色分配 Agent 与工具的使用权限，敏感操作触发二次鉴权。
  3. 合规性要求确保数据不出境，并保留完整审计日志以备追溯。
  4. 灰度发布按流量比例逐步放量新版本 Agent，待指标稳定后再全量铺开。
- 什么是Agent Harness Engineering？与Prompt Engineering、Context Engineering的关系？
  1. 定义：支撑 Agent 上线运行的全套工程底座体系，包含调度、部署、监控、灰度、容错、版本管理与流水线，是生产级 Agent 的核心底座。
  2. 三者层级递进：Prompt Engineering 最表层（优化指令话术）→ Context Engineering 中层（信息流转与上下文治理）→ Harness Engineering 底层底座（工程运维体系，支撑前两者稳定落地生产）。
  3. 核心能力：会话状态持久化与日志重放断点续传、轻量化沙箱执行隔离与统一调度托管、标准化异常重试与熔断兜底，解决崩溃丢失、状态错乱、无法自愈的痛点。
  4. 源自 OpenAI 2026 年文章，指在 Agent-First 世界中通过工程基础设施驾驭 AI 编写代码；核心公式 Agent = Model + Harness，典型成效为 3 人团队 5 个月编写超 100 万行代码、合并 1500 个 PR。
  5. 核心论点「变量是 Harness，不是 Model」：Harness 包含 Context、Context 包含 Prompt，三者嵌套而非替代，工程效益的边际产出已从 Prompt 转移到 Harness。
- Loop、Runtime、Sandbox 三者的嵌套关系？各层的职责边界？
  1. 嵌套关系呈现为三层结构：最外层为 Sandbox，中间层为 Runtime，最内层为 Agent Loop。
  2. 职责边界划分明确：Runtime 层负责工具校验、权限控制与记忆管理；Sandbox 层负责执行环境的隔离与资源限制。
- Runtime 和 Agent Loop 有什么区别？
  1. Agent Loop 作为决策层，负责确定‘做什么’；Runtime 作为基础设施层，负责执行‘怎么做’。
  2. Runtime 包含 LLM 管理、工具注册、记忆管理、执行调度与可观测性五层架构。
- 为什么需要 Harness？
  1. 缺乏 Harness 支撑的 Vibe Coding 存在三大致命问题：架构混乱、上下文雪崩与可维护性丧失。
  2. Harness Engineering 通过提供安全边界、可观测性、可靠性与扩展性，有效解决上述失控问题。
- Harness 的 6 大支柱是什么？
  1. 六大核心支柱：上下文管理、工具系统、执行编排与多 Agent 协作、状态与记忆、评估与观测、约束与恢复。
  2. 在 Coding 场景中，每个支柱均有对应的工具与实践支撑，例如 AGENTS.md、MCP/Skills/知识库、SDD 工作流、Git+Memories、自动测试+AI CR、Rules+Safety。
- 什么是「绑定约束论」？有哪些实验证据证明 Benchmark 表现由 Harness 主导？
  1. 绑定约束论：对长程任务，跨可比的前沿模型，Benchmark 成绩方差主要由 Harness 决定而非模型本身。
  2. 证据一（Bölük 2026a）：模型不动，仅调整 edit-tool 格式与脚手架即获得最高 10 倍提升。
  3. 证据二（Trivedy 2026）：固定 GPT-5.2 不变，重构系统提示、中间件与自验证带来 +13.7pp 提升。
  4. 证据三（Meta-Harness，Lee et al. 2026）：自动化 Harness 优化取得 76.4% 成绩，超越所有手工方案且未改动任何模型权重。
  5. 对比参照：模型代际升级通常仅 +2-4pp，Harness 优化可带来 +10pp 以上甚至 10 倍差距。
- Harness 六大基础设施组件分别解决什么问题？
  1. 文件系统解决「无工作环境」：提供项目目录、文件组织与版本控制，Agent 不能脱离真实项目凭空写代码。
  2. 沙箱执行解决「不能执行代码」：让 Agent 写出的代码能运行并验证结果对错。
  3. AGENTS.md 解决「知识过时」：无需训练即可注入项目规则、架构说明与编码约定。
  4. Web Search + MCP 解决「知识截止日期」：支持搜索最新信息与调用实时 API。
  5. 上下文工程解决「无记忆与信息腐烂」：滑动窗口 + 摘要压缩 + 关键信息保留。
  6. 编排 + Hooks 解决「无法协作」：多 Agent 调度配合执行前后检查（pre/post/error/approval hooks）。
- 为什么 AGENTS.md 比训练微调更适合 Agent 知识注入？
  1. 即写即生效：微调要花钱花时间训练，AGENTS.md 写完立刻生效。
  2. 随时可更新：微调知识嵌入权重难以修改，AGENTS.md 改文件即更新。
  3. 无需训练数据：微调需要大量训练样本，AGENTS.md 只需项目的事实规则。
  4. 多项目并行：微调模型无法同时服务多个项目，AGENTS.md 可每个项目一份。
  5. 边界：AGENTS.md 解决知识时效性而非知识深度，深度专业场景微调仍不可替代，两者互补而非互斥。
- 第一阶段基础建设具体做什么？
  1. IDE 插件安装：VSCode 通过 Install from VSIX 安装插件；JetBrains 系列通过 Install Plugin from Disk 安装 zip 文件，注意无需解压。
  2. 建立 team-harness 仓库作为规则与知识库的载体，并配置基础 Rules 与知识库。
- 实施路线图分哪几个阶段？
  1. 第一阶段为基础建设期（1~2周）：完成 Agent 工具链安装、团队 Harness 仓库搭建、基础 Rules 配置与知识库初始化。
  2. 第二阶段为工具接入期（2~4周）：完成 MCP 接入、Skills 沉淀，并跑通 Plan 模式下的 SDD 工作流。
  3. 第三阶段为持续优化期（长期）：建立度量看板、规范迭代机制与知识飞轮，支撑体系长效演进。
- AI Coding 一体化架构分哪几层？
  1. 从输入到度量的完整链路为：输入层 → 配置中心 → 模式引擎 → Agent 核心 → MCP 层 → 输出层 → 度量层。
  2. 数据流为：用户意图经输入层转化为结构化输入，配置中心加载约束，模式引擎选择策略，Agent 核心执行任务，MCP 层获取外部数据，输出层交付产物，度量层量化效果并反馈优化规范，形成闭环。
- 约束与恢复机制是什么？
  1. 三级约束机制：硬性红线（Rules）不可违反，如 API 必须添加 Swagger 注解；软性约束（Skills）推荐遵循；安全策略（Safety）提供兜底保护，如高风险操作前自动检测影响范围。
  2. 恢复机制：所有变更通过 Git 管理，可随时回滚；Spec Deltas 保证变更可追溯；编译失败时自动回退至稳定状态。
- 设计一个安全的 Agent Harness 架构需要考虑什么？
  1. 核心原则是安全边界内的最大自主性：不是绝对安全的过度约束，而是让 Agent 在安全范围内尽量自由地完成任务。
  2. 最小权限：工具白名单只列必需工具，高危操作需审批。
  3. 最大轮次限制：max-turns 防止无限循环与 Token 耗尽。
  4. 沙箱隔离：代码执行在沙箱中进行，资源受限、网络受限。
  5. 知识注入：AGENTS.md 写明项目规则与编码约定。
  6. 上下文管理：滑动窗口 + 摘要压缩 + 关键信息保留。
  7. 可观测性：全链路日志记录每步输入、输出、耗时与 Token。
  8. 渐进授权：简单任务严约束，复杂任务宽约束。
- 评估与观测分哪几层？
  1. 校验分四层：L1 语法（编译通过、Lint 检查）、L2 逻辑（单元测试通过）、L3 规范（符合 Rules 约束）、L4 架构（不破坏现有设计，人工+AI 联合审查）。
  2. 实际操作：引入 AI Code Review 进行合入前规范检查；代码完成后自动编译并自测；重大改动自动生成变更日志。
- Harness Engineering 的未来方向是什么？
  1. 自动化 Harness 优化：Meta-Harness 已证明自动优化超越人工调参，未来会出现类似编译器自动优化的「Harness 优化器」。
  2. Harness 标准化：MCP 正在标准化工具接口，AGENTS.md、沙箱配置与 Hooks 定义也将出现统一标准，如同 Docker 统一容器格式。
  3. Harness 即产品：Claude Code、Codex、Cursor 本质是在售卖 Harness，未来会出现更多 Harness as a Service——用户选模型，平台提供 Harness。
- Graph 的形式化组成是什么？
  1. 节点（V）：执行单元，一进一出，专注于单一职责，可为专用智能体或确定性步骤。
  2. 边（E）：节点间路由，决定执行流向，支持直通、条件分支、扇出/扇入与回环。
  3. 状态（S）：沿边流动的共享数据对象，供各节点读写，记录任务进度、证据、预算、产物与检查点。
  4. 策略（P）：约束节点创建、工具调用、图修改与副作用产生权限，相当于权限与审批规则。
- 验证器和路由在 Graph 中如何工作？
  1. Verifier 负责以独立视角专门审查最终结果，尝试推翻前序结论；校验通过则放行，否则打回重做。
  2. Router 承担分诊职能，按重要程度将任务路由至不同检查路径：普通观点快速核对，重要数据与安全结论进行多角度交叉审查。
  3. 验证策略包括对抗式（多个怀疑者分头驳斥结论）、多视角式（分别校验正确性、安全性与可复现性）以及评委制（对多个方案打分，并吸收亚军方案优点）。
- 为什么说 Graph 的核心价值是确定性？
  1. 图的杠杆效应不在于节点数量，而在于围绕最终结果构建了多少确定性；多数系统失败的根源在于模型既充当执行者又充当评判者。
  2. Graph 将“决策”与“验证”拆分为独立节点，由独立验证器基于全新上下文进行纠错，而非让执行者自我评判。
  3. 确定性工作交由代码处理：格式校验、测试运行、去重、排序、预算计算等均以普通代码实现；模型判断承载于节点上，代码可靠性承载于边上。
  4. 图必须贴近现实：若所有节点仅互相引用模型结论，而无任何节点触达真实世界，则无异于更大型的自嗨机器；硬锚点包括测试真实通过、资金真实到账、用户真实留存等。
- Anthropic 总结的五种工作流模式是什么？各适用于什么场景？
  1. Prompt Chaining（提示链）：当任务可清晰拆分为固定子任务时，以延迟换取准确率；每一步处理上一步的输出，并可设置检查点。
  2. Routing（路由）：输入类型多样时，先进行分类，再路由至对应的专用处理流程，避免单一提示词优化某类输入而拖累其他类型。
  3. Parallelization（并行化）：当子任务相互独立或需要多视角交叉验证时，并行执行后再汇总结果。
  4. Orchestrator-Workers（编排者-执行者模式）：当子任务无法预先确定时，由主智能体在运行时动态拆解任务、分派给执行者并汇总结果。
  5. Evaluator-Optimizer（评估-优化模式）：当存在明确评价标准且迭代可提升结果时，由一个生成器产出方案、一个评估器打分，循环迭代直至满足要求。
  6. Anthropic 尤为强调优先选择最简单方案：多数应用仅需单次模型调用、检索增强与少量示例即可解决，无需引入完整 Agent 或图工作流。
- 最常见的图编排拓扑有哪些？
  1. 三种基础拓扑：菱形模式（扇出扇入）、主管模式（Orchestrator-Workers）与流水线模式（Pipeline/Prompt Chaining），分别对应并行化、编排者-执行者与提示链工作流。
  2. 三种拓扑可拼装嵌套，真实生产系统中通常为主管模式嵌套菱形、菱形内再嵌套流水线。
- Graph 与知识图谱、流程图有什么区别？
  1. 知识图谱用于组织系统所知晓的知识，Graph 用于描述系统的组成结构与工作流转关系。
  2. 流程图是面向人的描述性材料；Graph 是面向机器的可执行结构，要求节点具备独立执行能力，边携带明确状态，且整个过程可检查、可暂停、可恢复、可追踪。
- Loop 模式有哪些结构性缺陷？
  1. 上下文腐烂：所有轮次的思考、工具调用与观察结果均被塞入同一上下文窗口，原始目标逐渐被淹没，模型后期会反复针对自身输出进行低效分析。
  2. 错误级联：模型在同一条推理链中难以识别循环或跳出循环，遇到错误后反复重试，导致大量 Token 被无效消耗。
  3. 工具过载：单个智能体挂载 15～20 个工具时，工具选择的准确率会急剧下降。
  4. 缺乏控制粒度：无法暂停子任务等待审批，无法为不同步骤配置不同模型，也无法在中途进行独立质检。
  5. 可观测性差：只能看到思考内容与工具调用记录，无法判断分支选择原因，也无法定位导致最终错误的具体步骤。
  6. 目标失明：循环仅优化被赋予的指标，可能以违背指标初衷的方式推高指标，即古德哈特定律。
- Graph Engineering 在 AI 工程演进中处于哪一层？
  1. Agent 工程化能力可划分为五层：Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering、Graph Engineering，各层逐层外叠、依次递进。
  2. 各层职责明确：Prompt 层负责单次对话的措辞设计，Context 层决定向模型提供哪些信息，Harness 层管理工具调用、护栏与跨会话状态，Loop 层驱动单个智能体的自主循环，Graph 层组织多个执行节点的协作关系。
  3. Graph 层位于最外层，其设计与实现需在前四层均已完善的基础上展开。
- Graph Engineering 这个术语是怎么火起来的？它真的新吗？
  1. 2026 年 7 月，Peter Steinberger 发布关于“循环还是图”的推文，三天内累计 270 万浏览，“Graph Engineering”一词由此传播开来；该词诞生时并无新框架或新模型发布。
  2. 节点、边、状态、有向图调度等概念并非新事物，LangGraph、ADK、AutoGen 在该词出现前两年已在实际应用；真正变化的是工程重心从单个智能体行为上移至群体智能体的组织协调。
  3. 其本质是经典的组织管理命题：分工、权责划分、监督与执行分离及容错机制；AI 仅相当于更换了一批执行者，重新回答同一管理问题。
- Graph Engineering 有哪些真实生产案例？
  1. LinkedIn SQL Bot 采用路由机制判定数据域，将请求分派给领域专家智能体与 SQL 编写智能体，再由自纠错智能体重试修正，失败后升级至人工处理，查询准确率与用户满意度达 95%。
  2. Uber 代码迁移项目面对 5000 名工程师、上亿行代码，采用子图按语言/仓库分工，主管图负责整体协调并预先解决冲突，利用检查点机制应对中断，累计节省超过 21000 个工程小时。
  3. Anthropic Research 采用编排者-工作者模式，主智能体负责规划，子智能体并行搜索，内部评测显示该模式比单智能体效果提升 90.2%。
- 什么是 Graph Engineering？它和 Loop Engineering 有什么区别？
  1. Loop Engineering 将驱动循环交由 AI 自主完成：AI 自行观察环境、执行动作、校验结果并决策下一步，形成闭环直至目标达成；人类仅设定目标与验收标准。
  2. Graph Engineering 在 Loop 之上再外扩一层，解决如何将多个智能体、工具与人员组织为可观测、可恢复、可扩展的系统。
  3. 采用三节点小图结构，让研究员节点并行扇出搜集信息并返回结构化笔记，写作节点仅基于干净笔记进行创作，审稿节点在全新上下文中独立审查，不合格则打回重写。
  4. 小图方案需要承担额外成本：维护多个提示词、设计节点间的状态结构，并处理漏信源、路由死循环、状态泄漏等新增失败模式。
  5. 决策标准：每日高频运行且对质量有要求的任务值得付出这些成本；仅运行一次的任务则完全是额外负担。
  6. 传统工作流将路径固化为代码，稳定但缺乏动态应变；ReAct 由模型全程边推理边执行，灵活但控制流混杂在对话记录中，难以复现、审计与管控；Graph 分层治理两者：边与整体结构固定可审计，节点内部保留自主决策。
  7. Anthropic 将工作流定义为通过预定义代码路径编排的系统，智能体则是由 LLM 动态决定自身流程的系统；Graph 架构是两者的融合。
- 如何设计Agent的「配置中心」？包含模型、Prompt版本、工具开关、灰度策略等
  1. 模型配置：统一管理模型版本、温度、最大 Token 与接口地址，支持动态切换。
  2. Prompt 版本管理：存储多版本提示词，支持在线切换。
  3. 工具权限开关：统一管控工具启用/禁用、权限与参数默认值。
  4. 灰度策略配置：在线配置流量比例、用户白名单与功能灰度规则，动态下发生效；全部支持动态生效，无需修改业务代码。
- Agent生产部署的核心挑战是什么？（延迟、并发、稳定性、成本）
  1. 延迟问题：模型推理、工具调用与长上下文导致响应耗时高，用户体验差。
  2. 并发问题：大模型推理算力受限，高并发场景容易排队、超时与阻塞。
  3. 稳定性问题：模型幻觉、接口超时、上下文污染与流程异常导致结果不可控。
  4. 成本问题：长 Token、多轮调用、向量检索与模型推理的算力与接口成本居高不下。
- 一个生产级 Agent 系统为什么仍然需要传统后端、分布式系统和高可用能力？
- 如何实现Agent的「版本管理」？Prompt迭代与工具定义变更如何管理？
  1. Prompt 版本化：每次话术迭代生成新版本，记录修改内容、时间与责任人，支持一键回滚与版本对比。
  2. 工具版本化：工具 Schema、入参逻辑与功能变更统一版本记录，避免更新后旧流程失效。
  3. 环境隔离：开发、测试、预发、生产环境版本隔离，灰度验证后再全量上线。
  4. 变更溯源：所有迭代留存日志，出现问题快速定位版本差异。
- 设计一个高并发Agent服务架构，包含负载均衡、缓存、异步队列等组件
- 如何设计支持百万级 DAU 的 Agent 服务架构？需要哪些稳定性保障？
  1. 分层架构：接入层（API Gateway）→ 路由层（简单意图走规则引擎，复杂意图走 LLM）→ Agent 编排层 → 工具执行层 → 模型推理层。
  2. 弹性伸缩：推理服务按 QPS 自动扩缩容，GPU 实例可选用竞价实例以降本。
  3. 缓存策略：热点查询走语义缓存，相似问题直接返回缓存结果，命中率可达 30%–40%。
  4. 限流降级：令牌桶限流 + 熔断器 + 降级策略，LLM 不可用时回退至检索式回复。
  5. 多活部署：跨机房多活部署，并在 DNS 层进行流量调度。
  6. 可观测性：全链路追踪（记录每一步耗时），监控 QPS、延迟、错误率与 Token 用量并配置告警。
- 如果一个 Agent 系统 QPS 很高，你怎么设计架构？
  1. 引入 Kafka/RabbitMQ 等异步任务队列，将请求接收与 Agent 执行解耦，实现削峰填谷。
  2. 实现 Agent 无状态化，状态统一存储于 Redis 或数据库，Worker 即可水平扩容。
  3. LLM 调用池化：维护 API Key 池或对自部署模型做多实例负载均衡，避免单点限流。
  4. 分级处理：简单查询直接走规则或缓存返回，复杂任务才进入完整 Agent 链路。
  5. 限流与排队：按用户或租户实施速率限制，超限请求排队处理而非直接拒绝。
  6. 预计算热点：对高频问题（如退货政策）预生成答案并缓存，命中时无需调用 LLM。
  1. 接入层：Nginx 负载均衡 + 限流熔断，均匀分发流量、拦截恶意请求。
  2. 缓存层：Redis 缓存高频问答、模型结果与配置信息，减少重复推理，降本提速。
  3. 服务层：无状态 API 服务集群，弹性扩容，负责请求校验与路由。
  4. 队列层：消息队列异步解耦、削峰填谷，堆积高并发请求，避免服务雪崩。
  5. 任务计算层：独立 Worker 集群负责任务执行、工具调用与长流程推理，与接入层彻底解耦。
- 什么是云边端一体化部署？三者如何分工协同？
  1. 云端承担全局统筹职能，负责大模型推理、复杂任务规划、全局记忆存储、权限管控、数据汇总与模型迭代。
  2. 边缘节点承接云端下发的任务，执行就近数据处理、轻量化推理与本地设备调度，降低云端压力与交互延迟。
  3. 端侧部署于手机、IoT及终端设备，实现实时感知、本地简单执行与数据初步过滤，具备低延迟和离线可用能力。
- 端云协同场景下，最容易出现的同步问题是什么？如何解决？
  1. 高频问题包括任务状态异步错乱、新旧数据相互覆盖、指令重复下发、离线数据丢失以及多端记忆冲突。
  2. 通过统一全局任务ID，实现多端状态的精准对齐。
  3. 离线任务在本地缓存，联网后通过增量同步与有序回放完成状态合并。
  4. 采用时序版本管控，确保新数据覆盖旧数据；由云端统一调度指令，避免多端自主执行引发冲突。
- IoT物联网场景下，端侧Agent如何落地？解决什么核心问题？
  1. 解决四大核心问题：海量设备指令全部上云导致带宽拥堵与高延迟、设备离线时无法工作、原始数据上云存在隐私泄露风险、传统设备缺乏自主判断能力。
  2. 落地方式：在端侧本地完成数据过滤、异常判断与简单调度，仅将核心有效数据及异常事件上报云端。
- 端侧Agent相比云端Agent，核心优缺点分别是什么？
  1. 端侧部署优势：超低执行延迟，支持离线运行，原始数据不上云可提升隐私安全性，同时节省云端算力成本。
  2. 端侧部署局限：设备算力有限，难以承载复杂大模型推理与复杂任务规划，存储与迭代能力弱于云端。
  3. 适配策略：简单实时、隐私敏感任务部署于端侧，复杂推理、全局调度与模型迭代部署于云端，通过云边协同互补短板。
- 如何设计支持离线运行的 Agent？无网环境下如何避免能力严重降级？
  1. 模型层：端侧部署轻量模型（如 1.8B 级 INT4 量化），保留基础推理能力。
  2. 知识层：本地知识库采用 SQLite 与轻量向量索引，预装高频场景知识。
  3. 工具层：工具分为在线与离线两套，离线侧保留本地可执行子集（文件操作、本地搜索、计算）。
  4. 缓存层：热点查询结果预缓存，思路类似 CDN。
  5. 同步机制：联网后以增量方式同步离线期间的操作日志与新知识。
  6. 降级策略：离线时切换至规则引擎兜底，复杂任务排队等待联网后处理。
- 如何解决端侧Agent算力不足、推理精度低的问题？
  1. 模型轻量化：通过模型裁剪、量化与蒸馏降低端侧算力需求。
  2. 边缘节点承接中等算力任务，有效分担中心侧压力。
  3. 缓存复用：高频固定推理结果在本地缓存，重复场景直接复用，减少重复计算。

- 高并发流量峰值场景，如何稳控流量？
  1. 限流：按 Agent 类型、用户维度、接口维度设置并发上限，拦截超额请求。
  2. 熔断：接口错误率超标自动熔断停止无效调用，超时任务快速止损，杜绝任务堆积连锁雪崩。
  3. 降级：峰值时非核心功能灰度降级、请求合并，简化复杂个性化推理，优先保障检索、下单等主链路稳定。
  4. 排队削峰：超额任务有序排队、延时处理，配合优先级调度让商品检索、下单链路优先执行，延后数据分析等非核心任务。
  5. 缓存预热：提前预热高频内容与热点数据，降低峰值推理压力。
  6. 资源隔离：防止单类任务堆积拖垮集群。
  7. 热点调控与用户分层：集中算力保障热点流量，优先高价值用户体验，均衡普通用户流量分配。
  8. 推理优化：动态批处理、轻量化推理，稳定高峰期模型耗时。
- 高并发场景下 Agent 服务如何做限流与降级？
  1. 入口限流：按用户或租户维度采用令牌桶、漏桶限速，超出容量部分排队等待或快速失败。
  2. 分级降级：高峰期将请求路由至更小更快的模型，缩短检索范围，并关闭非必要的工具调用。
  3. 关键路径保护：优先保障核心功能的资源，低优先级任务（如批量处理、报告生成）延后执行。
  4. 缓存复用：相同或相似请求命中缓存时直接返回，降低后端压力。
  5. 多租户配额隔离：防止单一租户的突发流量挤占全局容量。
- LLM 应用系统中如何做降级？
  1. LLM 降级链：GPT-4o 超时或限流后依次降级至 GPT-4o-mini、本地小模型，最终降级到规则引擎与模板回复。
  2. RAG 降级：向量检索超时后降级至 BM25 关键词检索，再降级至热门 FAQ 匹配。
  3. 功能降级：复杂多步推理 Agent 降级为单轮问答，个性化推荐降级为热门推荐。
  4. 熔断器模式：连续失败 N 次自动熔断，经过一段时间后进入半开状态试探恢复。
  5. 用户提示：降级时告知用户当前服务繁忙并提供简化回答，合理管理用户预期。
  6. 预案演练：提前定义各级降级策略并通过压测验证，避免线上故障时临时应对。
- 生产环境中 LLM 服务不稳定时，降级和熔断机制怎么设计？
  1. FallbackChain 按优先级依序尝试：主力模型 GPT-4o → 低成本备选 gpt-4o-mini → 本地自部署 Qwen → 相似问题缓存命中 → 固定兜底提示语。
  2. 熔断器三态流转：closed 态正常调用；连续失败达到阈值（如 5 次）转入 open 态，直接拒绝请求以避免冲击故障服务；超过恢复窗口（如 60 秒）转入 half-open 态，放行单个试探请求，成功则关闭熔断、恢复正常。
  3. 重试采用指数退避策略：延迟按 base×2^n 增长并附加随机抖动，同时设置最大延迟上限，避免重试风暴放大故障。
  4. 效果度量：上游大面积故障期间，服务可用性仍可保持在 99.5% 以上，用户仅感知到回答质量略有下降。

- 从0设计一套业务推荐Agent，完整落地架构？
  1. 多源感知输入层：实时采集用户行为、内容特征、场景时段、热点舆情、账号权重多维数据。
  2. 智能理解解析层：大模型语义解析用户隐性兴趣、内容核心价值与场景适配度，突破标签匹配局限。
  3. 业务决策核心层：个性化匹配、去同质化、热点调控、冷热流量平衡、内容优劣筛选，输出最优分发策略。
  4. 流量执行分发层：对接流量中台，完成短视频、直播、电商内容的千人千面精准推送。
  5. 风险兜底层：联动风控体系，拦截违规低质内容、规避流量乱象、防止用户体验恶化。
  6. 数据迭代闭环层：全链路采集效果数据，自主归因复盘、优化决策策略，实现「分发-效果-优化」持续闭环。

- 稳定型业务Agent核心架构？
  1. 前置校验层：统一校验参数、权限、调用频次，从源头拦截无效错误请求。
  2. 工具调用层：整合重试、幂等、限流机制，保障接口调用稳定安全。
  3. 异常处理层：分类处理各类异常，实现智能降级、优雅兜底。
  4. 知识协同层：落实数据优先级，自动校验、修复多库冲突问题。
  5. 自愈迭代层：全链路日志埋点，复盘高频问题，持续优化系统稳定性。

- 多Agent集群调度的三大核心原则是什么？
  1. 优先级优先：搜广推、商品检索核心链路优先占用资源。
  2. 资源隔离：不同 Agent 任务资源互不抢占，避免全域崩盘。
  3. 渐进降级：峰值时非核心功能降级，保障主链路高可用。

- 多Agent资源抢占严重，如何实现资源均衡？
  1. 调度 Agent 统一管控：设置各 Agent 算力配额、缓存配额与最大并发上限。
  2. 核心链路配额倾斜保障、非核心链路动态缩容
  3. 实时监控资源占用，超限自动限流、排队。

- 电商大促多Agent与长文本RAG协同落地架构？
  1. 流量感知层：实时监控大促流量峰值、请求量级、热点商品分布，预判并发压力。
  2. 任务调度层：调度 Agent 统一分配算力，区分优先级、资源隔离、动态配额，解决大促资源冲突。
  3. 长文本检索层：电商专属语义切片、结构化提纯、双层召回、精准精排，适配超长商品文本。
  4. 幻觉治理层：风控 Agent 全局校验、溯源比对、参数纠错，杜绝价格、活动、售后虚假信息。
  5. 高防防护层：限流、熔断、降级、缓存预热四重防护，保障大促集群不雪崩。
  6. 迭代自愈层：沉淀大促错题、检索失败案例、冲突数据，持续优化调度与检索策略。
- 如何设计一个高并发的 RAG 系统架构？
  1. 整体架构：API Gateway → 请求队列 → RAG Worker 集群 → 向量数据库集群 + LLM 服务池。
  2. 检索层：向量数据库（Milvus/Qdrant）多副本部署并读写分离，ES 集群承担 BM25 检索，Redis 做结果缓存。
  3. 计算层：Embedding 服务独立部署（GPU 推理加动态扩缩容），Rerank 服务独立部署。
  4. 生成层：LLM 调用经多 API Key 或多推理实例负载均衡，支持降级链。
  5. 数据层：文档入库走异步 Pipeline（上传→解析→Chunk→Embed→入库），不影响在线服务。
  6. 弹性伸缩：基于 QPS/延迟指标配置 K8s HPA 水平自动扩缩，峰谷差异大时效果显著。
  7. 可观测性：全链路 Tracing 记录每个请求的检索耗时、rerank 耗时与 LLM 耗时，便于定位瓶颈。

#### 8.5 服务生命周期与性能排查

- systemd 服务重启慢如何排查？
  1. 使用 journalctl 查看系统日志，定位时间消耗发生在服务停止阶段还是启动阶段。
  2. 通过调整 TimeoutStopSec 参数，优化旧进程不响应 SIGTERM 导致的停止等待耗时。
  3. 排查是否存在外部网络调用，并通过代理或磁盘缓存进行优化。
- systemd 的 TimeoutStopSec 参数有什么作用？
  1. 指定 systemd 发送 SIGTERM 后等待服务退出的时间，超时后发送 SIGKILL 强制终止。
  2. 原配置为 90 秒，因旧进程不响应 SIGTERM 导致等待过久，修改为 5 秒后停止阶段明显缩短。
  3. 修改配置文件后，需执行 systemctl daemon-reload 使配置生效。
- 服务收到 SIGTERM 后为什么没有立即退出？
  1. 进程内 API 429 重试线程处于 120 秒 sleep 状态，导致 SIGTERM 信号被忽略。
  2. 后台任务需及时响应退出信号，避免长时间 sleep 阻塞进程退出。
- 无外部控制通道、用“标记文件 + 实例纪元”做排空契约，代价在哪？什么场景下不成立？
  1. 运维面板通过写入排空标记文件下发指令，后台监视器周期性读取该文件；当检测到带有当前实例纪元的标记时，即切换为排空状态，拒绝接收新轮次；删除标记则取消排空。
  2. 纪元由内核启动时间与1号进程启动时间组合生成：重启机器会更换纪元，使旧标记自动失效；仅重启网关进程时纪元不变，在途排空操作继续生效。
  3. 代价：文件轮询存在响应延迟；契约演化需双向兼容；损坏的标记被刻意视为“排空生效”，以宁可多排空也不放行；面板无法查看实时状态，只能通过状态文件反推。
  4. 正面价值：不开放控制端口，将生命周期攻击面降至零；“存在即状态”使取消操作天然幂等；纪元的本质是为持久存储上的指令增加时效维度。
  5. 不成立场景：多实例部署下标记文件属于单进程契约，两个实例共享同一文件会互相干扰，需另行设计数据库级租约。
- 如何用 cProfile 定位 Python 服务的启动热点？
  1. 使用 cProfile 进行冷启动测试，分阶段统计 import、config、skill sync、MCP discovery、import runner 等环节的耗时。
  2. 结合子进程冷启动方式，排除环境干扰，精确定位耗时模块。
- 如何解决首次请求触发的外部网络调用导致响应慢？
  1. 通过代理加速外部 API 请求，例如 GitHub API 请求耗时由 9-10 秒降至 0.31 秒。
  2. 复用现有缓存逻辑，将模型列表持久化至 models_cache.json 文件，重启后直接读取，避免重复发起网络请求。
- GPU 显存泄漏如何排查？allocated、reserved 和驱动占用有什么区别？
  1. memory_allocated() 表示仍被活跃 Tensor 占用的显存，memory_reserved() 表示 CUDA Caching Allocator 管理的内存，两者都可能小于驱动看到的设备占用，排查时不能只看 nvidia-smi。
  2. allocated 持续上涨说明仍有 Tensor/计算图/KV Cache 被引用，优先查 Python 容器、会话状态和动态批处理序列；allocated 回落但 reserved 维持高位多为缓存分配器复用或碎片，不能直接认定泄漏；驱动占用上涨而 allocated/reserved 稳定则查 NCCL、CUDA 扩展、推理引擎等框架外分配。
  3. 修复：纯推理路径用 inference_mode() 或 no_grad()，写日志/指标/会话状态前把 Tensor 转成 .detach().cpu().item()，任务结束后删除对输出、Batch 和 KV Cache 的引用并让推理引擎回收已完成序列。
  4. empty_cache() 只能释放缓存分配器中完全空闲的 Segment，无法释放仍被引用的活跃 Tensor，频繁调用还会破坏缓存复用，不能当成常规修复。
- Linux 下如何查看进程信息和 GPU 使用情况？
  1. 进程监控：ps aux 查看静态进程列表，top/htop 动态监控 CPU 与内存占用。
  2. GPU 监控：nvidia-smi 可查看显卡显存占用、利用率及占用进程。
  3. 持续监控可配合 watch 或 nvidia-smi 的周期刷新参数，用于观察训练/推理过程中的显存变化。
- Agent 生产环境内存泄漏有哪几种？如何排查修复？
  1. 先区分四类易混淆问题：对象引用泄漏（存活对象与 retained size 持续增长，完整 GC 后不下降）、无界状态增长（会话 Map 无 TTL、Scratchpad 永久保留）、资源泄漏（流式响应/游标/FD/连接池/Pending Task 未关闭或持续增加）、分配器缓存与碎片（对象已释放但 RSS/显存居高不下）。
  2. 判断标准：同等负载下回收后的稳态基线一轮比一轮高才是泄漏，锯齿式上涨但每次 GC 后回到相近基线是正常分配；预热后上涨并稳定通常是正常缓存。
  3. 曲线形态线索：基线阶梯式抬升说明每批请求都有残留；内存与队列长度同步上涨多为背压失效；Heap 已回落但 RSS 不回落常见于分配器缓存或碎片。
  4. 六类常见根因：会话历史与执行状态无限增长、异步 Task/Future/回调残留、流式连接与外部资源未关闭、缓存/队列/可观测性缓冲区无界、GPU Tensor/计算图/KV Cache 被错误持有、原生库泄漏与碎片化。
  5. 排查顺序：固定负载做预热、施压、停止、回收实验，用四层指标（进程层 RSS/Heap、业务状态层会话数与缓存字节、并发资源层 Pending Task/队列/连接池、GPU 层 allocated/reserved）判断泄漏层。
  6. 对象级定位用三点快照差分（T0 基线、T1 负载、T2 回收），tracemalloc/pprof/Heap Dump 找持续增长对象，再沿 Dominator Tree 或 GC Root 引用链定位生命周期拥有者。
  7. 修复三原则：状态同时设最大条目、最大字节、TTL 与租户配额；资源所有权绑定作用域（TaskGroup、try/finally、async with、aclose）；用覆盖超时/取消/工具异常/客户端断开的长稳测试验证回收基线稳定，而非定时重启、强制 GC 或 empty_cache() 掩盖。

- JVM 垃圾回收了解吗？G1 和 ZGC 的区别是什么？
  1. G1 收集器：按 Region 管理堆内存，采用 Mixed GC，停顿时间可预测。
  2. ZGC 收集器：基于着色指针与读屏障，停顿时间几乎可忽略（低于 10ms），支持 TB 级堆。
  3. G1 适合中小堆（几 GB），ZGC 适合超大堆与低延迟场景。

### 09 Agent 通信协议

> 本章回答「双方如何通信」，沿用四层模型：序列化层（数据如何编码）→ 传输层（消息如何传输）→ 调用绑定层（调用如何表示）→ 应用语义层（双方交流什么）。
>
> 与相邻章节的边界：MCP 的协议机制在本章，工具侧的职责边界在 02.4；A2A 的协议机制在本章，协作业务在 03；传输通道的通信视角在本章，系统设计视角在 08。

#### 9.1 整体分层

```text
Agent-Communication
├── 应用语义层：通信双方交换什么业务语义
├── 调用绑定层：如何表示方法、请求、响应和错误
├── 传输层：消息通过什么通道传递
└── 序列化层：数据编码成什么格式
```

应用语义层解决的是“双方在交流什么”。比如 MCP 规定 Agent 如何发现和调用工具，A2A 规定 Agent 之间如何委派任务。调用绑定层解决的是“这次调用如何表达”，例如方法名、参数、结果和错误。传输层解决的是“消息通过什么通道传递”，例如 HTTP、SSE 和 WebSocket。序列化层解决的是“数据最终编码成什么形式”，例如 JSON 和 Protobuf。

#### 9.2 序列化层

序列化层位于整个通信体系的最底层，负责把程序内存中的对象转换成可以传输或存储的文本或二进制数据。

```
序列化层
├── JSON
├── Protobuf
├── NDJSON
├── MessagePack
├── CBOR
├── multipart/form-data
└── Base64
```

##### 1. JSON

JSON 是 Agent 系统中最常见的文本序列化格式。它支持对象、数组、字符串、数字、布尔值和 null，几乎所有编程语言都可以直接解析。

JSON 最大的优点是可读性强、调试方便、跨语言能力好。开发人员可以直接在日志、浏览器开发工具或命令行中查看消息内容。因此，MCP、ACP、AG-UI 和 A2A 的很多实现都使用 JSON。

JSON 的不足是**消息体积相对较大**。因为每条消息都会重复携带字段名称，同时 JSON 的类型约束比较弱，服务端通常还需要使用 **JSON Schema、Pydantic** 或其他机制校验字段类型。

JSON 不原生支持二进制数据。传输图片、音频或文件时，通常需要使用 Base64、multipart/form-data，或者在 JSON 中只传递文件 URL。

##### 2. Protobuf

Protobuf 协议缓冲区 是一种基于 Schema 的二进制序列化格式。开发者需要先通过 `.proto` 文件定义消息结构、字段编号和字段类型，再生成不同编程语言的代码。

Protobuf 使用字段编号而不是完整字段名进行编码，因此消息体积通常比 JSON 更小，序列化和反序列化性能也更高。字段类型由 Schema 明确定义，所以类型约束比 JSON 更强。

Protobuf 还支持接口演进。只要保留已有字段编号，新增字段通常不会导致旧版本完全无法解析新消息。

gRPC 默认使用 Protobuf，因此常见的组合是：

```
Protobuf
→ HTTP/2
→ gRPC
```

Protobuf 更适合内部高性能服务和跨语言 RPC，但它不方便直接阅读，需要维护 `.proto` 文件和生成代码，临时调试没有 JSON 灵活。

##### 3. NDJSON

NDJSON 是 Newline Delimited JSON，也就是每一行表示一个完整的 JSON 对象，不同对象之间使用换行符分隔。

```
{"type":"token","data":"Hello"}
{"type":"tool_call","name":"search"}
{"type":"finished","status":"success"}
```

NDJSON 适合日志、事件流和管道通信。接收方读取到一行后就可以立即解析，不需要等待一个完整 JSON 数组传输结束。

NDJSON 主要解决连续多个 JSON 对象之间如何划分消息边界的问题。它不规定这些对象具有什么业务含义，也不规定请求和响应如何匹配。

因此，NDJSON 属于序列化和消息分帧形式，不属于 MCP、A2A 或 JSON-RPC 这样的应用和调用协议。

##### 4. MessagePack

MessagePack 是一种二进制对象序列化格式，它的数据模型与 JSON 比较接近，支持对象、数组、字符串、数字和布尔值，同时原生支持二进制数据。

与 JSON 相比，MessagePack 不需要把所有内容表示为可读文本，因此消息体积通常更小，适合高频内部通信和带宽敏感场景。

MessagePack 不要求预先定义 Schema，因此比 Protobuf 更灵活，但它也缺少 Protobuf 的强类型约束、接口生成和跨版本治理能力。

可以把 MessagePack 理解为一种紧凑的二进制 JSON。它在开放 Agent 协议中的普及程度不如 JSON 和 Protobuf，但适合内部事件通信。

##### 5. CBOR

CBOR 是一种可扩展的二进制对象格式。它的数据模型与 JSON 相似，但原生支持字节串、整数、浮点数、数组、Map 和语义标签。

CBOR 不要求预先定义 Schema，所以比 Protobuf 更灵活；同时它采用二进制编码，消息体积通常又比 JSON 更小。

CBOR 的语义标签可以表示日期、大整数或其他扩展类型，因此在 IoT、边缘设备和资源受限环境中比较常见。

在通用 Agent 平台中，CBOR 的使用范围通常不如 JSON 和 Protobuf，但在设备 Agent 和受限网络环境中具有优势。

##### 6. multipart/form-data

multipart/form-data 是一种在同一个 HTTP 请求体中封装多个数据部分的格式。每个部分通过 Boundary 分隔，并且可以拥有独立的名称、Header 和 Content-Type。

它适合同时传输用户 Prompt、JSON 元数据、图片、音频和附件。例如多模态 Agent 可以把文本参数作为普通字段，把图片和文件作为二进制部分上传。

与把整个文件转换成 Base64 再放入 JSON 相比，multipart/form-data 通常更加高效，也不会产生 Base64 的额外体积开销。

它更准确地说是一种复合 HTTP 消息体格式，而不是通用对象序列化协议，但在 Agent 的文件上传和多模态输入中非常常见。

##### 7. Base64

Base64 是把二进制数据转换成可打印文本的编码方式。它不是加密算法，也不是完整的序列化协议。

Base64 常用于在 JSON 中嵌入小型图片、音频片段、文件内容或二进制 Token。因为编码结果是普通文本，所以可以通过只支持文本的通道传输。

Base64 会增加数据体积，并产生额外的编码和解码开销，因此不适合传输大型文件。大型文件更适合使用 multipart/form-data、对象存储 URL 或原生二进制通道。

Base64 只解决二进制数据如何表示成文本的问题，不提供机密性、完整性或身份认证能力。

#### 9.3 传输层

传输层负责将序列化后的消息从一端发送到另一端。这里的传输层是 Agent 工程中的承载通道层，不完全等同于 OSI 网络模型中的传输层。

```
传输层
├── HTTP / HTTPS
├── SSE
├── WebSocket
├── WebRTC
├── stdio
├── Webhook
└── Message Queue
```

##### 1. HTTP / HTTPS

HTTP 是最常见的请求响应协议。客户端发送请求，服务端处理后返回响应。请求通常由方法、URL、Header 和 Body 组成，响应通常由状态码、Header 和 Body 组成。

HTTPS 是运行在 TLS 之上的 HTTP，它提供传输加密、完整性保护和服务端身份认证。生产环境中的模型调用、远程 MCP、A2A 和 Agent API 通常都应该使用 HTTPS。

HTTP 适合发送用户消息、创建任务、查询状态、提交审批和上传文件。它本身主要采用请求响应模式，如果 Agent 需要持续返回 Token，一般会在 HTTP 连接上使用 SSE；如果需要高频双向通信，则可以使用 WebSocket。

HTTP/2 引入了二进制帧、多路复用和流控制，也是 gRPC 常用的底层承载方式。HTTP/3 则运行在 QUIC 上，可以进一步改善多路流传输。

##### 2. SSE

SSE 是基于 HTTP 的服务端事件流。客户端建立一个 HTTP 长连接，服务端将响应类型设置为 `text/event-stream`，然后持续向客户端发送文本事件。

SSE 的主要通信方向是服务端到客户端，因此非常适合 Agent 的 Token Streaming。除了 Token，服务端还可以通过 SSE 推送工具调用状态、任务进度、Subagent 状态和最终结果。

普通文本 Agent 经常采用下面的通信方式：

```
客户端 ── HTTP POST ──→ 提交任务
客户端 ←── SSE Stream ── 返回 Token 和状态
```

如果客户端需要中断任务、批准工具调用或补充信息，一般通过额外的 HTTP 请求提交。因此，SSE 连接本身主要负责服务端向客户端推送，但整个系统仍然可以实现双向业务交互。

SSE 的优点是实现简单、基于标准 HTTP、容易经过网关和反向代理，并且支持断线重连。缺点是缺少真正的全双工能力，不适合大量高频的客户端上行事件。

##### 3. WebSocket

WebSocket 是全双工长连接协议。连接建立后，客户端和服务端都可以随时主动发送消息，不需要为每条消息重新建立 HTTP 请求。

在 Agent 系统中，WebSocket 可以在一条连接上同时承载用户消息、Token 输出、工具调用、审批结果、中断指令、任务状态和设备控制。

WebSocket 适合高频双向交互。例如语音 Agent 需要客户端持续上传音频，服务端持续返回音频，并支持用户随时打断；远程设备 Agent 也可能需要服务端主动发送命令，设备实时返回状态。

WebSocket 的能力比 SSE 更强，但工程复杂度也更高。服务端需要处理心跳、断线重连、消息顺序、连接状态、负载均衡和水平扩展。

因此，普通文本 Agent 一般优先使用 HTTP 加 SSE；需要高频双向控制、实时语音或设备通信时，更适合使用 WebSocket。

##### 4. WebRTC

WebRTC 是面向低延迟实时音频、视频和数据通信的技术体系，主要用于浏览器、客户端和设备之间的实时媒体传输。

在语音 Agent 中，用户音频需要持续发送给服务端或实时模型，Agent 生成的音频也需要持续返回，同时还要支持用户实时打断。WebRTC 在低延迟音频通信方面通常比普通 HTTP 更合适。

WebRTC 支持音频和视频 Track，也支持通过 DataChannel 传输普通数据。它还会使用 ICE、STUN 和 TURN 处理网络发现、NAT 穿透和流量中继。

WebRTC 本身不负责最初的信令交换。客户端和服务端仍需要通过 HTTP 或 WebSocket 交换 SDP 和网络候选信息。

因此，WebRTC 主要负责实时媒体传输，HTTP 或 WebSocket 通常负责认证、会话创建和信令交换。

##### 5. stdio

stdio 是标准输入和标准输出的简称。宿主程序可以启动一个子进程，通过 stdin 向子进程发送请求，通过 stdout 读取子进程返回的响应。

这种通信方式不需要开放网络端口，也不需要单独运行远程服务，因此非常适合本地 MCP Server、Coding Agent、CLI 工具和插件进程。

使用 JSON-RPC over stdio 时，stdout 应当只输出协议消息，普通日志应该写入 stderr。否则日志可能与 JSON-RPC 消息混合，导致消息解析失败。

stdio 的优势是部署简单、攻击面较小，并且子进程生命周期可以由宿主程序统一管理。它的局限是主要适合本机父子进程，不适合直接跨机器通信。

##### 6. Webhook

Webhook 是一种基于 HTTP 的异步回调模式。调用方先向服务端提供回调地址，当任务完成或状态发生变化时，服务端主动向该地址发送 HTTP 请求。

Webhook 适合耗时较长的 Agent 任务。客户端不需要一直保持 SSE 或 WebSocket 连接，也不需要不断轮询任务状态，服务端完成任务后可以主动通知调用方。

Webhook 与轮询的区别是：

```
轮询：客户端不断询问任务是否完成
Webhook：服务端在状态变化后主动通知客户端
```

生产环境中的 Webhook 需要处理签名校验、幂等、重复通知、事件乱序、失败重试和重放攻击。

调用方不能假设一个事件只会收到一次，而应该使用事件 ID 或业务 ID 保证重复通知不会导致业务被重复执行。

##### 7. Message Queue

Message Queue 是异步消息通信机制。生产者把任务或事件发送到 Broker、Topic、Queue 或 Subject，消费者可以在之后读取和处理，双方不需要同时在线。

在 Agent 系统中，消息队列适合任务调度、长任务执行、Subagent 分发、事件总线和失败重试。例如 Gateway 收到任务后，可以把任务写入队列，由空闲的 Agent Worker 消费执行。

消息队列能够实现异步解耦和削峰填谷。如果 Agent Worker 暂时不可用，任务可以先保存在队列中，等服务恢复后再继续处理。

常见系统包括 Kafka、RabbitMQ、NATS 和 Redis Streams。它们在消息持久化、顺序、消费者组、确认机制和吞吐量方面各有侧重。

使用消息队列时还需要处理重复消费、消息确认、死信队列、顺序保证和最终一致性。消费者通常需要实现幂等，避免同一任务被重复执行。
- MCP 支持哪些 Transport？各适用什么场景？
  1. stdio 通过标准输入输出通信，适合本地进程间通信，启动快、零配置，是最常用的传输方式。
  2. HTTP+SSE 适合远程部署场景，Server 通过 Server-Sent Events 向客户端推送消息。
  3. Streamable HTTP 为 2025 年新增的传输方式，无状态 HTTP 请求可选升级为 SSE 流，兼顾简单性与实时性，正在替代纯 SSE 方案。

#### 9.4 调用绑定层

调用绑定层建立在序列化层和传输层之上，负责规定一次调用如何表示，包括调用哪个方法、传入哪些参数、如何关联请求和响应、结果如何返回以及错误如何表示。

```
调用绑定层
├── REST
├── JSON-RPC
├── gRPC
└── GraphQL
```

##### 1. REST

REST 是一种以资源为中心的接口设计风格。它通常使用 URL 表示资源，使用 HTTP 方法表示操作。

例如，GET 用于查询资源，POST 用于创建资源或执行操作，PATCH 用于部分更新，DELETE 用于删除资源。

REST 通常复用 HTTP 状态码表示调用结果，例如 `200` 表示成功，`400` 表示请求错误，`404` 表示资源不存在，`500` 表示服务端异常。请求和响应一般使用 JSON，但 REST 本身并不限定必须使用 JSON。

在 Agent 系统中，REST 适合任务创建、任务查询、Session 管理、文件上传和审批提交。例如可以使用 `POST /tasks` 创建 Agent 任务，再使用 `GET /tasks/{id}` 查询任务状态。

REST 的优点是简单、通用、容易调试，也容易经过 API Gateway 和负载均衡器。它主要适合请求响应场景，持续流式输出一般还需要结合 SSE，双向实时通信则通常结合 WebSocket。

##### 2. JSON-RPC

JSON-RPC 是一种轻量级远程过程调用协议。它不围绕资源组织接口，而是直接表达调用哪个方法。

一个 JSON-RPC 请求通常包含：

```
jsonrpc：协议版本
method：方法名称
params：调用参数
id：请求标识
```

调用成功时返回 result，失败时返回 error。id 用于匹配请求与响应。

如果一条消息没有 id，它通常表示 Notification，即发送方只通知接收方发生了某件事情，不要求返回结果。这种机制适合状态更新和事件通知。

JSON-RPC 与传输方式无关，可以运行在 stdio、HTTP、WebSocket 或其他消息通道上。MCP 和 ACP 使用 JSON-RPC，是因为它既支持普通请求响应，也支持通知和双向调用。

JSON-RPC 和 JSON 不是同一层概念。JSON-RPC 定义请求、响应和错误的消息结构，JSON 负责把这些结构编码成文本。

##### 3. gRPC

gRPC 是一种高性能、强类型的远程过程调用框架。开发者通常通过 `.proto` 文件定义 Service、Method、Request 和 Response，再生成不同语言的客户端和服务端代码。

gRPC 默认使用 Protobuf 进行序列化，并通常运行在 HTTP/2 上。它支持四种调用模式：

```
Unary：单请求、单响应
Server Streaming：单请求、多响应
Client Streaming：多请求、单响应
Bidirectional Streaming：双向持续通信
```

服务端流适合客户端提交一次请求后，服务端持续返回任务状态或增量结果。双向流适合客户端和服务端同时持续发送消息。

gRPC 的优势是类型明确、消息体积小、性能较高，并且原生支持超时、取消、Metadata 和标准错误码。它比较适合 Agent 平台内部的微服务通信和高吞吐 A2A 服务。

它的不足是消息不如 JSON 直观，需要维护 `.proto` 文件并生成代码，浏览器和人工调试也没有 HTTP+JSON 方便。

##### 4. GraphQL

GraphQL 是一种基于 Schema 的查询语言和服务执行模型。客户端可以明确声明需要哪些字段，服务端只返回这些字段。

GraphQL 主要包括：

```
Query：读取数据
Mutation：修改数据
Subscription：持续订阅事件
```

GraphQL 适合复杂 Agent 平台的数据聚合查询。例如管理页面可能同时需要任务信息、Session、用户信息、成本指标和日志摘要，前端可以通过一次 GraphQL 查询获取需要的数据。

GraphQL 一般不直接驱动 Agent Loop，因为 Agent Loop 会产生大量文本增量、工具调用和状态事件。这些实时事件通常仍通过 SSE 或 WebSocket 传输。

因此，GraphQL 在 Agent 系统中更适合作为控制面和管理平台的数据查询接口。
- 如何统一 OpenAI / Anthropic / Gemini 等多家模型的 API 接入？
  1. Provider 接口统一抽象：对消息结构、角色定义与系统提示词位置进行归一化映射。
  2. 工具调用差异适配：不同厂商 function calling 的 schema 格式与触发方式各异，需在适配层完成转换。
  3. 流式输出事件归一化：将不同厂商的 SSE 事件流映射为统一的内容增量、工具调用与结束事件。
  4. 统一错误处理与重试策略：将限流、超时、内容过滤等错误码映射为内部标准错误。
  5. 参数差异抽象：对 temperature、max_tokens、stop 序列等参数在不同 provider 之间做兼容映射。

#### 9.5 应用语义层

应用语义层位于整个通信体系的最上层，负责定义通信双方分别是什么角色、可以交换哪些业务对象、对象具有什么状态，以及整个交互流程遵循什么规则。

```
应用语义层
├── AG-UI：Frontend ↔ Agent
├── ACP：Editor / IDE ↔ Coding Agent
├── MCP：Agent ↔ Tool / Context
└── A2A：Agent ↔ Agent
```

##### 1. AG-UI

AG-UI 是前端应用与 Agent Runtime 之间的交互协议，主要解决 Agent 前端与后端之间缺少统一事件模型的问题。

普通聊天接口只需要传递用户消息和最终文本，但 Agent 执行过程中还会产生运行开始、文本增量、工具调用、工具结果、状态变化、人工审批和运行结束等事件。

AG-UI 将这些过程定义成标准事件。前端收到文本增量事件后可以逐步渲染答案，收到工具调用事件后可以展示 Agent 正在执行什么操作，收到状态更新后可以显示任务进度，收到审批事件后可以向用户展示确认界面。

AG-UI 规定的是事件分别具有什么业务含义，但不强制使用哪种传输方式。同一套 AG-UI 事件可以通过 SSE 传输，也可以通过 WebSocket 传输。

因此，AG-UI 解决的是前端如何理解 Agent 的运行过程，而 SSE 和 WebSocket 解决的是这些事件如何发送到前端。

##### 2. ACP

ACP 是编辑器或 IDE 与 Coding Agent 之间的交互协议。它的目标类似于 LSP：编辑器实现一次 ACP，就可以接入多个 Coding Agent；Coding Agent 实现一次 ACP，也可以接入多个编辑器。

Coding Agent 的交互不仅包含聊天消息，还包括读取文件、修改代码、展示 Diff、执行终端命令、返回执行进度和请求用户授权。

因此，ACP 定义的是一套面向软件开发场景的 Agent 交互语义。

本地环境中，通常由编辑器启动 Coding Agent 子进程，再通过 stdio 通信。ACP 一般使用 JSON-RPC 表示请求、响应和通知，数据采用 JSON 编码。

典型组合是：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

ACP 与 MCP 的区别在于，ACP 的通信双方是编辑器和 Coding Agent，关注的是会话、代码、终端和权限；MCP 的通信双方是 Agent 和外部能力服务，关注的是工具和数据访问。

##### 3. MCP

MCP 是 Agent 与外部工具、数据和上下文服务之间的标准协议，主要解决工具接入方式不统一的问题。

如果没有 MCP，不同 Agent 框架需要分别为文件系统、数据库、搜索引擎、GitHub 和各种企业服务开发专用连接器。

MCP 采用 Client-Server 模型。MCP Server 对外暴露能力，MCP Client 连接 Server、发现能力并发起调用。

MCP Server 通常可以提供：

```
Tool：可以执行的动作
Resource：可以读取的数据
Prompt：可以复用的提示模板
```

MCP 使用 JSON-RPC 表示请求、响应和通知，数据使用 JSON 编码。本地 MCP Server 一般通过 stdio 通信，远程 MCP Server 一般通过 Streamable HTTP 通信。

完整链路可以表示为：

```
JSON
→ stdio / Streamable HTTP
→ JSON-RPC
→ MCP
```

MCP 本质上是标准化能力调用协议。Agent 通常会发现工具名称、描述和参数，然后像调用结构化函数一样调用它。

因此，MCP 解决的是 Agent 如何连接和调用外部能力，而不是两个自主 Agent 如何协作。

##### 4. A2A

A2A 是独立 Agent 系统之间的通信和协作协议，适合跨框架、跨语言、跨服务甚至跨企业的 Agent 互操作。

A2A 的核心思想是黑盒协作。调用方不需要知道另一个 Agent 内部使用什么模型、Prompt、Memory 和 Tool，只需要知道这个 Agent 具有什么能力、如何提交任务、如何获取状态以及如何接收产物。

A2A 的核心对象包括：

```
Agent Card：描述 Agent 身份、能力、接口和认证方式
Message：Agent 之间交换的信息
Task：具有生命周期的任务
Part：消息或产物的内容单元
Artifact：任务生成的文档、代码或结构化结果
```

A2A 与普通工具调用不同。工具调用通常是传入确定参数并等待结果，而 A2A 面向的是一个具有自主能力的 Agent。

被调用 Agent 可以自己拆分任务、调用多个工具、运行较长时间，甚至在执行过程中请求调用方补充输入或完成授权。

因此，A2A 不仅定义任务提交，还需要定义任务状态、流式更新、取消、失败、补充输入和产物返回等语义。

A2A 可以采用多种底层组合：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

或者：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

##### 5. MCP 与 A2A

MCP 与 A2A 最核心的区别是，MCP 面向能力调用，A2A 面向任务委派。

通过 MCP 调用工具时，Agent 通常明确知道调用哪个工具、需要传入哪些参数，以及大致会返回什么结果。例如，Agent 调用搜索工具并传入查询条件，工具直接返回搜索结果。

通过 A2A 调用另一个 Agent 时，调用方通常只描述目标，不规定具体执行步骤。例如主 Agent 可以把“调研新能源汽车行业并生成报告”委派给 Research Agent，Research Agent 自己决定如何规划、搜索、整理和生成报告。

```
Main Agent
└── A2A → Research Agent
               ├── MCP → Search Tool
               ├── MCP → Database
               └── MCP → File System
```

因此，二者可以概括为：

```
MCP：Agent 调用一个能力
A2A：Agent 委派一个任务
```

- MCP 工具调用的幂等性如何设计？
- MCP 如何处理工具调用的并发与顺序问题？
  1. MCP 基于 JSON-RPC 2.0，每个请求携带唯一 ID，天然支持并发发送多个请求。
  2. Client 可同时发起多个工具调用，Server 异步处理并按 ID 匹配返回结果。
  3. 调用之间的顺序依赖由 Host 或上层 Agent 框架控制，MCP 协议本身不强制顺序。
- 如何设计 Agent 的工具调用系统，包括工具注册、选择与 MCP 的设计思路？
  1. 使用标准化 Schema 声明工具名称、功能描述与参数，供模型理解与匹配。
  2. 工具选择依赖准确的描述文本与 Function Calling 能力；工具数量过多时可先检索再精选。
  3. 工具调用错误处理：捕获异常后将错误信息回传模型以便重试或更换工具，并设置超时与结果校验。
  4. MCP（Model Context Protocol）以统一协议向任意客户端暴露工具与资源，将工具提供方与模型应用方解耦。
- 描述 Agent 通过 MCP 调用工具的整体流程。？
  1. 用户发出请求后，Agent 解析意图并规划任务，确定需要调用的工具。
  2. 通过 MCP 协议进行工具发现（Tool Discovery），获取可用工具列表与描述。
  3. 构造工具调用请求并填充参数，MCP Server 执行工具并返回结果。
  4. Agent 将结果整合进上下文继续推理，循环直至生成最终回复并返回用户。

- MCP 的未来发展方向有哪些？
  1. 远程 MCP Server 的标准化：目前以本地 stdio 为主，远程部署规范正在演进。
  2. 认证授权标准化：与 OAuth 2.1 集成。
  3. 工具市场或注册中心：类似 npm 的发现与安装机制。
  4. 多模态支持：图片、音视频等非文本内容的传输。
  5. 与 Agent 框架深度集成：LangChain、CrewAI 等已开始原生支持 MCP。
- MCP 与 OpenAPI/Swagger 是什么关系？
  1. OpenAPI 定义 REST API 的接口规范，MCP 定义 AI 工具与模型之间的通信协议，两者分属不同层次。
  2. MCP Server 可包装 OpenAPI 描述的 HTTP 接口，使 AI 模型能够发现并调用这些接口。
  3. 社区已有工具可将 OpenAPI spec 自动转换为 MCP Server。
  1. MCP（Model Context Protocol）是 Anthropic 于 2024 年底开源的标准化协议，定义 AI 应用与外部工具、数据源之间的通信规范。
  2. 核心解决 M×N 集成碎片化困境：此前每个 AI 应用需为每个外部服务编写定制集成代码；引入 MCP 后，工具开发者只需实现一次 Server，即可被所有支持 MCP 的 Host 调用，集成复杂度由 M×N 降为 M+N。
  3. 同时统一解决各厂商 Function Calling 格式不统一、缺少标准化工具发现机制、上下文注入无规范、权限控制无标准方案、平台间生态孤岛等痛点。
  4. 定位类似 USB 标准：以通用接口解决所有设备的兼容问题。
- MCP（Model Context Protocol）协议的架构设计和工作流程是怎样的？它解决了什么核心问题？
  1. MCP 解决的核心问题是标准化 Agent 与外部工具、数据源的通信：此前每个 Agent 框架自定义工具接口，彼此不可互通。
  2. 架构分三层角色：Host 是宿主应用（如 Claude Desktop），负责管理生命周期；Client 运行于 Host 中，负责与 Server 通信；Server 是暴露具体能力的服务端。
  3. Server 提供三类能力原语：Tools（可调用的函数）、Resources（可读取的数据）、Prompts（预定义的提示模板）。
  4. 通信基于 JSON-RPC 2.0，支持 stdio（本地进程通信）与 SSE over HTTP（远程服务）两种传输方式。
  5. 典型工作流程：Host 启动后 Client 连接 Server，Server 上报 capabilities，Client 获取可用 Tools 列表；Agent 决定调用后，Client 发送 tool call，Server 执行并返回结果。
  6. MCP 的价值常被类比为 USB 统一外设接口：它统一了 AI 工具的接入接口。
- MCP 的 capability negotiation（能力协商）是什么？为什么需要它？
  1. Client 与 Server 在建立连接时互相声明各自支持的功能，例如 Server 声明支持 tools、resources，Client 声明支持 sampling。
  2. 双方只使用共同支持的功能进行通信。
  3. 保证向前兼容：旧 Client 面对新 Server 时，不会因无法识别新增特性而崩溃。
- MCP 协议是有状态还是无状态的？
  1. MCP 连接是有状态的：Client 与 Server 建立连接后维护会话状态，例如协商好的 capabilities。
  2. 有状态连接还支撑订阅资源变更通知等能力。
  3. Streamable HTTP Transport 支持无状态模式：简单请求-响应无需维护长连接，需要时再升级为有状态 SSE 流。
- MCP 的四大核心组件是什么？各自的职责是什么？
  1. Host（宿主）为运行 LLM 的应用程序（如 Claude Desktop、Cursor 或自定义 Agent 框架），负责管理多个 Client 的生命周期，控制安全策略与权限边界。
  2. Client（客户端）为 Host 内部的协议实例，与每个 Server 维持 1:1 连接，负责协议协商（capability negotiation）、消息路由与请求响应生命周期管理。
  3. Server（服务端）对外暴露 Tools、Resources、Prompts 三类能力，采用轻量化设计，专注封装单一数据源或服务，例如 GitHub Server 提供 create_issue、list_repos 等工具。
  4. Transport（传输层）承载通信，包括 stdio（标准输入输出，本地进程最常用）、HTTP+SSE（远程推送）、Streamable HTTP（2025 年新增，替代 SSE）。
- MCP（Model Context Protocol）是什么？哪些框架支持它？
  1. MCP 是 Anthropic 提出的标准协议，定义了 LLM 应用与外部工具、数据源之间的通信标准，作用类似 USB 通用接口。
  2. 架构分两端：MCP Server 暴露工具与资源（如数据库查询、API 调用），MCP Client 位于 Agent 框架内部，负责调用 Server。
  3. 已支持的框架与产品包括 OpenAI Agents SDK、Google ADK、Mastra、LangChain、Cursor、Claude Desktop 等。
  4. MCP 正成为 AI 工具集成的事实标准。
- MCP 的三大原语是什么？各自如何工作？
- MCP 的 Sampling 机制是什么？
  1. Sampling 允许 Server 反向请求 Host 侧的 LLM 进行推理，形成 LLM 与 Server 的双向通信。
  2. 典型场景：Server 处理复杂任务时需借助 LLM 辅助决策，例如分析查询结果、生成摘要。
  3. 安全边界清晰：LLM 调用权限始终由 Host 控制，Server 无法绕过 Host 直接调用模型。
- MCP 中 Resource 和 Tool 有什么区别？什么时候应该用 Resource？
  1. Tool 是模型主动调用的函数，通常带有副作用，例如创建 issue、写入数据库。
  2. Resource 是被动提供的数据源（文件内容、数据库 Schema、API 文档），由应用程序控制注入时机，模型不直接执行。
  3. 当数据属于“背景信息”而非“操作”时，应使用 Resource 承载，例如将项目 README 作为 Resource 注入上下文。
- MCP 的三大能力原语是什么？它们的控制方分别是谁？
  1. Tools 为模型可调用的函数，是否调用由模型决定，例如 create_issue、query_db。
  2. Resources 为模型可读取的数据源（如文件内容、数据库 Schema、API 文档），由应用程序控制注入时机。
  3. Prompts 为预定义的提示模板，由用户主动触发选择，例如“总结这个 PR”。
  4. 设计理念是让不同能力由最合适的角色控制：模型控 Tools、应用控 Resources、用户控 Prompts。
- 以企业知识库 Agent 为例，MCP 的上下文组装流程是怎样的？
  1. 典型案例：企业文档系统的 MCP Server 暴露 Confluence 页面、Jira 工单等 Resource，知识库搜索、创建工单等 Tool，以及客服回复模板 Prompt；用户系统 Server 暴露用户画像 Resource 与更新用户标签 Tool。
  2. 组装流程：用户发起查询后，Client 先从用户系统拉取用户画像（Resource），再调用知识库搜索工具获取相关文档。
  3. 随后将用户画像、检索结果与对话历史组装为完整上下文，送入 LLM 生成回答。
  4. LLM 决定是否调用 Tools，调用结果再次注入上下文，形成闭环。
  5. 不同 AI 应用可复用同一套 MCP Server，无需为每个应用重写数据集成逻辑。
  1. Resources（资源）：只读上下文数据源，以统一 URI 格式标识（如 file://、db://、api://），由 Server 暴露、Client 按需拉取；支持静态资源与带模板参数的动态资源，资源变更可通过订阅机制通知 Client。
  2. Tools（工具）：基于 tools/list 与 tools/call 实现标准化的工具发现与调用；工具定义包含名称、描述与 JSON Schema 参数，支持流式返回与进度通知。
  3. Prompts（提示词）：Server 可暴露预定义 Prompt 模板，Client 可枚举并按需使用，支持参数化与动态组合。
  1. MCP（Model Context Protocol）是 Anthropic 于 2024 年底提出的开放协议，旨在标准化 AI 模型与外部数据源及工具之间的交互方式。
  2. 核心架构为：AI 应用（Host）内的 MCP Client 可连接多个 MCP Server，分别对接数据库、文件系统、API 服务与企业内部系统。
  3. 解决上下文数据注入：通过 Resources 协议标准化外部数据的读取与注入。
  4. 解决函数/工具路由：通过 Tools 协议标准化工具的发现、描述与调用。
  5. 解决提示词编排：通过 Prompts 协议标准化提示词模板的管理与复用。
  6. 其最大价值在于生态复用：一套 MCP Server 可被所有支持 MCP 的 AI 应用（ChatGPT、Claude、自研 Agent）直接复用，无需为每个应用重写数据集成逻辑，作用类似于 REST API 之于 Web 开发。
  1. 幂等性保证相同请求重复执行时仅生效一次且结果一致，避免重复扣费或写入等副作用。
  2. 采用唯一 request_id 作为幂等键，服务器据此去重；对已处理请求直接返回缓存结果。
  3. 幂等键及其结果需持久化存储（如 Redis 或数据库），并设置过期时间以管理存储增长。
  4. 重试时复用相同 request_id，确保重试不产生额外副作用。
- MCP、Function Calling 与 Plugin（平台插件）三者有什么区别和关系？
  1. 层次不同：Function Calling 位于模型推理层，Plugin 位于应用平台层，MCP 位于通信协议层。
  2. 解决的问题不同：Function Calling 解决“模型如何输出结构化工具调用指令”；Plugin 解决“平台如何注册、分发和管理工具”；MCP 解决“工具如何接入 AI 应用”。
  3. 标准化程度不同：Function Calling 各厂商格式互不兼容且绑定特定模型；Plugin 绑定特定平台；MCP 为开放标准，跨模型、跨平台可移植。
  4. 能力差异：MCP 协议内建 tools/list 工具发现、连接级状态管理与权限协商；Function Calling 通常手动注册工具并使用 API Key 认证；Plugin 走平台商店分发与 OAuth 认证。
  5. 三者互补而非竞争：MCP Server 暴露工具，Host 通过 Function Calling 让模型决定调用哪个，平台再以 Plugin 形式分发。
- MCP 和 Function Calling 是什么关系？
  1. Function Calling 是模型侧的能力：在提示中给出工具的 JSON Schema，模型生成结构化调用请求，由外部引擎解析执行后回传结果。
  2. MCP 是开放协议，标准化应用与工具提供方之间的连接，使同一套工具可被不同模型和宿主复用，解耦工具开发者与模型厂商。
  3. 两者互补而非竞争：MCP Server 暴露的工具最终仍以类似 function calling 的 schema 形式呈现给模型。
  4. 简言之，Function Calling 解决模型如何发起调用，MCP 解决工具从哪来、如何统一接入。
- 开发和实现一个 MCP Server 有哪些最佳实践？
  1. 工具描述必须精确，LLM 依靠描述决定何时调用，含糊描述会导致错误调用。
  2. 参数需使用 JSON Schema 严格约束类型、枚举、默认值与必填项。
  3. 错误处理应优雅：返回结构化错误信息，而非抛出异常导致连接断开。
  4. 幂等设计：同一调用多次执行应产生相同结果，避免重复操作带来副作用。
  5. 超时控制：长时间运行的工具应支持 progress notification 进度上报。
  6. 工程实现上，Python 可使用 FastMCP，TypeScript 可使用官方 MCP SDK，快速实现 tool/resource/prompt 三类能力。
- 设计一个 MCP Server 时，错误处理应该考虑哪些方面？
  1. 错误需区分可恢复与不可恢复两类：可恢复错误返回错误信息让模型重试，不可恢复错误返回明确失败原因。
  2. 采用 MCP 标准错误码（基于 JSON-RPC 错误码）；工具内部执行失败以结果中的 isError:true 标记，使 Host 能区分工具执行失败与协议级错误。
  3. 错误信息须做敏感信息脱敏，不得泄露内部实现细节。
  4. 长时间任务须配合 progress notification 上报进度，避免 Client 因超时断开连接。
- MCP 的安全模型是如何设计的？
  1. 协议层：通过 capability negotiation 进行能力协商，Client 与 Server 在建立连接时互相声明支持的能力。
  2. Host 层：由 Host 决定哪些 Server 可以连接、哪些工具可暴露给模型。
  3. 传输层：可叠加 TLS 加密与认证。
  4. 用户确认机制（human-in-the-loop）：敏感操作需经用户授权后方可执行。
- 如果一个 MCP Server 响应很慢，应该如何优化？
  1. 使用 progress notification 机制向 Client 报告进度，避免被判定为超时。
  2. 工具拆分：将耗时操作拆分为“提交任务”与“查询结果”两个工具，改为异步模式。
  3. 缓存常用数据，并在 Server 端执行异步处理。
  4. 传输层可考虑用 Streamable HTTP 替代 stdio，以支持并发请求。
- 如何设计工具调用的权限控制系统？MCP 场景下如何落地？
  1. 用户层：通过认证与 RBAC 角色控制，限定每个用户或 Agent 可用的工具集。
  2. 工具层：每个工具声明自身所需的权限与危险等级。
  3. 参数层：约束可操作的资源范围，例如仅允许查询本人订单，拒绝越权操作。
  4. 运行时层：通过速率限制防止滥用，审计日志确保全程可追溯。
  5. 确认机制：删除、转账等高危操作须经用户二次确认。
  6. MCP 落地时，Server 端通过 annotations 声明工具属性（如 readOnlyHint: true，此类字段为提示性元数据而非强制约束）；Host 端维护白名单，仅向模型暴露已授权工具；破坏性工具标记为 destructiveHint，并在调用前要求确认；多租户场景下在 Transport 层携带用户身份，由 Server 端完成鉴权。
- 企业级场景下如何管理大量 MCP Server？MCP 在企业中有哪些典型应用？
  1. 统一工具网关：企业内部多个 Agent 通过 MCP 接入统一工具注册中心，避免重复集成。
  2. 权限隔离与 RBAC：不同角色 Agent 经权限协商访问不同级别工具，且不同 Agent 可见的工具集不同。
  3. 审计追踪：所有工具调用均走标准协议，天然支持日志集中收集与审计。
  4. 多模型切换：工具层与模型层解耦，切换底层 LLM 时无需修改工具集成代码。
  5. 渐进式迁移：逐步将内部 API 封装为 MCP Server，无需一次性重构。
  6. 治理手段包括：统一 Server 注册中心（类似服务发现）、配置文件统一管理连接信息、健康检查与自动重连，以及支持灰度升级的版本管理。
- MCP 生态中有哪些知名的 Server 实现？这说明了什么？
  1. 官方与社区提供了大量现成 Server：GitHub（代码管理）、Filesystem（文件操作）、PostgreSQL/SQLite（数据库）、Brave Search（搜索）、Slack（消息）、Google Drive（文档）等。
  2. 这些 Server 可在 Claude Desktop、Cursor 等 Host 中即插即用。
  3. 这体现了 MCP 的生态优势：工具一次开发、处处可用，无需为每个 Host 重复适配。
- 如何测试和调试 MCP Server？
  1. 使用官方调试工具 MCP Inspector，可视化查看 Server 暴露的工具与资源。
  2. 单元测试：直接调用工具函数验证逻辑正确性。
  3. 集成测试：使用 MCP Client SDK 模拟真实连接，进行端到端验证。
  4. 日志：Server 通过 logging 能力将日志发送至 Host。
  5. 错误注入：模拟网络断开、超时等异常场景，验证容错表现。

#### 9.6 典型协议组合

##### 1. AG-UI

AG-UI 定义前端与 Agent Runtime 之间的文本增量、工具调用、工具结果、状态更新和运行生命周期。

这些事件可以通过 SSE 或 WebSocket 传输，通常使用 JSON 编码。

```
JSON
→ SSE / WebSocket
→ 事件模型
→ AG-UI
```

##### 2. ACP

ACP 定义编辑器与 Coding Agent 之间的会话、代码修改、终端执行、权限请求和执行状态。

本地 ACP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

##### 3. MCP

MCP 定义 Agent 如何发现和调用 Tool、Resource 和 Prompt。

本地 MCP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ MCP
```

远程 MCP 通常采用：

```
JSON
→ Streamable HTTP
→ JSON-RPC
→ MCP
```

##### 4. A2A

A2A 定义 Agent 发现、任务委派、状态流转和 Artifact 交换。

基于 JSON 的组合可以是：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

基于 gRPC 的组合可以是：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

#### 9.7 总结

Agent 通信协议可以按照自底向上的方式理解。

最底层是序列化层，它解决数据如何编码，常见方案包括 JSON、Protobuf、NDJSON、MessagePack 和 CBOR。

序列化后的数据通过传输层发送，常见通道包括 HTTP、SSE、WebSocket、WebRTC、stdio、Webhook 和消息队列。

传输层之上是调用绑定层，它负责定义方法、参数、结果和错误如何表示，常见方式包括 REST、JSON-RPC、gRPC 和 GraphQL。

最上层是应用语义层，它定义通信双方真正交换什么业务信息，主要包括 AG-UI、ACP、MCP 和 A2A。

```
JSON、Protobuf：数据如何编码
HTTP、SSE、WebSocket：消息如何传输
REST、JSON-RPC、gRPC：双方如何调用
AG-UI、ACP、MCP、A2A：双方交流什么
```

最终可以把整个链路概括为：

```
序列化层：把对象变成数据
传输层：把数据发送出去
调用绑定层：把数据组织成一次调用
应用语义层：让调用具有 Agent 业务含义
```

#### 9.8 ACP（Agent Client Protocol）与编码代理接入

- ACP（Agent Client Protocol）是什么？Agent Canvas 如何用它拉起第三方编码代理？
  1. ACP 是客户端与编码代理之间基于 JSON-RPC over stdio 的标准化协议。
  2. Agent Canvas 的 Agent Server 将 Codex、Claude Code、Gemini CLI 等作为子进程拉起，并通过 JSON-RPC 转发会话消息。
  3. 代理自身负责管理 LLM、工具与执行，Canvas 仅承担界面渲染与管控职能。
  4. 其意义在于从专用 SWE Agent 演进为通用控制平面，通过单一控制台统一管理多个 Harness。

#### 9.9 A2A 与 Agent 间通信

- A2A 框架与普通 Agent 框架的区别是什么？
  1. A2A（Agent-to-Agent）是 Google 提出的 Agent 间通信协议，核心目标是使不同框架、不同供应商构建的 Agent 能够互相发现与协作。
  2. 传统框架聚焦单个 Agent 的内部构建，通信依赖框架内部 API，发现机制依赖硬编码；A2A 面向 Agent 间的互操作，采用标准化协议（HTTP+JSON）与 Agent Card 能力声明。
  3. A2A 的三个核心概念是 Agent Card（声明能力与端点）、Task（标准化任务格式）与 Streaming（实时状态更新）。
  4. A2A 与 MCP 互补：MCP 解决 Agent 到工具的连接，A2A 解决 Agent 到 Agent 的连接。
- A2A 协议是什么？它和 MCP 有什么区别？
  1. A2A（Agent-to-Agent）是 Google 提出的 Agent 间通信协议；MCP 解决的是 Agent 与工具、数据源之间的连接问题。
  2. 两者互补：MCP 解决 Agent 如何使用工具，A2A 解决 Agent 之间如何协作，一个完整的多 Agent 系统可能同时用到两者。
  3. A2A 定义了 Agent Card 能力声明、Task 任务传递、Streaming 流式响应等标准。
  4. 目标是让不同框架构建的 Agent 能够互相调用。
- MCP 和 A2A 协议分别是什么？它们解决什么问题、有什么区别？
  1. MCP（Model Context Protocol）是 Anthropic 于 2024 年底提出的开放协议，将 LLM 应用与外部工具/数据源的连接方式标准化，可类比为 AI 的 USB 接口。
  2. 解决的问题：此前每个框架×每个工具均需单独适配（N×M 个适配器）；MCP 使工具开发者只实现一次 Server，所有支持的 Client 即可直接调用。
  3. 架构与传输：Server 提供 Tools（可调用函数）、Resources（可读取数据源）、Prompts（预定义模板），Client 通过标准协议调用；本地使用 stdio，远程使用 HTTP+SSE。
  4. A2A（Agent-to-Agent）是 Google 提出的 Agent 间通信协议，基于 Agent Card（能力描述）与 Task 协议，使不同框架/平台的 Agent 可以互相发现、通信与协作。
  5. 区别与关系：MCP 纵向连接 Agent 与工具（让 Agent 有能力），A2A 横向连接 Agent 与 Agent（让 Agent 会协作），两者互补而非竞争，完整的多 Agent 系统两者都需要；例如库存 Agent 用 MCP 查库存，通过 A2A 通知采购 Agent 补货，采购 Agent 再用 MCP 调供应商 API。
  6. ANP（Agent Network Protocol）是蚂蚁集团提出的智能体网络协议，面向开放网络环境的 Agent 互联，强调身份认证与安全。
- MCP、A2A、Skill 在企业 Agent 应用中分别负责什么？边界在哪？
  1. MCP（Model Context Protocol）：标准化模型与外部工具、数据源的连接，解决工具接入协议统一问题。
  2. A2A（Agent-to-Agent）：负责不同 Agent 之间的发现、委托与协作通信。
  3. Skill：将领域流程和知识打包为可加载的能力包，按需注入以扩展 Agent 能力。
  4. 边界划分：MCP 负责模型与工具之间的接口层，A2A 负责 Agent 之间的协作层，Skill 负责组织内部能力的封装复用。


### 30 计算机网络基础

- TCP 和 UDP 的区别是什么？TCP 为什么挥手要四次？
  1. TCP 面向连接、提供可靠传输与拥塞控制；UDP 无连接、不可靠但延迟更低。
  2. 三次握手用于同步双方初始序号并确认双向通路可用。
  3. 四次挥手：TCP 为全双工，两个方向的数据传输需独立关闭，ACK 与 FIN 不能总合并发送，故需四次。
  4. TIME_WAIT 状态确保最后一个 ACK 丢失后对方能够重传 FIN。
- HTTP/1.1 和 HTTP/2 的区别是什么？
  1. HTTP/1.1 支持长连接 keep-alive 与管道化，但队头阻塞严重。
  2. HTTP/2 支持多路复用（单连接并行多个流）、头部压缩（HPACK）、服务器推送与二进制帧传输。
  3. HTTP/2 可显著降低同一页面多个请求的延迟开销。
