- 为什么用按解析后会话 ID 的轮次租约，而不是全局锁或按路由键的锁？
  1. 按路由键加锁存在盲区：路由键到会话 ID 为多对一映射，两个不同路由键各自持锁时，仍可能在同一份转录上并发刷写，且该冲突无法被路由键级守卫识别。
  2. 全局锁虽能堵住并发漏洞，但会导致所有会话串行化；单个工具调用的长轮次可能持续数分钟，期间无关会话全部被阻塞。
  3. 轮次租约按解析定型后的会话 ID 加锁，竞争仅出现在真正的别名键路径上，其余路径零竞争，锁开销可忽略。
  4. 释放租约时必须携带所有权与运行代数校验；等待超时后采取失败开放策略，即降级为不串行继续执行并显式报错，体现可用性优先于强一致性。
  5. 判断标准：锁的键应取决于被保护资源的属主；当路由键到属主的映射为多对一时，必须在解析定型后补加一把按属主维度的锁。
  6. 路由键到会话ID为多对一映射，两个不同路由键可分别通过各自的路由键守卫，在同一份转录上并发刷写；按路由键加锁无法发现该冲突。
  7. 按会话ID加锁应在会话解析定型后、加载转录前获取，从而串行化整个“加载历史—运行—刷写”区间；竞争仅出现在真正共享会话ID的别名路径上，其余路径零竞争。
  8. 释放时校验所有权与运行代数，防止旧清理误释放新轮次；等待超时失败时开放释放，避免卡死会话；注册表有界且仅驱逐空闲项；压缩期间若会话ID发生轮换，则同一租约对象重新绑定。
  9. 该租约仅覆盖进程内；CLI与网关多进程共享同一会话是已知限制，需引入数据库级租约。
  10. 判断标准：被保护资源的属主与“路由键到属主”的映射是否多对一；若为多对一，则必须在解析定型后按属主（会话ID）加锁。

#### 8.2 缓存与状态存储

- 如何回溯 Agent 在哪一步走偏？完整对话存储会带来什么成本？
  1. 仅凭最终输出无法定位走偏步骤，需记录完整对话上下文（含工具调用与结果），方可重建模型每一步的所见信息。
  2. 完整持久化的成本在于磁盘占用随工具结果线性增长，且会话文件数量庞大、缺乏自动清理机制。
- 为什么选SQLite单行增量而不是JSONL追加或每轮全量写？
  1. JSONL 追加写入依赖锁机制协调并发，且无法支持历史数据查询；每轮全量写入则存在写放大问题。
  2. SQLite WAL 模式支持读写并发，且零外部依赖；单行增量写入使崩溃时最多丢失未提交的一条记录，并可通过 SQL 聚合查询会话数据。
  3. 代价是 Schema 版本治理与迁移脚本成为长期维护负担，当前版本号已迭代至 23，每次结构变更均需编写迁移脚本。
  4. 判断标准是并发写入者数量与历史数据查询需求的乘积：两者均低时文件存储即可满足，任一需求高则需引入数据库。
  5. SQLite 以单文件承载全部会话数据，具备事务原子性与并发读安全，适配 MCP 多客户端同时查询。
  6. JSONL 直接写路径免事务、无锁竞争，且可用标准文本工具处理，但并发读需额外加锁；选型判据为“读侧是否需要查询与并发 × 写侧是否单一追加者”。

- 高频调用场景下，如何设计缓存策略以减少LLM调用次数？
  1. 冷热分层缓存：高频固定问答、工具结果与配置信息设为热缓存长期常驻，低频任务不缓存节省空间。
  2. 语义缓存 + 精准缓存：精准匹配固定问题，语义匹配相似问题，双重兜底减少调用。
  3. 时效过期策略：按业务场景设置 TTL，动态过期刷新，避免陈旧数据。
  4. 主动更新 + 被动淘汰：知识库、规则变更时主动清空对应缓存，自动淘汰冗余失效缓存，保证数据一致性。
  5. 缓存击穿兜底：热点 Key 加互斥锁，避免瞬时大量穿透请求打爆 LLM 接口。

- 用户核心信息变更后，如何避免调用旧数据？
  1. 收货地址、手机号等核心信息变更后立即清空本地缓存。
  2. 每次工具调用前前置校验最新用户数据，同步刷新会话知识库上下文，全程杜绝旧数据调用。

- 用户高频重复提问，如何优化效率？
  1. 高频同类问题做语义缓存，同义问题直接复用历史结果，减少重复工具调用与知识检索。
  2. 设置定时刷新机制保证缓存时效性，兼顾响应速度与答案准确性。

- 多Agent协作中，如何避免重复检索、无效调用？
  1. 搭建多 Agent 共享缓存，同商品、同规则检索结果全局复用
  2. 语义去重拦截同类重复请求。
  3. 调度 Agent 统一分发任务，避免多 Agent 并行重复执行
  4. 大促热点商品数据预热缓存。

#### 8.4 系统架构

- 高并发服务设计
- 高并发场景下，Agent的核心性能瓶颈和隐形坑是什么？
  1. 显性瓶颈主要表现为Token消耗过高、单任务响应延迟增大以及工具调用排队拥堵。
  2. 隐性盲区包括并发场景下任务状态错乱、异步回调丢失、上下文复用冲突以及多任务记忆交叉干扰。
  3. 超时阈值设置不合理会导致静默失败，缺乏流量限流则可能引发服务雪崩。
  4. 解决方案包括任务状态隔离、异步独立调度、超时熔断、流量限流以及资源分片复用。
- 你的Agent是怎么应对高并发的？
  1. 计算真实负载：基于用户请求量、平均执行步数及每步扇出数估算下游调用量；需统计入口请求数、运行中任务数、模型Token吞吐与工具并发调用数，并对任务进行分级。
  2. 入口准入与背压：实施用户级与租户级限流，控制运行中任务数、Token预算及最大步骤数；使用有界队列，队列满时触发背压机制，设置优先级与截止时间。
  3. 长任务异步化：短任务采用同步流式返回，长任务通过消息队列异步执行；Worker无状态化，其状态与检查点存储于Redis或数据库中，支持任务取消、超时回收与断点续跑。
  4. 分层并发预算：为系统、租户、模型与工具设置多级并发预算；模型侧约束RPM、TPM、上下文长度与并发序列，工具侧使用独立连接池与Worker池。
  5. 资源隔离与状态一致性：采用隔舱模式隔离资源，为每个下游调用设置独立超时、熔断与有限重试；业务操作通过幂等键确保一致性。
  6. 过载降级：设计分级降级策略，包括缩短上下文、使用缓存、切换小模型、暂停低优先级任务，但不降级安全校验；基于多种信号触发并逐级恢复。
  7. 容量规划与可观测性：监控队列深度、Token吞吐、429比例及资源占用等关键指标；扩容绑定真实瓶颈，进行涵盖真实任务分布与故障注入的压力测试。
- 高并发企业场景，Agent如何保证决策稳定、不混乱？
  1. 任务隔离：多任务各自维护独立上下文、独立记忆与独立执行状态，从机制上杜绝交叉干扰。
  2. 优先级自主调度：根据任务紧急程度与权重自动排序执行，确保关键任务优先处理。
  3. 状态机管控：以标准化状态机约束任务流转，禁止无序执行与状态错乱。
  4. 限流熔断：突发高并发场景下自主降级与限流，优先保障核心任务稳定落地。
- 一个消息网关有30+平台同时进消息，同一段对话可能从多个入口进来，数据库里会话该怎么建模，才能让多平台的消息落成同一条主线而不是各记各的？
  1. 会话身份采用确定性路由键（平台/聊天类型/线程组合），通过路由键定型将多平台入口映射到稳定会话 ID，使同一对话收敛至单一会话主线。
  2. 路由键到会话 ID 为多对一映射：通过第二个聊天恢复命名会话、命令行续接、委派回指等别名键路径，不同路由键可指向同一会话。
  3. 数据库建模方面，会话表包含来源、路由键、父会话、结束原因、回退计数、交接状态、压缩冷却、归档标志等字段；消息表采用单行增量写入，附带软删除/压缩标志及 API 内容字节级保真旁路。
  4. 多平台并发写入通过 SQLite WAL 保证事务安全：消息在写事务内单行插入，会话级计数器同步更新，崩溃时仅丢失未提交的一条。

- 高并发企业办公场景，如何保障服务高可用？
  1. 资源隔离：多Agent沙箱独立运行，单任务故障不会扩散至全局。
  2. 容错自愈：支持断点续传、异常重试与故障实例替换，无需人工介入。
  3. 流量管控：通过限流、熔断与降级机制，有效抵御突发高并发冲击。
  4. 集群部署：多实例负载均衡，消除单点故障，保障7×24小时稳定运行。
- 如何实现多Agent系统的「灰度发布」，按用户/流量比例逐步启用新功能？
  1. 版本隔离：新旧版本 Agent 服务并行部署，独立运行、互不干扰。
  2. 流量灰度：按用户 ID、请求比例或场景维度分配流量，小比例放行新版本。
  3. 指标观测：实时监控新版本成功率、报错率与延迟，对比基线数据。
  4. 渐进放量 + 快速回滚：指标稳定逐步全量，出现异常立即切回旧版本，控制故障范围。
- 如何设计支持流式输出（SSE）的Agent框架？前端与后端如何配合？
  1. 后端层：基于 SSE 协议建立长连接，模型生成 Token 实时分片推送，工具调用、思考过程与异常信息同步流式返回。
  2. 数据分片规范：区分普通文本、工具调用与结束标记，结构化分片推送，避免前端解析混乱。
  3. 前端层：监听 SSE 长连接实时拼接渲染内容，监听结束标记关闭连接，异常自动重连。
  4. 异常处理：断连重连、超时兜底与流式中断收尾，保证用户体验完整。
- Agent服务如何部署到Kubernetes？无状态API层与有状态任务Worker如何分离？
  1. 无状态 API 层（Deployment）：负责接收请求、参数校验与路由分发，不存储任何任务状态，支持水平弹性扩容扛高并发。
  2. 有状态 Worker 层（StatefulSet）：负责任务执行、工具调用、状态持久化与断点续跑，独占任务状态保证执行唯一性。
  3. 消息队列解耦：API 层接收请求投递队列，Worker 消费执行，彻底隔离请求接入与任务计算。
- 什么是Agent Harness Engineering？与Prompt Engineering、Context Engineering的关系？
- Loop、Runtime、Sandbox 三者的嵌套关系？各层的职责边界？
  1. 嵌套关系呈现为三层结构：最外层为 Sandbox，中间层为 Runtime，最内层为 Agent Loop。
  2. 职责边界划分明确：Agent Loop 负责核心决策；Runtime 层负责工具校验、权限控制与记忆管理；Sandbox 层负责执行环境的隔离与资源限制。
- Runtime 和 Agent Loop 有什么区别？
  1. Agent Loop 作为决策层，负责确定‘做什么’；Runtime 作为基础设施层，负责执行‘怎么做’。
  2. Runtime 包含 LLM 管理、工具注册、记忆管理、执行调度与可观测性五层架构。
  1. 定义：支撑 Agent 上线运行的全套工程底座体系，包含调度、部署、监控、灰度、容错、版本管理与流水线。
  2. 三者层级递进：Prompt Engineering 最表层（优化指令话术）→ Context Engineering 中层（信息流转与上下文治理）→ Harness Engineering 底层底座（工程运维体系，支撑前两者稳定落地生产）。
  3. Harness 是生产级 Agent 的核心底座，提供原生托管运行架构。
  4. 支持会话状态持久化，故障后通过日志重放实现任务断点续传。
  5. 提供轻量化沙箱保障执行隔离，实现统一调度、资源管控与并发托管。
  6. 具备标准化异常重试与熔断兜底能力，解决崩溃丢失、状态错乱、无法自愈的痛点。
  7. Harness Engineering 源自 OpenAI 2026 年文章，指在 Agent-First 世界中，通过工程基础设施驾驭 AI 编写代码。
  8. 核心公式：Agent = Model + Harness，模型提供智能，Harness 将智能转化为生产力。
  9. 典型成效：3 人团队 5 个月用 AI Agent 编写超 100 万行代码、合并 1500 个 PR，效率提升约 10 倍。
- 为什么需要 Harness？
  1. 缺乏 Harness 支撑的 Vibe Coding 存在三大致命问题：架构混乱、上下文雪崩与可维护性丧失。
  2. Harness Engineering 通过提供安全边界、可观测性、可靠性与扩展性，有效解决上述失控问题。
- Harness 的 6 大支柱是什么？
  1. 六大核心支柱：上下文管理、工具系统、执行编排与多 Agent 协作、状态与记忆、评估与观测、约束与恢复。
  2. 在 Coding 场景中，每个支柱均有对应的工具与实践支撑，例如 AGENTS.md、MCP/Skills/知识库、SDD 工作流、Git+Memories、自动测试+AI CR、Rules+Safety。
- 第一阶段基础建设具体做什么？
  1. IDE 插件安装：VSCode 通过 Install from VSIX 安装插件；JetBrains 系列通过 Install Plugin from Disk 安装 zip 文件，注意无需解压。
  2. CLI 工具为可选安装，司内已集成多种 CLI 编程工具。
  3. 建立 team-harness 仓库作为规则与知识库的载体，并配置基础 Rules 与知识库。
- 实施路线图分哪几个阶段？
  1. 第一阶段为基础建设期（1~2周）：完成 Agent 工具链安装、团队 Harness 仓库搭建、基础 Rules 配置与知识库初始化。
  2. 第二阶段为工具接入期（2~4周）：完成 MCP 接入、Skills 沉淀，并跑通 Plan 模式下的 SDD 工作流。
  3. 第三阶段为持续优化期（长期）：建立度量看板、规范迭代机制与知识飞轮，支撑体系长效演进。
- AI Coding 一体化架构分哪几层？
  1. 从输入到度量的完整链路为：输入层 → 配置中心 → 模式引擎 → Agent 核心 → MCP 层 → 输出层 → 度量层。
  2. 数据流为：用户意图经输入层转化为结构化输入，配置中心加载约束，模式引擎选择策略，Agent 核心执行任务，MCP 层获取外部数据，输出层交付产物，度量层量化效果并反馈优化规范，形成闭环。
- 约束与恢复机制是什么？
  1. 三级约束机制：硬性红线（Rules）不可违反，如 API 必须添加 Swagger 注解；软性约束（Skills）推荐遵循；安全策略（Safety）提供兜底保护，如高风险操作前自动检测影响范围。
  2. 恢复机制：所有变更通过 Git 管理，可随时回滚；Spec Deltas 保证变更可追溯；编译失败时自动回退至稳定状态。
- 评估与观测分哪几层？
  1. 校验分四层：L1 语法（编译通过、Lint 检查）、L2 逻辑（单元测试通过）、L3 规范（符合 Rules 约束）、L4 架构（不破坏现有设计，人工+AI 联合审查）。
  2. 实际操作：引入 AI Code Review 进行合入前规范检查；代码完成后自动编译并自测；重大改动自动生成变更日志。
- Graph 的形式化组成是什么？
  1. 节点（V）：执行单元，一进一出，专注于单一职责，可为专用智能体或确定性步骤。
  2. 边（E）：节点间路由，决定执行流向，支持直通、条件分支、扇出/扇入与回环。
  3. 状态（S）：沿边流动的共享数据对象，供各节点读写，记录任务进度、证据、预算、产物与检查点。
  4. 策略（P）：约束节点创建、工具调用、图修改与副作用产生权限，相当于权限与审批规则。
- 验证器和路由在 Graph 中如何工作？
  1. Verifier 负责以独立视角专门审查最终结果，尝试推翻前序结论；校验通过则放行，否则打回重做。
  2. Router 承担分诊职能，按重要程度将任务路由至不同检查路径：普通观点快速核对，重要数据与安全结论进行多角度交叉审查。
  3. 验证策略包括对抗式（多个怀疑者分头驳斥结论）、多视角式（分别校验正确性、安全性与可复现性）以及评委制（对多个方案打分，并吸收亚军方案优点）。
- 为什么说 Graph 的核心价值是确定性？
  1. 图的杠杆效应不在于节点数量，而在于围绕最终结果构建了多少确定性；多数系统失败的根源在于模型既充当执行者又充当评判者。
  2. Graph 将“决策”与“验证”拆分为独立节点，由独立验证器基于全新上下文进行纠错，而非让执行者自我评判。
  3. 确定性工作交由代码处理：格式校验、测试运行、去重、排序、预算计算等均以普通代码实现；模型判断承载于节点上，代码可靠性承载于边上。
  4. 图必须贴近现实：若所有节点仅互相引用模型结论，而无任何节点触达真实世界，则无异于更大型的自嗨机器；硬锚点包括测试真实通过、资金真实到账、用户真实留存等。
- Anthropic 总结的五种工作流模式是什么？各适用于什么场景？
  1. Prompt Chaining（提示链）：当任务可清晰拆分为固定子任务时，以延迟换取准确率；每一步处理上一步的输出，并可设置检查点。
  2. Routing（路由）：输入类型多样时，先进行分类，再路由至对应的专用处理流程，避免单一提示词优化某类输入而拖累其他类型。
  3. Parallelization（并行化）：当子任务相互独立或需要多视角交叉验证时，并行执行后再汇总结果。
  4. Orchestrator-Workers（编排者-执行者模式）：当子任务无法预先确定时，由主智能体在运行时动态拆解任务、分派给执行者并汇总结果。
  5. Evaluator-Optimizer（评估-优化模式）：当存在明确评价标准且迭代可提升结果时，由一个生成器产出方案、一个评估器打分，循环迭代直至满足要求。
  6. Anthropic 尤为强调优先选择最简单方案：多数应用仅需单次模型调用、检索增强与少量示例即可解决，无需引入完整 Agent 或图工作流。
- 最常见的图编排拓扑有哪些？
  1. 菱形模式（扇出扇入）：将任务拆分为多个独立分支并行执行，再汇总合并，适用于并行信息搜集、评审与报告撰写。
  2. 主管模式（Orchestrator-Workers）：主智能体负责任务规划与分派，专职工人执行并返回结果，最终由主智能体汇总；Anthropic Research 即采用该模式。
  3. 流水线模式（Pipeline/Prompt Chaining）：按固定步骤串行执行，每一步处理上一步的输出，中间可插入程序化检查点。
  4. 三种拓扑可拼装嵌套，真实生产系统中通常为主管模式嵌套菱形、菱形内再嵌套流水线。
- Graph 与知识图谱、流程图有什么区别？
  1. 知识图谱用于组织系统所知晓的知识，Graph 用于描述系统的组成结构与工作流转关系。
  2. 流程图是面向人的描述性材料；Graph 是面向机器的可执行结构，要求节点具备独立执行能力，边携带明确状态，且整个过程可检查、可暂停、可恢复、可追踪。
- Loop 模式有哪些结构性缺陷？
  1. 上下文腐烂：所有轮次的思考、工具调用与观察结果均被塞入同一上下文窗口，原始目标逐渐被淹没，模型后期会反复针对自身输出进行低效分析。
  2. 错误级联：模型在同一条推理链中难以识别循环或跳出循环，遇到错误后反复重试，导致大量 Token 被无效消耗。
  3. 工具过载：单个智能体挂载 15～20 个工具时，工具选择的准确率会急剧下降。
  4. 缺乏控制粒度：无法暂停子任务等待审批，无法为不同步骤配置不同模型，也无法在中途进行独立质检。
  5. 可观测性差：只能看到思考内容与工具调用记录，无法判断分支选择原因，也无法定位导致最终错误的具体步骤。
  6. 目标失明：循环仅优化被赋予的指标，可能以违背指标初衷的方式推高指标，即古德哈特定律。
- Graph Engineering 在 AI 工程演进中处于哪一层？
  1. Agent 工程化能力可划分为五层：Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering、Graph Engineering，各层逐层外叠、依次递进。
  2. 各层职责明确：Prompt 层负责单次对话的措辞设计，Context 层决定向模型提供哪些信息，Harness 层管理工具调用、护栏与跨会话状态，Loop 层驱动单个智能体的自主循环，Graph 层组织多个执行节点的协作关系。
  3. Graph 层位于最外层，其设计与实现需在前四层均已完善的基础上展开。
- Graph Engineering 这个术语是怎么火起来的？它真的新吗？
  1. 2026 年 7 月，Peter Steinberger 发布关于“循环还是图”的推文，三天内累计 270 万浏览，“Graph Engineering”一词由此传播开来；该词诞生时并无新框架或新模型发布。
  2. 节点、边、状态、有向图调度等概念并非新事物，LangGraph、ADK、AutoGen 在该词出现前两年已在实际应用；真正变化的是工程重心从单个智能体行为上移至群体智能体的组织协调。
  3. 其本质是经典的组织管理命题：分工、权责划分、监督与执行分离及容错机制；AI 仅相当于更换了一批执行者，重新回答同一管理问题。
- Graph Engineering 有哪些真实生产案例？
  1. LinkedIn SQL Bot 采用路由机制判定数据域，将请求分派给领域专家智能体与 SQL 编写智能体，再由自纠错智能体重试修正，失败后升级至人工处理，查询准确率与用户满意度达 95%。
  2. Uber 代码迁移项目面对 5000 名工程师、上亿行代码，采用子图按语言/仓库分工，主管图负责整体协调并预先解决冲突，利用检查点机制应对中断，累计节省超过 21000 个工程小时。
  3. Anthropic Research 采用编排者-工作者模式，主智能体负责规划，子智能体并行搜索，内部评测显示该模式比单智能体效果提升 90.2%。
- 什么是 Graph Engineering？它和 Loop Engineering 有什么区别？
  1. Loop Engineering 将驱动循环交由 AI 自主完成：AI 自行观察环境、执行动作、校验结果并决策下一步，形成闭环直至目标达成；人类仅设定目标与验收标准。
  2. Graph Engineering 在 Loop 之上再外扩一层，解决如何将多个智能体、工具与人员组织为可观测、可恢复、可扩展的系统。
  3. 核心分工：Loop 负责让单个智能体持续工作，Graph 负责组织多个执行节点及其关联关系。
  4. Loop 在同一上下文中持续搜集、起草与自审，会导致上下文逐渐混杂、作者自我审查受限，且信源只能顺序读取。
  5. 采用三节点小图结构，让研究员节点并行扇出搜集信息并返回结构化笔记，写作节点仅基于干净笔记进行创作，审稿节点在全新上下文中独立审查，不合格则打回重写。
  6. 小图方案需要承担额外成本：维护多个提示词、设计节点间的状态结构，并处理漏信源、路由死循环、状态泄漏等新增失败模式。
  7. 决策标准：每日高频运行且对质量有要求的任务值得付出这些成本；仅运行一次的任务则完全是额外负担。
  8. 传统工作流将路径与节点固化为代码，稳定性强但缺乏动态应变能力；ReAct 范式由模型全程边推理边执行，灵活性高，但控制流混杂在对话记录中，难以复现、审计与管控。
  9. Graph 将稳定性与灵活性分层治理：边与整体结构固定，具备可治理性与可审计性；节点内部保留自主决策能力，以应对具体问题。
  10. Anthropic 将工作流定义为通过预定义代码路径编排的系统，智能体则是由 LLM 动态决定自身流程的系统；Graph 架构是两者的融合。
- 如何设计Agent的「配置中心」？包含模型、Prompt版本、工具开关、灰度策略等
  1. 模型配置：统一管理模型版本、温度、最大 Token 与接口地址，支持动态切换。
  2. Prompt 版本管理：存储多版本提示词，支持版本切换、回滚与对比。
  3. 工具权限开关：统一管控工具启用/禁用、权限与参数默认值。
  4. 灰度策略配置：在线配置流量比例、用户白名单与功能灰度规则，动态下发生效；全部支持动态生效，无需修改业务代码。
- Agent生产部署的核心挑战是什么？（延迟、并发、稳定性、成本）
  1. 延迟问题：模型推理、工具调用与长上下文导致响应耗时高，用户体验差。
  2. 并发问题：大模型推理算力受限，高并发场景容易排队、超时与阻塞。
  3. 稳定性问题：模型幻觉、接口超时、上下文污染与流程异常导致结果不可控。
  4. 成本问题：长 Token、多轮调用、向量检索与模型推理的算力与接口成本居高不下。
- 如何实现Agent的「版本管理」？Prompt迭代与工具定义变更如何管理？
  1. Prompt 版本化：每次话术迭代生成新版本，记录修改内容、时间与责任人，支持一键回滚与版本对比。
  2. 工具版本化：工具 Schema、入参逻辑与功能变更统一版本记录，避免更新后旧流程失效。
  3. 环境隔离：开发、测试、预发、生产环境版本隔离，灰度验证后再全量上线。
  4. 变更溯源：所有迭代留存日志，出现问题快速定位版本差异。
- 设计一个高并发Agent服务架构，包含负载均衡、缓存、异步队列等组件
  1. 接入层：Nginx 负载均衡 + 限流熔断，均匀分发流量、拦截恶意请求。
  2. 缓存层：Redis 缓存高频问答、模型结果与配置信息，减少重复推理，降本提速。
  3. 服务层：无状态 API 服务集群，弹性扩容，负责请求校验与路由。
  4. 队列层：消息队列异步解耦、削峰填谷，堆积高并发请求，避免服务雪崩。
  5. 任务计算层：独立 Worker 集群负责任务执行、工具调用与长流程推理，与接入层彻底解耦。
- 什么是云边端一体化部署？三者如何分工协同？
  1. 云端承担全局统筹职能，负责大模型推理、复杂任务规划、全局记忆存储、权限管控、数据汇总与模型迭代。
  2. 边缘节点承接云端下发的任务，执行就近数据处理、轻量化推理与本地设备调度，降低云端压力与交互延迟。
  3. 端侧部署于手机、IoT及终端设备，实现实时感知、本地简单执行与数据初步过滤，具备低延迟和离线可用能力。
  4. 三者联动模式为云端决策、边缘调度、端侧执行。
- 端云协同场景下，最容易出现的同步问题是什么？如何解决？
  1. 高频问题包括任务状态异步错乱、新旧数据相互覆盖、指令重复下发、离线数据丢失以及多端记忆冲突。
  2. 通过统一全局任务ID，实现多端状态的精准对齐。
  3. 离线任务在本地缓存，联网后通过增量同步与有序回放完成状态合并。
  4. 采用时序版本管控，确保新数据覆盖旧数据；由云端统一调度指令，避免多端自主执行引发冲突。
- IoT物联网场景下，端侧Agent如何落地？解决什么核心问题？
  1. 解决四大核心问题：海量设备指令全部上云导致带宽拥堵与高延迟、设备离线时无法工作、原始数据上云存在隐私泄露风险、传统设备缺乏自主判断能力。
  2. 落地方式：在端侧本地完成数据过滤、异常判断与简单调度，仅将核心有效数据及异常事件上报云端。
  3. 实现轻量化、高安全、低延迟的运维体系。
- 端侧Agent相比云端Agent，核心优缺点分别是什么？
  1. 端侧部署优势：超低执行延迟，支持离线运行，原始数据不上云可提升隐私安全性，同时节省云端算力成本。
  2. 端侧部署局限：设备算力有限，难以承载复杂大模型推理与复杂任务规划，存储与迭代能力弱于云端。
  3. 适配策略：简单实时、隐私敏感任务部署于端侧，复杂推理、全局调度与模型迭代部署于云端，通过云边协同互补短板。
- 如何解决端侧Agent算力不足、推理精度低的问题？
  1. 模型轻量化：适配昇腾端侧芯片，通过模型裁剪、量化与蒸馏实现降载。
  2. 任务分层：简单推理与实时判断保留在端侧，复杂高精度推理任务上云处理。
  3. 边缘节点承接中端算力任务，有效分担中心侧压力。
  4. 缓存复用：高频固定推理结果在本地缓存，重复场景直接复用，减少重复计算。

- 高并发流量峰值场景，如何稳控流量？
  1. 策略分级降级：峰值时刻简化复杂个性化推理，优先保障核心流量分发稳定。
  2. 热点流量定向调控：集中算力保障官方热点与优质内容分发，避免流量拥堵错乱。
  3. 用户分层保障：优先保障高价值用户体验，均衡普通用户流量分配
  4. 缓存预热：提前预热高频优质内容与热门兴趣标签，降低峰值推理压力。
  5. 立即执行优先级调度：优先商品检索、下单链路，延后数据分析、日志统计等非核心任务。
  6. 开启资源隔离防止单类任务堆积拖垮集群
  7. 非核心功能灰度降级、请求合并、流量削峰。
  8. 超时任务快速止损、重试熔断，杜绝任务堆积雪崩。
  9. 限流：按 Agent 类型、用户维度、接口维度设置并发上限，拦截超额请求。
  10. 熔断：接口错误率超标自动熔断，停止无效调用防连锁崩盘
  11. 降级：非核心功能降级，优先保障检索、推流、下单主链路。
  12. 排队削峰：超额任务有序排队、延时处理，避免瞬时打爆集群。

- 从0设计一套业务推荐Agent，完整落地架构？
  1. 多源感知输入层：实时采集用户行为、内容特征、场景时段、热点舆情、账号权重多维数据。
  2. 智能理解解析层：大模型语义解析用户隐性兴趣、内容核心价值与场景适配度，突破标签匹配局限。
  3. 业务决策核心层：个性化匹配、去同质化、热点调控、冷热流量平衡、内容优劣筛选，输出最优分发策略。
  4. 流量执行分发层：对接流量中台，完成短视频、直播、电商内容的千人千面精准推送。
  5. 风险兜底层：联动风控体系，拦截违规低质内容、规避流量乱象、防止用户体验恶化。
  6. 数据迭代闭环层：全链路采集效果数据，自主归因复盘、优化决策策略，实现「分发-效果-优化」持续闭环。
  7. 核心理念：以用户体验为基础、以业务指标为目标、以智能迭代为核心、以风险防控为兜底。

- 稳定型业务Agent核心架构？
  1. 前置校验层：统一校验参数、权限、调用频次，从源头拦截无效错误请求。
  2. 工具调用层：整合重试、幂等、限流机制，保障接口调用稳定安全。
  3. 异常处理层：分类处理各类异常，实现智能降级、优雅兜底。
  4. 知识协同层：落实数据优先级，自动校验、修复多库冲突问题。
  5. 自愈迭代层：全链路日志埋点，复盘高频问题，持续优化系统稳定性。

- 多Agent集群调度的三大核心原则是什么？
  1. 优先级优先：搜广推、商品检索核心链路优先占用资源。
  2. 资源隔离：不同 Agent 任务资源互不抢占，避免全域崩盘。
  3. 渐进降级：峰值时非核心功能降级，保障主链路高可用。

- 多Agent资源抢占严重，如何实现资源均衡？
  1. 调度 Agent 统一管控：设置各 Agent 算力配额、缓存配额与最大并发上限。
  2. 核心链路配额倾斜保障、非核心链路动态缩容
  3. 实时监控资源占用，超限自动限流、排队。

- 电商大促多Agent与长文本RAG协同落地架构？
  1. 流量感知层：实时监控大促流量峰值、请求量级、热点商品分布，预判并发压力。
  2. 任务调度层：调度 Agent 统一分配算力，区分优先级、资源隔离、动态配额，解决大促资源冲突。
  3. 长文本检索层：电商专属语义切片、结构化提纯、双层召回、精准精排，适配超长商品文本。
  4. 幻觉治理层：风控 Agent 全局校验、溯源比对、参数纠错，杜绝价格、活动、售后虚假信息。
  5. 高防防护层：限流、熔断、降级、缓存预热四重防护，保障大促集群不雪崩。
  6. 迭代自愈层：沉淀大促错题、检索失败案例、冲突数据，持续优化调度与检索策略。
  7. 核心思想：以大促高并发稳定为基础、以商品检索精准为核心，解决多 Agent 冲突与 RAG 幻觉两大痛点。

- 高峰期响应卡顿、推理耗时波动大，如何全链路优化？
  1. 缓存优化：高频问题、通用结果、常用工具返回值预热缓存，减少重复推理。
  2. 队列削峰：请求排队限流，瞬时流量削峰避免打爆集群
  3. 服务降级：高峰期降级非核心能力，集中资源保障对话与核心任务。
  4. 推理优化：动态批处理、轻量化推理，稳定模型耗时。

#### 8.5 服务生命周期与性能排查

- systemd 服务重启慢如何排查？
  1. 使用 journalctl 查看系统日志，定位时间消耗发生在服务停止阶段还是启动阶段。
  2. 通过调整 TimeoutStopSec 参数，优化旧进程不响应 SIGTERM 导致的停止等待耗时。
  3. 使用 cProfile 进行性能分析，并结合子进程冷启动隔离测量，定位启动阶段的代码热点。
  4. 排查是否存在外部网络调用，并通过代理或磁盘缓存进行优化。
- systemd 的 TimeoutStopSec 参数有什么作用？
  1. 指定 systemd 发送 SIGTERM 后等待服务退出的时间，超时后发送 SIGKILL 强制终止。
  2. 原配置为 90 秒，因旧进程不响应 SIGTERM 导致等待过久，修改为 5 秒后停止阶段明显缩短。
  3. 修改配置文件后，需执行 systemctl daemon-reload 使配置生效。
- 服务收到 SIGTERM 后为什么没有立即退出？
  1. 进程内 API 429 重试线程处于 120 秒 sleep 状态，导致 SIGTERM 信号被忽略。
  2. 后台任务需及时响应退出信号，避免长时间 sleep 阻塞进程退出。
- 无外部控制通道、用“标记文件 + 实例纪元”做排空契约，代价在哪？什么场景下不成立？
  1. 运维面板通过写入排空标记文件下发指令，后台监视器周期性读取该文件；当检测到带有当前实例纪元的标记时，即切换为排空状态，拒绝接收新轮次；删除标记则取消排空。
  2. 纪元由内核启动时间与1号进程启动时间组合生成：重启机器会更换纪元，使旧标记自动失效；仅重启网关进程时纪元不变，在途排空操作继续生效。
  3. 代价：文件轮询存在响应延迟；契约演化需双向兼容；损坏的标记被刻意视为“排空生效”，以宁可多排空也不放行；面板无法查看实时状态，只能通过状态文件反推。
  4. 正面价值：不开放控制端口，将生命周期攻击面降至零；“存在即状态”使取消操作天然幂等；纪元的本质是为持久存储上的指令增加时效维度。
  5. 不成立场景：多实例部署下标记文件属于单进程契约，两个实例共享同一文件会互相干扰，需另行设计数据库级租约。
- 如何用 cProfile 定位 Python 服务的启动热点？
  1. 使用 cProfile 进行冷启动测试，分阶段统计 import、config、skill sync、MCP discovery、import runner 等环节的耗时。
  2. 结合子进程冷启动方式，排除环境干扰，精确定位耗时模块。
- 如何解决首次请求触发的外部网络调用导致响应慢？
  1. 通过代理加速外部 API 请求，例如 GitHub API 请求耗时由 9-10 秒降至 0.31 秒。
  2. 复用现有缓存逻辑，将模型列表持久化至 models_cache.json 文件，重启后直接读取，避免重复发起网络请求。

#### 8.6 日志管理与轮转

- logrotate 如何配置日志轮转？
  1. 关键配置项：daily 按天触发切割，rotate 7 保留 7 份历史日志，maxsize 10M 限制单文件最大 10MB，copytruncate 采用复制后清空原文件，olddir 指定归档目录，dateext 添加日期后缀。
  2. 通过 cron 定时执行 logrotate，可将日志文件从 38MB 切割为 135 字节。

#### 8.7 多平台消息网关的会话状态链

- 如何为多平台消息网关维护会话身份→对话流持久化→执行串行化→崩溃续接的完整状态链，让每条消息都落盘、每个会话都不并发、每次重启都不打断对话？
  1. 该状态链包含四个环节：多平台消息到会话的确定性路由、SQLite WAL持久化、基于会话ID的轮次租约，以及崩溃后的自动续接。
  2. 会话身份通过确定性路由键（平台/聊天类型/线程组合）完成多对一映射，确保同一段对话从多个入口进入时落在同一条会话上。
  3. 持久化采用SQLite WAL，消息以单行增量写入，工具执行完毕后立即落盘；事务提交后崩溃仅丢失未提交事务，满足每条消息均落盘的要求。
  4. 并发纪律按会话ID获取进程内轮次租约，串行化“加载历史—运行—刷写”区间；释放时校验所有权与运行代数，等待超时则开放失败，注册表有界且仅驱逐空闲项。
  5. 崩溃恢复依赖优雅关闭时写入的待续接标记，重启后由恢复调度器预加载，经新鲜度门检查后自动续接，或按新对话处理。

### 09 Agent 通信协议

> 本章回答「双方如何通信」，沿用四层模型：序列化层（数据如何编码）→ 传输层（消息如何传输）→ 调用绑定层（调用如何表示）→ 应用语义层（双方交流什么）。
>
> 与相邻章节的边界：MCP 的协议机制在本章，工具侧的职责边界在 02.4；A2A 的协议机制在本章，协作业务在 03；传输通道的通信视角在本章，系统设计视角在 08。

#### 9.1 整体分层

```text
Agent-Communication
├── 应用语义层：通信双方交换什么业务语义
├── 调用绑定层：如何表示方法、请求、响应和错误
├── 传输层：消息通过什么通道传递
└── 序列化层：数据编码成什么格式
```

应用语义层解决的是“双方在交流什么”。比如 MCP 规定 Agent 如何发现和调用工具，A2A 规定 Agent 之间如何委派任务。调用绑定层解决的是“这次调用如何表达”，例如方法名、参数、结果和错误。传输层解决的是“消息通过什么通道传递”，例如 HTTP、SSE 和 WebSocket。序列化层解决的是“数据最终编码成什么形式”，例如 JSON 和 Protobuf。

#### 9.2 序列化层

序列化层位于整个通信体系的最底层，负责把程序内存中的对象转换成可以传输或存储的文本或二进制数据。

```
序列化层
├── JSON
├── Protobuf
├── NDJSON
├── MessagePack
├── CBOR
├── multipart/form-data
└── Base64
```

##### 1. JSON

JSON 是 Agent 系统中最常见的文本序列化格式。它支持对象、数组、字符串、数字、布尔值和 null，几乎所有编程语言都可以直接解析。

JSON 最大的优点是可读性强、调试方便、跨语言能力好。开发人员可以直接在日志、浏览器开发工具或命令行中查看消息内容。因此，MCP、ACP、AG-UI 和 A2A 的很多实现都使用 JSON。

JSON 的不足是**消息体积相对较大**。因为每条消息都会重复携带字段名称，同时 JSON 的类型约束比较弱，服务端通常还需要使用 **JSON Schema、Pydantic** 或其他机制校验字段类型。

JSON 不原生支持二进制数据。传输图片、音频或文件时，通常需要使用 Base64、multipart/form-data，或者在 JSON 中只传递文件 URL。

##### 2. Protobuf

Protobuf 协议缓冲区 是一种基于 Schema 的二进制序列化格式。开发者需要先通过 `.proto` 文件定义消息结构、字段编号和字段类型，再生成不同编程语言的代码。

Protobuf 使用字段编号而不是完整字段名进行编码，因此消息体积通常比 JSON 更小，序列化和反序列化性能也更高。字段类型由 Schema 明确定义，所以类型约束比 JSON 更强。

Protobuf 还支持接口演进。只要保留已有字段编号，新增字段通常不会导致旧版本完全无法解析新消息。

gRPC 默认使用 Protobuf，因此常见的组合是：

```
Protobuf
→ HTTP/2
→ gRPC
```

Protobuf 更适合内部高性能服务和跨语言 RPC，但它不方便直接阅读，需要维护 `.proto` 文件和生成代码，临时调试没有 JSON 灵活。

##### 3. NDJSON

NDJSON 是 Newline Delimited JSON，也就是每一行表示一个完整的 JSON 对象，不同对象之间使用换行符分隔。

```
{"type":"token","data":"Hello"}
{"type":"tool_call","name":"search"}
{"type":"finished","status":"success"}
```

NDJSON 适合日志、事件流和管道通信。接收方读取到一行后就可以立即解析，不需要等待一个完整 JSON 数组传输结束。

NDJSON 主要解决连续多个 JSON 对象之间如何划分消息边界的问题。它不规定这些对象具有什么业务含义，也不规定请求和响应如何匹配。

因此，NDJSON 属于序列化和消息分帧形式，不属于 MCP、A2A 或 JSON-RPC 这样的应用和调用协议。

##### 4. MessagePack

MessagePack 是一种二进制对象序列化格式，它的数据模型与 JSON 比较接近，支持对象、数组、字符串、数字和布尔值，同时原生支持二进制数据。

与 JSON 相比，MessagePack 不需要把所有内容表示为可读文本，因此消息体积通常更小，适合高频内部通信和带宽敏感场景。

MessagePack 不要求预先定义 Schema，因此比 Protobuf 更灵活，但它也缺少 Protobuf 的强类型约束、接口生成和跨版本治理能力。

可以把 MessagePack 理解为一种紧凑的二进制 JSON。它在开放 Agent 协议中的普及程度不如 JSON 和 Protobuf，但适合内部事件通信。

##### 5. CBOR

CBOR 是一种可扩展的二进制对象格式。它的数据模型与 JSON 相似，但原生支持字节串、整数、浮点数、数组、Map 和语义标签。

CBOR 不要求预先定义 Schema，所以比 Protobuf 更灵活；同时它采用二进制编码，消息体积通常又比 JSON 更小。

CBOR 的语义标签可以表示日期、大整数或其他扩展类型，因此在 IoT、边缘设备和资源受限环境中比较常见。

在通用 Agent 平台中，CBOR 的使用范围通常不如 JSON 和 Protobuf，但在设备 Agent 和受限网络环境中具有优势。

##### 6. multipart/form-data

multipart/form-data 是一种在同一个 HTTP 请求体中封装多个数据部分的格式。每个部分通过 Boundary 分隔，并且可以拥有独立的名称、Header 和 Content-Type。

它适合同时传输用户 Prompt、JSON 元数据、图片、音频和附件。例如多模态 Agent 可以把文本参数作为普通字段，把图片和文件作为二进制部分上传。

与把整个文件转换成 Base64 再放入 JSON 相比，multipart/form-data 通常更加高效，也不会产生 Base64 的额外体积开销。

它更准确地说是一种复合 HTTP 消息体格式，而不是通用对象序列化协议，但在 Agent 的文件上传和多模态输入中非常常见。

##### 7. Base64

Base64 是把二进制数据转换成可打印文本的编码方式。它不是加密算法，也不是完整的序列化协议。

Base64 常用于在 JSON 中嵌入小型图片、音频片段、文件内容或二进制 Token。因为编码结果是普通文本，所以可以通过只支持文本的通道传输。

Base64 会增加数据体积，并产生额外的编码和解码开销，因此不适合传输大型文件。大型文件更适合使用 multipart/form-data、对象存储 URL 或原生二进制通道。

Base64 只解决二进制数据如何表示成文本的问题，不提供机密性、完整性或身份认证能力。

#### 9.3 传输层

传输层负责将序列化后的消息从一端发送到另一端。这里的传输层是 Agent 工程中的承载通道层，不完全等同于 OSI 网络模型中的传输层。

```
传输层
├── HTTP / HTTPS
├── SSE
├── WebSocket
├── WebRTC
├── stdio
├── Webhook
└── Message Queue
```

##### 1. HTTP / HTTPS

HTTP 是最常见的请求响应协议。客户端发送请求，服务端处理后返回响应。请求通常由方法、URL、Header 和 Body 组成，响应通常由状态码、Header 和 Body 组成。

HTTPS 是运行在 TLS 之上的 HTTP，它提供传输加密、完整性保护和服务端身份认证。生产环境中的模型调用、远程 MCP、A2A 和 Agent API 通常都应该使用 HTTPS。

HTTP 适合发送用户消息、创建任务、查询状态、提交审批和上传文件。它本身主要采用请求响应模式，如果 Agent 需要持续返回 Token，一般会在 HTTP 连接上使用 SSE；如果需要高频双向通信，则可以使用 WebSocket。

HTTP/2 引入了二进制帧、多路复用和流控制，也是 gRPC 常用的底层承载方式。HTTP/3 则运行在 QUIC 上，可以进一步改善多路流传输。

##### 2. SSE

SSE 是基于 HTTP 的服务端事件流。客户端建立一个 HTTP 长连接，服务端将响应类型设置为 `text/event-stream`，然后持续向客户端发送文本事件。

SSE 的主要通信方向是服务端到客户端，因此非常适合 Agent 的 Token Streaming。除了 Token，服务端还可以通过 SSE 推送工具调用状态、任务进度、Subagent 状态和最终结果。

普通文本 Agent 经常采用下面的通信方式：

```
客户端 ── HTTP POST ──→ 提交任务
客户端 ←── SSE Stream ── 返回 Token 和状态
```

如果客户端需要中断任务、批准工具调用或补充信息，一般通过额外的 HTTP 请求提交。因此，SSE 连接本身主要负责服务端向客户端推送，但整个系统仍然可以实现双向业务交互。

SSE 的优点是实现简单、基于标准 HTTP、容易经过网关和反向代理，并且支持断线重连。缺点是缺少真正的全双工能力，不适合大量高频的客户端上行事件。

##### 3. WebSocket

WebSocket 是全双工长连接协议。连接建立后，客户端和服务端都可以随时主动发送消息，不需要为每条消息重新建立 HTTP 请求。

在 Agent 系统中，WebSocket 可以在一条连接上同时承载用户消息、Token 输出、工具调用、审批结果、中断指令、任务状态和设备控制。

WebSocket 适合高频双向交互。例如语音 Agent 需要客户端持续上传音频，服务端持续返回音频，并支持用户随时打断；远程设备 Agent 也可能需要服务端主动发送命令，设备实时返回状态。

WebSocket 的能力比 SSE 更强，但工程复杂度也更高。服务端需要处理心跳、断线重连、消息顺序、连接状态、负载均衡和水平扩展。

因此，普通文本 Agent 一般优先使用 HTTP 加 SSE；需要高频双向控制、实时语音或设备通信时，更适合使用 WebSocket。

##### 4. WebRTC

WebRTC 是面向低延迟实时音频、视频和数据通信的技术体系，主要用于浏览器、客户端和设备之间的实时媒体传输。

在语音 Agent 中，用户音频需要持续发送给服务端或实时模型，Agent 生成的音频也需要持续返回，同时还要支持用户实时打断。WebRTC 在低延迟音频通信方面通常比普通 HTTP 更合适。

WebRTC 支持音频和视频 Track，也支持通过 DataChannel 传输普通数据。它还会使用 ICE、STUN 和 TURN 处理网络发现、NAT 穿透和流量中继。

WebRTC 本身不负责最初的信令交换。客户端和服务端仍需要通过 HTTP 或 WebSocket 交换 SDP 和网络候选信息。

因此，WebRTC 主要负责实时媒体传输，HTTP 或 WebSocket 通常负责认证、会话创建和信令交换。

##### 5. stdio

stdio 是标准输入和标准输出的简称。宿主程序可以启动一个子进程，通过 stdin 向子进程发送请求，通过 stdout 读取子进程返回的响应。

这种通信方式不需要开放网络端口，也不需要单独运行远程服务，因此非常适合本地 MCP Server、Coding Agent、CLI 工具和插件进程。

使用 JSON-RPC over stdio 时，stdout 应当只输出协议消息，普通日志应该写入 stderr。否则日志可能与 JSON-RPC 消息混合，导致消息解析失败。

stdio 的优势是部署简单、攻击面较小，并且子进程生命周期可以由宿主程序统一管理。它的局限是主要适合本机父子进程，不适合直接跨机器通信。

##### 6. Webhook

Webhook 是一种基于 HTTP 的异步回调模式。调用方先向服务端提供回调地址，当任务完成或状态发生变化时，服务端主动向该地址发送 HTTP 请求。

Webhook 适合耗时较长的 Agent 任务。客户端不需要一直保持 SSE 或 WebSocket 连接，也不需要不断轮询任务状态，服务端完成任务后可以主动通知调用方。

Webhook 与轮询的区别是：

```
轮询：客户端不断询问任务是否完成
Webhook：服务端在状态变化后主动通知客户端
```

生产环境中的 Webhook 需要处理签名校验、幂等、重复通知、事件乱序、失败重试和重放攻击。

调用方不能假设一个事件只会收到一次，而应该使用事件 ID 或业务 ID 保证重复通知不会导致业务被重复执行。

##### 7. Message Queue

Message Queue 是异步消息通信机制。生产者把任务或事件发送到 Broker、Topic、Queue 或 Subject，消费者可以在之后读取和处理，双方不需要同时在线。

在 Agent 系统中，消息队列适合任务调度、长任务执行、Subagent 分发、事件总线和失败重试。例如 Gateway 收到任务后，可以把任务写入队列，由空闲的 Agent Worker 消费执行。

消息队列能够实现异步解耦和削峰填谷。如果 Agent Worker 暂时不可用，任务可以先保存在队列中，等服务恢复后再继续处理。

常见系统包括 Kafka、RabbitMQ、NATS 和 Redis Streams。它们在消息持久化、顺序、消费者组、确认机制和吞吐量方面各有侧重。

使用消息队列时还需要处理重复消费、消息确认、死信队列、顺序保证和最终一致性。消费者通常需要实现幂等，避免同一任务被重复执行。

#### 9.4 调用绑定层

调用绑定层建立在序列化层和传输层之上，负责规定一次调用如何表示，包括调用哪个方法、传入哪些参数、如何关联请求和响应、结果如何返回以及错误如何表示。

```
调用绑定层
├── REST
├── JSON-RPC
├── gRPC
└── GraphQL
```

##### 1. REST

REST 是一种以资源为中心的接口设计风格。它通常使用 URL 表示资源，使用 HTTP 方法表示操作。

例如，GET 用于查询资源，POST 用于创建资源或执行操作，PATCH 用于部分更新，DELETE 用于删除资源。

REST 通常复用 HTTP 状态码表示调用结果，例如 `200` 表示成功，`400` 表示请求错误，`404` 表示资源不存在，`500` 表示服务端异常。请求和响应一般使用 JSON，但 REST 本身并不限定必须使用 JSON。

在 Agent 系统中，REST 适合任务创建、任务查询、Session 管理、文件上传和审批提交。例如可以使用 `POST /tasks` 创建 Agent 任务，再使用 `GET /tasks/{id}` 查询任务状态。

REST 的优点是简单、通用、容易调试，也容易经过 API Gateway 和负载均衡器。它主要适合请求响应场景，持续流式输出一般还需要结合 SSE，双向实时通信则通常结合 WebSocket。

##### 2. JSON-RPC

JSON-RPC 是一种轻量级远程过程调用协议。它不围绕资源组织接口，而是直接表达调用哪个方法。

一个 JSON-RPC 请求通常包含：

```
jsonrpc：协议版本
method：方法名称
params：调用参数
id：请求标识
```

调用成功时返回 result，失败时返回 error。id 用于匹配请求与响应。

如果一条消息没有 id，它通常表示 Notification，即发送方只通知接收方发生了某件事情，不要求返回结果。这种机制适合状态更新和事件通知。

JSON-RPC 与传输方式无关，可以运行在 stdio、HTTP、WebSocket 或其他消息通道上。MCP 和 ACP 使用 JSON-RPC，是因为它既支持普通请求响应，也支持通知和双向调用。

JSON-RPC 和 JSON 不是同一层概念。JSON-RPC 定义请求、响应和错误的消息结构，JSON 负责把这些结构编码成文本。

##### 3. gRPC

gRPC 是一种高性能、强类型的远程过程调用框架。开发者通常通过 `.proto` 文件定义 Service、Method、Request 和 Response，再生成不同语言的客户端和服务端代码。

gRPC 默认使用 Protobuf 进行序列化，并通常运行在 HTTP/2 上。它支持四种调用模式：

```
Unary：单请求、单响应
Server Streaming：单请求、多响应
Client Streaming：多请求、单响应
Bidirectional Streaming：双向持续通信
```

服务端流适合客户端提交一次请求后，服务端持续返回任务状态或增量结果。双向流适合客户端和服务端同时持续发送消息。

gRPC 的优势是类型明确、消息体积小、性能较高，并且原生支持超时、取消、Metadata 和标准错误码。它比较适合 Agent 平台内部的微服务通信和高吞吐 A2A 服务。

它的不足是消息不如 JSON 直观，需要维护 `.proto` 文件并生成代码，浏览器和人工调试也没有 HTTP+JSON 方便。

##### 4. GraphQL

GraphQL 是一种基于 Schema 的查询语言和服务执行模型。客户端可以明确声明需要哪些字段，服务端只返回这些字段。

GraphQL 主要包括：

```
Query：读取数据
Mutation：修改数据
Subscription：持续订阅事件
```

GraphQL 适合复杂 Agent 平台的数据聚合查询。例如管理页面可能同时需要任务信息、Session、用户信息、成本指标和日志摘要，前端可以通过一次 GraphQL 查询获取需要的数据。

GraphQL 一般不直接驱动 Agent Loop，因为 Agent Loop 会产生大量文本增量、工具调用和状态事件。这些实时事件通常仍通过 SSE 或 WebSocket 传输。

因此，GraphQL 在 Agent 系统中更适合作为控制面和管理平台的数据查询接口。

#### 9.5 应用语义层

应用语义层位于整个通信体系的最上层，负责定义通信双方分别是什么角色、可以交换哪些业务对象、对象具有什么状态，以及整个交互流程遵循什么规则。

```
应用语义层
├── AG-UI：Frontend ↔ Agent
├── ACP：Editor / IDE ↔ Coding Agent
├── MCP：Agent ↔ Tool / Context
└── A2A：Agent ↔ Agent
```

##### 1. AG-UI

AG-UI 是前端应用与 Agent Runtime 之间的交互协议，主要解决 Agent 前端与后端之间缺少统一事件模型的问题。

普通聊天接口只需要传递用户消息和最终文本，但 Agent 执行过程中还会产生运行开始、文本增量、工具调用、工具结果、状态变化、人工审批和运行结束等事件。

AG-UI 将这些过程定义成标准事件。前端收到文本增量事件后可以逐步渲染答案，收到工具调用事件后可以展示 Agent 正在执行什么操作，收到状态更新后可以显示任务进度，收到审批事件后可以向用户展示确认界面。

AG-UI 规定的是事件分别具有什么业务含义，但不强制使用哪种传输方式。同一套 AG-UI 事件可以通过 SSE 传输，也可以通过 WebSocket 传输。

因此，AG-UI 解决的是前端如何理解 Agent 的运行过程，而 SSE 和 WebSocket 解决的是这些事件如何发送到前端。

##### 2. ACP

ACP 是编辑器或 IDE 与 Coding Agent 之间的交互协议。它的目标类似于 LSP：编辑器实现一次 ACP，就可以接入多个 Coding Agent；Coding Agent 实现一次 ACP，也可以接入多个编辑器。

Coding Agent 的交互不仅包含聊天消息，还包括读取文件、修改代码、展示 Diff、执行终端命令、返回执行进度和请求用户授权。

因此，ACP 定义的是一套面向软件开发场景的 Agent 交互语义。

本地环境中，通常由编辑器启动 Coding Agent 子进程，再通过 stdio 通信。ACP 一般使用 JSON-RPC 表示请求、响应和通知，数据采用 JSON 编码。

典型组合是：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

ACP 与 MCP 的区别在于，ACP 的通信双方是编辑器和 Coding Agent，关注的是会话、代码、终端和权限；MCP 的通信双方是 Agent 和外部能力服务，关注的是工具和数据访问。

##### 3. MCP

MCP 是 Agent 与外部工具、数据和上下文服务之间的标准协议，主要解决工具接入方式不统一的问题。

如果没有 MCP，不同 Agent 框架需要分别为文件系统、数据库、搜索引擎、GitHub 和各种企业服务开发专用连接器。

MCP 采用 Client-Server 模型。MCP Server 对外暴露能力，MCP Client 连接 Server、发现能力并发起调用。

MCP Server 通常可以提供：

```
Tool：可以执行的动作
Resource：可以读取的数据
Prompt：可以复用的提示模板
```

MCP 使用 JSON-RPC 表示请求、响应和通知，数据使用 JSON 编码。本地 MCP Server 一般通过 stdio 通信，远程 MCP Server 一般通过 Streamable HTTP 通信。

完整链路可以表示为：

```
JSON
→ stdio / Streamable HTTP
→ JSON-RPC
→ MCP
```

MCP 本质上是标准化能力调用协议。Agent 通常会发现工具名称、描述和参数，然后像调用结构化函数一样调用它。

因此，MCP 解决的是 Agent 如何连接和调用外部能力，而不是两个自主 Agent 如何协作。

##### 4. A2A

A2A 是独立 Agent 系统之间的通信和协作协议，适合跨框架、跨语言、跨服务甚至跨企业的 Agent 互操作。

A2A 的核心思想是黑盒协作。调用方不需要知道另一个 Agent 内部使用什么模型、Prompt、Memory 和 Tool，只需要知道这个 Agent 具有什么能力、如何提交任务、如何获取状态以及如何接收产物。

A2A 的核心对象包括：

```
Agent Card：描述 Agent 身份、能力、接口和认证方式
Message：Agent 之间交换的信息
Task：具有生命周期的任务
Part：消息或产物的内容单元
Artifact：任务生成的文档、代码或结构化结果
```

A2A 与普通工具调用不同。工具调用通常是传入确定参数并等待结果，而 A2A 面向的是一个具有自主能力的 Agent。

被调用 Agent 可以自己拆分任务、调用多个工具、运行较长时间，甚至在执行过程中请求调用方补充输入或完成授权。

因此，A2A 不仅定义任务提交，还需要定义任务状态、流式更新、取消、失败、补充输入和产物返回等语义。

A2A 可以采用多种底层组合：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

或者：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

##### 5. MCP 与 A2A

MCP 与 A2A 最核心的区别是，MCP 面向能力调用，A2A 面向任务委派。

通过 MCP 调用工具时，Agent 通常明确知道调用哪个工具、需要传入哪些参数，以及大致会返回什么结果。例如，Agent 调用搜索工具并传入查询条件，工具直接返回搜索结果。

通过 A2A 调用另一个 Agent 时，调用方通常只描述目标，不规定具体执行步骤。例如主 Agent 可以把“调研新能源汽车行业并生成报告”委派给 Research Agent，Research Agent 自己决定如何规划、搜索、整理和生成报告。

```
Main Agent
└── A2A → Research Agent
               ├── MCP → Search Tool
               ├── MCP → Database
               └── MCP → File System
```

因此，二者可以概括为：

```
MCP：Agent 调用一个能力
A2A：Agent 委派一个任务
```

- MCP 工具调用的幂等性如何设计？
  1. 幂等性保证相同请求重复执行时仅生效一次且结果一致，避免重复扣费或写入等副作用。
  2. 采用唯一 request_id 作为幂等键，服务器据此去重；对已处理请求直接返回缓存结果。
  3. 幂等键及其结果需持久化存储（如 Redis 或数据库），并设置过期时间以管理存储增长。
  4. 重试时复用相同 request_id，确保重试不产生额外副作用。

#### 9.6 典型协议组合

##### 1. AG-UI

AG-UI 定义前端与 Agent Runtime 之间的文本增量、工具调用、工具结果、状态更新和运行生命周期。

这些事件可以通过 SSE 或 WebSocket 传输，通常使用 JSON 编码。

```
JSON
→ SSE / WebSocket
→ 事件模型
→ AG-UI
```

##### 2. ACP

ACP 定义编辑器与 Coding Agent 之间的会话、代码修改、终端执行、权限请求和执行状态。

本地 ACP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

##### 3. MCP

MCP 定义 Agent 如何发现和调用 Tool、Resource 和 Prompt。

本地 MCP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ MCP
```

远程 MCP 通常采用：

```
JSON
→ Streamable HTTP
→ JSON-RPC
→ MCP
```

##### 4. A2A

A2A 定义 Agent 发现、任务委派、状态流转和 Artifact 交换。

基于 JSON 的组合可以是：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

基于 gRPC 的组合可以是：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

#### 9.7 总结

Agent 通信协议可以按照自底向上的方式理解。

最底层是序列化层，它解决数据如何编码，常见方案包括 JSON、Protobuf、NDJSON、MessagePack 和 CBOR。

序列化后的数据通过传输层发送，常见通道包括 HTTP、SSE、WebSocket、WebRTC、stdio、Webhook 和消息队列。

传输层之上是调用绑定层，它负责定义方法、参数、结果和错误如何表示，常见方式包括 REST、JSON-RPC、gRPC 和 GraphQL。

最上层是应用语义层，它定义通信双方真正交换什么业务信息，主要包括 AG-UI、ACP、MCP 和 A2A。

```
JSON、Protobuf：数据如何编码
HTTP、SSE、WebSocket：消息如何传输
REST、JSON-RPC、gRPC：双方如何调用
AG-UI、ACP、MCP、A2A：双方交流什么
```

最终可以把整个链路概括为：

```
序列化层：把对象变成数据
传输层：把数据发送出去
调用绑定层：把数据组织成一次调用
应用语义层：让调用具有 Agent 业务含义
```
