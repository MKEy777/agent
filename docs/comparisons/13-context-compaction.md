# 上下文压缩

## 读前思考

- 对话历史快要填满模型的上下文窗口时，你有三个选择：直接砍掉中间的旧消息、把旧消息交给 LLM 摘要成一段话、或者拒绝新输入。砍掉最省钱但信息丢失不可控，摘要可控但要多花一次 LLM 调用——而且摘要本身可能写坏。如果摘要写坏了（漏掉关键决策、编造不存在的进展），你怎么发现、怎么补救？
- 压缩还有一个隐藏代价：它改写了消息列表的前缀，导致 provider 的 prompt cache 全部失效——下一轮请求要按全价重新计费之前能打九折的部分。省下的上下文空间和损失的 cache 折扣，这笔账怎么算？四个项目里只有一个项目为此专门改造了摘要的存放位置。

## 核心问题

上下文压缩解决的核心问题是：**会话长度超过模型上下文窗口时，如何在不中断任务的前提下缩小历史，同时让模型仍然"记得刚才在做什么"。** 它是会话内的工作记忆管理，与跨会话的长期记忆（见 06-memory）互补：压缩决定"这次会话还能继续多久"，长期记忆决定"下次会话还知道什么"。

| 维度 | claudecode | deer-flow | hermes-agent | openclaw-TS | openclaw-Python |
|------|-----------|-----------|--------------|-------------|-----------------|
| 定位 | 最简可用：CLI 短会话 | cache 友好：企业级多轮 | 工业级健壮：长期个人助手 | 模板化可审计：平台级 | 兜底优先：嵌入式运行时 |
| 一句话特点 | 保尾四轮、其余全摘要 | 摘要移出消息通道保 cache | 滚动摘要 + 多级降级 | 固定模板 + 非破坏性检查点 | 质量评分 + 无 LLM 兜底 |

## 方案展示

### claudecode：固定缓冲 + 保尾全摘要（最简形态）

触发条件是"已用 token 超过窗口减去一个固定缓冲区"——缓冲区为新输入和模型回复预留空间。token 数不调 API 精确计数，而是按字节折算估算（纯文本和 JSON 结构化内容用不同折算率），零成本、每轮都能算。压缩策略同样简单：保留最近四轮对话原文，之前的全部消息转成纯文本喂给摘要模型，摘要提示词是自由文本四要点（关键决策、文件路径与代码位置、任务当前状态、未解决问题）。压缩后的消息列表变成"一条摘要边界消息 + 最近四轮原文"；如果之前已经压缩过，旧摘要会作为"前次摘要"文本嵌入本次摘要的输入，避免更早的信息彻底丢失。

触发有两个时机：每轮开始前的预检（主动压缩），以及收到"上下文过长"类 API 错误后的响应式压缩（每次查询只允许触发一次，防止无限循环）。这是四个项目共同收敛出的双时机模式——预检靠估算，估算不准时响应式兜底。

```mermaid
sequenceDiagram
    participant Loop as 主循环
    participant Est as token 估算
    participant Cmp as 压缩器
    participant LLM as 摘要模型

    Loop->>Est: 每轮预检：估算当前消息 token
    Est-->>Loop: 估算值
    alt 超过窗口 − 固定缓冲
        Loop->>Cmp: 发起压缩
        Cmp->>Cmp: 切分：最近 4 轮保留 / 其余待摘要
        Note over Cmp: 消息太少（不足约 10 条）则放弃压缩
        Cmp->>LLM: 旧消息转纯文本（工具结果截断）+ 前次摘要
        alt 摘要成功
            LLM-->>Cmp: 摘要文本
            Cmp-->>Loop: [摘要边界消息, 最近4轮原文]
            Note over Loop: 压缩不消耗轮次预算
        else 摘要失败或为空
            Cmp-->>Loop: 原消息列表原样返回（安全降级）
            Note over Loop: 连续失败 3 次后彻底放弃压缩
        end
    else 未超阈值
        Loop->>Loop: 正常调模型
    end
    Loop->>LLM: 正式请求
    alt 收到"上下文过长"错误
        Loop->>Cmp: 响应式压缩（仅允许一次）后重试
    end
```

**为什么这么选**：CLI 场景会话通常不长，压缩是低频事件，简单策略的失败面小、可预测。估算不准没关系——固定缓冲区吸收了低估误差，响应式压缩兜住漏网情况。**牺牲了什么**：全摘要意味着中间历史只剩一段自由文本，摘要质量完全依赖摘要模型且无校验；估算不含 system prompt 和工具 schema，长工具描述的场景会系统性低估。

### deer-flow：摘要移出消息通道（cache 友好派）

deer-flow 的压缩是中间件链中的一环（SummarizationMiddleware），触发器支持三种条件的任意组合：绝对 token 数、消息条数、窗口占比，满足其一即触发。保留最近 N 条消息，且 AI 消息与其工具结果消息永不切断——切点落在工具消息中间时整对后移。摘要调用自身的输入也有 token 上限，超长历史先裁剪再摘要，防止"为了压缩把摘要模型也撑爆"。

它最独特的设计是**摘要不作为消息存在**：摘要文本写入会话状态的独立字段并由检查点机制持久化，每轮请求时以隐藏数据消息的形式临时投影回上下文。这样静态 system prompt 和消息前缀不被摘要改写污染，prompt cache 的命中前缀尽可能长地保住。摘要模型可以配置成轻量小模型，压缩成本与主模型解耦。

**为什么这么选**：企业级多用户部署下，cache 折扣乘以用户量是真金白银；把摘要挪出消息通道是四个项目中唯一正面回答"压缩与 cache 对抗"的方案。**牺牲了什么**：整套机制深度绑定中间件框架和检查点持久化，无法单独摘出来用；token 用字符近似估算，精度垫底，只能靠宽松阈值补偿。

### hermes-agent：滚动摘要 + 多级降级（工业级健壮派）

hermes 的在线压缩器（context_compressor.py，约五千行）是四个项目中防御最重的。阈值默认为窗口的一半，但小窗口模型（上下文低于约 512K）自动抬升到四分之三——源码注释解释了原因：system prompt、工具 schema、保护尾、滚动摘要构成"不可压缩底座"，小窗口下一半阈值触发的压缩腾不出多少空间，会话会陷入每一两轮就重新压缩的抖动。

压缩分层执行：先做剪枝——把旧工具结果替换为一行语义概括（而非空占位符，模型仍知道"当时读了什么、结果大概是什么"）；上下文压力大时连保护尾内的大块工具输出也降级，但最后三条消息永远保留原文。真正的摘要采用**滚动更新**：在上次摘要的基础上增量改写，而非每次从头重读全部历史。摘要是结构化 checkpoint 模板，带两个独特设计：凭据脱敏（摘要前把密钥类内容替换掉，防止敏感信息在摘要中二次扩散）和时间锚定（把"正在做 X"改写为"某日已完成 X"，防止续接会话的模型把已完成的动作再执行一遍）。

失败路径同样分层：摘要模型调用失败进入冷却期，冷却期内不再尝试；上次压缩的节省率过低则记为无效压缩，累积后拒绝继续压缩并向用户发出警告——这是对"压缩抖动"的显式防御。

**为什么这么选**：个人助手会话以天为单位持续，压缩是高频事件，任何一个未处理的边界情况都会以周为周期复现。**牺牲了什么**：复杂度极高，阈值抬升、剪枝分级、冷却、反抖动各自引入配置项和状态，单元测试成本随之增长；滚动摘要的错误会跨压缩累积，一次写坏的摘要会污染后续所有增量更新。

### openclaw：TS 模板派 + Python 兜底派

TS 版的 token 计数直接取 provider 返回的真实用量（不估算），触发条件是"真实上下文 token 超过窗口减去预留量"。切点选择从尾部倒序累积消息 token，达到保留预算后在最近的**合法切点**下刀——合法意味着不切断工具调用对；如果切点仍落在某一轮中间，被切断轮的前半部分会单独走一个专用摘要提示词。摘要提示词是四个项目中最严格的：固定五段 Markdown 模板（目标 / 约束与偏好 / 进展：已完成、进行中、受阻 / 关键决策 / 下一步），并要求严格按此格式输出；已有摘要时切换为增量更新提示词，在旧摘要基础上修订。压缩产物是会话树中的一个检查点节点而非对历史的破坏性重写——原始消息仍在树中，可回溯、可审计。文件操作清单（读过、改过哪些文件）跨压缩累积传递，不靠摘要模型自觉记住。

Python 版走另一条路：75% 触发、90% 紧急双档阈值，且每多一条工具结果消息阈值降 1%（下限 50%）——工具结果是最可压缩的内容，越多越应该提前压。它的招牌是**摘要质量评分**：摘要生成后按"工具名提及率、错误信息覆盖、长度合理性"打 0-1 分，低于阈值直接弃用 LLM 摘要，改用无 LLM 的确定性兜底摘要（从消息中机械抽取工具调用、错误、代码片段拼装）；超时和异常也走同一兜底。外层还有三级降级序列：先截断单条超长结果，再整体压缩，最后硬截断。

**为什么这么选**：平台级长期运行的第一要求是"永远不能因为压缩失败而卡死会话"，TS 用模板可验证性和非破坏性检查点保证可审计，Python 用确定性兜底保证必有退路。**牺牲了什么**：TS 的固定模板对非编码类会话（闲聊、创作）过于刚性，五段结构未必贴合；Python 的机械兜底摘要质量明显低于 LLM 摘要，只是"不至于崩"。

## 横向对比

四个项目在压缩上的分岔可以归结为三个岔路口，每个岔路口的选择都由项目的部署假设决定。

**岔路口一：触发阈值怎么定——固定缓冲、比例、还是动态？** 因为对"上下文成本结构"的假设不同，四家走向三种阈值哲学。claudecode 和 openclaw-TS 用"窗口减固定预留"，隐含假设是窗口足够大（20 万以上）、预留量相对窗口可忽略；deer-flow 和 hermes 用比例阈值，因为要适配从小型开源模型到旗舰模型的多种窗口，固定值在 64K 窗口上会荒谬（hermes 甚至发现过比例下限在小窗口上退化为"永不触发"的缺陷，为此加了小窗口抬升规则）；openclaw-Python 的动态阈值（工具结果越多阈值越低）则假设工具输出是压缩收益的主要来源——工具结果可压缩性远高于人类对话，多攒一些提前压更划算。

**岔路口二：摘要形态——自由文本、结构化模板，还是滚动增量？** 分岔的根源是对"摘要质量能否被验证"的要求不同。自由文本（claudecode）灵活但不可验证，写坏了只能靠人发现；结构化模板（openclaw-TS 五段式、hermes checkpoint）让"约束丢没丢、进展记没记"变成可检查的问题，openclaw-Python 更进一步把检查自动化成质量评分。滚动增量（hermes、openclaw-TS）与全量重摘（claudecode、deer-flow）的分岔则是成本与错误传播的交换：增量更新不必每次重读全部历史，摘要调用的输入恒定小；但一次写坏的摘要会永久留在链条里，全量重摘每次都有机会自我修正。

**岔路口三：压缩与 prompt cache 的对抗怎么处理？** 压缩必然改写消息前缀，改写即 cache 全失效。deer-flow 是唯一正面解决的：摘要放独立状态字段、每轮临时投影，前缀不动。hermes 选择减少压缩次数（阈值抬升 + 反抖动），承认失效但控制频率。claudecode 和 openclaw 接受失效——前者会话短、压缩低频，后者用真实 usage 计数保证压缩只在真正必要时发生。这个岔路口的判断标准是"压缩频率 × cache 折扣幅度"：两者乘积大到超过工程改造成本时，才值得做 deer-flow 式的通道分离。

| 岔路口 | claudecode | deer-flow | hermes-agent | openclaw-TS | openclaw-Python |
|--------|-----------|-----------|--------------|-------------|-----------------|
| 阈值哲学 | 固定缓冲 | 比例（三条件任一） | 比例 + 小窗口抬升 | 固定预留 + 真实计数 | 双档比例 + 动态下调 |
| 摘要形态 | 自由文本全量 | 自由文本 + 独立通道 | 结构化 + 滚动增量 | 固定模板 + 增量 | 六要点 + 质量评分 |
| 工具对切断 | 按轮切天然安全 | 消息对整体移动 | 边界前移吸附 | 合法切点 + 前缀单独摘要 | 按条数切（最弱） |
| 失败退路 | 还原 + 三连败停 | —（框架层重试） | 冷却 + 反抖动 + 警告 | 重试 + 守卫层 | 评分弃用 + 确定性兜底 |
| cache 态度 | 接受失效 | 通道分离保 cache | 降频减损 | 接受失效 | 接受失效 |

**与长期记忆的接口**：压缩会永久删除消息原文，如果这些消息里有值得跨会话记住的事实，必须赶在摘要前落盘。deer-flow 是唯一做了这个联动的项目——压缩启动前先把待提取对话绕过防抖窗口立即送入记忆队列；且子代理的压缩链特意跳过这个刷写，因为子代理的内部轮次（中间工具调用过程）不应进入用户的长期记忆。其他三家不做联动的理由各不相同：claudecode 的记忆提取本来就每轮异步跑、时序上先于压缩；openclaw-TS 的记忆整合走独立的定时任务、数据源不依赖会话消息；hermes 的记忆写入靠模型主动调工具，压缩前模型有机会自己保存。细节见 06-memory 的"压缩与记忆的联动"一节。

## 面试要点

**1. 什么是"压缩抖动"？为什么会发生？怎么防？**

参考答案方向：压缩抖动指压缩刚完成、一两轮后又再次触发，会话大部分时间在做摘要而非干活。根因是"不可压缩底座"——system prompt、工具 schema、保留的尾部原文、摘要本身，这些内容压缩后依然占据窗口；如果底座占比高（小窗口模型尤甚），压缩腾出的空间很快被新一轮工具输出填满。防御手段分两层：事前，阈值随窗口大小自适应（小窗口把触发线抬高，让每次压缩至少腾出有意义的空间）；事后，追踪每次压缩的实际节省率，节省率过低说明已无可压缩内容，应拒绝继续压缩并提示用户开新会话。判断标准是"底座 token ÷ 窗口大小"——占比超过触发阈值与保留预算之差时，压缩注定无效。

**2. 压缩后模型"忘了"早期确立的约束（比如用户说过"不要改测试文件"），怎么办？**

参考答案方向：分约束的类型处理。静态约束（编码规范、项目规则）本就该放在 system prompt 或规则文件里，不参与压缩、天然免疫。会话内约束（用户临时说的偏好和禁令）依赖摘要保真，这正是结构化模板的价值——五段式模板里"约束与偏好"是必填段，摘要模型被强制回答"用户提过什么要求"，自由文本摘要则容易把约束淹没在进展描述里。再往上一层是机制化保底：把关键信息移出摘要通道，比如文件操作清单跨压缩机械传递、技能文件通过引用通道按需重读——凡是能结构化传递的就不要指望摘要模型自觉记住。判断标准是"约束违反的代价"：代价高的约束（不可逆操作类）不能只靠摘要，要走结构化通道甚至权限系统。

**3. 摘要压缩、直接截断、冻结快照三种上下文管理手段，什么场景选哪个？**

参考答案方向：截断零成本、零延迟，但信息丢失不可控，适合被截内容价值密度低的场景——超长工具输出保留头尾即可，中间的重复日志截掉几乎无损。摘要有一次 LLM 调用的成本和失败风险，但信息保留可控，适合历史中混有关键决策的场景——对话历史不能截断只能摘要，因为你不知道哪句话后面会用到。冻结快照（会话开始时检索注入、全程不变）不是压缩手段而是注入策略，它假设"会话中途产生的新信息不需要立即回注"，换取 prompt cache 命中。实践中三者组合使用：单条超长结果先截断、整体历史超限再摘要、跨会话知识用快照注入。判断标准是"内容的价值密度 × 任务对连续性的要求"：密度低用截断，密度高且任务长用摘要，跨会话复用用快照。
