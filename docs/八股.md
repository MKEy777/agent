### 09 Agent 通信协议

> 本章回答「双方如何通信」，沿用四层模型：序列化层（数据如何编码）→ 传输层（消息如何传输）→ 调用绑定层（调用如何表示）→ 应用语义层（双方交流什么）。
>
> 与相邻章节的边界：MCP 的协议机制在本章，工具侧的职责边界在 02.4；A2A 的协议机制在本章，协作业务在 03；传输通道的通信视角在本章，系统设计视角在 08。

#### 9.1 整体分层

```text
Agent-Communication
├── 应用语义层：通信双方交换什么业务语义
├── 调用绑定层：如何表示方法、请求、响应和错误
├── 传输层：消息通过什么通道传递
└── 序列化层：数据编码成什么格式
```

应用语义层解决的是“双方在交流什么”。比如 MCP 规定 Agent 如何发现和调用工具，A2A 规定 Agent 之间如何委派任务。调用绑定层解决的是“这次调用如何表达”，例如方法名、参数、结果和错误。传输层解决的是“消息通过什么通道传递”，例如 HTTP、SSE 和 WebSocket。序列化层解决的是“数据最终编码成什么形式”，例如 JSON 和 Protobuf。

#### 9.2 序列化层

序列化层位于整个通信体系的最底层，负责把程序内存中的对象转换成可以传输或存储的文本或二进制数据。

```
序列化层
├── JSON
├── Protobuf
├── NDJSON
├── MessagePack
├── CBOR
├── multipart/form-data
└── Base64
```

##### 1. JSON

JSON 是 Agent 系统中最常见的文本序列化格式。它支持对象、数组、字符串、数字、布尔值和 null，几乎所有编程语言都可以直接解析。

JSON 最大的优点是可读性强、调试方便、跨语言能力好。开发人员可以直接在日志、浏览器开发工具或命令行中查看消息内容。因此，MCP、ACP、AG-UI 和 A2A 的很多实现都使用 JSON。

JSON 的不足是**消息体积相对较大**。因为每条消息都会重复携带字段名称，同时 JSON 的类型约束比较弱，服务端通常还需要使用 **JSON Schema、Pydantic** 或其他机制校验字段类型。

JSON 不原生支持二进制数据。传输图片、音频或文件时，通常需要使用 Base64、multipart/form-data，或者在 JSON 中只传递文件 URL。

##### 2. Protobuf

Protobuf 协议缓冲区 是一种基于 Schema 的二进制序列化格式。开发者需要先通过 `.proto` 文件定义消息结构、字段编号和字段类型，再生成不同编程语言的代码。

Protobuf 使用字段编号而不是完整字段名进行编码，因此消息体积通常比 JSON 更小，序列化和反序列化性能也更高。字段类型由 Schema 明确定义，所以类型约束比 JSON 更强。

Protobuf 还支持接口演进。只要保留已有字段编号，新增字段通常不会导致旧版本完全无法解析新消息。

gRPC 默认使用 Protobuf，因此常见的组合是：

```
Protobuf
→ HTTP/2
→ gRPC
```

Protobuf 更适合内部高性能服务和跨语言 RPC，但它不方便直接阅读，需要维护 `.proto` 文件和生成代码，临时调试没有 JSON 灵活。

##### 3. NDJSON

NDJSON 是 Newline Delimited JSON，也就是每一行表示一个完整的 JSON 对象，不同对象之间使用换行符分隔。

```
{"type":"token","data":"Hello"}
{"type":"tool_call","name":"search"}
{"type":"finished","status":"success"}
```

NDJSON 适合日志、事件流和管道通信。接收方读取到一行后就可以立即解析，不需要等待一个完整 JSON 数组传输结束。

NDJSON 主要解决连续多个 JSON 对象之间如何划分消息边界的问题。它不规定这些对象具有什么业务含义，也不规定请求和响应如何匹配。

因此，NDJSON 属于序列化和消息分帧形式，不属于 MCP、A2A 或 JSON-RPC 这样的应用和调用协议。

##### 4. MessagePack

MessagePack 是一种二进制对象序列化格式，它的数据模型与 JSON 比较接近，支持对象、数组、字符串、数字和布尔值，同时原生支持二进制数据。

与 JSON 相比，MessagePack 不需要把所有内容表示为可读文本，因此消息体积通常更小，适合高频内部通信和带宽敏感场景。

MessagePack 不要求预先定义 Schema，因此比 Protobuf 更灵活，但它也缺少 Protobuf 的强类型约束、接口生成和跨版本治理能力。

可以把 MessagePack 理解为一种紧凑的二进制 JSON。它在开放 Agent 协议中的普及程度不如 JSON 和 Protobuf，但适合内部事件通信。

##### 5. CBOR

CBOR 是一种可扩展的二进制对象格式。它的数据模型与 JSON 相似，但原生支持字节串、整数、浮点数、数组、Map 和语义标签。

CBOR 不要求预先定义 Schema，所以比 Protobuf 更灵活；同时它采用二进制编码，消息体积通常又比 JSON 更小。

CBOR 的语义标签可以表示日期、大整数或其他扩展类型，因此在 IoT、边缘设备和资源受限环境中比较常见。

在通用 Agent 平台中，CBOR 的使用范围通常不如 JSON 和 Protobuf，但在设备 Agent 和受限网络环境中具有优势。

##### 6. multipart/form-data

multipart/form-data 是一种在同一个 HTTP 请求体中封装多个数据部分的格式。每个部分通过 Boundary 分隔，并且可以拥有独立的名称、Header 和 Content-Type。

它适合同时传输用户 Prompt、JSON 元数据、图片、音频和附件。例如多模态 Agent 可以把文本参数作为普通字段，把图片和文件作为二进制部分上传。

与把整个文件转换成 Base64 再放入 JSON 相比，multipart/form-data 通常更加高效，也不会产生 Base64 的额外体积开销。

它更准确地说是一种复合 HTTP 消息体格式，而不是通用对象序列化协议，但在 Agent 的文件上传和多模态输入中非常常见。

##### 7. Base64

Base64 是把二进制数据转换成可打印文本的编码方式。它不是加密算法，也不是完整的序列化协议。

Base64 常用于在 JSON 中嵌入小型图片、音频片段、文件内容或二进制 Token。因为编码结果是普通文本，所以可以通过只支持文本的通道传输。

Base64 会增加数据体积，并产生额外的编码和解码开销，因此不适合传输大型文件。大型文件更适合使用 multipart/form-data、对象存储 URL 或原生二进制通道。

Base64 只解决二进制数据如何表示成文本的问题，不提供机密性、完整性或身份认证能力。

#### 9.3 传输层

传输层负责将序列化后的消息从一端发送到另一端。这里的传输层是 Agent 工程中的承载通道层，不完全等同于 OSI 网络模型中的传输层。

```
传输层
├── HTTP / HTTPS
├── SSE
├── WebSocket
├── WebRTC
├── stdio
├── Webhook
└── Message Queue
```

##### 1. HTTP / HTTPS

HTTP 是最常见的请求响应协议。客户端发送请求，服务端处理后返回响应。请求通常由方法、URL、Header 和 Body 组成，响应通常由状态码、Header 和 Body 组成。

HTTPS 是运行在 TLS 之上的 HTTP，它提供传输加密、完整性保护和服务端身份认证。生产环境中的模型调用、远程 MCP、A2A 和 Agent API 通常都应该使用 HTTPS。

HTTP 适合发送用户消息、创建任务、查询状态、提交审批和上传文件。它本身主要采用请求响应模式，如果 Agent 需要持续返回 Token，一般会在 HTTP 连接上使用 SSE；如果需要高频双向通信，则可以使用 WebSocket。

HTTP/2 引入了二进制帧、多路复用和流控制，也是 gRPC 常用的底层承载方式。HTTP/3 则运行在 QUIC 上，可以进一步改善多路流传输。

##### 2. SSE

SSE 是基于 HTTP 的服务端事件流。客户端建立一个 HTTP 长连接，服务端将响应类型设置为 `text/event-stream`，然后持续向客户端发送文本事件。

SSE 的主要通信方向是服务端到客户端，因此非常适合 Agent 的 Token Streaming。除了 Token，服务端还可以通过 SSE 推送工具调用状态、任务进度、Subagent 状态和最终结果。

普通文本 Agent 经常采用下面的通信方式：

```
客户端 ── HTTP POST ──→ 提交任务
客户端 ←── SSE Stream ── 返回 Token 和状态
```

如果客户端需要中断任务、批准工具调用或补充信息，一般通过额外的 HTTP 请求提交。因此，SSE 连接本身主要负责服务端向客户端推送，但整个系统仍然可以实现双向业务交互。

SSE 的优点是实现简单、基于标准 HTTP、容易经过网关和反向代理，并且支持断线重连。缺点是缺少真正的全双工能力，不适合大量高频的客户端上行事件。

##### 3. WebSocket

WebSocket 是全双工长连接协议。连接建立后，客户端和服务端都可以随时主动发送消息，不需要为每条消息重新建立 HTTP 请求。

在 Agent 系统中，WebSocket 可以在一条连接上同时承载用户消息、Token 输出、工具调用、审批结果、中断指令、任务状态和设备控制。

WebSocket 适合高频双向交互。例如语音 Agent 需要客户端持续上传音频，服务端持续返回音频，并支持用户随时打断；远程设备 Agent 也可能需要服务端主动发送命令，设备实时返回状态。

WebSocket 的能力比 SSE 更强，但工程复杂度也更高。服务端需要处理心跳、断线重连、消息顺序、连接状态、负载均衡和水平扩展。

因此，普通文本 Agent 一般优先使用 HTTP 加 SSE；需要高频双向控制、实时语音或设备通信时，更适合使用 WebSocket。

##### 4. WebRTC

WebRTC 是面向低延迟实时音频、视频和数据通信的技术体系，主要用于浏览器、客户端和设备之间的实时媒体传输。

在语音 Agent 中，用户音频需要持续发送给服务端或实时模型，Agent 生成的音频也需要持续返回，同时还要支持用户实时打断。WebRTC 在低延迟音频通信方面通常比普通 HTTP 更合适。

WebRTC 支持音频和视频 Track，也支持通过 DataChannel 传输普通数据。它还会使用 ICE、STUN 和 TURN 处理网络发现、NAT 穿透和流量中继。

WebRTC 本身不负责最初的信令交换。客户端和服务端仍需要通过 HTTP 或 WebSocket 交换 SDP 和网络候选信息。

因此，WebRTC 主要负责实时媒体传输，HTTP 或 WebSocket 通常负责认证、会话创建和信令交换。

##### 5. stdio

stdio 是标准输入和标准输出的简称。宿主程序可以启动一个子进程，通过 stdin 向子进程发送请求，通过 stdout 读取子进程返回的响应。

这种通信方式不需要开放网络端口，也不需要单独运行远程服务，因此非常适合本地 MCP Server、Coding Agent、CLI 工具和插件进程。

使用 JSON-RPC over stdio 时，stdout 应当只输出协议消息，普通日志应该写入 stderr。否则日志可能与 JSON-RPC 消息混合，导致消息解析失败。

stdio 的优势是部署简单、攻击面较小，并且子进程生命周期可以由宿主程序统一管理。它的局限是主要适合本机父子进程，不适合直接跨机器通信。

##### 6. Webhook

Webhook 是一种基于 HTTP 的异步回调模式。调用方先向服务端提供回调地址，当任务完成或状态发生变化时，服务端主动向该地址发送 HTTP 请求。

Webhook 适合耗时较长的 Agent 任务。客户端不需要一直保持 SSE 或 WebSocket 连接，也不需要不断轮询任务状态，服务端完成任务后可以主动通知调用方。

Webhook 与轮询的区别是：

```
轮询：客户端不断询问任务是否完成
Webhook：服务端在状态变化后主动通知客户端
```

生产环境中的 Webhook 需要处理签名校验、幂等、重复通知、事件乱序、失败重试和重放攻击。

调用方不能假设一个事件只会收到一次，而应该使用事件 ID 或业务 ID 保证重复通知不会导致业务被重复执行。

##### 7. Message Queue

Message Queue 是异步消息通信机制。生产者把任务或事件发送到 Broker、Topic、Queue 或 Subject，消费者可以在之后读取和处理，双方不需要同时在线。

在 Agent 系统中，消息队列适合任务调度、长任务执行、Subagent 分发、事件总线和失败重试。例如 Gateway 收到任务后，可以把任务写入队列，由空闲的 Agent Worker 消费执行。

消息队列能够实现异步解耦和削峰填谷。如果 Agent Worker 暂时不可用，任务可以先保存在队列中，等服务恢复后再继续处理。

常见系统包括 Kafka、RabbitMQ、NATS 和 Redis Streams。它们在消息持久化、顺序、消费者组、确认机制和吞吐量方面各有侧重。

使用消息队列时还需要处理重复消费、消息确认、死信队列、顺序保证和最终一致性。消费者通常需要实现幂等，避免同一任务被重复执行。

#### 9.4 调用绑定层

调用绑定层建立在序列化层和传输层之上，负责规定一次调用如何表示，包括调用哪个方法、传入哪些参数、如何关联请求和响应、结果如何返回以及错误如何表示。

```
调用绑定层
├── REST
├── JSON-RPC
├── gRPC
└── GraphQL
```

##### 1. REST

REST 是一种以资源为中心的接口设计风格。它通常使用 URL 表示资源，使用 HTTP 方法表示操作。

例如，GET 用于查询资源，POST 用于创建资源或执行操作，PATCH 用于部分更新，DELETE 用于删除资源。

REST 通常复用 HTTP 状态码表示调用结果，例如 `200` 表示成功，`400` 表示请求错误，`404` 表示资源不存在，`500` 表示服务端异常。请求和响应一般使用 JSON，但 REST 本身并不限定必须使用 JSON。

在 Agent 系统中，REST 适合任务创建、任务查询、Session 管理、文件上传和审批提交。例如可以使用 `POST /tasks` 创建 Agent 任务，再使用 `GET /tasks/{id}` 查询任务状态。

REST 的优点是简单、通用、容易调试，也容易经过 API Gateway 和负载均衡器。它主要适合请求响应场景，持续流式输出一般还需要结合 SSE，双向实时通信则通常结合 WebSocket。

##### 2. JSON-RPC

JSON-RPC 是一种轻量级远程过程调用协议。它不围绕资源组织接口，而是直接表达调用哪个方法。

一个 JSON-RPC 请求通常包含：

```
jsonrpc：协议版本
method：方法名称
params：调用参数
id：请求标识
```

调用成功时返回 result，失败时返回 error。id 用于匹配请求与响应。

如果一条消息没有 id，它通常表示 Notification，即发送方只通知接收方发生了某件事情，不要求返回结果。这种机制适合状态更新和事件通知。

JSON-RPC 与传输方式无关，可以运行在 stdio、HTTP、WebSocket 或其他消息通道上。MCP 和 ACP 使用 JSON-RPC，是因为它既支持普通请求响应，也支持通知和双向调用。

JSON-RPC 和 JSON 不是同一层概念。JSON-RPC 定义请求、响应和错误的消息结构，JSON 负责把这些结构编码成文本。

##### 3. gRPC

gRPC 是一种高性能、强类型的远程过程调用框架。开发者通常通过 `.proto` 文件定义 Service、Method、Request 和 Response，再生成不同语言的客户端和服务端代码。

gRPC 默认使用 Protobuf 进行序列化，并通常运行在 HTTP/2 上。它支持四种调用模式：

```
Unary：单请求、单响应
Server Streaming：单请求、多响应
Client Streaming：多请求、单响应
Bidirectional Streaming：双向持续通信
```

服务端流适合客户端提交一次请求后，服务端持续返回任务状态或增量结果。双向流适合客户端和服务端同时持续发送消息。

gRPC 的优势是类型明确、消息体积小、性能较高，并且原生支持超时、取消、Metadata 和标准错误码。它比较适合 Agent 平台内部的微服务通信和高吞吐 A2A 服务。

它的不足是消息不如 JSON 直观，需要维护 `.proto` 文件并生成代码，浏览器和人工调试也没有 HTTP+JSON 方便。

##### 4. GraphQL

GraphQL 是一种基于 Schema 的查询语言和服务执行模型。客户端可以明确声明需要哪些字段，服务端只返回这些字段。

GraphQL 主要包括：

```
Query：读取数据
Mutation：修改数据
Subscription：持续订阅事件
```

GraphQL 适合复杂 Agent 平台的数据聚合查询。例如管理页面可能同时需要任务信息、Session、用户信息、成本指标和日志摘要，前端可以通过一次 GraphQL 查询获取需要的数据。

GraphQL 一般不直接驱动 Agent Loop，因为 Agent Loop 会产生大量文本增量、工具调用和状态事件。这些实时事件通常仍通过 SSE 或 WebSocket 传输。

因此，GraphQL 在 Agent 系统中更适合作为控制面和管理平台的数据查询接口。

#### 9.5 应用语义层

应用语义层位于整个通信体系的最上层，负责定义通信双方分别是什么角色、可以交换哪些业务对象、对象具有什么状态，以及整个交互流程遵循什么规则。

```
应用语义层
├── AG-UI：Frontend ↔ Agent
├── ACP：Editor / IDE ↔ Coding Agent
├── MCP：Agent ↔ Tool / Context
└── A2A：Agent ↔ Agent
```

##### 1. AG-UI

AG-UI 是前端应用与 Agent Runtime 之间的交互协议，主要解决 Agent 前端与后端之间缺少统一事件模型的问题。

普通聊天接口只需要传递用户消息和最终文本，但 Agent 执行过程中还会产生运行开始、文本增量、工具调用、工具结果、状态变化、人工审批和运行结束等事件。

AG-UI 将这些过程定义成标准事件。前端收到文本增量事件后可以逐步渲染答案，收到工具调用事件后可以展示 Agent 正在执行什么操作，收到状态更新后可以显示任务进度，收到审批事件后可以向用户展示确认界面。

AG-UI 规定的是事件分别具有什么业务含义，但不强制使用哪种传输方式。同一套 AG-UI 事件可以通过 SSE 传输，也可以通过 WebSocket 传输。

因此，AG-UI 解决的是前端如何理解 Agent 的运行过程，而 SSE 和 WebSocket 解决的是这些事件如何发送到前端。

##### 2. ACP

ACP 是编辑器或 IDE 与 Coding Agent 之间的交互协议。它的目标类似于 LSP：编辑器实现一次 ACP，就可以接入多个 Coding Agent；Coding Agent 实现一次 ACP，也可以接入多个编辑器。

Coding Agent 的交互不仅包含聊天消息，还包括读取文件、修改代码、展示 Diff、执行终端命令、返回执行进度和请求用户授权。

因此，ACP 定义的是一套面向软件开发场景的 Agent 交互语义。

本地环境中，通常由编辑器启动 Coding Agent 子进程，再通过 stdio 通信。ACP 一般使用 JSON-RPC 表示请求、响应和通知，数据采用 JSON 编码。

典型组合是：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

ACP 与 MCP 的区别在于，ACP 的通信双方是编辑器和 Coding Agent，关注的是会话、代码、终端和权限；MCP 的通信双方是 Agent 和外部能力服务，关注的是工具和数据访问。

##### 3. MCP

MCP 是 Agent 与外部工具、数据和上下文服务之间的标准协议，主要解决工具接入方式不统一的问题。

如果没有 MCP，不同 Agent 框架需要分别为文件系统、数据库、搜索引擎、GitHub 和各种企业服务开发专用连接器。

MCP 采用 Client-Server 模型。MCP Server 对外暴露能力，MCP Client 连接 Server、发现能力并发起调用。

MCP Server 通常可以提供：

```
Tool：可以执行的动作
Resource：可以读取的数据
Prompt：可以复用的提示模板
```

MCP 使用 JSON-RPC 表示请求、响应和通知，数据使用 JSON 编码。本地 MCP Server 一般通过 stdio 通信，远程 MCP Server 一般通过 Streamable HTTP 通信。

完整链路可以表示为：

```
JSON
→ stdio / Streamable HTTP
→ JSON-RPC
→ MCP
```

MCP 本质上是标准化能力调用协议。Agent 通常会发现工具名称、描述和参数，然后像调用结构化函数一样调用它。

因此，MCP 解决的是 Agent 如何连接和调用外部能力，而不是两个自主 Agent 如何协作。

##### 4. A2A

A2A 是独立 Agent 系统之间的通信和协作协议，适合跨框架、跨语言、跨服务甚至跨企业的 Agent 互操作。

A2A 的核心思想是黑盒协作。调用方不需要知道另一个 Agent 内部使用什么模型、Prompt、Memory 和 Tool，只需要知道这个 Agent 具有什么能力、如何提交任务、如何获取状态以及如何接收产物。

A2A 的核心对象包括：

```
Agent Card：描述 Agent 身份、能力、接口和认证方式
Message：Agent 之间交换的信息
Task：具有生命周期的任务
Part：消息或产物的内容单元
Artifact：任务生成的文档、代码或结构化结果
```

A2A 与普通工具调用不同。工具调用通常是传入确定参数并等待结果，而 A2A 面向的是一个具有自主能力的 Agent。

被调用 Agent 可以自己拆分任务、调用多个工具、运行较长时间，甚至在执行过程中请求调用方补充输入或完成授权。

因此，A2A 不仅定义任务提交，还需要定义任务状态、流式更新、取消、失败、补充输入和产物返回等语义。

A2A 可以采用多种底层组合：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

或者：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

##### 5. MCP 与 A2A

MCP 与 A2A 最核心的区别是，MCP 面向能力调用，A2A 面向任务委派。

通过 MCP 调用工具时，Agent 通常明确知道调用哪个工具、需要传入哪些参数，以及大致会返回什么结果。例如，Agent 调用搜索工具并传入查询条件，工具直接返回搜索结果。

通过 A2A 调用另一个 Agent 时，调用方通常只描述目标，不规定具体执行步骤。例如主 Agent 可以把“调研新能源汽车行业并生成报告”委派给 Research Agent，Research Agent 自己决定如何规划、搜索、整理和生成报告。

```
Main Agent
└── A2A → Research Agent
               ├── MCP → Search Tool
               ├── MCP → Database
               └── MCP → File System
```

因此，二者可以概括为：

```
MCP：Agent 调用一个能力
A2A：Agent 委派一个任务
```

#### 9.6 典型协议组合

##### 1. AG-UI

AG-UI 定义前端与 Agent Runtime 之间的文本增量、工具调用、工具结果、状态更新和运行生命周期。

这些事件可以通过 SSE 或 WebSocket 传输，通常使用 JSON 编码。

```
JSON
→ SSE / WebSocket
→ 事件模型
→ AG-UI
```

##### 2. ACP

ACP 定义编辑器与 Coding Agent 之间的会话、代码修改、终端执行、权限请求和执行状态。

本地 ACP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ ACP
```

##### 3. MCP

MCP 定义 Agent 如何发现和调用 Tool、Resource 和 Prompt。

本地 MCP 通常采用：

```
JSON
→ stdio
→ JSON-RPC
→ MCP
```

远程 MCP 通常采用：

```
JSON
→ Streamable HTTP
→ JSON-RPC
→ MCP
```

##### 4. A2A

A2A 定义 Agent 发现、任务委派、状态流转和 Artifact 交换。

基于 JSON 的组合可以是：

```
JSON
→ HTTP / SSE
→ JSON-RPC
→ A2A
```

基于 gRPC 的组合可以是：

```
Protobuf
→ HTTP/2
→ gRPC
→ A2A
```

#### 9.7 总结

Agent 通信协议可以按照自底向上的方式理解。

最底层是序列化层，它解决数据如何编码，常见方案包括 JSON、Protobuf、NDJSON、MessagePack 和 CBOR。

序列化后的数据通过传输层发送，常见通道包括 HTTP、SSE、WebSocket、WebRTC、stdio、Webhook 和消息队列。

传输层之上是调用绑定层，它负责定义方法、参数、结果和错误如何表示，常见方式包括 REST、JSON-RPC、gRPC 和 GraphQL。

最上层是应用语义层，它定义通信双方真正交换什么业务信息，主要包括 AG-UI、ACP、MCP 和 A2A。

```
JSON、Protobuf：数据如何编码
HTTP、SSE、WebSocket：消息如何传输
REST、JSON-RPC、gRPC：双方如何调用
AG-UI、ACP、MCP、A2A：双方交流什么
```

最终可以把整个链路概括为：

```
序列化层：把对象变成数据
传输层：把数据发送出去
调用绑定层：把数据组织成一次调用
应用语义层：让调用具有 Agent 业务含义
```
