# 总结：四个框架的设计哲学与适用场景

读完十个主题的横向对比，最值得带走的不是某个具体机制，而是四个项目各自贯穿始终的一条设计主线。同一个主题问题（怎么接入模型、怎么管上下文、怎么派子代理），四家给出的答案不同，但每一家的答案都能追溯到它对"自己是什么、跑在哪里、服务多久"的根本假设。看懂这条主线，就能预测一个项目在任意模块上大概会怎么选。

## 四条设计主线

### deer-flow：企业级中间件化——一切关注点皆中间件

deer-flow 的根本假设是"多用户、多租户、需要长期维护、团队协作开发"。这个假设推着它把每一个横切关注点都做成中间件链上的一环：权限检查是中间件、上下文压缩是中间件、token 计费是中间件、循环检测是中间件、记忆刷写是压缩中间件的钩子。这样做的好处是每个关注点独立可测、可插拔、可按声明的相对位置排序，新增功能不必读懂整条链。它在各模块的一致体现：LLM 层用子类补丁而非 fork（跟随上游好维护）、压缩把摘要移出消息通道以保住多用户场景下的 prompt cache 折扣、记忆用防抖批处理降低多用户下的提取成本、可观测性支持接入标准追踪后端。代价是调试要追踪十几个中间件的执行顺序，一个请求的完整路径横跨很多文件——用工程复杂度换取了关注点的解耦和团队并行开发的能力。

### hermes-agent：单体工业级健壮性——每个边界情况都有防御

hermes 的根本假设是"运行在用户本机、以天甚至周为单位持续工作的个人助手"。长期运行意味着任何未处理的边界情况都会以固定周期复现，所以它选择把主循环写成一个巨大的单文件，用大量状态变量和分支穷尽每一种异常路径——不是不会抽象，而是刻意不抽象，因为恢复路径之间的复杂交互放在一处比拆散到多个模块更容易推理。它在各模块的一致体现：错误恢复用二十多种分类精确匹配、压缩有阈值自适应和反抖动和冷却和确定性兜底、prompt cache 用滑动断点形成增量缓存链、记忆靠模型主动写入加零依赖的本地全文检索。代价是单文件规模巨大、可复用性差、多人协作易冲突——它用可维护性和优雅度，换取了单机长期运行下的极致健壮。

### openclaw：平台级长期运行——一切为了"跑数月不退化"

openclaw（尤其 TS 版）的根本假设是"作为平台服务大量用户、单个会话可能持续数月、进程会重启、provider 会波动"。这个假设让它在每个模块都为"长期不退化"投资：记忆有从短期到持久的晋升路径和定期"做梦"整合（不整合的记忆库会变成噪声）、压缩用固定模板保证可验证性且产物是可回溯的会话树检查点、LLM 层用三层故障转移应对 provider 不可用、子代理用持久化注册表加孤儿恢复扛住进程重启、还独有运行中"转向"子代理的能力。它的另一面是 Python 版的极简实现——同一个团队用两种语言回答了"最小可用"和"平台级完整"两种需求，本身就是绝佳的对照组。代价是 TS 版的状态变量和文件数量爆炸、类型安全从编译期退到运行时靠契约测试补偿——它用巨大的工程体量，换取了平台级的长期稳定和可审计。

### claudecode：纯函数内核——状态机可被任意入口驱动

claudecode 的根本假设是"还原 Claude Code 的内核、面向本地 CLI 的短会话、需要被多种入口复用"。这个假设让它把主循环做成一个不持有任何长期状态的纯函数——所有依赖参数注入、所有输出通过事件产出，于是同一个循环可以被 REPL、一次性管道、子代理、单元测试四种入口驱动，子代理与主代理天然同构（都是同一个循环传不同参数）。它在各模块的一致体现：LLM 层不做 Provider 抽象只用闭包分层、压缩用最简单的固定缓冲加保尾全摘要、可观测性直接内嵌在事件流里（终端就是 dashboard、零额外基础设施）、记忆按项目隔离存本地文件。代价是接线复杂度转移到装配层、没有编译期接口约束、没有持久化——它用"不抽象"和"最简可用"，换取了内核的可复用性和代码的可读性。

## 怎么选：一个决策视角

把四个项目当四种"部署形态的原型"，选型时先问三个问题。第一，**服务多少人**：单人本机选 hermes 或 claudecode 形态，多租户选 deer-flow 形态，平台级选 openclaw 形态。第二，**会话活多久**：秒到分钟级的一次性任务，简单方案（claudecode 的固定阈值压缩、无持久化子代理）就够；数小时到数月的长期会话，必须投资整合、持久化、自愈（openclaw 形态）。第三，**团队多大**：单人或小团队维护，单文件穷举（hermes）反而好调试；多人并行开发，中间件化或模块化（deer-flow）的解耦收益才超过其复杂度成本。

这三个问题的答案不是独立的——它们共同定义了一个项目的"部署假设"，而部署假设一旦确定，绝大多数模块的设计选择就有了默认方向。这正是读这套对比文档最大的收获：架构没有绝对的好坏，只有"在给定约束下的合理"，而看懂约束如何推导出选择，比记住任何一个具体机制都重要。
