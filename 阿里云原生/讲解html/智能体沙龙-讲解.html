全局理解：这个报告在讲什么

这个报告回答一个问题：当 MCP（Model Context Protocol，Agent 调用工具的标准协议）演进到无状态形态后，企业该怎么重建 Agent 的工具访问基础设施。讲师孙校来自 Higress 社区，内容分三章：第一章回顾 MCP 从本地 stdio、HTTP+SSE、Streamable HTTP 到 2026-07 Stateless Core 的四阶段演进，论证无状态让工具具备可调度、可识别、可治理三种基础设施属性；第二章把 Higress 定位为 Agent 与工具运行时之间的 Tool Access Plane（工具访问平面），用协议桥、REST-to-MCP、凭证隔离与 Tool 策略逐一消除协议升级、工具接入、执行治理三道摩擦；第三章展望从 MCP Gateway 演进到 Agent Gateway，把外界访问 Agent、Agent 访问模型、Agent 访问工具、Agent 间协作四类访问纳入同一个治理边界。官方沙龙回顾对本议题的摘要与此一致：Higress 提供协议桥接、REST-to-MCP 统一工具目录、凭证隔离与工具策略治理，未来把模型访问与 A2A 协作纳入统一治理（见沙龙回顾）；2026-07-28 新规范与 Higress 支持边界的细节见新规范解读。

第 4 页MCP 一直在摆脱连接状态

左半把 MCP 传输形态的历史演进排成四级台阶：最初是本地 stdio（标准输入输出，进程间通过本地管道通信），Agent 与工具运行在同一环境；2024-11 的 HTTP + SSE（Server-Sent Events，服务器通过 HTTP 长连接向客户端单向推送消息）支持了远程访问，但依赖双向连接；2025-03 的 Streamable HTTP 统一了 Endpoint（访问入口地址），长连接变为可选；2026-07 的 Stateless Core 做到请求独立处理、上下文随请求传递。右半展开 2026-07-28 新规范"请求自描述"的三个特征：无握手 / 无 Session（Session 指服务端为一条连接维持的会话状态），server/discover 按需调用；上下文随请求，请求元数据放在 HTTP Header 中携带；任意实例可处理，tools/list（查询工具列表）与 tools/call（执行某个工具）独立调度。底部给出演进主线：工具调用逐步脱离特定连接，走向标准的远程请求。

补充背景（线上资料）

2026-07-28 发布的 MCP 规范核心变化是无状态核心：请求自描述、无握手无 Session、上下文随请求传递，因此可以跑在普通 HTTP 基础设施上。Higress v2.2.4 是首个支持该协议 Tools 基线的开源网关；注意边界——聚焦 Tools 基线，不等于实现规范的全部能力。来源：MCP 新规范与 Higress 支持解读。

第 5 页无状态让 Tool 具备三种基础设施属性

页首前提：Transport Session（传输层会话）退出协议核心，Tool 调用开始具备标准基础设施属性。接着用箭头串起三个递进的边界：01 状态边界——状态不再藏在连接里，业务状态需要通过合理设计显式表达；02 调度边界——任意请求可以落到任意健康实例，扩缩容与故障切换不再依赖粘性会话（粘性会话指负载均衡把同一会话的请求固定发往同一实例）；03 治理边界——治理对象从 /mcp Endpoint 下沉到 Method（协议调用方法）与具体 Tool。三者合成一个公式：可调度 + 可识别 + 可治理 = 标准 Tool Workload（可被基础设施统一调度的工作负载单元）。底部特别提醒：协议不会自动提供治理，但它让 Tool 具备了被共享基础设施治理的条件——治理本身仍要靠网关等设施去建设。

第 6 页Agent 负责意图，基础设施守住边界

本页是一张三层架构图。上层是三类调用方：业务 Agent、研发 Agent、个人 Agent，三条线汇聚到中间的 Tool Access Plane（工具访问平面，即 Agent 与工具之间的统一接入与治理层）。平面内列六项能力：发现与目录、协议与兼容、身份与权限、路由与弹性、策略与限流、观测与审计。平面下方再分出三类后端：MCP Tools、REST APIs（传统 HTTP 风格接口）、企业服务。底部结论划分了职责：Agent 决定调用什么工具（意图层），基础设施保证调用可达、可控、可观测（执行层）。这张图给出了全报告反复使用的 Tool Access Plane 概念的能力清单。

第 7 页网关真正理解 MCP，才有资格治理 Tool

页首用乘法公式定义 MCP Gateway = 协议语义 × 兼容转换 × 工具治理，随后展开为三层能力。看得懂：识别 Version（协议版本）+ Method（调用方法）+ Tool Identity（工具身份），做协议识别与严格校验。接得住：在 Modern（新协议）/ Legacy（旧协议）/ REST 三种形态之间做明确转换，升级不要求全链路同时完成。管得好：身份 + 凭证 + 策略 + 观测组合起来，治理对象下沉到具体 Tool。底部结论：网关从单纯代理 /mcp 入口，走向理解协议版本、调用方法和 Tool 身份——做到这三点才谈得上治理工具。

第 9 页Higress：面向 AI 时代的云原生网关

左侧是 Higress 的定位卡片：AI Native API Gateway（AI 原生 API 网关），由云原生底座 × AI 流量治理 × MCP Server 托管组合而成，带 AI Gateway 与 MCP Gateway 两个能力标签，开源地址 github.com/higress-group/higress。上方两行给出管理范围与项目属性：统一管理 LLM API（大模型接口）、MCP Server 与传统 API；开源、CNCF Sandbox（CNCF 沙箱孵化阶段项目）、Apache 2.0 许可证、Wasm 可扩展（WebAssembly 插件扩展机制）。右侧三行展开：01 统一接入——LLM API、MCP Server、REST / 企业服务从同一层进入；02 统一治理——路由与弹性、认证鉴权、限流、观测审计；03 开放底座——Istio + Envoy、Wasm 插件、Kubernetes / Gateway API。底部蓝条落到报告主题：在 Agent 与 Tool Runtime（工具运行时）之间，提供一层可统一管理的 Tool Access Plane。

第 10 页企业 Agent 上线，通常先卡在三道门

本页把企业 AI 平台团队的上线之路画成上升阶梯。起点是团队目标：让业务 Agent 调用现有系统并进入生产。随后依次三道门：01 协议升级——Client 已升级、Server 仍依赖旧生命周期；02 工具接入——REST、OpenAPI（REST 接口的描述规范）与 MCP Server 形态和入口各不相同；03 执行治理——凭证、权限、审计分散。右上角标出总目标：可规模化上线。底部蓝条给出三条验收标准：工具可用、升级可控、调用可追踪；最后一行点出 Higress 的角色：逐一消除协议、接入与治理摩擦。后面第 11–13 页分别对应这三道摩擦的解法。

第 11 页新 Client 不等全链路升级，也能调用旧 Server

本页是一条从左到右的调用链，解决第 10 页的"协议升级"门。调用侧是 2026-07-28 的新 Client，发出自描述 tools/call：无握手、无 Session，版本与 Tool 身份随请求携带。中间 Higress 协议桥分三步处理：01 识别校验——核对版本、方法、Tool 身份；02 显式转换——按配置的 protocolStrategy 为 legacy 把新协议请求转成旧协议调用，即后端走旧协议是显式声明的，不是网关猜的；03 调用安全——两条纪律：不猜版本、不跨协议重试（失败后不换一种协议重发，避免同一次调用被执行两遍）。右侧后端是 Legacy MCP Server，仍跑旧生命周期：initialize 握手、Session 维持，传输为 SSE / Streamable HTTP。底部三句话总结效果：客户端先升级、服务端渐进迁移、一次调用只执行一次。

第 12 页存量系统不改造，也能进入统一 Tool 目录

本页解决"工具接入"门。图自上而下：Agent 统一用 tools/list 与 tools/call 访问企业 Tool 目录（标准 Tool 描述、统一入口、统一发现）；目录由 Higress 内两条转换路径支撑。左路 REST-to-MCP：把 API Path 映射为 Tool、Parameter 映射为 Args（工具参数），将 REST / OpenAPI / Database 等存量资产转成 MCP 工具；右路 MCP Proxy：代理已有 MCP Server，提供统一稳定的 /mcp 入口。两条路径共用同一条治理横条：统一入口、身份与凭证、Tool 策略、观测审计。图下方强调企业存量资产保持原状，后端不做改造。结论：后端保持原状，Agent 获得统一 Tool 语义。

第 13 页Skill + CLI 能执行，企业仍需 Tool 治理边界

本页解决"执行治理"门，左右对照两条执行路径：直接执行（Skill → Shell / CLI → 企业系统）与受控执行（Skill → MCP Tool → Higress → 企业系统）。这里的 Skill 指封装"怎么做某件事"的操作技能，CLI 即命令行工具。页首前提：能运行命令，不等于可以安全共享给多个 Agent。三组对照如下：

维度 直接执行的问题 受控执行的对策
01 权限与身份 Shell 权限过宽，业务动作与运行环境没有分离 调用侧身份：识别 Agent、用户与租户
02 凭证 Token 与版本散落，难以统一吊销、轮换和升级 凭证隔离：Client Token 与后端 Credential 分离
03 审计 命令字符串审计，缺少业务 Tool 语义 Tool 策略与观测：白名单、限流、指标、Trace（分布式调用链追踪）、审计

绿色横条给出审计答案的四要素：谁、调用哪个 Tool、使用哪份凭证、执行结果。底部分工结论：Skill 决定怎么做，MCP 定义能做什么，Higress 守住谁能做、如何执行。

第 15 页MCP Gateway 只覆盖了 Agent 的一条访问链

本页用一张图划出 MCP Gateway 的覆盖边界。大框是"Agent Gateway 的完整治理范围"，中心为 Agent Runtime（承载意图、规划、Memory、State），四周连出四条访问链：右侧蓝色实线椭圆是"Agent 访问工具"，标注 MCP Gateway 已覆盖；其余三条均为虚线，即需要统一治理——上方"外界访问 Agent"（User / App / External Agent → Agent API）、左侧"Agent 访问模型"、下方"Agent 与 Agent 协作"（A2A · Agent Card · Skill · Task）。图例说明：虚线 = 需要统一治理，蓝色 = MCP 已覆盖。其中 A2A 是 Agent 间协作协议，与管工具调用的 MCP 互补。底部结论：问题不是增加三套网关，而是把四类访问纳入同一个治理边界。

补充背景（线上资料）

A2A（Agent-to-Agent）是 Google 于 2025 年 4 月发布的 Agent 间协作协议，与 MCP 互补：MCP 管 Agent 到工具的调用，A2A 管 Agent 之间的通信，核心概念包括 Agent Card（Agent 的能力自描述）与 Task（协作任务）。官方沙龙回顾也把 Agent 间协作（A2A）列为 Higress 演进到 Agent Gateway 后要统一治理的访问类型之一。来源：Agent 开源开发者沙龙回顾。

第 16 页Higress Agent Gateway：目标形态与能力演进

本页给出 Agent Gateway 的目标形态，并用两种颜色标注能力状态：蓝色 = 已具备，紫色 = 待实现。顶部先划边界：Agent Runtime（Planner、Memory、State）保持在 Agent 侧，业务状态属于 Agent，网关不接管。Higress 能力边界框内，中心 Higress Agent Gateway 连接四个方向，每个方向都是"已有底座 + 待补语义"两层：Agent 服务入口——已具备网关入口、Streaming（流式响应）、认证底座，待实现 Agent API、身份、服务发现；模型访问——已具备模型路由、Fallback（主模型不可用时自动切换备用模型）、Token / 配额治理，待实现 Agent 级成本与策略语义；工具访问——已具备 MCP Gateway、REST-to-MCP、凭证隔离、Tool 策略 / 审计，待实现工具生命周期治理；Agent 间协作——已具备路由、安全、观测底座，待实现 A2A、Agent Card、Skill、Task。底部通用网关能力同样分两层：已具备身份、路由、限流、观测、审计；待实现 Agent 身份、策略、调用链、成本语义。结论：Agent Runtime 保持在 Agent 侧，Higress 在 AI Gateway 与 MCP Gateway 之上补齐统一访问、治理与协作能力。

第 22 页ReActAgent 核心组件

本页用七张卡片拆解 ReActAgent（ReAct 即"推理→行动→观察→再推理"循环的智能体）的核心组件，说明裸框架已经具备哪些能力。这七块也是后面 Harness 叠加工程能力的地基：

  • Agent 智能体：ReAct 推理-行动循环引擎；多用户/多会话并发安全；流式事件与结构化输出；中断/恢复与人机交互。
  • Model 模型层：Credential（凭证）+ ChatModel 两层架构；内置 DashScope、OpenAI、Anthropic、Gemini、Ollama 五大厂商；支持 Streaming（流式）、Thinking（思考过程）与多模态；可扩展自定义 Provider。
  • Tool 工具系统：用 @Tool 注解或继承 ToolBase 定义工具；集成 MCP 协议（Model Context Protocol，模型上下文协议，支持 STDIO/SSE/HTTP 三种传输）；Skill 以 Markdown 指令集形式热加载；Tool Group 按需激活、自管理。
  • Context 上下文：无状态引擎 + AgentState 持久化；RuntimeContext 承载每次调用（per-call）的元数据；用 Redis/MySQL 做分布式状态共享；支持跨节点故障转移与会话恢复。
  • Middleware 中间件：5 个生命周期 Hook（钩子）位置；洋葱式（Onion）+ 变换式（Transformer）两种组织方式；OpenTelemetry 全链路追踪；限流、回退、动态 Prompt。
  • Permission 权限：Rules + Mode + Built-in Checks 三层；五种模式 DEFAULT/EXPLORE/BYPASS/ACCEPT_EDITS/DONT_ASK；建议规则自动生成并持久化；危险路径不可绕过保护。
  • Message & Event：Msg 类型化内容块体系；AgentEvent 流式增量传输；Start→Delta→End 生命周期；SSE（Server-Sent Events，服务器单向推送）推送与断点重建消息。

可以看出，ReActAgent 已经把"模型、工具、上下文、权限、中间件、消息事件"都模块化，但它关注的是"一次推理循环如何正确执行"。长期运行所需的记忆沉淀、工作区进化、沙箱隔离等能力，则由下一章的 Harness 补齐。

第 23 页1.0 → 2.0 迁移指南

本页给老用户一份迁移清单，用绿/红/橙三栏把变更分成"总体兼容""破坏性变更""已废弃"三类，帮助判断升级成本。

绿色·总体兼容（平滑升级）：核心 API 保持一致，ReActAgent 的 Builder 模式不变，model/toolkit/sysPrompt 等参数平滑迁移；@Tool 注解完全兼容，已有 @Tool/@ToolParam 标注的工具类无需修改即可在 2.0 注册使用；MCP 客户端无缝衔接，McpClientBuilder API 不变，STDIO/SSE/Streamable HTTP 三种连接方式保持兼容；Model 层各 Provider（DashScope/OpenAI/Anthropic/Gemini/Ollama）的 ChatModel builder 接口不变；消息体系向后兼容，UserMessage/AssistantMessage/SystemMessage 构造方式不变。

红色·破坏性变更（必须改造）：状态管理架构重构为无状态 Agent 引擎，AgentState 按 (userId, sessionId) 寻址，不再绑定单一 agent 实例；RuntimeContext 替代旧调用模式，call() 必须传入 RuntimeContext，per-call 元数据不再挂在 agent 实例上；AgentStateStore 强制配置，分布式部署（sandbox）下必须配置 Redis/MySQL 等分布式状态后端，否则 build() 抛异常；Middleware 注册方式变更，新增 5 层 hook 体系，旧回调/拦截器需迁移为 MiddlewareBase 实现；Permission System 全新引入，工具执行前置权限检查成为必选项，需配置 PermissionContextState（至少选择 Mode）。

橙色·已废弃（v2.1 将移除）：Memory 接口（InMemoryMemory/LongTermMemory 等）标记 @Deprecated(forRemoval=true)，迁移到 AgentState.getContext() + AgentStateStore；ToolExecutionContext 标记废弃，底层自动桥接到 RuntimeContext、老代码暂不失效，建议迁移到 RuntimeContext；ToolCallParam.getContext() 已废弃，迁移到 getRuntimeContext()；ImageBlock/AudioBlock/VideoBlock 仍兼容但新代码建议统一用 DataBlock + mediaType；旧 interrupt() 无参重载在单 session 仍有效、多 session 下行为不确定，迁移到 interrupt(userId, sessionId)。

整体信号是：2.0 把"状态"从 agent 实例上剥离出来、按用户+会话寻址并强制分布式后端，这是支撑"企业级、分布式"的关键重构，也是迁移的主要成本所在；而工具、模型、消息等日常 API 尽量保持兼容以降低升级阻力。

第 27 页Workspace——智能体进化的 Source of Truth

Source of Truth 意为"唯一可信来源"。本页主张：「智能体是什么」+「学到了什么」都落成文件，集中在一个 Workspace 目录里。左侧把内容按生命周期分三类：

  • 静态资产（工程师编辑）：AGENTS.md、knowledge/、skills/、subagents/、tools.json——定义智能体的人格、知识、技能与工具。
  • 运行时文件（框架/agent 写）：agents/<id>/sessions/、agents/<id>/tasks/、plans/——记录会话、任务与计划。
  • 长期记忆（agent + 后台任务）：MEMORY.md、memory/YYYY-MM-DD.md——沉淀跨会话学到的事实。

右侧给出四条设计线索：① 定义与进化都是文件——不散落代码、不绑数据库，一个目录拷走就等于一个完整 agent；② 生命周期三分——静态/运行时/长期记忆走不同读写路径；③ 原生多租户隔离——IsolationScope 提供 SESSION / USER / AGENT / GLOBAL 四级隔离；④ Workspace 与 Filesystem 解耦（图中用垂直符号表示正交）——同一份目录布局可切换三种物理后端。第④点正是下一页"抽象文件系统"要展开的内容。

第 28 页抽象文件系统——Workspace 的物理载体

副标题点明价值：同一份逻辑目录，三种物理后端，agent 代码零改动。结构是顶部"Workspace·逻辑目录布局"经"AbstractFilesystem 接口·WorkspaceManager 路由"向下分发到三种后端。三种后端的取舍如下：

后端 定位 / Shell 关键特性
Local + Shell 默认；提供 Shell Overlay 叠加 workspace + project；路径策略 ROOTED / SANDBOXED；单进程、本机开发、信任环境；快、简单、无外部依赖
Remote KV 多副本；不提供 Shell 后端可选 Redis·JDBC·OSS·Nacos；本机模板 + 远端覆盖（两层读）；多副本共享 MEMORY/sessions；管理台改文件下轮生效
Sandbox 隔离；容器内 Shell 支持 Docker·K8s·E2B·Daytona·AgentRun；Workspace Projection（SHA-256 增量投影）；快照恢复 pip / npm install 状态；生产跑不可信代码首选

这里 KV 指键值存储，Overlay 指把 workspace 与 project 两层目录叠加读取，Projection 指把逻辑目录增量投影进沙箱。三者的分工很清晰：本机开发用 Local（快、零依赖），多副本分布式共享用 Remote KV（状态集中、可共享），生产环境跑不可信代码用 Sandbox（隔离 + 快照恢复）。因为上层只依赖 AbstractFilesystem 接口，切换后端时 agent 代码不用改。

第 29 页内置上下文压缩策略——四道防线

目标一句话：让对话保持在 token（模型计费与上下文长度的基本单位）预算内，同时不丢关键信息。中部是"压缩流水线（按触发时机排布）"，起点是 Tool 执行（产生工具结果），随后依次经过四道防线：

  • Result Eviction（结果卸载）：单条结果 > 80K 就落盘，上下文里只留首尾 + 指针。
  • Truncate Args（参数截断）：把大参数字符串截断，零 LLM 成本。
  • Summary LLM（摘要）：把对话前缀压成结构化摘要，尾部保留原文。
  • Overflow Recover（溢出恢复）：真的撞墙（超出上限）时做极端压缩，并自动重试一次。

左下"可调节的杠杆"列出五个配置维度：触发阈值（triggerMessages·triggerTokens）、保留窗口（keepMessages·keepTokens）、Flush 时机（ALWAYS·NEVER·THROTTLED）、独立小模型（compaction.model / memory.model，即用便宜小模型做压缩）、卸载排除（read_file·grep_files 默认排除）。

右下"压缩不会触碰的内容"列出五类受保护数据：Plan Mode 状态（AgentState.planModeContext）、子 agent 后台任务（agents/<id>/tasks/<sid>.json）、todo_write 清单（AgentState.tasksContext）、权限规则（AgentState.permissionContext）、以及永不压缩的对话日志（sessions/<sid>.log.jsonl）。这保证压缩只瘦身对话本身，不会破坏计划、任务、权限和审计日志这些关键状态。

第 30 页双层长期记忆——事实自动沉淀

目标：让 agent 记住跨会话的事实，同时避免上下文无限膨胀。主流程是一条沉淀链：当前"对话 messages（当前上下文）"在每次 call 结束时经 Flush LLM 抽取，写入第一层·日流水账（memory/YYYY-MM-DD.md，追加、未去重）；第一层再经后台节流的 Consolidation LLM（最少 30 min/次）合并去重，沉淀为第二层·MEMORY.md（合并去重、策划后的长期记忆）；第二层每轮注入 System Prompt 的 <memory_context> 段，供模型直接使用。这样日常事实先快速记流水账，再低频整理成精炼长期记忆，既记得住又不让上下文膨胀。

除了自动注入，agent 还有三个主动查询工具：memory_search、memory_get、session_search；图中注明"见到 MEMORY.md 截断提示时会自动调用"，即注入内容被截断时 agent 会主动回查完整记忆。

底部列出"管线里的三次独立 LLM 调用（定制入口）"，各自可配 prompt：Flush（MemoryConfig.flushPrompt，从对话窗口抽取长期事实到日流水账）、Consolidation（MemoryConfig.consolidationPrompt，把每日流水账合并去重到 MEMORY.md）、Compaction Summary（CompactionConfig.summaryPrompt，把对话前缀压成一条摘要服务于当下上下文）。前两次属于长期记忆管线，第三次属于上一页的上下文压缩，二者共用小模型但职责不同：记忆管"跨会话沉淀"，压缩管"当下上下文瘦身"。

第 31 页子智能体编排、委派、并行、异步通知

这一页讲主智能体如何把任务分出去。页顶一句话给出委派原则：把独立、上下文重、可并行的任务交给专家型子 agent——即主智能体不把所有事揽在自己上下文里，而是拆给专职子智能体。父智能体（Parent Agent）通过两个工具发起委派：agent_spawn（创建子智能体）与 agent_send（向子智能体发消息），向下分出四种形态：

  • 同步子 agent（timeout > 0）：父智能体阻塞等待结果，子智能体的输出流式转发回来，适合必须拿到结果才能继续的任务。
  • 后台任务（timeout = 0）：不等待，立即返回 task_id，任务完成后反向通知父智能体。图中黑色横条点明通知方式：system-reminder 自动反向注入——完成消息作为系统提醒自动写进父智能体上下文，父智能体无需轮询。
  • 远程子 agent：通过 url + headers 以 Agent Protocol HTTP 调用部署在别处的子智能体，子智能体不必与父智能体同进程。
  • 暴露给用户（expose_to_user=true）：子智能体直接对用户可见，用户可以绕过父智能体直连子 agent 对话。

页底"关键能力"列出六条工程保障：workspace 支持 ISOLATED（隔离）/ SHARED（共享）两种模式；流式事件带 source 路径，能分辨事件来自哪一层子智能体；persistSession 复用实例，同一会话可复用子智能体；递归 3 层硬上限，防止子智能体无限套娃；DENY 权限自动继承，子智能体拿不到父智能体被禁止的权限；父智能体处于 Plan Mode 时子智能体自动只读。这六条分别解决了隔离、可追溯、复用、防失控、权限收敛、模式一致性六个问题。

第 32 页沙箱管理：隔离、恢复与分布式

沙箱即隔离的执行环境。本页口号是"把危险操作关进容器，把安装状态存进快照"，左侧三个设计点层层递进：01 执行边界——文件与 shell 命令都在隔离容器里执行，宿主完全不参与，危险命令只影响容器；02 跨调用恢复——pip install、npm install、临时文件都随快照保留，下次 call 无需重装重传，沙箱不是一次性的，环境状态可以跨调用延续；03 多副本可用——通过分布式 store + 远端快照，任意节点都能 resume 出同一份工作区，沙箱不绑定单机，这是分布式部署的关键。

快照后端提供四种选择：Local（本地磁盘）、Redis（低延迟）、OSS/S3（多副本）、JDBC（关系库），按部署形态挑选存储介质。

右侧是每次 call() 生命周期里的沙箱决策：先问"容器 & workspace 还在吗？"，然后三级分支——有 → 复用（最快路径）；无容器但有快照 → 恢复（快照重建）；都没有 → 冷启动（按 WorkspaceSpec 全量初始化）。即"复用优先、恢复次之、冷启动兜底"，把最贵的全量初始化留到最后。

页底给出后端矩阵：Docker、Kubernetes、Daytona、E2B、AgentRun 五种沙箱后端可选。最下方小字补充并发语义：IsolationScope 决定沙箱 slot 复用——USER 为默认粒度；SESSION 粒度天然并发安全；AGENT/GLOBAL 粒度则需要 executionGuard 串行化，即多个调用共享同一个沙箱时要加锁排队，防止并发写坏环境。

第 33 页Skills：四层注册中心 & 沙箱内执行

Skills 是可复用的能力包，页顶给出组成公式：SKILL.md（能力描述文件）+ references/（参考资料）+ scripts/（脚本）= 一个能力包。页面分左右两半，左半讲"技能从哪里来"，右半讲"技能怎么进沙箱执行"。

左半是注册中心的四层优先级，从低到高：L1 projectGlobalSkillsDir，项目全局目录 ~/.agentscope/skills/；L2 skillRepository(...)，市场后端，可接 Git / Nacos / MySQL / Classpath；L3 workspace/skills/，工作区共用，放项目特有约定；L4 <userId>/skills/，用户级隔离目录，优先级最高，可覆盖共用版。规律是越贴近具体用户、越私有的目录优先级越高，个人定制可以压过项目约定和市场版本。

右半是"沙箱内执行·三步透明化"，即把技能从注册中心落到沙箱文件系统的三步：01 物化 Stager——市场 skill 从内存写到宿主 .skills-cache/，做 SHA-256 文件级去重（相同内容不重复写），并启发式恢复 chmod +x（补回脚本执行权限）；02 Workspace Projection——把 skills/ + .skills-cache/ 打成 tar，hydrate（注入）进沙箱 /workspace，用内容 SHA-256 整体比对做增量，只同步变化部分；03 容器内执行——<files-root> 用容器内绝对路径，agent 不用猜路径，且快照保留 pip/npm install 副作用，技能脚本装过的依赖下次调用还在。三步合起来保证技能在沙箱里"路径确定、内容增量、状态延续"。

第 34 页计划模式：想清楚 -> 写下来 -> 再动手

计划模式把"先规划后执行"固化成四步工作流：设计 → 写计划 → 人确认 → 执行。页顶的完整链路是：用户请求 → plan_enter（进入计划模式）→ 只读调查 → plan_write 写出 PLAN.md → plan_exit（退出计划模式）→ HITL 确认（Human-In-The-Loop，人在回路中审批）→ 执行阶段工具解禁。中间橙色横条点明：人确认这一步复用权限系统的 ASK 机制——计划审批不是新造的交互，而是走已有的权限询问通道。

左下是 Plan 阶段的工具白名单，思考阶段只放行只读与查询类工具：只读文件工具（read_file、grep_files、glob_files、list_files）、内存查询工具（memory_search、memory_get、session_search）、Plan 三件套（plan_enter、plan_write、plan_exit）、任务清单（todo_write）；Shell 为可选项，调用 .allowShellInPlanMode() 后才放开且仅限只读用途。写操作一律禁止，从工具层面保证"只想不动"。

右下强调判断状态不能只看 isPlanModeActive 一个布尔值，而要区分四种终态：未进入（模型直接 build，任务与 workspace 不匹配）；进入 → plan_exit（成功：规划完 + 获批 → build 模式）；仍 plan · 有 PLAN（已起草但未退出，后续消息可批准继续）；仍 plan · 无 PLAN（只说不做：文本像计划但没写出文件）。后两种是需要单独处理的滞留态，最后一种尤其是对"模型口头规划却不落盘"的防御性识别。

第 35 页Channel：消息平台 -> Gateway -> Agent

Channel 即消息接入通道。本页是一张左中右三段拓扑，副标题点明价值："一行接线，自动完成会话管理·并发·路由·流式"——开发者只需一行配置把平台接进来，剩下的治理工作全由 Gateway 承担。

左列是七种消息平台/协议：HTTP / SSE（SSE 即 Server-Sent Events，服务器向客户端的流式推送）、WebSocket、钉钉、飞书、企业微信、GitHub、GitLab。中间是 Gateway 的路由与治理层（GatewayBootstrap），内含五项职责：会话管理——把 userId 映射为稳定的 sessionId，同一用户多条消息落到同一会话；Per-session 并发——同 session 的消息公平排队，会话内串行、会话间并行；Agent 路由——多 agent 场景按 agentId 分发；子 agent 桥——把 expose_to_user 的子智能体反向暴露给客户端（与第 31 页的"暴露给用户"形态呼应）；流式转发——把 Flux<AgentEvent> 事件流直通 SSE 推给客户端。

右列是 HarnessAgent 实例池，图中列出四个实例：sales（main 主智能体）、support、billing（均为 HarnessAgent）、reviewer（exposed subagent，即暴露给用户直连的子智能体）。整页的信息是：平台差异在 Channel 层被抹平，Gateway 统一做会话、排队、路由、流式，Agent 实例池只关心业务。

第 37 页AgentScope Service - 企业级智能体编排控制面

页顶的定位声明是本章核心主张：AgentScope Service 的目标不是替换你现有的 Agent 框架，而是提供一层统一控制面，把用不同框架（AgentScope、Langchain、ADK 等）、不同技术栈（Claude、OpenClaw、QwenPaw 等）搭建的智能体统一管控、协作起来。

下方系统架构图自上而下分四层。用户层（USER）是 Human；接入入口层（ENTRY）有两个入口：Dashboard（Browser 可视化控制台，给人用）与 REST API（SDK / curl，供第三方系统集成）；两者汇入中间的控制面（CONTROL PLANE）AgentScope Service Control Plane；控制面向下连接智能体接入层（AGENTS），图中并列五种接入方式：Managed Agents（平台托管运行）、AgentScope（原生接入）、LangChain（instrument sdk，即在框架里埋入上报 SDK）、Claude（Sidecar 接入）、QwenPaw（Sidecar 接入）。Sidecar 指与智能体伴生部署的边车进程，由它负责上报与受控，智能体本体不用改造。

五种接入方式的差异正体现了"不替换框架"的设计：自家框架原生接入，第三方框架靠埋点 SDK 或边车接入，完全托管的则由平台直接运行——控制面只做统一管控，不要求重写已有智能体。

第 46 页依然是发布 / 订阅模型

先讲清楚"什么没变"：LiteTopic 与传统 Topic 本质相同，都是基于主题的 Pub/Sub（发布/订阅）异步消息模型。图中 Producer 通过 PUB 把消息发往 Topic（代码形态为 msg.setTopic(T)），Consumer 通过 SUB 订阅 Topic（subscribe(Topic)），中间的主题框标注"传统 Topic / LiteTopic 本质相同"。右侧卡片总结共同本质：异步解耦、削峰填谷，消息沿 Message → Topic → Consumer 流动。

页面底部点出"区别在于"：LiteTopic 在模型细节和使用场景上有自己的特点——更轻量的生命周期管理、更大规模的队列支撑、更灵活的订阅方式，也就是接下来四页要展开的内容。先立共同本质再讲差异，是为了说明 LiteTopic 不是新协议，而是同一模型下的轻量化形态。

第 47 页特性一：动态创建与销毁

特性一对比两种队列的生命周期管理方式，副标题概括为"不需要预配置，业务运行时数据面决定队列名字，随用随建、用完即走"。

传统 TopicLiteTopic
预先创建，生命周期长动态创建和生成，运行时即建即用
与应用/业务生命周期一致业务数据面决定其名字
如交易系统中的 "Order" Topic一个 SessionId、TaskId、RequestId 均可
创建需审批、配置路由、分配资源粒度可粗可细，由业务场景决定

页面底部的彩色条示意运行时随时冒出的队列：Session-A、Task-42、Request-xyz、Session-B……随时创建。对照来看，传统 Topic 是"控制面先规划好、业务再使用"，LiteTopic 把命名权和创建时机交给业务数据面，队列粒度可以细到一次会话、一个任务甚至一个请求。

补充背景（线上资料）

LiteTopic 是 RocketMQ 5.x 引入的轻量级队列形态：发消息到一个不存在的队列即自动创建，无需预创建流程，这正是"运行时即建即用"的实现方式。见 Alibaba Cloud 博客：Model Studio Gateway in Practice。

第 48 页特性二：低成本 · 海量规模

两张数字卡片构成对比：传统 Topic 上限（商业实例）为 3,000，受实例规格限制、创建成本高；LiteTopic 支撑规模为 20W ~ KW，即 20 万到千万级，轻量化设计使创建与维护成本极低。副标题称之为"从数千到千万级的跨越"。

规模放大后必须回答"用完的队列谁来清理"。页面下方给出 TTL（Time To Live，此处指不活跃超时时间）自动回收：当某个 LiteTopic 不活跃时间超出配置后，自动销毁回收、释放 Quota 空间，无需人工清理、资源零泄漏。动态创建与自动回收合起来构成闭环，才撑得起海量短生命周期会话——否则队列只增不减，规模优势会被资源泄漏吃掉。

补充背景（线上资料）

线上资料给出的口径是单 Broker 支撑百万级队列、不活跃超 TTL 自动回收，与本页"20W ~ KW"的集群级规模口径互为补充。见 阿里云开发者社区：LiteTopic 技术文章。

第 49 页特性三：差异化订阅

左侧是传统消费模型：基于 Group 分组的集群消费——相同订阅主题、相同处理逻辑的一组消费实例通过 Group 归组，一条消息在集群内被其中一个实例消费。图中 Topic-A 与 Topic-B 都指向 Group-1（内含 C1 / C2 / C3），再"集群内选一"。这个模型的前提是组内订阅关系整齐划一，无法按实例区分。

右侧是 Lite 消费模型：在单个客户端维度添加自己感兴趣的主题，多个客户端可订阅相同集合，也可部分相同、完全不同。图中 Lite-A / Lite-B / Lite-C 三个主题被 Client-1、Client-2 自由组合成 A,B / B,C / A,B,C 三种集合，每个 Client 独立订阅。订阅关系从"组级统一"变为"客户端级自由组织"，这为后面案例中"放行通知只回到持有用户连接的那台机器"提供了模型基础。

第 50 页特性四：顺序消费

左侧传统顺序消息：同一 Topic 下有多个逻辑队列，消息落入哪个队列由 ShardingKey（业务 ID）的 Hash 决定；同一业务 ID 的消息一定在同一队列上保持顺序，但不同业务 ID 可能共享同一队列。图中 Queue-0 里 sessA 与 sessB 的消息交错排列（sessA-m1、sessB-m1、sessB-m2、sessA-m2……），Queue-1 里 sessC 与 sessE 交错，Queue-N 里是 sessD、sessF；图注总结为"同 ID 必同队列（保序），不同 ID 可共享队列（交错排列）"。

右侧 LiteTopic 顺序：一个 LiteTopic 全局只有一个逻辑队列，默认就是 FIFO（First In First Out，先进先出）消费；队列内全部是同一个 LiteTopic 的消息，天然有序，无需 ShardingKey。图中 sessionA 的 m1 至 m5 依次排成一列。页面同时给出可选项"拆分"：并发度高且无顺序要求时，可拆分为 sessionA-1 / sessionA-2 / sessionA-3 等多个独立 LiteTopic，用放弃顺序换取并发度。

第 52 页背景：百万租户 × 稀缺 GPU，限流误差被成倍放大

背景页用三张卡片层层递进，解释为什么百炼的限流必须做得精准。第一，百万级租户抢算力：百万级用户同时调用数十种大模型，GPU 是最稀缺的生产要素，限流本质上是在分配稀缺算力。第二，误判即双向损失：限流误判会让用户超时、频繁重试；过载放行则浪费算力、劣化他人体验——两个方向判错都有代价。第三，误差被百万租户放大：一次误判的影响会沿租户规模扩散，小误差酿成大故障。标题中"成倍放大"指的就是这种规模效应：同样的限流误差率，在百万租户下造成的绝对影响完全不是一个量级。

第 53 页从"门口直接拦人"升级为"取号等候区"

左侧传统限流是两态：放行——在阈值内立即通过；拒绝——超出即返回 429（HTTP 状态码，表示请求过多）。其缺陷被概括为两条：突发流量被直接误伤；只能"拒绝"，不能"缓冲"。

右侧平滑限流加入中间态变成三态：PASS——能过就立即过；QUEUE——过不了就排队等候；REJECT——排满了才拒绝；并明确手段是"用异步队列削峰填谷"。两态与三态的差别在于是否给超限请求一个缓冲机会：突发往往只是"来得太密"而不是"真的太多"，排队等到流量低谷就能自然消化，只有队列都排满才真正拒绝。页面底部一句话结论：排队等一等，好过直接被拒之门外。

第 54 页限流识别 → MQ 缓冲入队 → 排队整形 → 模型服务

本页是方案的整体流程图，自上而下四层。第一层流量来源"海量用户、多种模型"：用户A（Qwen3.7-max）、用户B（Deepseek-v4）、用户C（Happyhorse-1.0）直至用户M（Wan2.7），示意大量用户各自调用不同模型。第二层"限流识别"把请求分成三路：正常请求走绿色"bypass 不入队"直通模型服务；TPM（Tokens Per Minute，每分钟 token 数）超限拒绝直接挡回；突发限流一路向下进入"Message Queue 缓冲入队"。第三层"排队整形"：入队后由集群 #1 至集群 #N 多个消费集群承接，每个集群对应一组 topic / group（topic_1 / group_1 等），用专有机器控速消费，把突发流量整形成平滑放行后再调第四层"模型服务"（Qwen、happyhorse、智谱AI、DeepSeek、MiniMax 等）。

右侧小图与底部三张卡片指出用传统 Topic 承载这条链路的代价。右图标题"传统 Topic - 隔离单元 = 队列"：用户A 至用户E 的消息落进共享 Q0、共享 Q1 两条队列，红字标注"N 个用户挤 M 条队列，消息混排"，不同用户的消息在同一队列内交错。由此引出底部三个问题：其一队头阻塞——传统消费模型自带 HOL Blocking（队头阻塞，队首消息处理慢会挡住后面所有消息），每个【用户+模型】需创建独立 Topic/Group 保证互不影响；其二运维成本高、无法合池——独立消费集群无法跨用户/模型共享，资源利用率低；其三缺乏扩展性——特殊用户特殊配置、无法动态调整，新增用户或模型需新增配置，topic 以 userId + model 命名。这三个问题正是下一页 LiteTopic 四个适配要解决的对象。

补充背景（线上资料）

"排队整形"即漏桶限流思路：请求先入队缓冲，按固定速率放行，把突发流量整形成平滑流量。线上回顾文章将百炼方案概括为"从直接拒绝到排队放行"的平滑限流。见 阿里云开发者社区：沙龙回顾。

第 55 页四个基于 LiteTopic 的适配

左侧四张卡片是百炼方案落在 LiteTopic 上的四个适配。1 海量：为每个 userId、userId + model、APIkey 创建独立队列，精准限流。2 动态：需要开启的用户直接 Diamond（配置中心）配置，入口处生效。3 Suspend 语义：按队列挂起，毫秒到小时级控制。4 精准订阅：放行通知回到用户连接机器。

右侧示意图展示适配后的形态：一个用户一条 lite 队列，做用户级限流与挂起；用户A、C、D、E 均"消费中"，只有用户B 因"触发限流 → 挂起消费"而"已挂起"，消息积压在自己队列里；图注强调队列间逻辑隔离——单用户堆积、限流、挂起均不影响其他用户，到期自动恢复，规模可至百万级用户，按用户隔离消费。对照上一页：传统 Topic 要靠独立 Topic/Group 加独立集群才能做到的隔离与控速，现在每条队列自身即可完成。底部效果条给出结果：限流异常比例下降 10×，用户可感知问题收敛，资源合池。

补充背景（线上资料）

Suspend 语义的具体机制：消费回调返回 Suspend N（毫秒）可让 Broker 暂停该队列投递 N 毫秒而不影响其他队列，相当于把漏桶的"放行速率控制"落到 Broker 层；百炼按 userId + model 维度建队列实现用户级隔离限流。见 Alibaba Cloud 博客 与 开发者社区技术文章。

第 56 页从百炼方案抽象出的四个关键点

本页把百炼的具体做法抽象成一条通用流程。上方流程图：Start 出发，先"根据用户和模型查找限流配置"，再做"突发限流校验"（框上标注"以X倍基础限流校验"），随后进入"是否限流"判断——判定限流的分支直接走向 End；另一分支进入红框标出的核心两步："投递到用户模型队列"→"按基础限流消费"，之后是"推理"→"突发限流用量后计量"，最后回到 End。红框强调的正是"缓冲队列 + 按基础速率放行"这一段平滑限流的核心。

下方四张卡片把流程归纳为四个关键点：1 用户级限流配置——按用户 + 模型查找限流配置；2 突发限流识别——以 X 倍基础限流做突发校验；3 缓冲队列——超限请求投递到用户模型队列；4 放行及调用后处理——按基础限流消费，推理后计量。注意第 4 点把计量放在推理之后：限流额度按实际调用结果扣减，而不是请求一进门就扣。

第 57 页插件整体架构：spring-cloud-gateway-rocketmq-ratelimiter

本页给出通用限流插件 spring-cloud-gateway-rocketmq-ratelimiter 的组件图。请求路径（绿线）：Client Request 以 inbound HTTP 进入插件核心过滤器 BufferedRateLimitGatewayFilterFactory，由它编排 PASS / QUEUE / REJECT 三态；PASS 的请求经 PASS forward 转发到下游 Backend Service；REJECT 429 / timeout 504 沿红线直接返回客户端。插件由自动装配类 RocketMQRateLimiterAutoConfiguration 装配进网关。

过滤器向三个方向委派（灰线）。向左是宿主应用（Host Application，business policy）的两个 SPI（Service Provider Interface，框架留给业务实现的扩展点）：RateLimitRequestResolver 负责 resolve requestKey + specs，即解析本次请求按哪个键、哪些限流规格来限；PostCounter 负责 count POST dimensions，即响应后的计量维度。向下左是限流判定接口 BurstRateLimiter（标注 dual bucket，双桶设计），有两个实现：Bucket4jBurstRateLimiterImpl（local、in-memory 内存版）与 RedisBurstRateLimiterImpl（redis、distributed 分布式版），后者通过 Lua eval 在 Redis 中原子判定。向下右是缓冲队列接口 BurstRequestQueue，默认实现 RocketMQBurstRequestQueueImpl（标注 SmartLifecycle 管理启停），经 produce/consume 对接 RocketMQ；enqueue / dequeue 箭头表示入队与出队回调回到过滤器。左下 Legend 说明四种线型：request path、reject / timeout response、delegates、implements，并注明 limiter 可通过配置项 gateway.burst.limiter 在 local / redis 间切换。图下方一句话总结分工：业务方只需实现 Resolver / PostCounter 两个 SPI，其余由插件自动装配。

第 58 页五项能力，开箱即用

五张卡片列出插件的关键能力。1 削峰不阻塞：排队全异步，不拖垮网关事件循环（事件循环是网关处理所有请求的异步调度线程，一旦被阻塞会影响整机请求）。2 多维度同时限流：按用户、API、IP 等多维度原子管控。3 按结果计量：支持响应后按流量 / 行数计数，而不是只按请求数计数。4 单机/分布式：内存版与 Redis 版可插拔切换。5 一键集成：以 Spring Boot Starter 交付，引入依赖即可使用。页面底部点明定位：这是一个通用化的插件，而非百炼专用代码——案例中的能力被沉淀为任何 Spring Cloud Gateway 业务都可复用的组件。

要点回顾

  • LiteTopic 仍是发布/订阅模型，差异在四个特性：运行时动态创建与销毁、20 万至千万级规模加 TTL 自动回收（传统商业实例上限 3,000）、客户端级差异化订阅、单队列天然 FIFO 且可选拆分换并发。
  • 平滑限流把"放行/拒绝"两态改为 PASS/QUEUE/REJECT 三态：突发请求先入队缓冲、按基础速率放行，排满才拒绝，用异步队列削峰填谷。
  • 传统 Topic 的隔离单元是队列，多用户消息混排导致队头阻塞，被迫为每个用户+模型开独立 Topic/Group 与独立消费集群，成本高且无法合池；LiteTopic 以"一个用户一条队列 + 按队列 Suspend 挂起 + 精准订阅"把隔离与控速下沉到队列自身。
  • 百炼落地效果：限流异常比例下降 10×，用户可感知问题收敛，资源合池。
  • 方案最终抽象为通用插件 spring-cloud-gateway-rocketmq-ratelimiter：业务只实现 Resolver / PostCounter 两个 SPI，削峰不阻塞、多维度限流、按结果计量、单机/分布式可插拔、Spring Boot Starter 一键集成。

第 69 页LoongSuite Pilot 架构总览

架构总览图自上而下是一条数据流水线。最上层是 AI Coding Agents 的原始数据源：IDE 历史文件、SQLite 数据库（轻量嵌入式数据库）、Hook JSONL 日志（JSONL 即每行一个 JSON 对象的文本格式）、Session 日志、Patch 拦截输出等。Pilot 内部第一层 Discovery + Deployment：AgentDiscoveryService 用 fs.watch 文件监听加轮询发现已安装 Agent，DeploymentManager 按 4 种策略自动注入，agents.d/*.json 是声明式配置。第二层 Input Layer（InputManager）按数据源配五种输入：HookInput 做 JSONL 增量读取、IdeInput 取 IDE 快照、SqliteInput 用 rowid 游标增量查询（rowid 是 SQLite 每行的自增编号，记住读到的位置即可只读新增）、SessionInput 轮询会话文件、CliForwarder 转发 CLI 遥测。第三层 Processing 做四件事：Normalization 把原始数据归一化为统一的 AgentActivityEntry、Content Policy 按 Agent 控制采集粒度、Masking 对 AK/Key/URI/私钥脱敏、Git Enrichment 关联 repo 与 branch。第四层 MultiFlusher 并行扇出到四个输出：SLS Logstore（生产实时查询）、本地 JSONL（零依赖调试）、HTTP Endpoint（对接自建后端）、OTLP Trace（OTLP 是 OpenTelemetry 的传输协议，对接 CMS 2.0 / Jaeger / Langfuse）。右侧独立的 Checkpoint 栏保障可靠性：StateStore 持久化读取偏移（input-state.json）、SnapshotStore 做快照去重（snapshot-store.json），合起来实现断点续采、不丢不重。框内底边是运维能力条：HookWatchdog、AutoUpdater、Metrics、StatusBar、LogRetention。框外底部是存储与分析后端：阿里云 SLS、CMS 2.0 / Langfuse、本地 JSONL、自建后端。

第 70 页选择一：ALL IN ONE 架构

第一个设计选择：一次部署、一个二进制，自动覆盖所有已安装的 AI Coding Agent。图自上而下：Pilot 读取 agents.d/ 目录下每个 Agent 一份的 JSON 声明（claude-code、cursor、codex、qoder、qoder-work、wukong、qwen-code-cli 等）；DeploymentManager 做声明驱动部署，提供 HookStrategy、PluginProbe、PluginInject、DetectionOnly 四种策略，并由 HookManager + HookWatchdog 负责自愈（Hook 被破坏或失效时自动修复）。底部七张 Agent 卡片各带一个激活绿点并标注采集方式：Cursor、Claude Code、Codex 走 Hook，Qoder 走 IDE，Qoder Work 走 SQLite，Wukong 走 Session，Qwen Code CLI 走 CLI。关键数字与机制：已声明 11 个 Agent，运行时按实际检测结果激活——声明是全集，装了哪个才激活哪个。页底结论：新增一个 Agent 适配 = 一个 JSON 声明 + 一个 Input 实现，无需改框架代码。

第 71 页选择二：多 Agent 采集矩阵

第二个设计选择用"5 种采集基类 × 多种 Agent = 全覆盖"的矩阵表达。左列五个基类各封装一种数据源读法：BaseHookInput（Hook JSONL 日志增量读取）、BaseIdeInput（IDE 历史文件快照轮询）、BaseSqliteInput（SQLite rowid 游标增量查询）、BaseSessionInput（Session 文件轮询）、BaseCliForwarder（CLI 遥测日志转发）。右列是每个 Agent 实际使用的组合：Cursor 仅 Hook 注入；Claude Code 与 Codex 为 Hook + Node.js 启动项注入；Qoder 组合 IDE 快照 + Hook + Session 三种；Qoder Work 组合 SQLite + Hook；虚线框列出 OpenClaw / Gemini CLI / Cline 等待扩展对象。图中连线表示复用关系，例如 Hook 基类同时被 Cursor、Claude Code、Codex 复用，IDE 与 Session 基类的线都汇到 Qoder。页底给出扩展成本：新增 Agent 只需继承基类 + 编写 agents.d/*.json 声明文件 + 实现数据转换方法。

第 72 页选择三：统一语义规范

第三个设计选择：统一语义规范，基于 OpenTelemetry GenAI Semantic 与 OTEL GenAI Util SDK。OpenTelemetry（OTel）是可观测性开源标准，GenAI Semantic Conventions 是它针对生成式 AI 场景约定的字段命名与语义。页面上方给出四层链路：Session → Turn → Step → LLM / Tool，即一个会话包含多轮对话，每轮包含多个步骤，每个步骤落到一次模型调用或工具执行。下方三张卡片是统一语义带来的三个收益：口径对齐——所有 Agent 使用相同字段名和语义定义，如 gen_ai.usage.input_tokens、gen_ai.session.id；层级化链路——还原 Agent 完整执行链路，看清每一轮 ReAct 循环的思考→工具调用→推理；基础设施复用——接入新 Agent 时看板、告警、分析查询自动生效，无需重新开发。

第 73 页选择四 & 五：安全脱敏 + 多目标输出

左栏是选择四"安全脱敏"，主张灵活粒度、平衡观测与安全：采集粒度控制可按 Agent 类型配置是否采集消息内容、工具参数；敏感信息自动脱敏把云 AK、API Key、数据库连接串、私钥分别替换为 [ACCESSKEY_MASKED]、[APIKEY_MASKED]、[DATABASEURL_MASKED]、[PRIVATEKEY_MASKED] 占位符；mask.mode 提供 none / all / custom 三种模式。右栏是选择五"多目标输出，不绑定后端"：本地 JSONL（零依赖落盘、本地调试）、SLS Logstore（生产级实时查询）、HTTP Endpoint（对接自建后端）、OTLP Trace（CMS 2.0 / Jaeger / Langfuse，其中 Jaeger 是开源分布式追踪系统、Langfuse 是开源 LLM 观测平台）。右栏底部的工程约束很重要：并行扇出，单个目标失败不阻塞其他通道。

第 84 页背景：研发组织的"职能类工作"之痛

本页用四张卡片说明为什么需要数字员工，对象是研发组织中的"职能类工作"——值班、答疑、工单、社区维护这类必须有人承担、但又不属于核心研发主线的工作。四类痛点分别是：

  • 01 重复消耗：大量工时被重复劳动吞噬。值班答疑、工单处理、社区 Issue（社区用户提交的问题单）、取数提单，日复一日消耗研发工时。
  • 02 频繁打断：碎片任务打断主线工作。碎片化请求不断插入，工程师难以持续专注于核心研发主线。
  • 03 专家单点：关键知识集中在少数人。专家成为单点瓶颈，权限只能"全有或全无"，无法安全分级下放。
  • 04 7×24 压力：响应压力不分昼夜。社区与告警不分时区、不分工作日，团队被迫 7×24 待命响应。

这四条分别对应后文的解法方向：重复与打断交给数字员工承接、专家单点靠分级授权化解、7×24 压力靠全天候在线的团队响应。

第 85 页核心破题思路：一项职能 = 一支 Agent 团队

第 86 页从机器人到数字员工团队：范式升级

本页用左右对照表说明"范式升级"升在哪里。左侧是传统脚本 / 单点机器人，定位是按指令执行的"工具"；右侧是带"推荐"标记的 AgentTeams 数字员工团队，定位是主动交付结果的"团队"。五个维度逐条对照：

维度传统脚本 / 单点机器人AgentTeams 数字员工团队
流程应变固定流程：只能按预设脚本执行，无法应变按需调用工具与技能：动态编排，灵活应变
协作方式单一技能：一个机器人只会做一件事多角色协作：Leader 规划 + Worker 专业执行
长任务无法拆解长任务：复杂链路一断即停任务拆解与并行：长任务自动分解、同步推进

第 87 页AgentTeams 协同模型：Leader × Worker

本页给出团队的形式化定义：Team = Human + Leader + N Workers。一句话流程：Human 触发，Leader 规划、分派并汇总反馈，Worker 专业执行。左侧结构图中，Human（触发任务）连接 Leader（规划 / 分派 / 汇总反馈），Leader 再分叉连接 Worker 1、Worker 2 直至 Worker N；图上特别注明"Leader 和 Worker 都是 Agent"，即团队内部全是智能体，人只负责触发与接收结果。右侧把分工拆成三条：Leader 负责中枢决策——理解意图、制定 Plan（执行计划）、选择工具与 Worker，并统一管理上下文；Workers 专业化执行——按领域拆分子任务，分别调用知识、系统、工具完成可验证动作；反馈归 Leader 汇总——Worker 只回传执行结果，由 Leader 汇总为报告或操作结论，再反馈给 Human。这个"单一出口"设计让人类面对的不是 N 个机器人的碎片输出，而是一份汇总结论。

第 90 页落地流程：从定义到进化的闭环

本页给出数字员工全生命周期的六步闭环，副标题强调"交付不是终点，运行经验持续回流、持续进化"。六步依次为：

  • 01 定义：五件套配置规范 + 技能编写，定义身份、契约与能力边界。
  • 02 规范检查：路径 / 映射 / 凭证 / Git 四项审计，发布前逐项把关。
  • 03 打包发布：统一打包 + 模版发布，两步走灰度（先小范围验证再放量）防止打穿全量。
  • 04 批量建站：五阶段自动化 + AI 语义审核 + 断点续连（中断后从断点恢复），规模化交付。
  • 05 运行监控：拨测探活（周期性主动探测是否存活）+ 响应时延跟踪，持续掌握运行健康度。
  • 06 回流进化：运行时变更回流 Git，经验沉淀反哺定义与技能。

第六步回接到第一步，使流程成为闭环：运行中产生的经验与变更回到版本库，再进入下一轮定义与发布。这与第 101 页的"进化回流"工程闭环是同一主张在交付流程层面的表述。

第 91 页场景一痛点：开源社区维护

从本页起进入四个落地场景。场景一的案例描述：Apache RocketMQ 是阿里开源的分布式消息中间件，GitHub 上持续产生大量 Issue（问题单）和 PR（Pull Request，代码合并请求）；核心维护团队有限，需要自动化方案保障响应速度与代码质量。左下框点出关键挑战：用自动化放大有限维护人力。右栏列传统方式的五个痛点：01 Issue 响应周期长——人工确认、定位、修复方案平均 3–5 个工作日；02 Code Review 瓶颈——单个 PR 需阅读 diff（代码改动对比）、上下文和安全/兼容性，耗时 30–60 分钟；03 跨仓库一致性难保证——rocketmq 与 rocketmq-clients 协议同步易遗漏；04 新贡献者 CI 审批延迟——CI（持续集成，提交代码后的自动构建测试流程）首次贡献需 maintainer 手动 approve，受时区影响；05 社区活跃度受影响——响应慢导致贡献热情下降、Issue 堆积。这五条痛点在第 92 页被逐条对应到团队工作流与量化收益。

第 98 页可信护栏：可解释、可追溯、可拒绝

左栏给出原则与指标。衡量指标：权限覆盖率 / 拦截次数 / 审计完整率。"执行前门禁"的总原则是：把四道关卡压进外部治理链路，模型只给建议，代码决定能否执行——安全裁决权在模型之外的确定性代码里。四道关卡各一句：身份——调用者与目标资源一致；权限——按矩阵裁决可做什么；预案——影响面与回滚先写清；确认——确认内容绑定执行内容。

右栏是"AgentTeams Ops 团队四道关卡治理链路"的变更执行架构图，副标题说明四道关卡把高危操作纳入可裁决、可审计、可拒绝的外部治理链路，图内注明"四道强制关卡，任一不通过即拒绝"。流程从发起侧开始：用户在对话里提出变更，然后顺序过四关。关卡一身份：从会话上下文反查元数据台账，查不到或多个同名即拒绝（R1），唯一命中才放行。关卡二权限：按代码里的角色 × 操作 × 范围矩阵裁决，矩阵之外或混入越界目标则整单拒绝（R2）。关卡三预案：生成预案并冻结完整参数快照。关卡四确认：确认码经钉钉带外（对话通道之外的独立通道）送达发起人，码错 / 超时 / 非本人即拒绝（R3）。四关全过才"按快照执行，不重新推导参数"，最后结果回报。所有通过、拒绝与预案路径都虚线写入右侧审计中心：本地审计库（必写）+ SLS 日志服务（阿里云日志服务，远端副本），做到全量记录、不可篡改、可检索、可追溯。图左下"设计要点（关卡即强制边界）"四条：顺序通过（必须依次通过四道关卡）、单点否决（任一关卡不通过即终止）、快照执行（冻结参数，执行不重算）、全程审计（本地必写，远端副本）；图例区分通过路径、拒绝路径、审计写入三种线。页底三卡片对应标题三性：可解释——变更范围、理由可见；可追溯——全程留痕，记录 SLS；可拒绝——风险拦截，快速失败。

第 99 页高危操作治理：两段式确认机制

本页细化第 98 页的"确认"关卡。左栏"协议只留三件事"：1 先冻结 payloadhash（变更参数的哈希指纹），锁定变更意图；2 带外随机码经钉钉发送，原通道回填；3 通过本人 + TTL（Time To Live，有效期）+ hash 校验后执行。总结句：确认链路绑定意图、确认人、时效与 payload（变更内容本体）。

右栏是"两段式变更单（Plan-Apply）"时序图，原则为"写操作不直接执行，先出预案；确认码走带外通道，只在用户回复时进入对话"。四个参与方：U 发起人、M 模型、S 脚本（护栏）、D 钉钉（带外通道）。Plan 阶段（只生成预案）：①发起人提出"把某某从团队里移除"；②模型调 plan 命令请求生成预案；③脚本校身份、校权限、冻结参数快照，不执行任何写操作；④脚本随机生成确认码（示例 7K9Q-2M8L-P6T3，有效期 5 分钟）发往钉钉；⑤钉钉单聊送达发起人（模型看不到）；⑥脚本只返回预案文本给模型（不含确认码）；⑦模型把预案原样透传发起人（不暗示已执行）。Apply 阶段（真正执行）：⑧发起人在对话中回复确认码；⑨模型调 apply 命令提交确认码；⑩脚本校码、校有效期、校是否本人（发起人），任一失败则拒绝执行；⑪按冻结快照执行（精确到对象与字段、幂等与去重保护）；⑫⑬执行结果（成功/失败 + 明细）经模型透传回发起人。

图右"关键设计"五条：不出现在模型上下文（确认码由脚本随机生成、钉钉单聊发送，模型全程不可见、不可预测）；必须是发起者本人（脚本校验钉钉用户身份 = 发起者身份，群聊中他人拿到码也无法通过校验）；有效期校验（确认码过期自动失效，降低泄露与重放风险）；两段式语义（Plan 只生成预案不执行，Apply 才执行，杜绝"预案当已执行"的幻觉）；冻结快照（Apply 严格按 Plan 冻结的快照执行，防中途被篡改）。"安全性保障"四条与之呼应：模型无法预测或伪造确认码、带外通道传递绕开模型路径、可验证的人类确认、杜绝幻觉与冒充（没有确认码就无法通过 Apply，模型无法"替用户确认"）。示例钉钉单聊消息为"变更预案已生成，请查看对话。确认码：7K9Q-2M8L-P6T3，有效期：5 分钟，注意：请勿将确认码泄露给他人"。页底结论句：随机码不会出现在 LLM 上下文中，防止模型绕过审计执行任何高危操作。

第 101 页可观测与自进化：数字员工也要被运营

副标题定调：上线只是起点，数字员工需要持续拨测、审计回流与版本化发布，才能长期可信。左面板"被运维的对象自己也变了性质"用两行对照表说明传统运维假设为何失效：第一行，传统假设"存活 = 进程健康"，传统做法是 HTTP 探针端口通、返回 200 就是活的；但运维 Agent 时会出现"探针全绿，但它已经不能干活了"（HTTP/端口/数据库探针全绿而 Agent 实际失能）。第二行，传统假设"部署物是不变的"，传统做法把运行时的偏离都当配置漂移、重新部署抹平；但 Agent"自己改出的东西，往往比初始版本更好"（原版 v1.0 → 自主迭代主动升级到进化版 v2.0+），抹平等于丢掉进化。左下因此给出可观测侧答案：除了 Loongsuite 指标采集 + ProbeAgent 探针，保障 Agent 可用性——即不能只看进程存活，还要看业务可用性。

右面板"把单向交付链路接成环：让 Agent 的进化成为正式资产"，并注明"运行时是进化的发生地，不是它的存放地"。正向链路七步：①代码仓库（唯一权威源）→ ②CI 构建（静态检查、单元测试、模版打包）→ ③Agent 模版（版本化制品，如 v1.3.0）→ ④发布 → ⑤模版库（多版本 v1.3.0 / v1.2.3 / v1.1.5…）→ ⑥创建 / 升级（滚动升级 / 批量升级）→ ⑦运行中的 Agent（持有 MEMORY、AGENTS.md、skills）。回流链路：运行中的 Agent 发生运行时自我变更（MEMORY / AGENTS.md / skills，来源是真实任务反馈、Trace（调用链追踪）复盘提炼经验、自身配置修正）→ ⑧改动提取 → MR（提取 → 结构化 → 生成 MR；MR 即 Merge Request，代码合并请求）→ ⑨人评审合入（代码评审 / 安全检查 / 合入主干）→ 回到①代码仓库。闭环后的效果五条：进化可累积、全程可视化（所有变更以 MR 形式呈现，可 diff、可追溯）、可回滚（任何版本模版都可回滚）、批量传播（合入后的版本通过模版库分发至同类 Agent）、带着进化重来（新部署不再从零开始，而是把沉淀的进化一起交付上线）；并强调"仓库仍是唯一权威源，只是多了一个来源：Agent 自己"。

右下"边界与纪律：AI 自主性的护栏"五条：白名单回流（只允许白名单路径回流，如 AGENTS.md、skills、MEMORY）；敏感路径排除（凭证、密钥、系统配置、运行态数据等敏感路径一律不回流）；删除不同步（运行时的删除操作不回流，Agent 删掉能力更可能是问题）；必须人审合入（所有回流必须经过人类评审，合入主干后才生效）；全程审计留痕（提取、生成 MR、评审、合入全程留痕，可审计可追溯）。面板结论句：让 Agent 的自我改进，从"随容器消失的临时状态"变成可累积、可评审、可回滚的资产。页底两块标签收束全页：可观测——Loongsuite 指标采集 + ProbeAgent 探针保障可用性；进化回流——Badcase（失败案例）与经验进入 MR、Review、Release，形成可回滚的工程闭环。
